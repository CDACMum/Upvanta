What is a data warehouse?

Data Warehouse Fundamentals 7 min read Difficulty: Beginner 1 of 37
Definition

A data warehouse is a centralized repository that stores integrated, historical data from multiple sources, optimized for analytical queries and reporting.

Key properties: Subject-oriented (organized by business domain), Integrated (unified from multiple sources), Non-volatile (data is not modified after loading), Time-variant (maintains historical snapshots).

Classic Definition: Bill Inmon's definition (1992): "A subject-oriented, integrated, non-volatile, time-variant collection of data in support of management's decisions."
Data Warehouse OLAP Subject-Oriented Integrated Non-Volatile Time-Variant
How It Works — Step by Step
Step 1 / 5
  1. 1OLTP (Online Transaction Processing) — applications interact with a normalized relational DB optimized for fast reads and writes of individual records.
  2. 2OLTP databases handle many short transactions with low latency — INSERT, UPDATE, DELETE on current data.
  3. 3ETL/ELT processes extract data from OLTP systems and load it into a Data Warehouse — a denormalized, column-oriented store for analytics.
  4. 4OLAP (Online Analytical Processing) serves BI tools, dashboards, and reports with complex aggregation queries across historical data.
  5. 5Key insight: OLTP is write-optimized for current state; OLAP is read-optimized for historical analysis. A data warehouse bridges the gap.
Cross Questions
Why not just query the production database?
1) OLTP databases are optimized for writes, not complex analytics. 2) Analytical queries would slow down production apps. 3) Production DBs have only current state, not historical data. 4) Data from multiple systems needs to be integrated.
What is the difference between a data warehouse and a database?
A database (OLTP) stores current operational data for fast reads/writes. A data warehouse (OLAP) stores historical, integrated data from many databases for complex analysis. Different access patterns, different optimizations.

What is the difference between OLTP and OLAP?

Data Warehouse Fundamentals 7 min read Difficulty: Beginner 2 of 37
Definition

OLTP (Online Transaction Processing) handles day-to-day operations — fast inserts, updates, deletes on current data. OLAP (Online Analytical Processing) handles complex queries — aggregations, joins, and analysis on historical data.

OLTP is row-oriented and normalized; OLAP is often column-oriented and denormalized.

OLTP OLAP Row-Oriented Column-Oriented Normalization Denormalization
OLTP vs OLAP
AspectOLTPOLAP
PurposeRun the business (operations)Analyze the business (decisions)
QueriesSimple (SELECT by key, INSERT)Complex (GROUP BY, JOIN, window functions)
Data VolumeSmall per query (single row)Large per query (millions of rows)
SchemaNormalized (3NF)Denormalized (star/snowflake)
UsersApplication users (thousands)Analysts, managers (dozens)
DataCurrent state onlyHistorical (years of data)
StorageRow-oriented (MySQL, PostgreSQL)Column-oriented (Redshift, BigQuery)
Response timeMillisecondsSeconds to minutes
Cross Questions
Why are OLAP systems column-oriented?
Analytical queries read a few columns across millions of rows (e.g., SUM(amount)). Column stores keep each column contiguous on disk — reading only the needed columns is much faster than scanning entire rows. Also enables better compression.
Can one system do both OLTP and OLAP?
HTAP (Hybrid Transactional/Analytical Processing) systems try: TiDB, AlloyDB, SingleStore. But most architectures still separate them — the workload patterns are fundamentally different.

What is the Inmon vs Kimball approach?

Data Warehouse Fundamentals 8 min read Difficulty: Beginner 3 of 37
Definition

Two foundational approaches to data warehouse design: Inmon (top-down) — build a normalized enterprise data warehouse first, then create dimensional data marts. Kimball (bottom-up) — build dimensional data marts first, integrate through conformed dimensions.

Most modern warehouses use Kimball's dimensional modeling (star schemas) for its simplicity and query performance.

Inmon Kimball Top-Down Bottom-Up Dimensional Modeling Data Mart
Inmon vs Kimball
AspectInmon (Top-Down)Kimball (Bottom-Up)
ArchitectureEnterprise DW → data martsData marts → integrated DW
SchemaNormalized (3NF)Denormalized (star schema)
Build timeLong — full DW before first reportFast — deliver one mart at a time
ComplexityHigh — enterprise-wide modeling upfrontLower — incremental, business-process-driven
ETLETL into normalized DW, then transform to martsETL directly into dimensional marts
Query performanceSlower (many joins in 3NF)Faster (fewer joins in star schema)
FlexibilityHandles complex relationships wellSimpler but may have redundancy
CostHigher upfront, lower maintenanceLower upfront, requires governance
Interview Tip

"In practice, Kimball's dimensional modeling is more widely adopted — especially in modern cloud warehouses (Snowflake, BigQuery, Redshift). It delivers value faster (one data mart at a time), is easier for analysts to query (star schema), and aligns with agile delivery. Inmon is still used in large enterprises (banking, telecom) where a single source of truth in 3NF is valued."

Cross Questions
What is a data mart?
A data mart is a subset of a data warehouse focused on a single business area — sales mart, finance mart, HR mart. In Kimball, marts are the primary unit; in Inmon, they are derived from the enterprise DW.
Can you combine both approaches?
Yes — a "hybrid" approach: build an integrated staging area (normalized, Inmon-style), then transform into dimensional data marts (Kimball-style) for end users. This is common in large organizations.

What is a data mart?

Data Warehouse Fundamentals 5 min read Difficulty: Beginner 4 of 37
Definition

A data mart is a focused subset of a data warehouse designed for a specific business area, department, or use case (e.g., sales, finance, marketing).

Data marts are smaller, faster to build, and optimized for the queries that a specific team runs. They can be dependent (fed from the DW) or independent (fed directly from sources).

Data Mart Dependent Independent Hybrid Business Area
Data Mart Types
TypeData SourceProsCons
DependentCentral data warehouseConsistent, governed, single source of truthRequires full DW to exist first
IndependentDirectly from source systemsFast to build, no DW dependencySilos, inconsistencies across marts
HybridDW + additional sourcesFlexible, can extend centrally managed dataMore complex ETL
Cross Questions
What is the difference between a data warehouse and a data mart?
A data warehouse is the enterprise-wide repository; a data mart is a department-specific subset. DW = the whole store; data mart = one department's shelf. Marts are smaller, faster to query, and tailored to specific analytics needs.
When should you use a data mart vs a full data warehouse?
Start with a data mart when: a single team needs analytics fast, budget is limited, or you're prototyping. Build a full DW when: multiple teams need consistent metrics, regulatory compliance requires a single source of truth, or data integration across systems is essential.

What is ETL vs ELT?

Data Warehouse Fundamentals 6 min read Difficulty: Beginner 5 of 37
Definition

ETL (Extract, Transform, Load): data is transformed in a staging area before loading into the warehouse. ELT (Extract, Load, Transform): data is loaded raw into the warehouse first, then transformed using the warehouse's compute power.

Modern cloud warehouses (Snowflake, BigQuery) favor ELT because they can efficiently transform data at scale using SQL.

ETL ELT Extract Transform Load Staging
How It Works — Step by Step
Step 1 / 5
  1. 1Source systems — OLTP databases, APIs, flat files, event streams — produce the raw data that feeds the warehouse.
  2. 2Extract — pull data from sources into a staging area (raw, as-is copies). This isolates the warehouse from source system changes.
  3. 3Transform — clean, conform, and restructure data: apply business rules, handle SCDs, denormalize into star schema format.
  4. 4Load — write the transformed data into fact and dimension tables in the data warehouse.
  5. 5Serve — BI tools, dashboards, and analysts query the warehouse for reports and ad-hoc analysis.
ETL vs ELT
AspectETLELT
Transform locationExternal engine (Informatica, Talend, Spark)Inside the warehouse (SQL)
Data loadedClean, transformed dataRaw data first, then transformed
Warehouse loadLower (only clean data)Higher (stores raw + transformed)
FlexibilityMust anticipate transformations upfrontRaw data available for ad-hoc transforms
Speed to loadSlower (transform is blocking)Faster (load is simple COPY)
ToolsInformatica, Talend, SSIS, Sparkdbt, Snowflake SQL, BigQuery SQL
Best forOn-prem DW, complex transformationsCloud DW, iterative analytics
Cross Questions
Why is ELT becoming more popular?
Cloud warehouses (Snowflake, BigQuery, Redshift) have massive compute that can transform data efficiently with SQL. Load raw data fast (COPY), then use dbt or SQL for transforms. Cheaper, faster iteration, and raw data is always available for new use cases.
What is dbt and how does it fit?
dbt (data build tool) is the "T" in ELT. It lets you write transformations as SQL SELECT statements with version control, testing, and documentation. It runs inside the warehouse — no separate compute. It has become the standard for modern ELT.

What is a star schema?

Dimensional Modeling 8 min read Difficulty: Beginner 6 of 37
Definition

A star schema is the most common dimensional modeling pattern: a central fact table surrounded by denormalized dimension tables.

The fact table stores measurable events (amounts, quantities, counts) with foreign keys to dimensions. Dimension tables are wide, flat, and denormalized — all descriptive attributes in one table.

Star Schema Fact Table Dimension Table Denormalized Foreign Key
How It Works — Step by Step
Step 1 / 4
  1. 1The fact table sits at the center — it stores measurable business events (sales, orders, clicks) with foreign keys to dimensions and numeric measures.
  2. 2Dimension tables provide context: Date and Product describe the "who, what, when, where" of each fact row.
  3. 3More dimensions (Store, Customer) connect via foreign keys. Each dimension is denormalized — all attributes in one wide table.
  4. 4The star shape: one fact table at the center, dimensions radiating outward. Each query JOINs the fact table directly to dimensions — no chaining.
Why Star Schema?
AdvantageWhy
Simple queriesEach dimension is one JOIN away from the fact table — no chaining
Fast performanceFewer JOINs, predictable query plans, easy to optimize
Easy to understandBusiness users can intuit the model (facts + context)
BI tool friendlyAll major BI tools (Tableau, Power BI) are optimized for star schemas
Aggregation readyGROUP BY on any combination of dimension attributes
Cross Questions
What is denormalization and why is it used here?
Denormalization combines normalized tables into wider tables with redundant data. In a star schema, the Product dimension has category_name repeated across rows (not in a separate Category table). This trades storage for query speed — one JOIN instead of many.
How many dimensions is typical?
A typical fact table has 5–15 dimension foreign keys. Common dimensions: Date, Customer, Product, Store/Location, Employee, Promotion, Channel. The Date dimension is almost always present.

What is a snowflake schema?

Dimensional Modeling 6 min read Difficulty: Beginner 7 of 37
Definition

A snowflake schema is a variation of the star schema where dimension tables are normalized into sub-tables. Each level of hierarchy becomes its own table.

Example: instead of a Product dimension with category_name, you have Product → Category → Department as separate tables.

Snowflake Schema Normalized Dimensions Sub-Dimensions Hierarchy
How It Works — Step by Step
Step 1 / 5
  1. 1The snowflake schema starts like a star — a central fact table with dimension foreign keys.
  2. 2Dimensions are normalized — instead of one wide table, attributes are split into sub-tables (Product → Category → Department).
  3. 3Each level of normalization creates another branch, like a snowflake crystal. Product links to Category, which links to Department.
  4. 4The Store dimension is also normalized: Store → City → State. This eliminates data redundancy but adds more JOINs.
  5. 5Trade-off: snowflake saves storage (no repeated "Electronics" across products) but queries require more JOINs and are harder to write and optimize.
Star vs Snowflake
AspectStar SchemaSnowflake Schema
DimensionsDenormalized (one flat table)Normalized (hierarchy tables)
JOINsFewer (fact → dim)More (fact → dim → sub-dim)
StorageMore (repeated data in dims)Less (no redundancy)
Query speedFasterSlower (more JOINs)
ComplexitySimpler for usersMore complex to query
MaintenanceEasier (fewer tables)Harder (more tables, more ETL)
Use caseMost OLAP workloadsWhen storage matters or dims are very large
Cross Questions
Which is better — star or snowflake?
Star schema is preferred in the vast majority of cases. Modern columnar warehouses handle the redundancy well, and the simpler queries outweigh storage savings. Snowflake is used when dimensions are extremely large (millions of products with deep hierarchies) or strict normalization is required.
What is a galaxy schema?
A galaxy schema (or fact constellation) has multiple fact tables sharing common dimension tables. For example, Sales_Fact and Inventory_Fact both use the Product and Date dimensions. This is how most real-world warehouses look.

What is a fact table?

Dimensional Modeling 8 min read Difficulty: Beginner 8 of 37
Definition

A fact table stores quantitative, measurable data about business events or processes — the "what happened" and "how much."

Each row represents one event at the defined grain. Columns include foreign keys to dimension tables and measures (numeric values for analysis).

Critical Rule: The grain is the FIRST design decision: "What does one row represent?" — one sale, one daily balance, one order lifecycle.
Fact Table Measures Grain Foreign Keys Additive Semi-Additive
How It Works — Step by Step
Step 1 / 5
  1. 1Transaction facts — one row per discrete business event. Most common: each sale, each click, each payment. Rows only grow.
  2. 2Periodic snapshot facts — one row per entity per time period. Captures state at regular intervals: daily account balance, monthly sales totals.
  3. 3Accumulating snapshot facts — one row per business process lifecycle. Updated as milestones are reached: order placed → picked → shipped → delivered.
  4. 4Key difference: transaction facts are append-only; periodic snapshots replace per period; accumulating snapshots update existing rows.
  5. 5Choose the type based on the business question. Most warehouses combine all three types across different fact tables.
Types of Measures
Measure TypeDescriptionExample
AdditiveCan be summed across all dimensionsRevenue, quantity, cost
Semi-additiveCan be summed across some dimensions (not time)Account balance, inventory count
Non-additiveCannot be summed meaningfullyRatios, percentages, unit price
Cross Questions
What is a factless fact table?
A fact table with no measures — only foreign keys. It records that an event occurred without quantifying it. Example: a student_attendance fact tracks which student attended which class on which date. The "measure" is the presence of the row itself.
What is the grain of a fact table?
The grain defines the level of detail — what one row represents. "One row per transaction per product" or "one row per customer per day." Always define the grain FIRST — it determines which dimensions and measures are possible.

What is a dimension table?

Dimensional Modeling 7 min read Difficulty: Beginner 9 of 37
Definition

A dimension table stores descriptive attributes that provide context to fact table measures — the "who, what, when, where, why, how" of business events.

Dimensions are typically wide (many columns, 50–100+), short (thousands to millions of rows), and denormalized (all attributes in one table for easy JOINs).

Cross Questions
What is a surrogate key?
A warehouse-generated integer key (1, 2, 3, …) used as the primary key of a dimension table. It replaces the natural business key (customer_id, product_code) to handle SCDs, protect against source system key changes, and improve join performance.
What is a conformed dimension?
A dimension shared identically across multiple fact tables and data marts. The Date dimension with the same date_key, attributes, and values is used by Sales, Inventory, and HR facts. This ensures consistent reporting — "Q1" means the same thing everywhere.

What is the grain of a fact table?

Dimensional Modeling 6 min read Difficulty: Beginner 10 of 37
Definition

The grain (or granularity) defines what a single row in the fact table represents. It is the most important decision in dimensional modeling — everything else follows from it.

Examples: "one row per sales transaction per line item," "one row per customer per day," "one row per order lifecycle."

Best Practice: Kimball's rule: always choose the lowest (finest) grain available. You can aggregate up but never drill down past the grain.
Grain Granularity Atomic Aggregated Drill-Down
How It Works — Step by Step
Step 1 / 4
  1. 1The grain defines what one row in the fact table represents. It is the first decision in dimensional modeling — everything else follows.
  2. 2Coarse grain — one row per store per month. Pre-aggregated, smaller table, but you can't drill down to individual transactions.
  3. 3Fine grain (atomic) — one row per individual transaction. Largest table, but supports any aggregation: by day, product, store, customer.
  4. 4Kimball's rule: always store at the finest grain possible. You can always aggregate up (roll-up) but you can never disaggregate (drill down past the grain).
Cross Questions
How do you state the grain?
Write one clear English sentence: "One row per ___." Examples: "One row per retail transaction per line item." "One row per patient per hospital visit." "One row per daily account balance." If you can't state it clearly, your design isn't ready.
What is a pre-aggregated fact table?
A fact table at a coarser grain than the atomic data — e.g., monthly sales instead of individual transactions. Used for performance (faster queries) but limits drill-down. Always keep the atomic fact table alongside pre-aggregated ones.

What are Slowly Changing Dimensions (SCDs)?

Slowly Changing Dimensions 9 min read Difficulty: Basic 11 of 37
Definition

Slowly Changing Dimensions (SCDs) handle the problem of dimension attributes that change over time. When Anuj moves from Mumbai to Pune, how should the Customer dimension reflect this?

SCDs define strategies for tracking these changes — from ignoring history (Type 1) to preserving full history (Type 2). The choice depends on whether historical analysis matters for that attribute.

SCD Type 1 Type 2 Type 3 History Surrogate Key
How It Works — Step by Step
Step 1 / 4
  1. 1SCD Type 1: Overwrite — simply update the value in place. Old data is lost. Use for corrections (e.g. fixing a typo) or when history doesn't matter.
  2. 2SCD Type 2: Add New Row — insert a new row with the updated value, keeping the old row with an end date. Uses surrogate keys, start/end dates, and a current flag.
  3. 3SCD Type 3: Add Column — add a "previous" column alongside the current value. Only tracks one change — limited history.
  4. 4Type 2 is the standard choice in production warehouses. It preserves full history and supports point-in-time analysis. Surrogate keys decouple the DW from source system IDs.
SCD Types
TypeStrategyHistoryComplexityWhen to Use
Type 0Never changeOriginal value onlyLowestImmutable attributes (date of birth, original signup date)
Type 1OverwriteNone — old value lostLowCorrections, non-critical attributes (phone format fix)
Type 2Add new rowFull history preservedMediumMost attributes — enables point-in-time analysis
Type 3Add columnPrevious + current onlyLowWhen only the last change matters (previous department)
Type 4History tableFull history in separate tableHighWhen current dimension must stay small / fast
Type 6Hybrid (1+2+3)Full history + current value columnHighestWhen you need both historical joins and current state quickly
Cross Questions
Which SCD type is most common?
Type 2 is the standard for most attributes. It preserves full history using surrogate keys, start/end dates, and a current flag. Type 1 is used alongside for corrections. Most dimensions use a mix: Type 2 for important attributes, Type 1 for non-critical ones.
What is SCD Type 6?
A hybrid of Types 1+2+3: like Type 2, it adds a new row on change, but it also adds a "current" column (like Type 3) and updates that column in ALL rows for that entity (like Type 1). This way, every historical row also shows the latest value for easy filtering.

How does SCD Type 2 work in detail?

Slowly Changing Dimensions 8 min read Difficulty: Basic 12 of 37
Definition

SCD Type 2 adds a new row whenever a tracked attribute changes, preserving the old row with an end date. This provides full history and enables point-in-time analysis.

Each row has: a surrogate key (unique per version), the natural key (links versions), effective_start, effective_end, and is_current flag.

SCD Type 2 Surrogate Key Effective Date is_current Point-in-Time
SCD Type 2 Example
SCD Type 2 Walkthrough
# Customer dimension with SCD Type 2

# Step 1: Anuj signs up (initial load)
# | surr_key | cust_id | name | city   | start_date | end_date   | is_current |
# |----------|---------|------|--------|------------|------------|------------|
# | 1001     | C101    | Anuj | Mumbai | 2023-01-15 | 9999-12-31 | Y          |

# Step 2: Anuj moves to Pune on 2024-06-01

# Old row updated (close it out):
# | 1001 | C101 | Anuj | Mumbai | 2023-01-15 | 2024-05-31 | N |

# New row inserted:
# | 1002 | C101 | Anuj | Pune   | 2024-06-01 | 9999-12-31 | Y |

# Querying:
# "What were Anuj's sales when he was in Mumbai?"
# SELECT SUM(amount) FROM sales s
# JOIN dim_customer c ON s.cust_key = c.surr_key  -- surr_key preserves history
# WHERE c.cust_id = 'C101' AND c.city = 'Mumbai'

# "What city was Anuj in on 2024-03-15?"
# SELECT city FROM dim_customer
# WHERE cust_id = 'C101'
#   AND '2024-03-15' BETWEEN start_date AND end_date
Cross Questions
Why use surrogate keys with SCD Type 2?
The natural key (cust_id) is the same across versions — you can't use it as a primary key. The surrogate key (1001, 1002) is unique per version. The fact table stores the surrogate key, which locks each fact row to the correct historical dimension version.
How does end_date = 9999-12-31 work?
It marks the current row as "still active." Using a far-future date (instead of NULL) simplifies BETWEEN queries: WHERE sale_date BETWEEN start_date AND end_date works for all rows, current and historical. 9999-12-31 is a convention, not a standard.

What is a surrogate key vs a natural key?

Slowly Changing Dimensions 6 min read Difficulty: Basic 13 of 37
Definition

A natural key is a business identifier from the source system (employee_id, product_code, SSN). A surrogate key is a warehouse-generated integer with no business meaning.

Data warehouses use surrogate keys as primary keys in dimension tables. The natural key is stored alongside for reference.

Cross Questions
Why not just use the natural key as the primary key?
Three reasons: 1) SCD Type 2 creates multiple rows per natural key — you need a unique surrogate per version. 2) Source system keys can change (company reorg, system migration). 3) Integrating multiple sources may have conflicting keys (both systems use cust_id=1).
What about the Date dimension — does it use a surrogate key?
Often yes, but as a "smart key": 20240615 (YYYYMMDD format integer). This serves as both surrogate and natural key — easy to read, fast to join, and supports WHERE date_key BETWEEN 20240101 AND 20240630 without a join.

What are degenerate dimensions and junk dimensions?

Slowly Changing Dimensions 7 min read Difficulty: Basic 14 of 37
Definition

A degenerate dimension is a dimension key stored directly in the fact table with no associated dimension table. Common examples: order number, invoice number, transaction ID.

A junk dimension combines low-cardinality flags and indicators into a single dimension table, reducing the number of foreign keys in the fact table.

Cross Questions
What is a role-playing dimension?
The same physical dimension table used multiple times with different meanings. A Date dimension appears as order_date_key, ship_date_key, and delivery_date_key in an orders fact table. In SQL, you JOIN the same Date table three times with three aliases.
What is a mini-dimension?
A subset of frequently changing attributes extracted from a large dimension. Instead of creating a new SCD Type 2 row every time demographics change on a million-row Customer dim, extract age_band, income_band, etc. into a small separate dimension. Reduces Type 2 row explosion.

What are OLAP operations?

OLAP & Query Patterns 8 min read Difficulty: Basic 15 of 37
Definition

OLAP operations are the core analytical actions performed on a multidimensional data cube: slice, dice, drill-down, roll-up, and pivot.

These operations navigate the cube to answer business questions at different levels of detail and from different perspectives.

OLAP Slice Dice Drill-Down Roll-Up Pivot Cube
How It Works — Step by Step
Step 1 / 6
  1. 1A data cube organizes measures (e.g. sales amount) along multiple dimensions (Time, Product, Store). OLAP operations navigate this cube.
  2. 2Slice — fix one dimension to a single value, reducing the cube by one dimension. "Show sales for Q1 2024 only."
  3. 3Dice — fix multiple dimensions to specific values or ranges. "Q1 2024 + Electronics + Mumbai stores."
  4. 4Drill-down goes to finer detail (Year → Quarter); Roll-up summarizes to coarser levels (Month → Quarter). Both navigate the hierarchy.
  5. 5Pivot rotates the cube — swapping which dimension appears on rows vs columns. Same data, different perspective.
  6. 6These five operations are the core of OLAP analysis. SQL equivalents: WHERE (slice/dice), GROUP BY with hierarchies (drill/roll), and PIVOT.
SQL Examples
OLAP Operations in SQL
# OLAP operations in SQL

# SLICE: fix one dimension
SELECT product, store, SUM(amount)
FROM sales
WHERE year = 2024              -- slice on Time = 2024
GROUP BY product, store;

# DICE: fix multiple dimensions
SELECT product, SUM(amount)
FROM sales
WHERE year = 2024
  AND region = 'West'           -- dice on Time + Region
  AND category = 'Electronics'
GROUP BY product;

# DRILL-DOWN: finer granularity (Year → Quarter)
SELECT quarter, SUM(amount)
FROM sales
WHERE year = 2024
GROUP BY quarter;

# ROLL-UP: coarser granularity (Month → Year)
SELECT year, SUM(amount)
FROM sales
GROUP BY year;

# PIVOT: restructure the output
SELECT product,
    SUM(CASE WHEN quarter = 'Q1' THEN amount END) AS Q1,
    SUM(CASE WHEN quarter = 'Q2' THEN amount END) AS Q2,
    SUM(CASE WHEN quarter = 'Q3' THEN amount END) AS Q3,
    SUM(CASE WHEN quarter = 'Q4' THEN amount END) AS Q4
FROM sales WHERE year = 2024
GROUP BY product;
Cross Questions
What is MOLAP vs ROLAP?
MOLAP (Multidimensional OLAP) stores data in pre-computed cubes — very fast reads but slow to update. ROLAP (Relational OLAP) uses the warehouse's relational engine — slower reads but no pre-computation needed. HOLAP is a hybrid. Modern column-store warehouses make ROLAP fast enough for most use cases.
What are GROUPING SETS, ROLLUP, and CUBE in SQL?
They generate multiple levels of aggregation in one query. ROLLUP generates hierarchical subtotals (year → quarter → month → grand total). CUBE generates all possible combinations. GROUPING SETS lets you specify exactly which groupings to compute. Much more efficient than UNION ALL of separate queries.

How do you store hierarchies in a star schema?
Flatten them into the dimension table. A Product dimension has columns: item_name, subcategory, category, department — all in one row. This enables GROUP BY at any level without extra JOINs. The trade-off is redundancy (department name repeated across products).

Why not just add multiple promo columns to the fact?

What is a weighting factor?
A decimal (0 to 1) that allocates the fact measure proportionally across the many-to-many members. If an order used two promotions, each gets weight 0.5 — so SUM(amount * weight) still totals to the correct amount. Without it, you double-count.

When do you use accumulating snapshots vs transaction facts?

How does partitioning improve data warehouse performance?

Partitioning divides large tables into smaller, manageable segments based on column values. Queries that filter on the partition key scan only relevant partitions — not the entire table.

Types: Range (date ranges), List (specific values), Hash (even distribution). Most DW partitioning is range-based on date columns, matching how analysts query: by month, quarter, or year.

# Range partitioning by date (most common in DWs)
CREATE TABLE fact_sales (
    sale_key    BIGINT,
    date_key    INT,
    product_key INT,
    store_key   INT,

What is partition pruning?
The query optimizer automatically skips partitions that cannot contain matching rows. If you query WHERE date_key BETWEEN 20240101 AND 20240331, only the Q1 2024 partition is scanned. This is automatic — no query changes needed. Check with EXPLAIN to verify pruning is happening.
How do you choose a partition key?
Pick the column most commonly used in WHERE clauses — almost always the date column in a DW. Good partition keys: high selectivity (filters eliminate most partitions), used in most queries, monotonically increasing (new data goes to the latest partition). Bad: columns with too few values (2 partitions) or too many (millions).

What is columnar storage and why is it used in data warehouses?

Definition

Columnar storage stores data by column instead of by row. A query that reads 3 columns out of 100 touches only 3% of the data — dramatically reducing I/O for analytical queries.

Row-based storage (OLTP) reads all columns per row — good for single-row lookups. Column-based storage (OLAP) reads only needed columns — good for aggregations across millions of rows.

Why does columnar storage compress better?
Same-type values stored together (all integers, all strings) have high redundancy. Run-length encoding: "Mumbai, Mumbai, Mumbai, Pune" → "Mumbai×3, Pune×1." Dictionary encoding: replace repeated strings with small integers. A 1 TB row-store table might compress to 100–200 GB columnar.
What file formats use columnar storage?
Apache Parquet (most popular — used by Spark, Databricks, Snowflake internally). Apache ORC (Hive ecosystem). Both support predicate pushdown (skip row groups based on min/max statistics), column pruning, and excellent compression. CSV and JSON are row-oriented — avoid them for large analytical datasets.

Query Plan EXPLAIN Full Scan Spilling Query Rewrite Optimization
Query Optimization Patterns
Query Anti-Patterns & Fixes
# Common DW query anti-patterns and fixes

# BAD: Function on column prevents partition pruning
SELECT * FROM fact_sales
WHERE YEAR(sale_date) = 2024;

# GOOD: Direct range filter — partition pruning works
SELECT * FROM fact_sales
WHERE sale_date BETWEEN '2024-01-01' AND '2024-12-31';

# BAD: SELECT * reads all columns (columnar waste)
SELECT * FROM fact_sales WHERE region = 'West';

# GOOD: Select only needed columns
SELECT date_key, product_key, amount
FROM fact_sales WHERE region = 'West';

# BAD: Cartesian join (missing join condition)
SELECT * FROM fact_sales f, dim_product p;  -- millions × thousands

# GOOD: Explicit join
SELECT f.amount, p.product_name
FROM fact_sales f
JOIN dim_product p ON f.product_key = p.product_key;

# BAD: Correlated subquery (runs once per row)
SELECT * FROM fact_sales f
WHERE amount > (SELECT AVG(amount) FROM fact_sales WHERE store_key = f.store_key);

# GOOD: Window function or CTE
WITH store_avg AS (
    SELECT store_key, AVG(amount) AS avg_amt FROM fact_sales GROUP BY store_key
)
SELECT f.* FROM fact_sales f
JOIN store_avg s ON f.store_key = s.store_key
WHERE f.amount > s.avg_amt;
Cross Questions
What does spilling to disk mean?
When a query needs more memory than allocated (large sorts, joins, aggregations), the warehouse writes intermediate results to disk — which is 10–100x slower. Fix: increase warehouse size (Snowflake), reduce data volume with better filters, or break the query into stages. EXPLAIN ANALYZE shows spill metrics.
How do you read a query plan?
Look for: 1) Full table scans (should see partition pruning). 2) Data volume at each step (are filters applied early?). 3) Join types (hash join for large-large, nested loop for large-small). 4) Spilling indicators. 5) Estimated vs actual rows (large differences indicate stale statistics). In Snowflake: use Query Profile in the web UI.

If a query is byte-identical to one run in the last 24 hours AND the underlying data hasn't changed, Snowflake returns the cached result instantly — no compute used, no credits charged. Even a suspended warehouse returns cached results. Adding a space or changing case breaks the cache match.
When should you bypass the cache?
During performance testing — you want to measure actual query time, not cache hits. Snowflake: ALTER SESSION SET USE_CACHED_RESULT = FALSE. BigQuery: use the --nouse_cache flag. Also bypass when you need guaranteed-fresh results after a data load that might not have invalidated the cache yet.

How do you handle requirements that cross business processes?
That's where the Bus Matrix shines. If Orders and Inventory both use dim_product and dim_date (conformed dimensions), you can drill-across: "Compare sales to inventory levels by product by month." Build the highest-value process first, conform its dimensions, then add processes that reuse them.
How many fact tables should a warehouse have?
One per business process at the atomic grain, plus aggregates. A typical enterprise: 10–30 atomic fact tables (sales, inventory, shipments, returns, web clicks, HR, finance). Each has its own grain. Cross Questions
What is an unknown member row?
A placeholder dimension row (surr_key = -1 or 9999) used when a fact references a dimension member that doesn't exist yet. Every dimension should have one. When the real member arrives, either: 1) update the placeholder (simple), or 2) insert the real row and re-key the facts (correct for SCD Type 2).
How do you make ETL idempotent for late data?
Idempotent = running the same load twice produces the same result. Use MERGE (upsert) instead of INSERT. Include a load_date and batch_id. For reprocessing: DELETE WHERE batch_date = X, then re-INSERT. In Spark/Delta: MERGE INTO handles this natively with matched/not-matched clauses.

Cross Questions
When do you use a bridge table vs a factless fact?
Factless fact: when the relationship IS the event (enrollment, attendance, coverage). No measures needed — the row's existence is the fact. Bridge table: when you need to allocate a measure across the M:M relationship (split sales credit across promotions, allocate budget across skills). Weighting factors prevent double-counting.
How do you handle arrays or JSON in dimensions?
Don't store arrays in dimension columns — they break GROUP BY and JOIN. Instead: 1) Bridge table (standard approach). 2) In modern DWs: LATERAL FLATTEN (Snowflake) or UNNEST (BigQuery) to explode arrays into rows at query time. The bridge table is better for performance; UNNEST is convenient for semi-structured exploration.

What is Change Data Capture (CDC) in a DW context?

Design Patterns & Real-World Scenarios 7 min read Difficulty: Expert 35 of 37
Definition

Change Data Capture (CDC) identifies and captures only the data that changed in source systems (inserts, updates, deletes) — avoiding full table reloads on every ETL run.

CDC feeds incremental changes to the warehouse, enabling near-real-time updates. Tools: Debezium (log-based, open source), AWS DMS, Oracle GoldenGate, Fivetran (managed).

Cross Questions
How does log-based CDC work with Debezium?
Debezium reads the database transaction log (MySQL binlog, PostgreSQL WAL, Oracle redo log) and emits change events to Kafka topics. Each event contains: operation type (INSERT/UPDATE/DELETE), before/after values, timestamp, and source metadata. The DW consumer applies these as MERGE operations to stay in sync.
How does CDC feed into SCD Type 2?
CDC provides a stream of INSERT/UPDATE/DELETE events. For SCD Type 2: INSERT → new dimension row. UPDATE on tracked attribute → close current row (set end_date), insert new row. DELETE → close current row (soft delete). The CDC timestamp becomes the effective_start date of the new version.

How does dbt handle testing?
dbt has built-in tests: unique, not_null, accepted_values, relationships (referential integrity). Custom tests are SQL queries that return failing rows. Tests run after each dbt build: dbt test. What is source-to-target reconciliation?
Compare source system totals to warehouse totals after each load. Example: SELECT COUNT(*), SUM(amount) FROM source_orders WHERE order_date = '2024-06-01' — then compare to the same query on fact_sales. Differences indicate: dropped rows (ETL filter bug), duplicates (missing dedup), or transformation errors (rounding, type casting).

Cross Questions
What is the One Big Table anti-pattern?
Joining all dimensions directly into the fact table — one massive denormalized table. Problems: huge row width (100+ columns), repeated dimension data wastes storage, updates require rewriting the entire table, and ad-hoc queries are confusing. A star schema keeps the fact narrow (keys + measures) and dimensions separate.
Why is mixing grains dangerous?
If you put order-level data (shipping cost) and line-item-level data (item price) in the same fact table, SUM(shipping_cost) is multiplied by the number of line items. This is the #1 cause of wrong numbers in reports. Rule: one grain per fact table, stated as one clear English sentence.
