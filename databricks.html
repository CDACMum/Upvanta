What is Databricks? What problems does it solve and when should you use it?

Databricks Foundations 8 min read Difficulty: Beginner 1 of 40
Definition

Databricks is a cloud data and AI platform built by the original creators of Apache Spark. It runs on AWS, Microsoft Azure (as Azure Databricks) and Google Cloud and gives one workspace for data engineering, SQL analytics, data science, machine learning and generative-AI applications.

Its core pieces are: managed Apache Spark plus the native Photon engine for compute; Delta Lake, an open table format that adds ACID transactions to files in your cloud storage; Unity Catalog for governance (permissions, lineage, auditing); and tools such as notebooks, Lakeflow (ingestion, declarative pipelines and jobs), Databricks SQL, MLflow and Mosaic AI. Databricks calls this architecture the lakehouse.

Lakehouse Apache Spark Photon Delta Lake Unity Catalog MLflow AWS / Azure / GCP
Analogy
Think of a large college campus built around one central library (your cloud storage). Every department, from the exam cell to the placement cell to the research lab, works from the same books, with one librarian (Unity Catalog) deciding who may read what. Nobody keeps private photocopies of the whole library.
How It Works — Step by Step
Step 1 / 4
  1. 1Data arrives from operational databases, files, event streams and SaaS tools.
  2. 2Databricks provides managed Apache Spark (and the Photon engine), stores tables in the open Delta Lake format in your cloud storage, and governs them with Unity Catalog.
  3. 3The same tables serve data engineering pipelines, SQL analytics and dashboards, data science and machine learning, and generative-AI applications.
  4. 4This is the lakehouse idea: one copy of the data in open formats, with warehouse-style reliability and governance on top of a data lake.
When to Use It
Use Databricks when…Think twice when…
Large volumes of raw files, logs or events must be cleaned and joinedThe data fits comfortably in one PostgreSQL or MySQL server
The same data feeds both BI dashboards and machine learningYou need an OLTP database for an application with millisecond row updates
You need batch and streaming pipelines on the same tablesThe team only writes SQL reports and a managed warehouse already covers it
You want open formats (Delta, Parquet, Iceberg) in your own storageYou must run entirely on-premises with no cloud account
Real-World Scenario
Who uses it
  • Banks, retailers, telecoms, healthcare and media companies use Databricks for ETL, streaming, reporting and ML.
  • Typical users: data engineers writing PySpark and SQL pipelines, analysts in Databricks SQL or Power BI, and data scientists training models tracked with MLflow.
  • At C-DAC scale: attendance logs, CCEE exam results and placement data from every centre land as files; pipelines turn them into clean Delta tables; the exam cell queries them with SQL while a data science team trains a "likely to be placed" model on the same tables.

Cross Questions
Is Databricks the same as Apache Spark?
No. Spark is the open-source engine. Databricks is a managed platform that includes an optimised Spark runtime plus Photon, Delta Lake, Unity Catalog, notebooks, job orchestration, SQL warehouses and ML tooling.
Where does the data live?
In your cloud object storage (S3, ADLS Gen2 or GCS), mostly as Delta tables (Parquet data files + a transaction log). Databricks does not lock the data inside a proprietary store.
Is Databricks a data warehouse?
It includes warehouse capabilities (Databricks SQL, SQL warehouses), but the platform is broader: it is a lakehouse that also covers streaming, data engineering and ML on the same tables.

Explain the Databricks architecture: control plane, compute plane and workspace.

Databricks Foundations 8 min read Difficulty: Beginner 2 of 40
Definition

Databricks is split into two planes. The control plane is managed by Databricks in its own cloud account: the web application, notebooks and their code, the job scheduler, the cluster manager, and Unity Catalog metadata.

The compute plane is where data is processed. With classic compute, clusters are virtual machines launched in your cloud account and virtual network. With serverless compute, Databricks runs the machines in a serverless compute plane in its account, in the same region, isolated per workspace.

A workspace is one deployment of the UI and its objects (notebooks, jobs, clusters, SQL warehouses) for a team. An account can have many workspaces, and they can share one Unity Catalog metastore per region.

Control plane Classic compute plane Serverless compute plane Workspace Account Metastore
Analogy
An airline: the control tower (control plane) plans flights and gives instructions but carries no passengers. The aircraft (compute) carry the load; some are your own planes (classic), some are chartered and ready on the runway (serverless). The cargo (data) is stored in your own warehouse at the airport, not in the tower.
How It Works — Step by Step
Step 1 / 4
  1. 1The control plane is run by Databricks: the workspace UI, notebooks, the job scheduler, the cluster manager and the Unity Catalog metastore.
  2. 2In classic compute, clusters are virtual machines created inside your cloud account and network.
  3. 3With serverless compute, Databricks runs the machines in its own account in your region; they start in seconds and you do not manage instances.
  4. 4Either way, table data stays in your cloud storage. Compute reads and writes it; the control plane only coordinates.

Cross Questions
Does table data pass through the control plane?
No. Compute reads and writes your data directly in cloud storage. The control plane stores notebook code, job definitions, query history and metadata, and sends commands to the compute.
Why would a bank prefer classic compute?
To keep processing inside its own network with private connectivity, custom routes or firewalls, specific instance types or GPUs. Serverless now supports many network controls, so the choice is narrowing.
What is the difference between an account and a workspace?
The account is the top-level billing and identity boundary (users, groups, metastores, workspaces). A workspace is one environment inside it where people do their work.

A lakehouse keeps data as open files in a lake but adds a metadata and transaction layer (Delta Lake) and a governance layer (Unity Catalog), so the files behave like reliable warehouse tables.

Data lake Data warehouse Lakehouse Open table format ACID Schema-on-read
Analogy
A data lake is a storeroom where anyone drops boxes; cheap, but nobody knows what is inside. A warehouse is a shop with labelled shelves, but everything must be repacked into the shop's own boxes. A lakehouse puts labels, a register and a lock on the storeroom, so it works like the shop without repacking.
How It Works — Step by Step
Step 1 / 4
  1. 1A data lake stores any file cheaply, but it has no transactions or schema checks, so it easily becomes a "data swamp".
  2. 2A data warehouse gives reliable, fast SQL, but data must be loaded into its own storage and copied again for ML.
  3. 3A lakehouse keeps open files in the lake and adds a transaction log and governance layer on top, so one copy serves BI and ML.
  4. 4The Delta transaction log is what turns a folder of Parquet files into a table with atomic commits, DML, schema enforcement and time travel.
Real-World Scenario
The old two-system setup

Before a lakehouse, a typical setup copied data twice: raw files into a lake (for data science), then a nightly ETL into a warehouse (for BI). The two copies drifted apart, numbers in dashboards and models disagreed, and both were paid for. On Databricks the raw files and the curated tables live in the same storage, and dashboards and ML read the same Delta tables.

Example: A Table Is Files + a Log
Python (PySpark notebook cell)
spark.sql("CREATE TABLE results AS SELECT roll_no, marks FROM students WHERE course = 'PGCP-BDA'")
spark.sql("UPDATE results SET marks = marks + 2 WHERE marks < 60")

loc = spark.sql("DESCRIBE DETAIL results").first()["location"]
for f in dbutils.fs.ls(loc):
    print(f.name)
print("--- _delta_log ---")
for f in dbutils.fs.ls(loc + "/_delta_log"):
    print(f.name)
Output
_delta_log/
part-00000-f76c…-c000.snappy.parquet
part-00000-ffdc…-c000.snappy.parquet
--- _delta_log ---
00000000000000000000.json
00000000000000000001.json

A Delta table is just a folder: Parquet data files plus a _delta_log folder with one JSON file per commit. Commit 0 is the CREATE TABLE AS SELECT; commit 1 is the UPDATE. The UPDATE did not change the first Parquet file in place: it wrote a second file and recorded in …001.json that the new file replaces the old one. The old file stays for time travel.

Steps
  1. Land raw data in the lake
    Files go to cloud storage or a Unity Catalog volume, unchanged.
  2. Convert to Delta tables
    Pipelines write cleaned data as Delta tables (bronze → silver → gold).
  3. Govern
    Register tables in Unity Catalog and grant access to groups.
  4. Serve
    BI uses SQL warehouses; data science reads the same tables from notebooks.
Cross Questions
Is a lakehouse just Parquet files?
No. Plain Parquet folders have no transactions: a failed job can leave half-written files and readers may see them. Delta adds an ordered transaction log that defines exactly which files make up each version of the table.
Can other engines read a Delta table?
Yes. Delta Lake is open source; Spark, Trino, Flink, DuckDB, Polars and others have Delta readers. With UniForm, a Delta table can also be read as an Apache Iceberg table.
Does a lakehouse make a warehouse unnecessary?
For many teams, yes: Databricks SQL warehouses serve BI directly on Delta tables. Some organisations still keep a separate warehouse for existing tools, but the lakehouse removes the need to copy data into it.

Can a SQL cell use a DataFrame created in Python?
Yes, register it first: df.createOrReplaceTempView("att"), then %sql SELECT * FROM att. Both languages share the same Spark session.
What is the difference between %run and dbutils.notebook.run()?
%run runs the other notebook inline in the same session (shared variables). dbutils.notebook.run(path, timeout, args) starts it as a separate run and only returns a string exit value; it is used for simple orchestration.
Why should secrets come from dbutils.secrets and not be written in the code?
Code is saved, versioned and shared. dbutils.secrets.get(scope, key) reads the value at run time, and Databricks redacts it if it is printed.

A classic cluster is one driver node plus zero or more worker nodes, running a chosen Databricks Runtime (DBR) version, such as an LTS release, or DBR ML with ML libraries pre-installed. Step 1 / 4
  1. 1Databricks has several kinds of compute: all-purpose clusters for interactive work, job compute created for each job run, serverless compute, and SQL warehouses for SQL and BI.
  2. 2A classic cluster has one driver that plans the work and several workers whose executors run the tasks.
  3. 3With autoscaling the cluster adds workers when there is a backlog of tasks and removes them when they are idle. Auto-termination shuts an idle cluster down.

Cross Questions
Why is job compute cheaper than all-purpose compute?
Databricks charges a lower DBU rate for automated job workloads than for interactive all-purpose clusters, and job clusters exist only for the duration of the run.
What is the difference between a standard (shared) and a dedicated (single-user) access mode?
Standard mode lets many users share a cluster with Unity Catalog isolation between them (some low-level APIs are restricted). Dedicated mode assigns the cluster to one user or group and allows all features, such as RDD APIs and some ML libraries.
What is Photon?
A vectorised query engine written in C++ that runs Spark SQL and DataFrame operations faster. It is enabled on SQL warehouses and serverless and can be enabled on clusters; it uses a higher DBU rate but often finishes jobs in much less time.

How does Spark execute code on Databricks? Explain driver, executors, jobs, stages, tasks and lazy evaluation.

Apache Spark on Databricks 9 min read Difficulty: Basic 6 of 40
Definition

Every Databricks cluster runs Apache Spark. The driver runs your notebook code, builds an execution plan and schedules work. Executors on the worker nodes run tasks, one per data partition, using one CPU core each.

Spark operations are either transformations (select, filter, join, groupBy), which only describe a new DataFrame, or actions (count, collect, show, display, writes), which need a result. Transformations are lazy: each action starts a job, the job is divided into stages at every shuffle, and each stage runs as many tasks as it has partitions.

Driver Executor Job Stage Task Partition Lazy evaluation Catalyst
Analogy
The driver is an exam controller who plans how answer sheets will be evaluated; executors are the evaluators, each checking one bundle (partition) at a time. Nothing is evaluated until the result is actually requested (the action), so the controller can first plan the cheapest way to do it.
How It Works — Step by Step
Step 1 / 5
  1. 1You write transformations (read, filter, groupBy) and finally an action such as count(), collect(), display() or a write.
  2. 2The driver turns the code into a logical plan, optimises it with the Catalyst optimiser and creates a physical plan.
  3. 3Each action becomes a job. The job is split into stages at every shuffle (data exchange between machines).
  4. 4Each stage runs as many tasks as there are partitions. Tasks run in parallel on the executors' cores.
  5. 5Transformations are lazy: Spark only records them. Work starts when an action needs a result, which lets Spark optimise the whole chain at once.
Real-World Scenario
Why lazy evaluation matters

A notebook reads a 2 TB attendance table, filters one centre, and selects three columns. Because nothing runs until display(), the Catalyst optimiser pushes the filter and the column list into the file scan: Spark reads only the needed columns of the Parquet files and skips row groups whose statistics rule out the centre.

Example
Python (PySpark notebook cell)
from pyspark.sql import functions as F

df  = spark.table("students")
bda = df.filter(F.col("course") == "PGCP-BDA").select("name", "marks")   # transformations: nothing runs yet
print(type(bda).__name__)

bda.explain()                                                            # the plan Spark will run
print("rows:", bda.count())                                              # action: a job runs now
print("partitions:", df.rdd.getNumPartitions(), "| cores:", spark.sparkContext.defaultParallelism)

On the executors, in Python worker processes next to the JVM. Data is serialised between the JVM and Python, which is why built-in functions are usually faster.

What are narrow and wide transformations? Explain shuffles, partitions, repartition and coalesce.

Apache Spark on Databricks 9 min read Difficulty: Basic 8 of 40
Definition

A narrow transformation (filter, select, withColumn, union) computes each output partition from one input partition. A wide transformation (groupBy, join, orderBy, distinct, window functions) needs rows with the same key together, so Spark performs a shuffle: data is written to local disk, sent across the network and re-read. In a plan a shuffle appears as Exchange.

After a shuffle the number of partitions is spark.sql.shuffle.partitions (200 by default). Adaptive Query Execution (AQE), on by default, measures the real shuffle sizes and coalesces many small partitions into fewer ones. On Databricks, spark.sql.shuffle.partitions = auto lets the platform pick the number.

How It Works — Step by Step
Step 1 / 4
  1. 1A narrow transformation produces each output partition from one input partition, so it runs inside a stage with no data movement.

Adaptive Query Execution (AQE) re-optimises a query between stages using actual statistics. It coalesces shuffle partitions, converts sort-merge joins to broadcast joins when a side turns out small, and splits skewed partitions in sort-merge joins (spark.sql.adaptive.skewJoin.enabled).

Step 1 / 4
  1. 1When one side of a join is small (below spark.sql.autoBroadcastJoinThreshold, 10 MB by default), Spark can use a broadcast hash join.
  2. 2The small table is sent to every executor and kept in memory as a hash table. The large table is joined where it already is, with no shuffle.
  3. 3When both sides are large, Spark uses a sort-merge join: both are shuffled by the join key, sorted, and merged partition by partition.

What is data skew in a join?
One key has far more rows than others (e.g. a default centre id), so one task gets most of the data and runs for hours while others finish in seconds. AQE splits such partitions; salting (adding a random suffix to the key) is the manual fix.
Why does a non-equi join become slow?
Hash and sort-merge joins need equality keys. Conditions such as a.ts BETWEEN b.start AND b.end fall back to nested-loop joins, which compare many pairs of rows. Add an equality key (e.g. date) if possible.

How does caching work? Compare Spark caching, the Databricks disk cache and Photon.

Definition

Spark caching: df.cache() (or persist(level)) marks a DataFrame to be kept in executor memory and disk after it is first computed. It is lazy, specific to that DataFrame's plan, and released with unpersist(). In SQL: CACHE TABLE t.

What is Delta Lake? How does the transaction log provide ACID transactions?

Delta Lake Fundamentals 10 min read Difficulty: Intermediate 11 of 40
Definition

Delta Lake is an open-source table format (a Linux Foundation project) and the default for every table on Databricks. A Delta table is a directory of Parquet data files plus a _delta_log directory: the transaction log.

Each commit is an ordered JSON file (00000000000000000000.json, …001.json, …) containing actions: add and remove for data files (with per-file statistics), metaData (schema, partitioning, properties), protocol (required reader/writer features) and commitInfo (operation, parameters, metrics). Every 10 commits or so a checkpoint Parquet file summarises the state.

ACID propertyHow Delta provides it
AtomicityA commit is one new log file: it is written completely or not at all
ConsistencySchema enforcement and constraints are checked before the commit
IsolationOptimistic concurrency: writers check for conflicts with commits made since they started; readers always see a complete snapshot (WriteSerializable by default)
DurabilityData and log live in durable cloud storage
Delta Lake Transaction log _delta_log add / remove Checkpoint Optimistic concurrency ACID
Analogy
The transaction log is a bank passbook. Money (data files) is never altered; every deposit or withdrawal is a new line. To know the balance at any date you read the passbook up to that line, and two clerks cannot write the same line number.
How It Works — Step by Step
Step 1 / 5
  1. 1Creating the table writes data file A and the first commit, 00000000000000000000.json, which records "add A" plus the schema and properties.
  2. 2Each later write adds a new numbered JSON commit. An INSERT records "add B".
  3. 3An UPDATE never modifies a Parquet file. It writes file C with the changed rows and commits "remove A, add C". A stays on disk for time travel.
  4. 4A reader replays the commits up to a version to find the current set of files. A commit is a single new file, so readers see all of it or nothing: that is atomicity. Concurrent writers use optimistic concurrency and retry or fail on conflicts.
  5. 5Every few commits a checkpoint Parquet file summarises the state, so readers do not have to replay thousands of JSON files.
Real-World Scenario
A failed nightly job

A Spark job writing the day's attendance crashes halfway after writing 140 of 300 Parquet files. With plain Parquet, dashboards would read the half-written folder. With Delta, the commit JSON was never written, so readers keep seeing the previous complete version; the orphaned files are invisible and are cleaned up later by VACUUM.

    It validates schema and constraints, and checks for conflicting commits.
  3. Commit
    It atomically creates the next numbered JSON file listing add/remove actions.
  4. Read
    Readers load the latest checkpoint and later JSON files to get the snapshot.
Cross Questions
What happens when two jobs write to the same table at once?
Both write their files, then try to commit the same next version. One wins; the other checks whether the winner touched data it read. If not (e.g. two blind appends) it retries with the next number; if yes it fails with a ConcurrentModificationException such as ConcurrentAppendException.
Why are there statistics in the add actions?
Each add stores the row count and min/max/null counts for the first 32 columns. Readers use them for data skipping: files whose ranges cannot match a filter are not read at all.
Is Delta Lake only for Databricks?
No. It is open source (delta.io) and works with Apache Spark, and there are readers/writers for Flink, Trino, Rust (delta-rs), Python (Polars, DuckDB) and more. This page's outputs were produced locally with delta-rs and Spark.

What is schema enforcement and schema evolution in Delta Lake?

Definition

Schema enforcement (schema validation) rejects writes whose schema is not compatible with the table: unknown columns, or types that cannot be safely cast. The write fails as a whole and nothing is committed.

How do UPDATE, DELETE and MERGE work in Delta Lake? Write an upsert.

Delta Lake Fundamentals 10 min read Difficulty: Intermediate 14 of 40
Definition

Delta supports full DML. UPDATE and DELETE find the files that contain matching rows and rewrite them (or, with deletion vectors, mark the rows as deleted without rewriting the file). MERGE INTO combines a source with the target on a join condition and applies clauses:

ClauseAction
WHEN MATCHED [AND cond] THEN UPDATE SET … / UPDATE SET *Change matched target rows
WHEN MATCHED [AND cond] THEN DELETERemove matched target rows
WHEN NOT MATCHED [AND cond] THEN INSERT … / INSERT *Add source rows that have no match
WHEN NOT MATCHED BY SOURCE [AND cond] THEN DELETE / UPDATEHandle target rows missing from the source

Each statement is one atomic commit. If several source rows match the same target row, MERGE fails, because the result would be ambiguous.

UPDATE DELETE MERGE INTO Upsert WHEN NOT MATCHED BY SOURCE Deletion vectors Copy-on-write
Analogy
MERGE is updating the class register from a correction list: names on both lists get their marks corrected, new names are added, and students no longer in the official list are struck off, all in one signed entry.
How It Works — Step by Step
Step 1 / 5
  1. 1MERGE joins a source (new or corrected rows) to the target table on a key.
  2. 2Rows that match are updated (or deleted) by WHEN MATCHED clauses, optionally with an extra condition.
  3. 3Source rows with no match are inserted by WHEN NOT MATCHED.
  4. 4Target rows with no source row can be deleted or updated by WHEN NOT MATCHED BY SOURCE, which keeps a table in sync with a full snapshot.
  5. 5All of it is one transaction: one new table version.

What is the small-files problem? How do OPTIMIZE, Z-ORDER and data skipping help?

Delta Lake: Time Travel & Optimisation 9 min read Difficulty: Intermediate 17 of 40
Definition

Many small writes (streaming micro-batches, hourly appends, over-partitioned tables) produce thousands of small files. Every file costs a cloud-storage request, metadata in the log and task-scheduling overhead, so reads slow down: the small-files problem.

OPTIMIZE t compacts small files into larger ones (bin-packing, target about 1 GB) in a new version; readers are not blocked. OPTIMIZE t ZORDER BY (col) also sorts rows along one or more columns so that each file covers a narrow range of values. Delta keeps min/max statistics per file, and queries skip files that cannot match a filter (data skipping).

Does OPTIMIZE change query results?

How many columns should you Z-order by?
One to three columns that appear in selective filters. Each extra column weakens the clustering of the others, and Z-ordering a column without statistics or with low cardinality does little.
Is Z-ORDER incremental?
No. Re-running it rewrites the files in scope. Liquid clustering is incremental, which is one reason Databricks recommends it for new tables.

What does VACUUM do? How do retention periods and deletion vectors affect it?

Delta Lake: Time Travel & Optimisation 8 min read Difficulty: Intermediate 19 of 40
Definition

VACUUM t permanently deletes data files that are not referenced by the current version and were marked removed longer ago than the retention threshold (default 7 days, table property delta.deletedFileRetentionDuration). It also deletes files left by failed writes. VACUUM t DRY RUN lists the files without deleting them; RETAIN n HOURS overrides the threshold.

A retention below 168 hours is refused unless spark.databricks.delta.retentionDurationCheck.enabled = false, because long-running readers or writers might still need those files. After VACUUM, time travel to versions that need deleted files fails.

Deletion vectors mark deleted or updated rows in a small file instead of rewriting the data file. The old rows physically remain until the file is rewritten (OPTIMIZE, or REORG TABLE … APPLY (PURGE)) and then vacuumed, which matters for GDPR-style deletion requests.

VACUUM DRY RUN RETAIN HOURS deletedFileRetentionDuration retentionDurationCheck Deletion vectors REORG PURGE
Analogy
VACUUM is emptying the recycle bin. Files in it can still be restored, but the bin is only emptied of items older than a week, and once emptied they are gone for good.
How It Works — Step by Step
Step 1 / 4
  1. 1UPDATE, DELETE, MERGE and OPTIMIZE leave old files on disk, marked as removed in the log. Storage keeps growing.
  2. 2VACUUM deletes files that are not part of the current version and were removed longer ago than the retention threshold (7 days by default).
  3. 3Recently removed files are kept so that running readers and short time travel still work.
  4. 4After a file is vacuumed, versions that need it can no longer be queried, even if they still appear in DESCRIBE HISTORY.

Does OPTIMIZE free storage?
Not immediately: it adds compacted files and marks the small ones removed. Storage drops after VACUUM deletes the removed files.

Definition

Analogy

Step 1 / 3
  1. 1Enable the Change Data Feed with a table property. From then on, Delta records row-level changes for every commit.
  2. 2Read them with table_changes() (SQL) or readChangeFeed (Python). Updates appear as a pre-image and a post-image; each row has the version and commit timestamp.
  3. 3Downstream tables can process only what changed since the last run instead of recomputing from the full table.

Cross Questions
CDF or Structured Streaming on the table?
A plain Delta stream only reads appends and fails (or must ignore) when rows are updated or deleted. A stream with readChangeFeed receives updates and deletes as rows, so it can propagate them.
Does CDF cost extra storage?

Is CDF the same as CDC from a database?
Similar idea, different source: CDC tools (Debezium, Lakeflow Connect) capture changes from an operational database; CDF exposes changes made to a Delta table. They are often chained: CDC → bronze → MERGE → silver → CDF → gold.

What is the medallion architecture? Build a bronze, silver and gold pipeline.

Ingestion, Streaming & the Medallion Architecture 10 min read Difficulty: Intermediate 21 of 40
Definition

The medallion architecture organises a lakehouse into layers of increasing quality. Bronze holds raw data as received (append-only, with ingestion metadata), so it can always be replayed. Silver holds cleaned, validated, de-duplicated and conformed data, typically one row per business entity or event. Gold holds business-level tables: aggregates, KPIs, dimensional models and ML features.

It is a design pattern, not a product feature: each layer is just a set of Delta tables, often in separate schemas such as cdac.bronze, cdac.silver and cdac.gold, with permissions to match.

Bronze Silver Gold Raw data Data quality Replay Incremental processing
Analogy
Gold ore (bronze) is stored as mined, so it can be re-processed if refining improves. It is then refined (silver) and finally made into jewellery (gold) for customers. You never throw away the ore.
How It Works — Step by Step
Step 1 / 4
  1. 1Bronze tables keep the raw data exactly as received, plus metadata such as ingest time and source file, so any later step can be re-run from it.
  2. 2Silver tables are cleaned and conformed: correct types, valid values, duplicates removed, related data joined.
  3. 3Gold tables are shaped for consumption: aggregates, KPIs, features for ML, often one table per use case.
  4. 4Each layer adds quality guarantees and is read by a different audience. The layers are a convention, not a product feature.
Real-World Scenario

What is Auto Loader? How is it different from COPY INTO and plain spark.read?

Ingestion, Streaming & the Medallion Architecture 8 min read Difficulty: Intermediate 22 of 40
Definition

Auto Loader is a Databricks Structured Streaming source, spark.readStream.format("cloudFiles"), that incrementally and efficiently loads new files from cloud storage or volumes. It tracks processed files in the stream checkpoint (exactly once), infers and stores the schema (cloudFiles.schemaLocation), handles schema evolution, and puts non-matching values in _rescued_data. It discovers files by directory listing or by file notification events, which scales to millions of files.

COPY INTO is a SQL command that loads files from a location into a Delta table. It is idempotent: files already loaded are skipped. It suits thousands of files and simple SQL-only loads; Auto Loader suits millions of files, continuous arrival and schema drift.

How It Works — Step by Step
Step 1 / 4
  1. 1Structured Streaming treats a stream as a table that keeps growing. You write ordinary DataFrame code; Spark runs it incrementally in micro-batches and writes to a sink.

How do you upsert streaming data into a Delta table with foreachBatch and MERGE?

Ingestion, Streaming & the Medallion Architecture 9 min read Difficulty: Intermediate 24 of 40
Definition

A Delta streaming sink can only append (or overwrite in complete mode). To apply updates from a stream (CDC events, corrections) use writeStream.foreachBatch(fn): Spark calls fn(batch_df, batch_id) once per micro-batch with an ordinary DataFrame, and inside it you can run any batch code, typically a MERGE.

Rules: de-duplicate inside the batch (latest change per key), make the function idempotent because a failed batch is retried with the same batch_id, and use batch_df.sparkSession for SQL inside the function. In Lakeflow Declarative Pipelines, AUTO CDC (formerly APPLY CHANGES) does this declaratively, including SCD Type 2.

foreachBatch MERGE Upsert CDC Idempotent batch_id AUTO CDC
Analogy
foreachBatch is like a clerk who receives a tray of correction slips every few minutes: she sorts the tray, keeps only the latest slip per student, and updates the register in one go. If she is interrupted, she processes the same tray again, so updating (not appending) is what keeps the register right.
How It Works — Step by Step
Step 1 / 4
  1. 1A streaming source delivers new and changed records, for example marks corrections or CDC events.
  2. 2foreachBatch hands every micro-batch to your function as an ordinary DataFrame, so you can use any batch operation, including MERGE.
  3. 3Inside the function, keep one row per key (latest change), then MERGE it into the target table.
  4. 4A batch can be retried after a failure, so the logic must be idempotent: MERGE on a key is; blind appends are not (use txnVersion / txnAppId options for those).
Real-World Scenario
Re-evaluation results

Re-evaluation results arrive throughout the week, sometimes twice for the same student. A foreachBatch stream keeps silver_marks current within minutes; the de-duplication step makes sure the later of two corrections wins even when both arrive in the same batch.

Example
Python (PySpark notebook cell)
from pyspark.sql import functions as F, Window

spark.sql("CREATE TABLE silver_marks AS SELECT roll_no, name, marks FROM students")

corrections = (spark.readStream.format("json")
                    .schema("roll_no INT, marks DECIMAL(5,2), changed_at TIMESTAMP")
                    .load("/Volumes/cdac/bda/landing/corrections/"))

def upsert(batch_df, batch_id):
    latest = Window.partitionBy("roll_no").orderBy(F.col("changed_at").desc())
    (batch_df.withColumn("rn", F.row_number().over(latest)).filter("rn = 1")
             .createOrReplaceTempView("changes"))
    batch_df.sparkSession.sql("""
        MERGE INTO silver_marks AS t
        USING changes AS c
        ON t.roll_no = c.roll_no
        WHEN MATCHED THEN UPDATE SET t.marks = c.marks
        WHEN NOT MATCHED THEN INSERT (roll_no, marks) VALUES (c.roll_no, c.marks)
    """).show()

q = (corrections.writeStream.foreachBatch(upsert)
                .option("checkpointLocation", "/Volumes/cdac/bda/checkpoints/silver_marks")
                .trigger(availableNow=True).start())
q.awaitTermination()
spark.table("silver_marks").filter("roll_no IN (2404, 2408, 2412)").orderBy("roll_no").show()

Cross Questions
Why not just append the changes and de-duplicate at query time?
You can (an append-only log is a valid bronze design), but every reader then pays for the de-duplication. MERGE moves the cost to write time once.
Is foreachBatch exactly-once?
It is at-least-once: a batch can run again after a failure. MERGE on a key makes repeated runs give the same result. For appends inside foreachBatch, set the Delta writer options txnAppId and txnVersion (the batch_id) so Delta ignores a duplicate commit.
How do you handle deletes from a CDC source?
Add a clause such as WHEN MATCHED AND c.op = 'D' THEN DELETE, or use AUTO CDC with APPLY AS DELETE WHEN op = 'D'.

explode or a higher-order function?
Explode when you need one row per element (joins, group by subject). Use transform/filter/aggregate when the result stays one row per record; it avoids multiplying the rows.

from pyspark.sql import functions as F

def bronze_results():
    return (spark.readStream.format("cloudFiles")
                 .option("cloudFiles.format", "json")

@dp.expect_or_drop("valid_marks", "marks BETWEEN 0 AND 100")

                 .select(F.col("roll_no").cast("int").alias("roll_no"), "subject",

Streaming table for append-style sources where each row is processed once (files, Kafka). Materialized view for results that depend on all of the data (joins, aggregates) and must reflect updates and deletes upstream.

    return "A" if m >= 85 else "B" if m >= 70 else "C"

    Spark UI → SQL/DataFrame tab or query profile.
  3. Read task metrics
    Duration and input distribution (skew), spill, shuffle sizes, files read.
  4. Fix the cause
    Data layout, join strategy, partitions, UDFs, or code that collects to the driver.
  5. Re-measure
    Compare time and DBUs; keep changes that help.
Cross Questions
Will a bigger cluster fix skew?
No. The skewed partition is still processed by one task on one core. More workers only help when work is spread evenly.
What is salting?
Adding a random number (0–N) to the hot key on the big side and replicating the small side N times, so the hot key's rows spread over N partitions. AQE skew join makes it unnecessary in many cases.
When should you enable Photon?
For SQL and DataFrame workloads with joins, aggregations and scans on Delta/Parquet, which Photon accelerates. Jobs dominated by Python UDFs or RDD code gain little.

How do you control access to data? Explain GRANT, row filters, column masks and dynamic views.

Definition

Privileges are granted to principals (users, groups, service principals) on securables. To read a table, a principal needs USE CATALOG on the catalog, USE SCHEMA on the schema and SELECT on the table. Privileges granted on a catalog or schema are inherited by the objects inside it. Every object has an owner who can grant privileges on it.

PrivilegeAllows
USE CATALOG / USE SCHEMATraverse into the container
SELECTRead tables and views
MODIFYINSERT, UPDATE, DELETE, MERGE
CREATE TABLE, CREATE SCHEMA, …Create objects in a container
READ VOLUME / WRITE VOLUMEFiles in a volume
EXECUTECall a function or use a model
MANAGE, ALL PRIVILEGESAdminister the object / everything except ownership

For finer control: a row filter is a SQL function attached to a table that returns true for rows the current user may see; a column mask is a function that returns the value or a masked version. Both can test is_account_group_member() or current_user(). Dynamic views do the same inside a view. ABAC policies apply filters and masks automatically to every table carrying a governed tag.

Analogy
Grants are the keys to buildings, floors and rooms (catalog, schema, table). A row filter is a librarian who shows each centre coordinator only their own centre's files; a column mask blacks out phone numbers on the copy you are given.
How It Works — Step by Step
Step 1 / 4
  1. 1Privileges are granted to groups on securables. To read a table a user needs USE CATALOG, USE SCHEMA and SELECT.
  2. 2A row filter is a SQL function attached to the table that decides which rows each user may see.
  3. 3A column mask is a function that returns the real value or a masked value depending on who is asking.
  4. 4One table, one copy of the data, but every user sees only what they are allowed to.
Real-World Scenario
Coordinators and the placement cell

All centres share one students table. A row filter returns only the coordinator's own centre (group coord-kharghar sees Kharghar rows), the exam cell sees everything, and a column mask shows phone numbers in full only to the placement-cell group. There is one table to maintain instead of one copy per centre.

Example
Databricks SQL (shown, not executed)
GRANT USE CATALOG ON CATALOG cdac       TO `exam-cell`;
GRANT USE SCHEMA  ON SCHEMA  cdac.bda   TO `exam-cell`;
GRANT SELECT      ON TABLE   cdac.bda.students TO `exam-cell`;
GRANT MODIFY      ON TABLE   cdac.bda.students TO `sp-results-pipeline`;   -- a service principal
REVOKE MODIFY     ON TABLE   cdac.bda.students FROM `faculty`;
SHOW GRANTS ON TABLE cdac.bda.students;

-- row filter: coordinators see their own centre, the exam cell sees all
CREATE OR REPLACE FUNCTION cdac.bda.centre_filter(centre STRING)
RETURN is_account_group_member('exam-cell')
    OR (centre = 'Kharghar' AND is_account_group_member('coord-kharghar'))
    OR (centre = 'Juhu'     AND is_account_group_member('coord-juhu'));
ALTER TABLE cdac.bda.students SET ROW FILTER cdac.bda.centre_filter ON (centre);

-- column mask: phone visible only to the placement cell
CREATE OR REPLACE FUNCTION cdac.bda.mask_phone(phone STRING)
RETURN CASE WHEN is_account_group_member('placement-cell') THEN phone
            ELSE concat(left(phone, 2), 'xxxxxx', right(phone, 2)) END;
ALTER TABLE cdac.bda.students ALTER COLUMN phone SET MASK cdac.bda.mask_phone;

-- dynamic view: the older way, still useful for shares and complex logic
CREATE OR REPLACE VIEW cdac.bda.students_secure AS
SELECT roll_no, name, centre,
       CASE WHEN is_account_group_member('placement-cell') THEN phone ELSE NULL END AS phone
FROM   cdac.bda.students
WHERE  is_account_group_member('exam-cell') OR centre = 'Kharghar';
Steps
  1. Use groups
    Grant to groups synced from the identity provider, never to individuals.
  2. Least privilege
    Readers get SELECT; only pipelines (service principals) get MODIFY.
  3. Grant at the right level
    Schema-level grants for a team's area; table-level for exceptions.
  4. Protect sensitive data
    Row filters and column masks, or tag-based ABAC policies at scale.
  5. Review
    SHOW GRANTS and the audit system table regularly.
Cross Questions
Why does a user with SELECT on a table still get "permission denied"?
They are probably missing USE CATALOG or USE SCHEMA on the parents, or the compute they use does not support Unity Catalog (e.g. a no-isolation cluster).
Row filter or dynamic view?
Row filters and masks protect the table itself, whichever way it is queried. A dynamic view only protects users who query the view, so you must also stop them reading the base table.
Who can grant privileges?
The object owner, users with MANAGE on it, owners of the parent catalog/schema, and metastore admins.

Real-World Scenario
What could go wrong, and how the design handles it
  • A centre uploads twice: the silver MERGE on (roll_no, subject) updates instead of duplicating.
  • A mark of 120: goes to quarantine with the reason; the CHECK constraint on silver is a second safety net.
  • A late correction: re-running the job MERGEs the new value and the gold table is rebuilt from silver.
  • A bug in the rank logic: fix the code and rebuild gold from silver; bronze still holds every original row.

from pyspark.sql import functions as F

# ---------------- bronze: raw rows + where they came from
(spark.read.json("/Volumes/cdac/bda/landing/ccee/")
      .withColumn("source_file", F.element_at(F.split(F.col("_metadata.file_path"), "/"), -1))
      .withColumn("ingested_at", F.current_timestamp())
      .write.mode("append").saveAsTable("bronze_ccee"))

# ---------------- silver + quarantine
spark.sql("""CREATE TABLE IF NOT EXISTS silver_ccee (
               roll_no INT NOT NULL, name STRING, course STRING, centre STRING,
               subject STRING NOT NULL, marks INT,
               CONSTRAINT valid_marks CHECK (marks BETWEEN 0 AND 100))""")

checked = (spark.table("bronze_ccee")
                .withColumn("reason", F.when(F.col("roll_no").isNull(), "missing roll_no")
                                       .when(~F.col("marks").between(0, 100), "marks out of range")))
checked.filter("reason IS NOT NULL").select("roll_no", "subject", "marks", "source_file", "reason") \
       .write.mode("overwrite").saveAsTable("quarantine_ccee")
checked.filter("reason IS NULL").createOrReplaceTempView("valid_rows")

spark.sql("""
  MERGE INTO silver_ccee AS t
  USING (SELECT CAST(roll_no AS INT) AS roll_no, name, course, centre, subject,
                CAST(marks AS INT) AS marks FROM valid_rows) AS s
  ON t.roll_no = s.roll_no AND t.subject = s.subject
  WHEN MATCHED THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *""").show()

# ---------------- gold: rank list per course
spark.sql("""
  CREATE OR REPLACE TABLE gold_rank_list AS
  SELECT course, roll_no, name, centre,
         SUM(marks) AS total,
         CASE WHEN MIN(marks) >= 40 THEN 'PASS' ELSE 'FAIL' END AS result,
         RANK() OVER (PARTITION BY course ORDER BY SUM(marks) DESC) AS course_rank
  FROM   silver_ccee
  GROUP  BY course, roll_no, name, centre""")

Students with the same total should share a rank (1, 2, 2, 4). ROW_NUMBER would give them different ranks arbitrarily; DENSE_RANK would give 1, 2, 2, 3.
How would you make this incremental for 10 lakh students?
Auto Loader with availableNow for bronze; MERGE only the new rows into silver (read bronze incrementally with a stream or CDF); recompute gold only for affected courses, or make it a materialized view in a declarative pipeline.

A declarative pipeline expresses bronze, silver (with expectations and AUTO CDC) and gold (materialized view) with far less code and handles retries and incremental refresh; a job with notebooks gives more control. Both are valid answers if you can justify them.

Scenario: implement a Slowly Changing Dimension Type 2 table with MERGE in Delta Lake.

Databricks SQL, Cost & Real-World Scenarios 10 min read Difficulty: Expert 39 of 40
Definition
SCD typeWhat happens on a changeHistory kept?
Type 0Never change the attributen/a
Type 1Overwrite the old valueNo
Type 2Close the current row (end date, flag) and insert a new current rowYes, full history
Type 3Keep the previous value in an extra columnOnly one previous value

A Type 2 dimension has validity columns such as start_date, end_date and is_current. In Delta Lake one atomic MERGE can close the old row and insert the new one, using a common trick: the source contains every changed row twice, once with the real key (it matches the current row, which is closed) and once with a NULL merge key (it never matches, so it is inserted). In a declarative pipeline, AUTO CDC … STORED AS SCD TYPE 2 does all of this for you.

SCD Type 2 Slowly changing dimension MERGE merge_key is_current AUTO CDC Point-in-time query
Analogy
A Type 2 dimension is a passport's address history: when you move, the old address is not erased; it gets an "until" date, and the new address is added below with a "from" date.
How It Works — Step by Step
Step 1 / 4
  1. 1A Type 2 dimension keeps one row per version of an entity, with validity dates and a current flag.
  2. 2When an attribute changes (a student transfers centres), the history must be kept.
  3. 3The current row is closed (end date, current = false) and a new current row is inserted, in the same transaction.
  4. 4One MERGE can do both: the source contains each changed row twice, once with the real key (to close the old row) and once with a NULL key (so it is inserted).
Real-World Scenario
Centre transfers and old reports

Kabir moves from Kharghar to Juhu on 10 March. February attendance reports must still count him at Kharghar, while March reports count him at Juhu. With a Type 2 dim_student, facts are joined to the dimension row that was valid on the fact's date, so old reports never change.

Example
Databricks SQL
SELECT * FROM student_updates ORDER BY roll_no;

MERGE INTO dim_student AS d
USING (
  SELECT u.roll_no AS merge_key, u.* FROM student_updates u          -- matches: closes the old row
  UNION ALL
  SELECT NULL AS merge_key, u.*                                      -- never matches: inserts the new version
  FROM   student_updates u
  JOIN   dim_student d ON d.roll_no = u.roll_no AND d.is_current AND d.centre <> u.centre
) AS s
ON d.roll_no = s.merge_key AND d.is_current
WHEN MATCHED AND d.centre <> s.centre THEN
  UPDATE SET d.is_current = false, d.end_date = s.effective_date
WHEN NOT MATCHED THEN
  INSERT (roll_no, name, centre, start_date, end_date, is_current)
  VALUES (s.roll_no, s.name, s.centre, s.effective_date, NULL, true);

SELECT * FROM dim_student ORDER BY roll_no, start_date;

-- point-in-time lookup: where was 2404 on 1 March?
SELECT name, centre FROM dim_student
WHERE  roll_no = 2404
  AND  DATE'2026-03-01' >= start_date
  AND  (end_date IS NULL OR DATE'2026-03-01' < end_date);

Steps
  1. Design the dimension
    Business key, tracked attributes, start/end dates, current flag (and a surrogate key if needed).
  2. Prepare the source
    One row per key per load; detect changed attributes.
  3. MERGE with the NULL-key union
    Close changed current rows and insert new versions in one commit.
  4. Query by date
    Join facts on key and date range, or filter is_current for the latest view.
Cross Questions
Why not run an UPDATE and then an INSERT?
Two commits mean a reader can see the old row closed before the new one exists, and a failure between them leaves the dimension inconsistent. MERGE does both atomically.
How do you add a surrogate key?
Use an identity column (student_sk BIGINT GENERATED ALWAYS AS IDENTITY) so each version gets its own key, and store that key in fact tables.
What does SEQUENCE BY do in AUTO CDC?
It orders changes for the same key, so out-of-order events are applied correctly: a late, older change does not overwrite a newer one.
