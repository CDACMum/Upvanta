What is dbt? Why do data teams use it?

dbt Foundations 8 min read Difficulty: Beginner 1 of 40
Definition

dbt (data build tool) is an open-source command-line tool that lets analysts and engineers transform data inside the warehouse by writing SELECT statements. dbt turns each SELECT (a model) into a view or table, works out the order to build them from their dependencies, and adds testing, documentation, version control and CI/CD practices to SQL work.

dbt handles only the T of ELT: data is extracted and loaded by other tools; dbt uses the warehouse's own compute (Snowflake, BigQuery, Databricks, Redshift, Postgres, DuckDB…).

dbt ELT Transformation Analytics Engineering SQL Data Warehouse
Analogy
Before dbt, transformations were like handwritten recipes on loose sheets: each cook kept their own copy, nobody knew which dish depended on which sauce, and mistakes were found by customers. dbt is a professional kitchen system: recipes in one book (Git), each recipe lists its ingredients (ref), dishes are prepared in the right order automatically, and every dish is tasted (tests) before it leaves the kitchen.
How It Works — Step by Step
Step 1 / 5
  1. 1Data starts in operational systems: the exam MySQL database, the attendance API, CSV exports.
  2. 2An extract-and-load tool copies it, unchanged, into the warehouse's raw schema.
  3. 3Now the raw data sits in a warehouse whose SQL engine can transform terabytes quickly.
  4. 4dbt runs the T: you write SELECT statements (models); dbt wraps them in CREATE VIEW/TABLE, runs them in dependency order and builds staging and mart layers.
  5. 5dbt itself moves no data in or out: all computation happens inside the warehouse.
Real-World Scenario
C-DAC placement analytics

Marks, attendance and placement data land in a warehouse every night. Previously, 40 stored procedures and Excel macros built the placement report; nobody knew the order or what broke when a column changed. In dbt, each step is a model in Git, dbt build runs them in order, tests check roll numbers and marks ranges, and the generated docs show exactly where each report column comes from.

Industry

dbt is used by thousands of companies (JetBlue, HubSpot, Siemens…) and created the "analytics engineer" role: people who apply software-engineering practices to SQL transformations.

Steps to Start a dbt Project
  1. Install dbt with an adapter
    pip install dbt-core dbt-duckdb (or dbt-snowflake, dbt-bigquery…).
  2. Create a project
    dbt init cdac_dw and configure the connection in ~/.dbt/profiles.yml.
  3. Check the connection
    dbt debug.
  4. Write a model
    A .sql file with a SELECT in models/; use ref() for other models.
  5. Build and test
    dbt build; then dbt docs generate && dbt docs serve.
Cross Questions
Is dbt an ETL tool?
Only the T. It does not extract or load data and does not process data on its own servers; it generates SQL that the warehouse executes.
What skills does dbt need?
SQL first, then a little Jinja (templating), YAML for configuration, and Git. No Python is required (Python models exist for some adapters).
Why not just use stored procedures?
dbt adds dependency management, modular reusable models, version control, automated tests, documentation, environments (dev/prod) and CI, which stored procedures lack or do ad hoc.

An adapter is a plugin that teaches dbt how to connect to a particular platform and generate its SQL dialect (dbt-snowflake, dbt-bigquery, dbt-databricks, dbt-redshift, dbt-postgres, dbt-spark, dbt-duckdb…). The project code stays mostly the same.

dbt Core dbt Cloud Adapter dbt-duckdb dbt-snowflake Open Source
Analogy
dbt Core is a car engine you install in your own vehicle and maintain yourself; dbt Cloud is a taxi service using the same engine, with a driver, maintenance and booking app included. Adapters are the fittings that let the engine work with different car models (warehouses).
How It Works — Step by Step
Step 1 / 4
  1. 1dbt Core is the free, open-source command-line tool: pip install dbt-core plus an adapter for your warehouse.
  2. 2With Core you provide everything around it: scheduling (Airflow, cron, CI), logs, and hosting of documentation.
  3. 3dbt Cloud is the paid managed platform: a browser IDE, job scheduler, CI for pull requests, hosted docs and lineage, and the Semantic Layer.
  4. 4Both run the same project files. Adapters translate dbt's work into each warehouse's SQL dialect.
Real-World Scenario
Choosing for the institute

The training lab uses dbt Core with DuckDB on student laptops (free, works offline). A company running Snowflake with 30 analysts chose dbt Cloud for the IDE, managed scheduling and CI; another with an existing Airflow platform runs dbt Core inside Airflow.

Can the same project run on Core and Cloud?
Yes. The project files are identical; only where it runs and how it is scheduled differ.
Is SQL portable across adapters?
Mostly, but functions differ by platform. Cross-database macros (dbt.dateadd, dbt.concat…) and dispatch help keep code portable.

What is profiles.yml? What are targets and how do dev and prod environments work?

dbt Foundations 7 min read Difficulty: Beginner 4 of 40
Definition

profiles.yml (by default in ~/.dbt/, outside the project) holds connection details. A profile contains one or more targets (e.g. dev, prod), each with its own database, schema, credentials and thread count.

The project's profile: setting picks the profile; target: in the profile is the default and --target prod overrides it. Inside Jinja, target.name, target.schema etc. are available.

profiles.yml Target dev prod Environment env_var threads
Analogy
The project is a play script; targets are stages. You rehearse on the practice stage (dev schema) and perform on the main stage (prod). Same script, different venue.
How It Works — Step by Step
Step 1 / 4
  1. 1The same models are deployed to different places. The project never contains credentials.
  2. 2Each developer runs against a dev target that writes into a personal schema, so experiments never touch production.
  3. 3The scheduler runs with --target prod, building the real tables dashboards read.
  4. 4Connection details live in profiles.yml (outside the repo); secrets come from environment variables.
Real-World Scenario
Safe development

Each analyst's dev target writes to dbt_<name>. The production job in Airflow runs dbt build --target prod with a service account whose password comes from env_var('DBT_PROD_PASSWORD').

Steps to Configure Environments
  1. Create profiles.yml
    dbt init prompts for it, or write it by hand in ~/.dbt/.
  2. Add a dev target
    Personal schema, few threads.
  3. Add a prod target
    Service account; secrets via env_var(), never committed.
  4. Verify
    dbt debug --target prod.
  5. Use in code sparingly
    e.g. {% if target.name == 'dev' %} limit 1000 {% endif %} to keep dev runs cheap.
Cross Questions
Why is profiles.yml not inside the project?
It contains credentials and differs per person/environment; keeping it outside avoids committing secrets. (DBT_PROFILES_DIR can point elsewhere.)
What do threads control?
How many models dbt builds in parallel, limited by the DAG and the warehouse's capacity.

What happens internally when you run dbt run? What is compilation?

dbt Foundations 8 min read Difficulty: Beginner 5 of 40
Definition

dbt run parses the project, compiles each model by rendering Jinja into plain SQL (ref() → real relation names), builds the DAG from the refs, then executes models in dependency order, wrapping each SELECT in the DDL/DML of its materialization. Results go to target/.

dbt compile does everything except execution, which is useful to inspect generated SQL.

dbt run dbt compile Jinja DAG Parsing target folder
Analogy
Like a mail-merge: the template letter (model with Jinja) is filled in with real names and addresses (compiled SQL), letters are sorted by route (DAG), then delivered (executed) one route after another.
How It Works — Step by Step
Step 1 / 5
  1. 1Parse: dbt reads every model, YAML file and macro in the project.
  2. 2Compile: Jinja is rendered: ref() becomes the real schema.table name for the current target, macros expand to SQL.
  3. 3Build the DAG: the ref() calls define dependencies, so dbt knows the order and what can run in parallel (threads).
  4. 4Execute: each model's SELECT is wrapped in DDL for its materialization (view, table, incremental merge) and sent to the warehouse.
  5. 5Artifacts: results, timings and the full project graph are written to target/, used by docs, CI and orchestration.
Real-World Scenario

What is a dbt model?

Models, Sources & Seeds 7 min read Difficulty: Basic 6 of 40
Definition

A model is a .sql file in the models/ folder containing exactly one SELECT statement. dbt builds it into a database object (view, table…) named after the file. Models reference each other with ref(), configure themselves with config(), and can use Jinja and macros.

Since dbt 1.3, some adapters (Snowflake, BigQuery, Databricks) also support Python models returning a DataFrame.

Model SELECT ref config Python Model
Analogy
A model is like a recipe card: it only lists what goes into the dish (SELECT … FROM …), not how to set up the kitchen. dbt is the kitchen staff that reads the card and produces the dish in the right container (view or table).
How It Works — Step by Step
Step 1 / 4
  1. 1You write only a SELECT in a .sql file. No CREATE, no INSERT, no DROP.
  2. 2dbt wraps it in the right DDL for the warehouse and creates an object named after the file.
  3. 3The file name becomes the relation name; the folder usually maps to a layer (staging, marts).
  4. 4Switching from view to table or incremental is a one-line config change; the SELECT stays the same.
Real-World Scenario

    Its name becomes the object name, so use clear names (fct_, dim_, stg_).

Why no semicolon at the end?

What is ref()? How does dbt build the DAG and lineage?

Models, Sources & Seeds 8 min read Difficulty: Basic 7 of 40
Definition

{{ ref('model_name') }} refers to another model (or seed/snapshot). At compile time it becomes the fully qualified relation for the current target ("cdac"."dev"."stg_marks"), and it records a dependency. All refs together form a Directed Acyclic Graph (DAG): dbt uses it to order builds, run independent models in parallel, support graph selection (+model) and draw lineage in docs.

ref DAG Lineage Dependencies Directed Acyclic Graph
Analogy
ref() is like writing "see chapter 3" instead of copying its page numbers: the book can be re-printed in any format (dev or prod) and the cross-references stay correct, and an editor can draw a map of which chapters depend on which.
How It Works — Step by Step
Step 1 / 5
  1. 1Raw seeds/sources are the starting nodes.
  2. 2Each staging model refs one raw table: {{ ref('raw_students') }}.
  3. 3dim_students refs two staging models, so it must wait for both.
  4. 4fct_marks refs stg_marks and dim_students. dbt infers all of this from ref(); you never write the order yourself.
  5. 5The graph powers selection (+model, model+), parallel runs, and the lineage diagram in dbt docs.

How do incremental models work? Explain is_incremental(), unique_key and incremental strategies.

Materializations, Snapshots & Config 11 min read Difficulty: Intermediate 12 of 40
Definition

An incremental model builds the full table on the first run, and on later runs processes only new/changed rows. Inside the model, {% if is_incremental() %} adds a filter (usually against {{ this }}, the existing table). With unique_key, dbt merges (updates existing keys, inserts new); without it, rows are appended.

Strategies (adapter-dependent): append, merge, delete+insert, insert_overwrite (replace partitions), microbatch (dbt 1.9+, time-batched). on_schema_change controls what happens when columns change; --full-refresh rebuilds from scratch.

Incremental is_incremental unique_key merge append microbatch full-refresh this
Analogy
Updating the attendance register: on day one you copy the whole class list (full build); every following day you only add today's entries (is_incremental filter), and if a correction comes for an existing entry you overwrite that line (unique_key merge) instead of writing a duplicate.
How It Works — Step by Step
Step 1 / 5
  1. 1The first run (or when the table does not exist) builds the whole table like a normal table model.
  2. 2On later runs is_incremental() is true, so the {% if is_incremental() %} filter limits the SELECT to rows newer than what the table already holds ({{ this }}).
  3. 3Only those few thousand rows are processed and written, so runs stay fast as the table grows.
  4. 4With a unique_key, dbt merges: rows with existing keys are updated, new keys inserted. Without one, rows are appended.
  5. 5When the logic changes, --full-refresh drops and rebuilds the table completely.

What are snapshots? How do you implement SCD Type 2 with dbt?

Materializations, Snapshots & Config 10 min read Difficulty: Intermediate 13 of 40
Definition

A snapshot records how rows in a mutable source table change over time (Slowly Changing Dimension Type 2). Each run compares the current source rows with the snapshot table; changed rows get their old version closed (dbt_valid_to set) and a new version inserted. Meta columns: dbt_scd_id, dbt_updated_at, dbt_valid_from, dbt_valid_to (null = current).

Strategies: timestamp (uses an updated_at column, preferred) or check (compares listed columns). Run with dbt snapshot. Since dbt 1.9 snapshots can be defined in YAML.

Snapshot SCD Type 2 dbt_valid_from dbt_valid_to timestamp strategy check strategy
Analogy
A snapshot is a diary next to a whiteboard. The whiteboard (source table) is erased and rewritten; every evening you copy any changed line into the diary with the date it became true and the date it stopped being true.
How It Works — Step by Step
Step 1 / 5
  1. 1The source table holds only the current value: student 2402 lives in Pune.
  2. 2dbt snapshot copies the row and adds dbt_valid_from and dbt_valid_to (null = current).
  3. 3Next day the source row is updated in place: the city is now Navi Mumbai. The old value is gone from the source.
  4. 4The next snapshot run closes the old version (sets dbt_valid_to) and inserts the new one. History is preserved.
  5. 5Changes are detected by a timestamp column or by checking chosen columns for differences.

What are model contracts, constraints and versions?

Best Practices & Performance 8 min read Difficulty: Advanced 33 of 40
Definition

A model contract (dbt 1.5+) declares the exact columns and data types a model must return (contract: {enforced: true}). dbt checks the SELECT against it before building and fails on any mismatch. Constraints (not_null, primary_key, unique, foreign_key, check) are added to the DDL where the platform enforces them. Model versions (versions:) let you publish v2 of a model while consumers migrate from v1, and access (private/protected/public) controls who may ref it. Together they support multi-team "dbt Mesh" projects.

Contract Constraints Model Versions access dbt Mesh Breaking Changes
Analogy
A contract is an API specification for a table: the consuming team builds on "student_id is an integer, never null". If someone tries to change that, the build is stopped before the promise is broken.
How It Works — Step by Step
Step 1 / 4
  1. 1A contract lists the exact column names and data types a model must produce, plus optional constraints.
  2. 2When the model's SELECT matches, dbt builds it (and applies supported constraints in the DDL).
  3. 3If a change would alter the shape (renamed column, wrong type), dbt fails before replacing the table, so consumers never see a broken shape.
  4. 4Contracts, model versions and access levels (public/protected/private) support large, multi-team projects (dbt Mesh).

Scenario: Late-arriving records are missing from an incremental model. How do you fix it?

Real-World Scenarios 9 min read Difficulty: Expert 37 of 40
Definition

An incremental filter like event_date > (select max(event_date) from {{ this }}) skips rows that arrive after newer rows were already loaded. Fixes: a look-back window (reprocess the last N days every run) with a unique_key so reprocessed rows merge instead of duplicating; filter on load time (_loaded_at) instead of event time; or the microbatch strategy with lookback. Periodic full refreshes reconcile any remaining drift.

Late-Arriving Data Incremental Lookback unique_key microbatch Full Refresh
Analogy
Closing the attendance register each evening and refusing late slips means students who submitted late are marked absent forever. Keeping the last three days' pages open for corrections (look-back) fixes it.
How It Works — Step by Step
Step 1 / 4
  1. 1An incremental model normally loads rows newer than the latest date already in the table.
  2. 2A record for an earlier date that arrives late is older than that maximum, so a strict filter never picks it up.
  3. 3A look-back window reprocesses the last few days on every run.
  4. 4Combined with a unique_key (merge), re-processed rows update instead of duplicating.

Where does dbt fit in the modern data stack? What are exposures and the semantic layer?

Real-World Scenarios 8 min read Difficulty: Expert 40 of 40
Definition

In the modern data stack, EL tools (Fivetran, Airbyte) load raw data into a cloud warehouse/lakehouse; dbt transforms it; BI and ML tools consume it; orchestrators, observability and catalogue tools operate around it.

Exposures declare downstream consumers (dashboards, ML models, apps) in YAML so lineage shows what each model feeds and dbt build --select +exposure:name refreshes exactly what a dashboard needs. The dbt Semantic Layer (MetricFlow) defines metrics once (e.g. pass rate) so every BI tool computes them identically.

Analogy
dbt is the central kitchen of a food chain: suppliers deliver raw ingredients (EL), the kitchen prepares standard dishes (models), outlets serve them (BI), and the menu card (semantic layer) guarantees "pass rate" tastes the same in every outlet.

Cross Questions
Why do analytics engineers exist as a role?
dbt made it practical for SQL-strong analysts to own production transformations with engineering practices (Git, tests, CI), between data engineers (pipelines/platform) and analysts (insights).
What are the limits of dbt?
It only transforms data already in a supported platform; it is batch-oriented (not streaming); it depends on the warehouse's performance and cost; and very complex non-SQL logic is better done in Spark/Python.
