What is Apache HBase? What are its features and when should you use it?

HBase Foundations 8 min read Difficulty: Beginner 1 of 40
Definition

Apache HBase is an open-source, distributed, column-family-oriented NoSQL database that runs on top of HDFS. It is modelled on Google's Bigtable and provides random, real-time read/write access to very large tables: billions of rows and millions of columns.

Key features: strongly consistent reads and writes per row, automatic sharding of tables into regions, automatic failover of RegionServers, rows sorted by key (fast range scans), multiple versions per cell, block cache and Bloom filters, and integration with MapReduce, Spark, Hive and Phoenix. The current stable line is HBase 2.x (2.5/2.6).

NoSQL Wide-column Bigtable HDFS Random read/write Strong consistency Regions
Analogy
HDFS is a warehouse of sealed cartons: great for storing and shipping whole cartons. HBase is the indexed shelving system built inside that warehouse, so you can pick or replace one item by its label in seconds.
How It Works — Step by Step
Step 1 / 4
  1. 1HDFS is excellent for storing huge files and scanning them in batch, but it cannot update or fetch one small record quickly.
  2. 2HBase adds a database layer on top: you can read or write any single row by its key in milliseconds, even in tables with billions of rows.
  3. 3Rows are kept sorted by row key, every row operation is strongly consistent, and tables split automatically into regions spread over many servers.
  4. 4Underneath, data is stored in HFiles on HDFS and the cluster is coordinated by ZooKeeper. The design follows Google's Bigtable paper (2006).
Real-World Scenario
Who uses it
  • Facebook Messages (2010) and many large Chinese internet companies (Alibaba, Xiaomi) ran some of the biggest deployments.
  • Banks and telecoms keep customer event history (call records, transactions) for real-time lookups next to their Hadoop data lake.
  • At C-DAC scale: per-student activity and attendance history that must be updated live and read by key, on the same Hadoop cluster used for analytics.

Cross Questions
Is HBase a column-oriented database like a columnar warehouse?
Not really. It is column-family oriented: each family is stored separately, but within a family data is stored row by row. Columnar warehouses (Parquet, Redshift) store each column separately for analytic scans.
Does HBase support SQL?
Not natively; it has a get/put/scan API and the shell. Apache Phoenix adds SQL, and Hive can query HBase tables through a storage handler.
When is HBase the wrong choice?
Small data (use an RDBMS), complex ad-hoc queries and joins (use a warehouse), or when you have no Hadoop/HDFS platform and want minimal operations (consider Cassandra or a managed service).

Analogy
An RDBMS table is a printed form with the same boxes for everyone, many left blank. An HBase row is a file folder with labelled sections (families) where you add only the pages you actually have.
How It Works — Step by Step
Step 1 / 5
  1. 1In a relational table every row has the same columns, and missing values are stored as NULL.
  2. 2Adding a column means an ALTER TABLE for the whole table.
  3. 3In HBase only the column family is declared. Each row stores only the cells that were actually written.
  4. 4A new column qualifier can be added at any time just by writing it. Sparse data costs nothing.
  5. 5The trade-off: no SQL, no joins, no secondary indexes and no multi-row transactions out of the box (Apache Phoenix adds SQL on top).

Steps to Move a Table from RDBMS to HBase
  1. List access patterns
    HBase only serves key-based access efficiently.
  2. Design the row key
    From the most common lookup or scan.
  3. Group columns into 1–3 families
    By how they are read and how long they live.
  4. Denormalise
    Store what a read needs in the row instead of joining.
Cross Questions
What data types does HBase have?
None: row keys, qualifiers and values are byte arrays. The application (or Phoenix) decides how to encode numbers, dates and strings.
Can you update a row in HBase?
Yes: a put to an existing row/column writes a newer version, which reads then return. Old versions are kept up to the family's VERSIONS setting.

Cross Questions
Can Hive query HBase tables?
Yes, with an external table using org.apache.hadoop.hive.hbase.HBaseStorageHandler, but such queries scan HBase and are slower than Hive on ORC/Parquet.
Why not just use HBase for analytics?
HBase reads rows through RegionServers and is optimised for point and range access; columnar formats on HDFS are far faster for scanning a few columns of billions of rows.

Explain the HBase data model: row key, column family, qualifier, cell, timestamp.

HBase Foundations 10 min read Difficulty: Beginner 4 of 40
Definition
TermMeaning
TableCollection of rows, belongs to a namespace (default if none).
Row keyUnique byte-array identifier of a row. Rows are stored sorted by row key (byte order). The only index.
Column familyGroup of columns declared at table creation. Stored separately on disk; has settings (VERSIONS, TTL, compression).
Column qualifierName of a column within a family, created on write: info:name. Unlimited and different per row.
CellThe intersection {row, family:qualifier, timestamp} holding a value (bytes).
Timestamp / versionEvery cell value has a timestamp (ms); several versions can be kept, newest returned by default.

Logically HBase is a sorted, sparse, multidimensional map: (row key, family, qualifier, timestamp) → value.

Row key Column family Qualifier Cell Version Timestamp Sparse map
Analogy
A library catalogue drawer: the drawer label is the row key, the colour of the card is the family, the field name on the card is the qualifier, and corrections are added as new dated cards on top instead of erasing the old ones.
How It Works — Step by Step
Step 1 / 5
  1. 1A row key identifies each row. Rows are stored sorted by this key, as raw bytes.
  2. 2Columns are grouped into column families (info, marks), which are declared when the table is created and stored separately on disk.
  3. 3Inside a family, column qualifiers (name, city, sql…) are created freely at write time. Empty cells are simply not stored.
  4. 4Each cell can keep several versions, identified by timestamp. A read returns the newest version by default.
  5. 5So HBase is a sorted, sparse, multidimensional map: row → family → qualifier → timestamp → value. Everything is bytes.

  1. Pick the row key
    What is the main lookup/scan key?
  2. Pick families
    Group columns by access pattern and settings; keep 1–3.

Cross Questions
Are rows sorted by family or qualifier too?
Rows are sorted by row key; inside a row, cells are sorted by family, qualifier, then timestamp (newest first).
Where is the table schema stored?
In the table descriptor (families and their settings), kept by the master in hbase:meta-related system tables / filesystem. Qualifiers are not part of the schema.

Is HBase CP or AP? What consistency and atomicity guarantees does it give?

HBase Foundations 8 min read Difficulty: Beginner 5 of 40
Definition

HBase is a CP system: each region is served by exactly one RegionServer, so all reads and writes of a row go through one place and always see the latest committed data (strong consistency). If that server fails, its regions are briefly unavailable until reassigned.

Guarantees: operations on a single row are atomic (a put of many columns, even across families, is all-or-nothing), with atomic increment, append and checkAndMutate. There are no multi-row transactions (Phoenix/Omid/Tephra add them on top). Scans are not snapshot-isolated across rows.

CP Strong consistency Row-level atomicity checkAndMutate No multi-row transactions
Analogy
Each file has exactly one clerk responsible for it. You always get the latest version, and nobody sees a half-updated page; but if that clerk falls ill, the file is unavailable until another clerk takes over.
How It Works — Step by Step
Step 1 / 5
  1. 1A table is split into regions; each region is served by exactly one RegionServer at a time.
  2. 2So every read and write of a given row goes through the same server, which always has the latest value: strong consistency.
  3. 3Operations on a single row are atomic, even across column families: a reader never sees half a put. There are no multi-row transactions.
  4. 4If that RegionServer fails, its regions are unavailable until the HMaster reassigns them and the WAL is replayed.
  5. 5This is the CP choice in CAP: consistency over availability, the opposite trade-off to Cassandra.
Real-World Scenario

Steps
  1. Keep data that must change together in one row
    Row-level atomicity is the only built-in transaction.
  2. Use incr / checkAndMutate for races
    Counters, state transitions, "only once" actions.
  3. Plan for brief unavailability
    Client retries; region replicas for read availability.
Cross Questions
How is this different from Cassandra?
Cassandra lets any replica accept writes and resolves conflicts by timestamp (AP, tunable). HBase routes each row to one server (CP), giving strict consistency but less availability during failures.
Are reads from region replicas consistent?
No: with REGION_REPLICATION > 1, secondary replicas serve timeline-consistent reads that may be slightly stale; the client must request Consistency.TIMELINE.

Definition

How do counters (incr) and append work in HBase?

HBase Shell & Data Operations 7 min read Difficulty: Basic 10 of 40
Definition

incr 't', 'row', 'cf:q', n atomically adds n to a 64-bit long stored in the cell and returns the new value; the cell is created at 0 if absent. get_counter reads it as a number (a plain get shows 8 raw bytes). append atomically appends bytes to a cell's value.

Both are executed by the RegionServer under the row lock, so concurrent clients never lose updates. A counter cell must contain exactly 8 bytes; incrementing a cell written with put (text) fails.

incr get_counter append Atomic 8-byte long
Analogy
A turnstile counter at the exam hall gate: every person clicks it, the machine adds one atomically, and the display always shows the exact total.
How It Works — Step by Step
Step 1 / 4
  1. 1Many clients increment the same counter cell concurrently.
  2. 2The RegionServer serialises increments on the row (row lock), so each one reads the current value, adds, and writes atomically. None are lost.
  3. 3The result is exact, because one server owns the row (unlike Cassandra's distributed counters).
  4. 4Counters are stored as 8-byte big-endian longs, so the shell shows them as \x bytes; use get_counter to read them as a number.

Definition

Why is row key design the most important decision in HBase? What are the principles?

Row Key & Schema Design 10 min read Difficulty: Intermediate 16 of 40
Definition

The row key is HBase's only index and decides data placement (which region), sort order (what a range scan returns) and load distribution. A query that cannot use the key becomes a full table scan.

  • Lead the key with the attribute you look up or scan by (e.g. roll|date for "a student's history").
  • Avoid monotonically increasing leading parts (timestamps, sequences): they create write hotspots.
  • Keep keys short: the row key is stored with every cell (also family and qualifier names).
  • Use fixed-width parts and a separator so prefixes and ranges are unambiguous.
  • Row keys are immutable: "changing" one means writing a new row and deleting the old one.

  1. 1A get by row key goes straight to one region and is answered in milliseconds.
  2. 2Because rows are sorted by key, rows with a common key prefix are stored next to each other, so a range scan reads them together.

  4. 4Hence the rules: lead with the query field, avoid hotspots, keep keys short (the key is repeated in every cell on disk), use fixed-width parts, and remember a key cannot be updated.

How It Works — Step by Step
Step 1 / 5
  1. 1With a timestamp (or sequence number) as the key, every new row sorts after the previous one, so all writes go to the last region: one RegionServer does all the work (a hotspot).
  2. 2Salting prefixes the key with a small bucket number computed from the data, e.g. hash(id) % 4.
  3. 3Consecutive writes now land in 4 different key ranges, i.e. different regions on different servers.
  4. 4The price is on reads: a time-range query must scan each salt bucket and merge the results.
  5. 5Other options: hashing the whole key (spreads perfectly but kills range scans) or reversing a field whose end varies most (phone numbers, domain names).

How do you design row keys for time-series data and "latest first" reads?

Definition

Typical key: entity | time (plus a salt if writes are very concentrated). Putting the entity first keeps one source's readings together and spreads writes across entities. Time inside the key gives range scans per entity.

How should you design column families? Why should there be few of them?

Deletes, TTL & Column Families 8 min read Difficulty: Intermediate 24 of 40
Definition

A column family is a physical unit: in each region it is a separate Store with its own MemStore and HFiles, and its own settings. Guidelines from the HBase reference guide:

  • Use 1–3 families. Flushes and compactions happen per region; a small family is flushed along with a big one, producing many tiny files.
  • Families with very different sizes in the same table make scans of the small family slow (spread over many regions).
  • Group columns read together and columns with the same lifetime/settings (TTL, VERSIONS, compression).
  • Use short names (often one letter): the family name is stored in every cell.
Column family Store MemStore per family Flush Short names
Analogy
Families are like separate filing cabinets per subject in every office. Each cabinet needs its own clerk and clean-up schedule, so having twenty cabinets for a few papers each creates a lot of overhead.
How It Works — Step by Step
Step 1 / 4
  1. 1Each column family is a separate Store inside every region, with its own MemStore and its own HFiles on disk.
  2. 2Flushing is per region: when one family's MemStore fills up, the other families are typically flushed too, creating many small files if their data volumes differ a lot.
  3. 3Therefore keep 1–3 families, give them short names (the family name is stored in every cell) and group columns that are read together.
  4. 4Families are also where storage settings live: versions, TTL, compression, Bloom filters, caching.

Explain the HBase write path: WAL, MemStore and HFile.

Architecture & Internals 9 min read Difficulty: Advanced 28 of 40
Definition
  • The client sends the put to the RegionServer hosting the row's region.
  • The edit is appended to the Write-Ahead Log (WAL) on HDFS (one WAL per RegionServer, shared by its regions).
  • The edit is written to the column family's MemStore (in-memory, sorted). The client is acknowledged.
  • When a MemStore reaches hbase.hregion.memstore.flush.size (128 MB) or the server is under memory pressure, it is flushed to a new immutable HFile on HDFS.
  • Once data is flushed, the corresponding WAL files can be archived.

How It Works — Step by Step
Step 1 / 5
  1. 1A client sends a put to the RegionServer hosting the row's region.
  2. 2The edit is first appended to the Write-Ahead Log (WAL) on HDFS, so it survives a server crash.
  3. 3Then it is added to the MemStore of the column family, an in-memory sorted buffer, and the client gets success.

Definition

  • Recent edits are in the MemStore; older data is in the store's HFiles.
  • Bloom filters (per HFile) let the server skip files that cannot contain the row (or row+column).
  • For the remaining files, the HFile block index locates the 64 KB data block; the BlockCache (on-heap LRU and/or off-heap BucketCache) is checked before reading from HDFS.

Step 1 / 6
  1. 1A get for row 2401 reaches the region's RegionServer.

What are minor and major compactions? What is in an HFile?

Architecture & Internals 9 min read Difficulty: Advanced 30 of 40
Definition

HFile: the immutable on-disk format of a store, written by flushes and compactions. It contains sorted data blocks (64 KB default), a multi-level block index, Bloom filter blocks, file info and a trailer.

How do you bulk load large data into HBase? Why is it faster than puts?

Clients, Recovery & Tools 8 min read Difficulty: Advanced 34 of 40
Definition

Bulk loading generates HFiles directly with MapReduce or Spark, partitioned and sorted according to the table's region boundaries, and then hands them to the RegionServers (completebulkload). The data never passes through the WAL or MemStore, so it causes no flushes or compaction storms and is far faster than millions of individual puts.

Tools: ImportTsv (CSV/TSV, with -Dimporttsv.bulk.output), HFileOutputFormat2 in custom jobs, the hbase-spark connector's hbaseBulkLoad, and BulkLoadHFiles. Pre-split the table first so the job writes into many regions.

Bulk load ImportTsv HFileOutputFormat2 completebulkload No WAL
Analogy
Instead of handing a clerk 1 crore forms one by one, you deliver ready-sorted, bound volumes that go straight onto the shelves.
How It Works — Step by Step
Step 1 / 6
  1. 1Start from source files, e.g. a historical export on HDFS.
  2. 2A MapReduce (ImportTsv / HFileOutputFormat2) or Spark job sorts records by row key and partitions them by the table's region boundaries.
  3. 3It writes complete HFiles, one set per region.
  4. 4completebulkload (LoadIncrementalHFiles / BulkLoadHFiles) moves the files into the regions atomically.
  5. 5The data never goes through the WAL or MemStore, so huge loads are fast and do not disturb live traffic.
  6. 6Because there is no WAL entry, cluster replication needs bulk-load replication enabled separately.

Definition

Features: typed columns (correct numeric ordering), UPSERT, secondary indexes (global, local, covered, functional), salting (SALT_BUCKETS), views, joins and sub-queries, ACID transactions (with Omid/Tephra), and integration with Spark and Hive.

How It Works — Step by Step
Step 1 / 5
  1. 1Phoenix gives HBase a SQL interface through a JDBC driver.
  2. 2It compiles SQL into HBase scans and uses coprocessors to filter and aggregate inside the RegionServers.
  3. 3A table's PRIMARY KEY columns are concatenated into the HBase row key, so key design still matters.

Troubleshooting: What are common HBase performance problems and how do you fix them?

Scenarios & Ecosystem 10 min read Difficulty: Expert 39 of 40
Definition

Most problems come from row key or family design, or from resource limits on RegionServers:

  • Hotspots: one server busy → salt/hash keys, pre-split, check request counts per region.
  • Write stalls ("Blocking updates", "Too many store files") → tune flush size and compaction, fewer families, faster disks.
  • Long GC pauses → RegionServer considered dead (ZooKeeper timeout) → off-heap BucketCache, G1/ZGC, moderate heap (≈ 16–32 GB).
  • Slow random reads → Bloom filters, block cache size, major compaction, data locality.
  • Too many small regions → merge / normaliser, larger max.filesize.
  • Slow scans → scanner caching (CACHE), limit columns, use snapshots for analytics.

Analogy
HBase is a well-organised central archive with one authoritative clerk per drawer; Cassandra is a network of branch offices that each keep copies and keep working even when cut off from each other.
How It Works — Step by Step
Step 1 / 5
  1. 1HBase has master-based coordination and stores files on HDFS; Cassandra is a masterless peer-to-peer ring with its own storage.
  2. 2HBase gives strong consistency per row (CP); Cassandra stays available and lets each query choose its consistency (AP by default).
  3. 3HBase keys are ordered across the whole table, so range scans over any key range are natural; Cassandra hashes partition keys. HBase also has exact atomic counters and check-and-put.
  4. 4Pick HBase inside a Hadoop platform needing consistent reads and scans; pick Cassandra for always-on, multi-data-centre, write-heavy workloads.
  5. 5Both share Bigtable's storage engine design: memory buffer, immutable sorted files, compaction.
Real-World Scenario
Choosing for C-DAC workloads
  • Attendance and results already in a Hadoop platform, needing consistent reads and range scans → HBase.
  • A national, always-on exam event platform across two data centres, write-heavy → Cassandra.
  • Either way, the data model starts from the queries and the key design.

Steps to Choose
  1. Do you already run Hadoop/HDFS?
    HBase fits naturally.
  2. Must it stay writable during any failure, across regions?
    Cassandra.
  3. Need range scans over arbitrary key ranges or exact counters?
    HBase.
  4. Team skills and operations
    HBase needs HDFS + ZooKeeper operations; Cassandra is self-contained.
Cross Questions
What do they have in common?
Both are wide-column stores derived from Bigtable's storage design: in-memory buffer, append-only log, immutable sorted files, compaction, Bloom filters, versions/timestamps.
What about Google Cloud Bigtable?
Google's managed Bigtable service exposes an HBase-compatible API, so HBase knowledge transfers directly.
