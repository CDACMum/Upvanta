What is version control, and why is Git called a distributed version control system?

Git Foundations 7 min read Difficulty: Beginner 1 of 40
Definition

A version control system records changes to files over time so you can see who changed what and why, go back to any earlier state, and let many people work on the same project in parallel. Git stores the project as a series of snapshots (commits) of the whole tree, each identified by a SHA hash of its content, so history cannot be altered silently.

Git is distributed: every clone is a full repository with the complete history. Committing, branching, viewing history and diffing work offline; collaboration happens by exchanging commits with remotes (GitHub, GitLab, a server). Centralised systems (SVN) keep history only on the server. GitHub/GitLab are hosting services built around Git, not Git itself.

version control snapshot commit SHA hash distributed clone remote GitHub vs Git
Analogy
Git is a save-game system for your project: every commit is a save point you can return to, with a note saying what changed. And every player has the full set of save files on their own console, not just the server.
How It Works — Step by Step
Step 1 / 4
  1. 1In centralized systems the history lives only on the server; developers hold working copies and need the server for almost everything.
  2. 2In Git every clone is a complete repository. GitHub is a shared copy the team agrees on, not a different kind of system.
  3. 3git init creates the .git folder — that folder is the repository. The first commit gets a hash (1408405 in our run) and the main branch points to it.
  4. 4Because history is local, everyday commands are fast and work offline; only sharing needs the network.
Real-World Scenario
Course material for three centres

The PG-DBDA lab manuals are edited by faculty at Kharghar, Juhu and Pune. With Git each faculty member has the full history locally, works offline, and pushes changes to a shared repository; any page can be traced to the commit and person that changed it, and a bad edit can be reverted in seconds.

Cross Questions
Git vs GitHub?
Git is the version control tool that runs on your machine; GitHub is a hosting service that stores Git repositories and adds pull requests, issues and CI.
What does the .git folder contain?
The whole repository: objects (snapshots), refs (branches and tags), HEAD, config and the index. Deleting it turns the folder back into plain files.
Why snapshots rather than diffs?
Each commit points to a full tree; unchanged files are shared by reference, so snapshots stay small while making checkout, branching and comparison fast.

Explain the working directory, staging area (index) and repository. How do git status, git add and git commit move changes between them?

Git Foundations 8 min read Difficulty: Beginner 2 of 40
Definition

Git has three places for your changes: the working directory (the files you edit), the staging area / index (the exact content of the next commit, built with git add) and the repository (.git, the committed history, written by git commit).

git status reports files as untracked (new, never added), modified (changed but not staged) or staged ("Changes to be committed"). Staging lets you commit only part of your work (git add file, git add -p). git commit -a stages tracked modified files automatically but never adds untracked ones.

working directory staging area index git status git add git commit untracked
Analogy
The working directory is your desk, the staging area is the parcel box you are packing, and a commit seals and posts the box with a label. You can put only some things from the desk into the box.
How It Works — Step by Step
Step 1 / 6
  1. 1Two new files exist only in the working directory: git status shows them as ?? (untracked).
  2. 2git add hive_lab.sql copies that file's current content into the staging area — the draft of the next commit.
  3. 3git commit stores the staged snapshot permanently in the repository. spark_lab.py was not staged, so it is not in the commit.
  4. 4Editing hive_lab.sql again makes the working copy differ from the last commit: " M" (modified, not staged).
  5. 5git add with both files stages the modification (M) and the new file (A).
  6. 6The second commit (3647d34) contains both. Working directory, index and HEAD now match: the tree is clean.
Real-World Scenario
Two unrelated changes in one sitting

While fixing a typo in the Hive lab, a faculty member also starts rewriting the Spark lab. Staging only the Hive file lets her commit the typo fix on its own with a clear message, and keep the half-finished Spark work out of the commit.

How do you configure Git? Explain system, global and local config, and how clone and init differ.

Git Foundations 7 min read Difficulty: Beginner 3 of 40
Definition

git config reads and writes settings at three levels: system (/etc/gitconfig, all users), global (~/.gitconfig, your user) and local (.git/config, one repository). The more specific level wins, so a repository can use your work email while others use your personal one. git config --list --show-origin shows every setting and where it comes from.

Essential settings: user.name, user.email, init.defaultBranch, core.editor, pull.rebase, aliases (alias.lg). git init creates a new empty repository; git clone URL copies an existing one with all history, sets up the remote origin and checks out the default branch.

git config --global --local --show-origin user.email alias git init git clone
Analogy
Config levels are like rules at a hostel: the university rules (system), your own habits (global) and the special rules of one room (local). The room rule wins inside that room.
How It Works — Step by Step
Step 1 / 5
  1. 1Git reads three files in order: system, global, local. A value set at a more specific level overrides the same key above it.
  2. 2The global file holds your identity and aliases (here user.name Asha Patil, email asha@cdac.example and the lg alias).
  3. 3Inside the course repository a local user.email is set — only this repository uses it.
  4. 4The commit therefore records the global name with the local email: Asha Patil .
  5. 5Use --show-origin to debug which file a value comes from; aliases work in every repository.
Real-World Scenario
Personal and institutional accounts

A faculty member uses her personal email globally but must commit to the C-DAC course repository with her institutional address. A local user.email in that one repository does it, and --show-origin proves which setting is in effect.

How do you explore history? Explain git log options, git show and good commit messages.

Git Foundations 8 min read Difficulty: Beginner 4 of 40
Definition

git log lists commits from newest to oldest. Useful options: --oneline, --graph --all (branch structure), -n 5, --stat (files changed), -p (patches), --author, --since/--until, --grep (message text), -- path (history of one file), --format for custom output. git show COMMIT displays one commit's metadata and diff; git show COMMIT:path prints a file as it was.

Good commit messages make history useful: a short imperative summary line (≤ 50–72 chars, "Add marks validation", not "changes"), a blank line, then the why in the body. Commit one logical change at a time.

git log --oneline --graph --stat --grep git show commit message
Analogy
git log is the project diary; good commit messages are diary entries that say "why", not just "worked on stuff today". Six months later, they are the only explanation anyone has.
How It Works — Step by Step
Step 1 / 5
  1. 1Four commits, newest on the right. Each points back to its parent; main (and HEAD) point to the newest, 0fb78d4.
  2. 2Relative names count back from HEAD: HEAD~1 is the parent, HEAD~2 the grandparent, and so on.
  3. 3git log -S finds the commit whose diff added or removed a string — here the change to a pass mark of 50.
  4. 4git show : prints a file as it was then, without checking anything out.
  5. 5--format and --date build one-line reports with exactly the fields you need.
Real-World Scenario
"When did the pass mark change?"

An auditor asks when and why the pass mark in the grading script changed from 40 to 50. git log -S "PASS_MARK = 50" -p -- grade.py finds the exact commit, its author, date and the message explaining the academic council decision.

How does Git store data internally? Explain blobs, trees, commits and SHA hashes.

Git Foundations 9 min read Difficulty: Beginner 5 of 40
Definition

Git is a content-addressable store. Every object is named by the SHA-1 hash of its content: a blob stores file content (no name), a tree stores a directory listing (names, modes, and the hashes of blobs and sub-trees), and a commit stores a tree hash, parent commit hash(es), author, committer and message. Tags are objects too.

Consequences: identical content is stored once; changing one byte changes the blob hash, which changes the tree hash and the commit hash, so history is tamper-evident; a branch is just a file containing a commit hash. Inspect with git cat-file -t / -p and git hash-object.

blob tree commit object SHA-1 content-addressable cat-file hash-object
Analogy
Git objects are sealed envelopes labelled with a fingerprint of their contents. A commit envelope holds the fingerprint of the folder envelope, which holds the fingerprints of the file envelopes. Alter any page and every fingerprint above it changes.
How It Works — Step by Step
Step 1 / 5
  1. 1A commit object stores a pointer to one tree, the author, committer, time and message.
  2. 2The root tree lists names and modes and points to blobs (file contents) and other trees.
  3. 3Identical content is stored once: marks.csv is one blob, and lab1 and lab2 are the same tree 5029819. git count-objects reports 4 objects.
  4. 4Changing one file creates a new blob and new trees only along its path; everything else is shared with the previous commit.
  5. 5Every object is named by the hash of its content — that is why Git can detect corruption and deduplicate automatically.
Real-World Scenario
Why the same file is not stored twice

Thirty lab folders contain the same 2 MB sample dataset. Git stores one blob for it and thirty tree entries pointing to that blob, so the repository stays small; and anyone can verify that the dataset in a given commit is byte-for-byte the one originally committed.

Why do three copies of the file produce one blob?

How do you see what changed? Explain git diff, git diff --staged and comparing commits or branches.

Everyday Git 7 min read Difficulty: Basic 6 of 40
Definition

git diff compares the working directory with the index (unstaged changes). git diff --staged (alias --cached) compares the index with the last commit — exactly what the next commit will contain. git diff HEAD shows both together.

Between commits: git diff A B, git diff HEAD~2, git diff main..feature (tips) and git diff main...feature (changes on feature since it branched). Useful flags: --stat, --name-only, --word-diff, -- path. Lines starting with - were removed, + added; @@ hunks give line ranges.

git diff --staged --cached HEAD A..B A...B --stat --word-diff
Analogy
git diff is a track-changes view: red for what you deleted, green for what you added. --staged shows the redlines of the parcel you are about to post, plain git diff shows what is still on your desk.
How It Works — Step by Step
Step 1 / 5
  1. 1grade.py has the same content in the working directory, the index and the last commit.
  2. 2After editing, plain git diff shows working directory vs index: the change that is not yet staged.
  3. 3After git add, git diff is empty; git diff --staged shows what the next commit will contain.
  4. 4Adding a debug line makes the working copy differ from both; git diff HEAD shows everything since the last commit, here as a word diff.
  5. 5git diff A B compares any two commits; summary options keep the output short.
Real-World Scenario
Reviewing before committing

Before committing changes to the evaluation script, a faculty member runs git diff --staged and notices a debug print she staged by accident — unstaging it takes one command and keeps the commit clean.

How do you undo changes? Compare git restore, git reset (soft, mixed, hard) and git revert.

Definition

Definition

What does git rebase do? How is it different from merge, and what is the golden rule of rebasing?

Branching & Merging 9 min read Difficulty: Intermediate 14 of 40
Definition

git rebase main (run on a feature branch) takes the feature's commits since the merge base and replays them on top of main, creating new commits with new hashes. The result is a linear history, as if the feature had been started from the latest main; a later merge into main is then a fast-forward.

Merge preserves the true history (with merge commits); rebase rewrites it into a straight line. Conflicts are resolved commit by commit (git add, git rebase --continue, or --abort). Golden rule: never rebase commits that others have already pulled — rewrite only your own, unshared (or explicitly agreed) branches.

git rebase replay commits linear history new hashes rebase --continue golden rule
Analogy
Rebase is moving your stack of drafts onto the newest version of the textbook and rewriting each draft so it fits; merge is stapling a note that says "these drafts were written against last week's edition".

Definition

Definition

What is the reflog and how do you recover "lost" commits or branches?

Definition

The reflog (git reflog) is a local journal of every position HEAD (and each branch) has pointed to: commits, checkouts, resets, rebases, merges, amends. Entries look like HEAD@{3}. Commits removed from a branch by reset --hard, a bad rebase or a deleted branch are not destroyed immediately: they stay in the object database and are reachable from the reflog (by default for 90 days, 30 for unreachable entries) until garbage collection.

How does git bisect find the commit that introduced a bug? How do you automate it?

Working with History 9 min read Difficulty: Advanced 23 of 40
Definition

git bisect performs a binary search over history. Mark a known bad commit (usually HEAD) and a known good one; Git checks out the midpoint, you test and answer git bisect good or bad, and it halves the range each time. With n commits it needs about log₂(n) tests: 1,000 commits → about 10 steps.

git bisect run ./test.sh automates it: the script returns 0 for good, 1–127 (except 125) for bad, 125 to skip an untestable commit. Finish with git bisect reset to return to where you started. Bisect works best with small commits that each build.

Definition

When you switch away, commits made while detached become unreachable (Git warns and prints their hash) and are eventually garbage-collected. To keep them, create a branch: git switch -c new-branch while still detached, or later git branch name SHA using the hash from the warning or the reflog.

detached HEAD checkout SHA switch --detach tag checkout orphaned commits switch -c
Analogy
Detached HEAD is visiting an old station without being on a train. You can walk around and even build something there, but unless you park a train (a branch) at it, nobody will find it again.
How It Works — Step by Step
Step 1 / 5
  1. 1git switch --detach v1.0 checks out the tagged commit. HEAD now stores a commit hash directly; no branch is checked out.

  3. 3Switching back to main leaves it behind; Git warns, because nothing references it any more.
  4. 4Rescue it with a branch at its hash, found in the warning or the reflog.
  5. 5Best practice: if you plan to commit, create a branch first with git switch -c.

How do merge commit, squash merge and rebase merge differ when merging a pull request?

Team Workflows & Practices 9 min read Difficulty: Advanced 27 of 40
Definition

Hosting platforms offer three ways to merge a PR. Merge commit (git merge --no-ff): keeps every feature commit and adds a merge commit — full history, easy to revert the whole feature. Squash and merge (git merge --squash + commit): turns the whole branch into one commit on main — clean, one commit per PR, but individual steps are lost and the branch is not recorded as merged.

Rebase and merge: replays each feature commit onto main without a merge commit — linear history with all commits, but new hashes. Teams usually pick one method per repository; squash suits noisy PR branches, merge commits suit large features, rebase suits curated commit series.

Definition

How do you authenticate to GitHub? Compare HTTPS with personal access tokens and SSH keys.

Definition

GitHub no longer accepts account passwords for Git operations. Two options: HTTPS with a personal access token (PAT; fine-grained, with an expiry and limited scopes) stored by a credential helper, or SSH with a key pair: the private key stays on your machine (never shared, ideally passphrase-protected), the public key (.pub) is added to your GitHub account.

Analogy

How It Works — Step by Step
Step 1 / 5
  1. 1ssh-keygen creates a key pair: the private key (readable only by you) and the public key.
  2. 2You give GitHub only the public key.
  3. 3On each connection GitHub sends a challenge; your SSH client signs it with the private key and GitHub checks the signature. No password crosses the network.
  4. 4A Host alias in ~/.ssh/config picks the key; the remote URL is switched from HTTPS to SSH with git remote set-url.
  5. 5HTTPS works too, but GitHub requires a token instead of a password; store it in a credential helper.

Definition

Definition

Scenario: a file was deleted some time ago and is needed again. How do you find when it was deleted and restore it?

Scenario-Based Questions 7 min read Difficulty: Expert 40 of 40
Definition

Git keeps every committed version, so a deleted file can be found in history. git log --diff-filter=D --oneline -- path (or --diff-filter=D --summary to search all deletions) finds the commit that deleted it; the last good version is in that commit's parent (<commit>^).

Restore it with git restore --source=<commit>^ --staged --worktree -- path (without --staged the file comes back untracked; or the older git checkout <commit>^ -- path), review and commit. git show <commit>^:path prints the content without restoring. If you do not know the exact path, git log --all --diff-filter=D --name-only lists deleted files.

--diff-filter=D git restore --source commit^ git show commit:path deleted file history search
Analogy
Deleting a committed file is like removing a book from the shelf in a library that photographs the shelf every day. Find the day it disappeared, look at the photo from the day before, and put the same book back.
How It Works — Step by Step
Step 1 / 5
  1. 1The file existed until commit 0430d1e removed it; three more commits followed.
  2. 2--diff-filter=D shows only commits in which the path was deleted.
  3. 3The last good version is in the parent of the deleting commit (0430d1e^); git show prints it without touching the working tree.
  4. 4git restore --source=0430d1e^ brings it back; --staged also stages it (otherwise it would be untracked).
  5. 5Commit the restored file. With an unknown name, list all deleted files with --name-only.
Real-World Scenario

A cleanup three weeks ago removed timetable_generator.py as "unused". The academic office needs it for the new batch. git log --diff-filter=D finds the cleanup commit in seconds, and git restore brings back the exact last version, with its history intact.

Steps to Restore a Deleted File
  1. Find the deletion
    git log --diff-filter=D --oneline -- path.
  2. Look at the last version
    git show ^:path.
  3. Restore it
    git restore --source=^ --staged --worktree -- path.
  4. Review and commit
    git status, git diff --staged, git commit.
  5. Unknown name?
    git log --all --diff-filter=D --name-only.
Cross Questions
Why use the parent (^) of the deleting commit?
In the deleting commit the file no longer exists; its parent has the last version.
What if the file was never committed?
Git cannot help; only committed (or staged, via dangling blobs from git fsck --lost-found) content is recoverable.
How do you restore a whole folder as it was at a tag?
git restore --source=v1.0 -- folder/ (then commit), or git checkout v1.0 -- folder/.
