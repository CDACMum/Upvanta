What is Apache Airflow? Why use it instead of cron?

Airflow Foundations 7 min read Difficulty: Beginner 1 of 49
Definition

Apache Airflow is an open-source platform to author, schedule and monitor workflows as code. A workflow is a Python-defined DAG of tasks with dependencies; Airflow decides when each task should run, runs it on workers, retries failures and records everything in a database and UI.

It was created at Airbnb in 2014 and is an Apache top-level project. Airflow 3.0 was released in April 2025; this module uses Airflow 3.3 and notes where Airflow 2 differs.

Key idea: Airflow is an orchestrator, not a processing engine. It tells Spark, SQL, dbt or a Python script when to run and in which order; the heavy data work happens in those systems.

When to Use It

Airflow is a good fit for batch pipelines that run on a schedule or when data arrives: ETL/ELT, ML training, reports, data-quality checks. It is not a streaming engine (use Kafka/Flink/Spark Streaming), and it is not meant to move large volumes of data between its own tasks.

Cross Questions
Is Airflow an ETL tool?
No. It orchestrates ETL. The extract/transform/load work is done by the systems the tasks call (SQL engines, Spark, Python, dbt).
Name some alternatives.
Prefect, Dagster, Luigi (older), Apache Oozie (Hadoop), Azure Data Factory, AWS Step Functions, Argo Workflows. Managed Airflow: AWS MWAA, Google Cloud Composer, Astronomer.

Explain the Airflow architecture and its components

Airflow Foundations 9 min read Difficulty: Beginner 2 of 49
Definition

An Airflow deployment is a set of cooperating services around a metadata database: the DAG processor parses DAG files, the scheduler decides what should run, the executor and workers run tasks, the API server serves the UI and APIs, and the triggerer handles deferred (async) waits.

Scheduler DAG Processor Executor Worker API Server Triggerer Metadata DB
How It Works — Step by Step
Step 1 / 7
  1. 1You write DAGs as Python files in the dags folder (in Airflow 3 a DAG bundle, which can also be a Git repo).
  2. 2The DAG processor parses the files continuously and stores a serialized version of each DAG in the metadata database (PostgreSQL or MySQL in production).
  3. 3The scheduler reads the serialized DAGs, creates DAG runs when their schedule is due, and decides which task instances are ready (dependencies met, slots free).
  4. 4Ready tasks are handed to the executor, which decides where they run: local processes, a Celery worker pool, or one Kubernetes pod per task.
  5. 5Workers execute your task code. In Airflow 3 they report state and read XComs, variables and connections through the API server's Task Execution API, not by connecting to the database directly.
  6. 6The API server also serves the web UI and the REST API, so you monitor runs, read logs and trigger DAGs through it.
  7. 7The triggerer runs deferred tasks (async sensors and waits) in an event loop, so thousands of waits cost almost nothing and occupy no worker slot.

Cross Questions
Why did Airflow 3 stop workers from accessing the DB directly?
Security and isolation: task code (which can be anything) no longer holds database credentials, and it enables remote/edge workers and task SDKs in other languages.
What happens if the scheduler stops?
Running tasks finish, but nothing new is scheduled. That is why production setups run 2+ schedulers (active-active, coordinated through DB row locks).

What is a DAG? Why must it be acyclic?

Airflow Foundations 6 min read Difficulty: Beginner 3 of 49
Definition

A DAG (Directed Acyclic Graph) is a collection of tasks with directed dependencies and no cycles. In Airflow a DAG also carries scheduling settings: dag_id, schedule, start_date, catchup, default arguments and tags.

DAG Directed Acyclic dag_id Graph
How It Works — Step by Step
Step 1 / 4
  1. 1A DAG is a set of tasks with dependencies. Here extract must finish before clean and validate, which both run before load.
  2. 2It is directed (dependencies have a direction) and acyclic (no path leads back to where it started), so there is always a valid order to run the tasks.
  3. 3If A waited for C, C for B and B for A, none of them could ever start: a cycle.
  4. 4Airflow checks this when parsing the file and refuses to load a DAG with a cycle. Loops must be modelled differently, for example with dynamic task mapping or by re-triggering the DAG.
Example: Airflow Detects the Cycle
Python (Airflow 3)
from airflow.sdk import DAG
from airflow.providers.standard.operators.empty import EmptyOperator

with DAG("cycle_demo", schedule=None) as dag:
    a = EmptyOperator(task_id="A")
    b = EmptyOperator(task_id="B")
    c = EmptyOperator(task_id="C")
    a >> b >> c >> a            # cycle!

print("Python accepted the definition")
dag.check_cycle()              # the DAG processor runs this check when it parses the file
Output
Python accepted the definition
airflow.sdk.exceptions.AirflowDagCycleException: Cycle detected in Dag: cycle_demo. Faulty task: C
Cross Questions
Can a DAG have just one task?
Yes. A DAG is simply the unit Airflow schedules; one task is valid.
How do you repeat something "until done" without a cycle?
Use a sensor (wait until a condition is true), dynamic task mapping (N parallel copies), or trigger a new DAG run at the end.

What is the difference between an Operator, a Task, a Task Instance and a DAG Run?

Definition

An operator is a template class for a kind of work (BashOperator, PythonOperator). A task is an operator placed in a DAG with a task_id. A DAG run is one execution of the DAG for a logical date, and a task instance is one execution of a task within a DAG run.

How do you write a DAG with classic operators?

Writing DAGs 8 min read Difficulty: Basic 7 of 49
Definition

A DAG file is a Python module in the dags folder. The classic style creates a DAG object (usually with a with block), instantiates operators inside it, and wires them with >>.

DAG BashOperator PythonOperator with DAG dag_id task_id
Example
DAG (Airflow 3)
import pendulum
from datetime import timedelta
from airflow.sdk import DAG
from airflow.providers.standard.operators.bash import BashOperator
from airflow.providers.standard.operators.python import PythonOperator

def compute_grade():
    marks = {"Anuj": 82, "Vineeta": 91, "Aarshvi": 77}
    for name, m in marks.items():
        grade = "A" if m >= 85 else "B" if m >= 75 else "C"
        print(f"{name}: {m} -> {grade}")

with DAG(
    dag_id="grade_report",
    schedule="0 7 * * *",                       # every day at 07:00
    start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Kolkata"),
    catchup=False,
    default_args={"owner": "vineeta", "retries": 2, "retry_delay": timedelta(minutes=5)},
    tags=["reports"],
) as dag:
    download = BashOperator(task_id="download_marks", bash_command="echo downloading marks.csv")
    grade = PythonOperator(task_id="compute_grade", python_callable=compute_grade)
    notify = BashOperator(task_id="notify", bash_command="echo report ready for {{ ds }}")

    download >> grade >> notify

Points to Remember
  • dag_id must be unique across the deployment; task_id unique within the DAG.
  • start_date should be a fixed, timezone-aware date (pendulum), never datetime.now().

  • The file is parsed every few seconds to minutes, so keep top-level code light: no DB queries or API calls outside tasks.

Why did my bash_command ending in .sh fail with a Jinja error?
A bash_command ending in .sh is treated as a template file path. Add a trailing space ("bash run.sh ") or set template_searchpath.

What is the TaskFlow API? How is it different from classic operators?

Writing DAGs 8 min read Difficulty: Basic 8 of 49
Definition

The TaskFlow API (Airflow 2.0+) turns plain Python functions into tasks with the @task decorator and DAGs with @dag. Return values are passed between tasks automatically through XCom, and calling one task with another's output also creates the dependency.

TaskFlow @dag @task XCom multiple_outputs @task.bash
Example
DAG (Airflow 3)
import pendulum
from airflow.sdk import dag, task

@dag(schedule="@daily", start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Kolkata"),
     catchup=False, default_args={"owner": "aarshvi"})
def sales_summary():

    @task
    def extract():
        return [{"rep": "Anuj", "amount": 52000}, {"rep": "Vineeta", "amount": 61000},
                {"rep": "Aarshvi", "amount": 47000}, {"rep": "Anuj", "amount": 18000}]

    @task(multiple_outputs=True)            # each dict key becomes its own XCom
    def transform(rows):
        totals = {}
        for r in rows:
            totals[r["rep"]] = totals.get(r["rep"], 0) + r["amount"]
        best = max(totals, key=totals.get)
        return {"totals": totals, "best_rep": best}

    @task.bash                              # the function returns a shell command
    def announce(best_rep):
        return f"echo 'Rep of the day: {best_rep}'"

    @task
    def load(totals):
        print(f"writing {len(totals)} rows to warehouse: {totals}")

    result = transform(extract())
    announce(result["best_rep"])
    load(result["totals"])

sales_summary()

How do you set task dependencies? Explain >>, <<, chain and cross_downstream

Writing DAGs 6 min read Difficulty: Basic 9 of 49
Definition

Dependencies say which task must finish before another can start. Use a >> b (a before b), a << b (b before a), lists for fan-out/fan-in, chain() for sequences and cross_downstream() to connect every task of one list to every task of another.

>> << set_downstream chain cross_downstream Fan-out Fan-in
How It Works — Step by Step
Step 1 / 4
  1. 1The bit-shift operator >> means "runs before". One line can describe the whole flow.
  2. 2A list on the right of >> fans out: both extracts depend on start and run in parallel.
  3. 3A list on the left fans in: transform waits for both extracts (by default, trigger rule all_success).
  4. 4Python cannot apply >> between two lists, so for "every task in A before every task in B" use cross_downstream. For a long linear sequence use chain(t1, t2, t3, …).
Example: Checking the Wiring
Python (Airflow 3)
from airflow.sdk import DAG, chain, cross_downstream
from airflow.providers.standard.operators.empty import EmptyOperator as E

with DAG("deps_demo", schedule=None) as dag:
    start, transform, load = E(task_id="start"), E(task_id="transform"), E(task_id="load")
    ex_o, ex_c = E(task_id="extract_orders"), E(task_id="extract_customers")
    start >> [ex_o, ex_c] >> transform >> load

    a1, a2, b1, b2 = (E(task_id=t) for t in ("a1", "a2", "b1", "b2"))
    cross_downstream([a1, a2], [b1, b2])

    s1, s2, s3 = E(task_id="s1"), E(task_id="s2"), E(task_id="s3")
    chain(s1, s2, s3)                     # same as s1 >> s2 >> s3

for t in dag.tasks:
    if t.upstream_task_ids:
        print(f"{t.task_id:<18} waits for {sorted(t.upstream_task_ids)}")

Cross Questions
Is [a, b] >> [c, d] valid?
No: Python cannot apply >> between two lists (TypeError). Use cross_downstream, or a loop.
How do you make a task depend on a task in another DAG?
Not with >>. Use Assets (data-aware scheduling), ExternalTaskSensor, or TriggerDagRunOperator. See the Scenarios section.

What are default_args? How do retries, retry_delay and execution_timeout work?

Explain start_date, schedule, logical date and data interval. When does a daily DAG actually run?

Scheduling 10 min read Difficulty: Intermediate 13 of 49
Definition

start_date is the first date the DAG may be scheduled for. schedule says how often. Each DAG run has a logical date (formerly execution_date) that identifies it, and a data interval (start, end) describing the period of data it should process.

With an interval timetable, a run is created only after its interval ends, so the run with logical date 1 Oct starts at 2 Oct 00:00. Airflow 3's default trigger timetable for cron strings instead runs at the cron time and has an empty interval.

start_date schedule logical_date data_interval_start data_interval_end CronTriggerTimetable CronDataIntervalTimetable
How It Works — Step by Step
Step 1 / 4
  1. 1Two timetables can interpret the same @daily. Airflow 3 uses CronTriggerTimetable by default (setting create_cron_data_intervals = False).
  2. 2A trigger timetable simply fires at each cron time. The run at 1 Oct 00:00 has logical date 1 Oct, and its data interval has zero length (start = end).
  3. 3Airflow 2 (and Airflow 3 with CronDataIntervalTimetable) gives each run a data interval: the day of data it is responsible for.
  4. 4The run for interval 1 → 2 Oct can only start once that day is over, at 2 Oct 00:00, yet its logical date is 1 Oct. This "runs one interval late" behaviour is the most-asked scheduling question.

What are XComs? How do tasks share data?

Definition

XCom ("cross-communication") lets tasks exchange small pieces of data. A value is stored with a key, the task id and the DAG run; other tasks in the same run pull it. A task's return value is pushed automatically under the key return_value.

XCom xcom_push xcom_pull return_value Custom XCom Backend Object Storage
How It Works — Step by Step
Step 1 / 4
  1. 1A task's return value is automatically pushed as an XCom with the key return_value.
  2. 2XComs are stored per DAG run and task instance. In Airflow 3 workers write them through the API server, which saves them in the metadata DB.
  3. 3A downstream task pulls the value. With TaskFlow you just pass the return value as an argument and Airflow pulls it for you (and also sets the dependency).

How does branching work in Airflow?

Task Communication & Control Flow 7 min read Difficulty: Intermediate 20 of 49
Definition

A branch task decides at run time which downstream path to follow. With @task.branch (or BranchPythonOperator) the function returns one task_id or a list of them; all other directly downstream tasks are skipped.

@task.branch BranchPythonOperator Skipped trigger_rule BranchDayOfWeekOperator
How It Works — Step by Step
Step 1 / 4
  1. 1A branch task returns the task_id (or list of ids) that should run next.
  2. 2Airflow follows that branch and marks every other directly downstream task as skipped.
  3. 3Trap: a join task with the default trigger rule all_success is skipped too, because skip propagates downstream.
  4. 4Give the join task trigger_rule="none_failed_min_one_success": it runs if at least one branch succeeded and none failed.

What are trigger rules? Explain all_success, all_done, one_failed, none_failed and others

Task Communication & Control Flow 8 min read Difficulty: Intermediate 21 of 49
Definition

A task's trigger_rule decides, from the states of its upstream tasks, whether it should run. The default is all_success. Other rules allow tasks to run after failures (cleanup, alerting) or tolerate skipped branches.

trigger_rule all_success all_done one_failed none_failed none_failed_min_one_success upstream_failed
How It Works — Step by Step
Step 1 / 5
  1. 1A downstream task has three upstream tasks that ended as success, failed and skipped. Its trigger_rule decides whether it runs.
  2. 2With the default all_success it does not run and is marked upstream_failed. all_failed needs every upstream to fail.
  3. 3all_done (all finished, whatever the result), one_success, one_failed and always let it run. These suit cleanup, alerting and "best effort" tasks.
  4. 4The none_* rules are about tolerating skips. They still stop on a failure, which is what you want for a join after branching.
  5. 5Careful: the DAG run's final state comes from its leaf tasks. An all_done cleanup task at the end can hide upstream failures unless you add alerts or a final check task.

What is dynamic task mapping? How do expand() and partial() work?

Task Communication & Control Flow 9 min read Difficulty: Intermediate 23 of 49
Definition

Dynamic task mapping (Airflow 2.3+) creates a variable number of task instances at run time, one per element of an input list, similar to map in Python. .expand() takes the mapped arguments; .partial() fixes the arguments that stay the same.

expand partial map_index Mapped Tasks Reduce expand_kwargs max_active_tis_per_dag
How It Works — Step by Step
Step 1 / 4
  1. 1An upstream task returns a list. Its length is not known when the DAG file is written: today 3 files, tomorrow maybe 50.
  2. 2.expand() creates one mapped task instance per element at run time: process[0], process[1], process[2]. They run in parallel and retry independently.
  3. 3A downstream task that takes the mapped output receives all results as a list (a "reduce" step).
  4. 4This replaces generating tasks in a Python loop at parse time, which can only use information available when the file is parsed.
Example
DAG (Airflow 3)
import pendulum
from airflow.sdk import dag, task
from airflow.providers.standard.operators.bash import BashOperator

@dag(schedule=None, start_date=pendulum.datetime(2026, 10, 1, tz="UTC"), catchup=False)
def mapping_demo():

    @task
    def list_files():                        # decided at run time (e.g. from S3)
        return ["anuj.csv", "vineeta.csv", "aarshvi.csv"]

    @task
    def process(path: str, min_score: int):
        scores = {"anuj.csv": 82, "vineeta.csv": 91, "aarshvi.csv": 77}
        s = scores[path]
        return {"file": path, "passed": s >= min_score}

    @task
    def summarize(results):                  # receives all mapped results
        passed = [r["file"] for r in results if r["passed"]]
        print(f"{len(passed)} of {len(results)} passed: {passed}")

    results = process.partial(min_score=80).expand(path=list_files())
    summarize(results)

    # Classic operators map too: one bash task per city
    BashOperator.partial(task_id="ping_city").expand(
        bash_command=["echo Mumbai", "echo Pune", "echo Delhi"])

What are sensors? Explain poke, reschedule and deferrable modes

Sensors, Hooks, Connections & Pools 9 min read Difficulty: Advanced 26 of 49
Definition

A sensor is an operator that waits until a condition is true: a file lands, a partition exists, an API returns "ready", another DAG's task finishes. It checks every poke_interval seconds and fails (or is skipped with soft_fail=True) after timeout seconds.

Sensor FileSensor poke_interval timeout mode=reschedule deferrable soft_fail @task.sensor
How It Works — Step by Step
Step 1 / 5
  1. 1A sensor waits for a condition. Three ways to wait for the same file that only appears after an hour.
  2. 2poke (default): the task keeps its worker slot for the whole wait, sleeping between checks. Simple, but 100 waiting sensors = 100 blocked slots.
  3. 3reschedule: after each check the task gives back its slot and is rescheduled for the next check. Good for long waits with a large poke_interval.
  4. 4deferrable: the task hands the wait to a trigger running in the triggerer (async event loop) and exits. When the trigger fires, the task resumes on a worker.
  5. 5Prefer deferrable versions of sensors and long-running operators where they exist (many provider operators have deferrable=True).

Explain the task instance lifecycle and its states

Executors, States & Scaling 7 min read Difficulty: Advanced 34 of 49
Definition

A task instance moves through states as the scheduler, executor and worker act on it: none → scheduled → queued → running → success / failed, with side paths for retries, sensors, deferral, skipping and upstream failure.

scheduled queued running up_for_retry up_for_reschedule deferred skipped upstream_failed
How It Works — Step by Step
Step 1 / 5
  1. 1Each DAG run starts with task instances in state none. When dependencies are met (trigger rule satisfied) the scheduler sets them to scheduled.
  2. 2When a slot is available (parallelism, pool, max_active_tasks), the task is queued to the executor, and becomes running when a worker starts it.
  3. 3It ends in success or failed.
  4. 4Intermediate states: up_for_retry (failed, will retry after retry_delay, back to scheduled), up_for_reschedule (sensor in reschedule mode) and deferred (waiting on a trigger).
  5. 5Some tasks never run: skipped (branching, short-circuit, AirflowSkipException) and upstream_failed (trigger rule cannot be met because of failures). Others you may meet: removed, restarting, and awaiting_input for human-in-the-loop tasks (Airflow 3.1+).

What does it mean for a task to be idempotent? Why does it matter in Airflow?

Best Practices & Operations 9 min read Difficulty: Expert 36 of 49
Definition

A task is idempotent if running it several times for the same DAG run gives the same final result as running it once. Airflow re-runs tasks all the time (retries, clears, backfills), so non-idempotent tasks silently create duplicates or wrong totals.

Tasks should also be atomic: either the whole result is written or nothing is, so a crash halfway never leaves a half-loaded table.

Idempotency Atomicity Retries Backfill DELETE + INSERT MERGE Partition Overwrite
How It Works — Step by Step
Step 1 / 4
  1. 1The first run loads 1,240 rows for 10 Oct into the target. Both approaches look correct so far.
  2. 2A downstream task fails and the load task is retried (or someone clears it). The plain INSERT appends the same 1,240 rows again; the idempotent version first deletes the 10 Oct partition, so the count stays 1,240.
  3. 3Backfills and manual reruns make it worse for the plain INSERT. Airflow re-runs tasks routinely, so every task must be safe to repeat.
  4. 4Ways to be idempotent: overwrite a partition (DELETE + INSERT in one transaction, INSERT OVERWRITE), MERGE/upsert on a key, or write files to a path determined by the run (dt={{ ds }}) and replace them.
Example: Same Crash, Two Loading Styles

Why should you avoid top-level code in DAG files? How do you keep parsing fast?

Best Practices & Operations 8 min read Difficulty: Expert 37 of 49
Definition

Top-level code is anything in a DAG file outside task callables and templates. It runs every time the file is parsed, which happens continuously, not when the DAG runs. Slow or side-effecting top-level code delays every DAG in the deployment and can cause parse timeouts.

Top-level Code DAG Parsing dagbag_import_timeout min_file_process_interval airflow dags report
How It Works — Step by Step
Step 1 / 3
  1. 1The DAG processor re-imports every DAG file periodically (min_file_process_interval, 30 s by default) to pick up changes. Only the resulting DAG structure is stored.
  2. 2Anything at module level runs on every parse, not once per DAG run: API calls, DB queries, Variable.get(), reading big files. It slows parsing for all DAGs and can hit dagbag_import_timeout.
  3. 3Keep files declarative and fast to import. Do real work inside tasks, read variables via templates or inside tasks, and import heavy libraries inside the task function.

Design a daily DAG that loads new and changed orders from MySQL into a data lake and a warehouse

Real-world Scenarios 12 min read Difficulty: Expert 43 of 49
Definition

A classic interview design question. A good answer is incremental (only the run's data interval), idempotent (safe to retry and backfill), validated before publishing, and observable (alerts, clear task boundaries).

Incremental Load Data Interval Idempotent Partition Data Quality Backfill
How It Works — Step by Step
Step 1 / 5
  1. 1Extract only the rows that changed in this run's data interval, from a read replica, using the indexed updated_at column.
  2. 2Write them to the lake under a path built from the run (dt={{ ds }}), replacing any earlier file for that date.
  3. 3Check the data before publishing: row counts, null keys, duplicates. Fail loudly instead of loading bad data.
  4. 4Load the warehouse idempotently: MERGE (upsert) on the order key, or delete the 10 Oct partition and insert the new rows in one transaction.
  5. 5Notify on failure. Because every step is scoped to the interval and idempotent, retries, backfills and manual reruns are all safe.
Example: airflow dags test orders_incremental 2026-10-11 (processes 10 Oct)
DAG (Airflow 3)
import csv, os, pendulum
from datetime import timedelta
from airflow.sdk import dag, task
from airflow.timetables.interval import CronDataIntervalTimetable
from airflow.providers.sqlite.hooks.sqlite import SqliteHook   # MySqlHook in production

LAKE = "/tmp/lake/orders"

@dag(schedule=CronDataIntervalTimetable("@daily", timezone="UTC"),   # one run per day of data
     start_date=pendulum.datetime(2026, 10, 1, tz="UTC"), catchup=False, max_active_runs=3,
     default_args={"owner": "vineeta", "retries": 2, "retry_delay": timedelta(minutes=5)},
     tags=["sales", "incremental"])
def orders_incremental():

    @task
    def seed_source():                       # demo only: a tiny "MySQL" source
        h = SqliteHook(sqlite_conn_id="shop_replica")
        h.run("DROP TABLE IF EXISTS orders")
        h.run("CREATE TABLE orders (order_id INT, customer TEXT, amount INT, updated_at TEXT)")
        h.insert_rows("orders", [
            (101, "Anuj", 4500, "2026-10-09 23:10:00"),     # belongs to the previous run
            (102, "Vineeta", 61000, "2026-10-10 09:30:00"),
            (103, "Aarshvi", 2500, "2026-10-10 18:45:00"),
            (101, "Anuj", 5200, "2026-10-10 20:05:00"),     # order 101 was updated today
            (104, "Ravi", 800, "2026-10-11 00:02:00"),      # next run's data
        ])

    @task
    def extract_delta(data_interval_start=None, data_interval_end=None):
        h = SqliteHook(sqlite_conn_id="shop_replica")
        rows = h.get_records(
            "SELECT order_id, customer, amount, updated_at FROM orders "
            "WHERE updated_at >= ? AND updated_at < ? ORDER BY updated_at",
            parameters=(data_interval_start.strftime("%Y-%m-%d %H:%M:%S"),
                        data_interval_end.strftime("%Y-%m-%d %H:%M:%S")))
        path = f"{LAKE}/dt={data_interval_start.to_date_string()}/orders.csv"   # partition = the day of data
        os.makedirs(os.path.dirname(path), exist_ok=True)
        with open(path, "w", newline="") as f:              # overwrite: same path for the same run
            csv.writer(f).writerows(rows)
        print(f"interval {data_interval_start} → {data_interval_end}: {len(rows)} rows → {path}")
        return path

    @task
    def quality_check(path):
        rows = list(csv.reader(open(path)))
        assert rows, "no rows extracted"
        assert all(r[0] for r in rows), "null order_id"
        latest = {r[0]: r for r in rows}                  # keep the latest version of each order
        print(f"{len(rows)} change rows, {len(latest)} distinct orders")
        return path

    @task
    def load_warehouse(path, data_interval_start=None):
        rows = list(csv.reader(open(path)))
        latest = {r[0]: r for r in rows}.values()
        h = SqliteHook(sqlite_conn_id="warehouse")
        conn = h.get_conn()
        with conn:
            conn.execute("CREATE TABLE IF NOT EXISTS fact_orders (order_id INT PRIMARY KEY, customer TEXT, amount INT, load_dt TEXT)")
            conn.executemany("INSERT INTO fact_orders VALUES (?, ?, ?, ?) "
                             "ON CONFLICT(order_id) DO UPDATE SET amount = excluded.amount, load_dt = excluded.load_dt",
                             [(int(r[0]), r[1], int(r[2]), data_interval_start.to_date_string()) for r in latest])
        print("fact_orders now:", conn.execute("SELECT * FROM fact_orders ORDER BY order_id").fetchall())

    seed_source() >> load_warehouse(quality_check(extract_delta()))

How do you make one DAG depend on another DAG?

Real-world Scenarios 8 min read Difficulty: Expert 47 of 49
Definition

Dependencies between DAGs are expressed with Assets (data-aware scheduling), ExternalTaskSensor (wait for a task in another DAG), or TriggerDagRunOperator (start another DAG). Prefer Assets for producer → consumer data dependencies.

ExternalTaskSensor TriggerDagRunOperator Assets execution_delta Cross-DAG
How It Works — Step by Step
Step 1 / 4
  1. 1DAG B must run only after DAG A has loaded the orders. Three common ways to express a cross-DAG dependency.
  2. 2ExternalTaskSensor (pull): B waits for a task in A for the matching logical date. Works, but B occupies (or defers) a slot while waiting and the two schedules must be aligned.

Data for past days keeps arriving late. How do you design the DAG to handle it?

Real-world Scenarios 8 min read Difficulty: Expert 49 of 49
Definition

If records can arrive up to N days late, each run should reprocess a lookback window (e.g. its own day plus the previous 2 days) idempotently, or a separate correction DAG should re-run affected dates. Either way the load must overwrite or merge, never append.

Late-arriving Data Lookback Window Reprocessing Idempotent Overwrite Watermark
Example: Each Run Rebuilds Its Day Plus the 2 Days Before
DAG (Airflow 3)
import pendulum
from airflow.sdk import dag, task
from airflow.timetables.interval import CronDataIntervalTimetable

LOOKBACK_DAYS = 2

@dag(schedule=CronDataIntervalTimetable("@daily", timezone="UTC"),
     start_date=pendulum.datetime(2026, 10, 1, tz="UTC"), catchup=False)
def late_data_demo():

    @task
    def plan_window(data_interval_start=None, data_interval_end=None):
        start = data_interval_start.subtract(days=LOOKBACK_DAYS)
        days = [start.add(days=i).to_date_string() for i in range((data_interval_end - start).days)]
        print(f"run interval {data_interval_start.to_date_string()} → {data_interval_end.to_date_string()}, "
              f"reprocessing {days}")
        return days

    @task

Clear / backfill specific dates on requestManual, fine for rare cases
