What is a Database and a DBMS?

Foundations 5 min read Difficulty: Beginner 1 of 57
Definition

A database is an organised collection of related data stored so that it can be easily accessed, managed and updated.

A Database Management System (DBMS) is the software that sits between users/applications and the stored data. It lets you define, create, query, update and administer the database while handling security, concurrency, backup and recovery for you.

One-line answer: The database is the data; the DBMS is the software that manages the data. MySQL, PostgreSQL, Oracle and SQL Server are DBMS products — the databases are what you create inside them.
Database DBMS Data Management Data Independence Concurrency Recovery
Detailed Explanation

A DBMS takes care of everything an application would otherwise have to build by itself:

FunctionWhat it means
Data definitionCreate and change structures — tables, columns, data types, constraints
Data manipulationInsert, update, delete and retrieve data through a query language
IntegrityEnforce rules such as "age cannot be negative" or "every order must have a customer"
SecurityUsers, roles and permissions — who can read or change what
Concurrency controlMany users can work at once without corrupting each other's changes
Backup & recoveryRestore a consistent state after a crash or failure
Data independenceApplications are shielded from how and where data is physically stored

Types of DBMS:

  • Hierarchical — tree structure, parent → child (IBM IMS). Historic.
  • Network — graph structure, records with many parents (IDMS). Historic.
  • Relational (RDBMS) — data in tables linked by keys (MySQL, PostgreSQL, Oracle). Most widely used.
  • Object-oriented — stores objects as used in OOP languages (db4o).
  • NoSQL — document, key-value, column-family and graph stores (MongoDB, Redis, Cassandra, Neo4j).
Real-World Scenario
College admission system

Without a DBMS, each department keeps its own Excel sheet of students. The accounts office has a student's old phone number, the exam cell has the new one, and two clerks editing the same file overwrite each other's work.

With a DBMS, there is one students table that every department reads from. Access is controlled by role, simultaneous updates are handled safely, and a nightly backup protects the data.

Cross Questions
Is Excel a DBMS?
No. Excel is a spreadsheet. It stores data in rows and columns but does not enforce data types or relationships, does not support safe multi-user concurrent updates, has no transaction or recovery mechanism, and does not scale to millions of rows. It is fine for analysis, not for managing shared data.
Is MySQL a database or a DBMS?
MySQL is a DBMS (more precisely an RDBMS). Inside one MySQL server you can create many databases, e.g. college_db and library_db.
What is metadata?
"Data about data" — table names, column names, data types, constraints, indexes and users. The DBMS stores it in the data dictionary / system catalog (in MySQL: information_schema).

What is an RDBMS? How is it different from a DBMS?

Definition

An RDBMS (Relational Database Management System) is a DBMS based on the relational model proposed by E. F. Codd in 1970. Data is stored in tables (relations), and tables are linked to each other through keys — primary keys and foreign keys.

Every RDBMS is a DBMS, but not every DBMS is relational.

Example: Relationship in Action

Two related tables in a college database. dept_id in students refers to dept_id in departments:

Defining related tables
CREATE TABLE departments (
    dept_id    INT PRIMARY KEY,
    dept_name  VARCHAR(50) NOT NULL
);

CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(100) UNIQUE,
    dept_id    INT,
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);

INSERT INTO departments VALUES (1, 'Big Data Analytics'), (2, 'Artificial Intelligence');
INSERT INTO students VALUES (101, 'Asha',  'asha@mail.com',  1),
                            (102, 'Rohit', 'rohit@mail.com', 2);

-- The relationship lets us combine the tables
SELECT s.name, d.dept_name
FROM students s
JOIN departments d ON s.dept_id = d.dept_id;
Output
+-------+-------------------------+
| name  | dept_name               |
+-------+-------------------------+
| Asha  | Big Data Analytics      |
| Rohit | Artificial Intelligence |
+-------+-------------------------+
Note: Trying to insert a student with dept_id = 9 fails, because department 9 does not exist. The RDBMS enforces the relationship for you — this is referential integrity.
Visual Understanding

A foreign key in one table points to the primary key of another — the heart of the relational model

Cross Questions
Who proposed the relational model?
Dr. E. F. (Edgar Frank) Codd of IBM, in his 1970 paper "A Relational Model of Data for Large Shared Data Banks". He later published Codd's 12 rules that define what a fully relational DBMS must satisfy.
Can you name a few of Codd's rules?
Information rule — all data is stored as values in tables. Guaranteed access — every value is reachable by table name + primary key + column name. Systematic treatment of NULL. Active online catalog — metadata is itself stored in tables. Data independence (physical and logical). No commercial RDBMS satisfies all 12 completely.
Is MongoDB an RDBMS?
No. MongoDB is a NoSQL document database. It stores JSON-like documents in collections, has a flexible schema and does not enforce foreign keys.

What are the disadvantages of a file system compared to a DBMS?

Definition

Before DBMSs, applications stored data in plain files (text, CSV, binary). Each program managed its own files and its own logic for reading them. A DBMS replaces this with one shared, centrally controlled store.

Interview Tip
Memory trick: Remember the 8 problems with the phrase "RIDI-AICS": Redundancy, Inconsistency, Difficult access, Isolation, Atomicity, Integrity, Concurrency, Security.

Interviewers usually expect 4–5 points with one example each — redundancy, inconsistency, atomicity, concurrency and security are the strongest.

Cross Questions
When would you still prefer plain files?
For large, write-once, read-many data that is processed in bulk — log files, images, video, or data lake files like Parquet/CSV on HDFS or S3. Data engineers use files plus engines like Spark for analytics, and an RDBMS for transactional data.
What is data redundancy and is it always bad?
Redundancy is the same data stored in multiple places. In OLTP systems it causes anomalies, so we normalize. In data warehouses, controlled redundancy (denormalization) is added deliberately to make analytical queries faster.

Example: Identifying the Terms
students
-- students table
+------------+-------+-----------------+---------+
| student_id | name  | email           | dept_id |
+------------+-------+-----------------+---------+
| 101        | Asha  | asha@mail.com   | 1       |
| 102        | Rohit | rohit@mail.com  | 2       |
| 103        | Meera | meera@mail.com  | 1       |
+------------+-------+-----------------+---------+
  • Degree = 4 (student_id, name, email, dept_id)
  • Cardinality = 3 (three rows)
  • Tuple = (102, 'Rohit', 'rohit@mail.com', 2)
  • Domain of dept_id = the set of existing department ids {1, 2}
Watch out: "Cardinality" has a second meaning in ER modelling — the type of relationship (1:1, 1:N, M:N). Clarify which one the interviewer means.
Detailed Explanation

Properties of a relation — interviewers sometimes ask for these:

  • Each cell holds a single atomic value (no lists inside a cell).
  • Each column has a unique name, and all values in a column come from the same domain.
  • No two rows are identical (in the pure model — SQL tables allow duplicates unless a key prevents it).
  • The order of rows does not matter, and the order of columns does not matter.
Cross Questions
If a table has 5 columns and 1,000 rows, what are its degree and cardinality?
Degree = 5, cardinality = 1,000.
Does the order of rows in a table matter?
No. A relation is a set, so rows have no guaranteed order. If you need an order, you must use ORDER BY — never rely on insertion order.
What is a NULL value?
NULL means "unknown" or "not applicable". It is not zero and not an empty string. Any comparison with NULL using = gives UNKNOWN, so you must use IS NULL / IS NOT NULL.

What is SQL? Explain DDL, DML, DQL, DCL and TCL

Foundations 7 min read Difficulty: Beginner 5 of 57
Definition

SQL (Structured Query Language) is the standard language for creating, querying and managing relational databases. It is declarative: you describe what result you want, and the database's query optimizer decides how to get it.

SQL is standardised by ANSI/ISO (SQL-86, SQL-92, SQL:1999 … SQL:2023). Each vendor adds its own extensions — MySQL, PostgreSQL and Oracle each have small syntax differences.

SQL Declarative DDL DML DQL DCL TCL
The Five Sub-Languages
CategoryFull formPurposeCommands
DDLData Definition LanguageDefine or change structureCREATE, ALTER, DROP, TRUNCATE, RENAME
DMLData Manipulation LanguageChange the dataINSERT, UPDATE, DELETE, MERGE
DQLData Query LanguageRead the dataSELECT
DCLData Control LanguagePermissionsGRANT, REVOKE
TCLTransaction Control LanguageManage transactionsCOMMIT, ROLLBACK, SAVEPOINT, SET TRANSACTION
Example: One Command from Each Category
SQL
-- DDL: define structure
CREATE TABLE courses (
    course_id   INT PRIMARY KEY,
    course_name VARCHAR(60) NOT NULL,
    fee         DECIMAL(10,2)
);
ALTER TABLE courses ADD COLUMN duration_months INT;

-- DML: change data
INSERT INTO courses VALUES (1, 'PGCP-BDA', 95000, 6);
UPDATE courses SET fee = 98000 WHERE course_id = 1;

-- DQL: read data
SELECT course_name, fee FROM courses WHERE fee > 50000;

-- DCL: permissions
GRANT SELECT ON college_db.courses TO 'report_user'@'localhost';

-- TCL: transactions
START TRANSACTION;
DELETE FROM courses WHERE course_id = 1;
ROLLBACK;   -- the delete is undone
Interview Tip
Favourite trick question: TRUNCATE is DDL, not DML — even though it removes data. It deallocates the table's data pages instead of deleting row by row, and in MySQL it causes an implicit commit, so it cannot be rolled back.

Also note: in MySQL and Oracle, every DDL statement causes an implicit COMMIT. PostgreSQL is different — DDL can run inside a transaction and be rolled back.

Cross Questions
Is SELECT part of DML or DQL?
Both answers appear in textbooks. Many classify SELECT as DML (it manipulates data for retrieval); others separate it as DQL. Mention both — the five-category split (DDL/DML/DQL/DCL/TCL) is the most common in interviews.
What does "SQL is declarative" mean?
You state the result you want (SELECT name FROM students WHERE dept_id = 1) without writing loops or saying which index to use. Compare with procedural code (Python, Java), where you write the step-by-step algorithm.
Is SQL case-sensitive?
Keywords are not (select = SELECT). Whether table names and string comparisons are case-sensitive depends on the DBMS, operating system and collation. In MySQL on Linux, table names are case-sensitive by default; on Windows they are not.

What is the difference between schema and instance? Explain the three-schema architecture

Foundations 8 min read Difficulty: Beginner 6 of 57
Definition

Schema — the design or structure of the database: tables, columns, data types, constraints and relationships. It changes rarely.

Instance (state) — the actual data in the database at a particular moment. It changes every time data is inserted, updated or deleted.

Analogy: Schema is like the blueprint of a building; instance is the people inside it right now.
Schema Instance ANSI-SPARC Data Independence Physical Level Logical Level View Level
Detailed Explanation

The ANSI/SPARC three-schema architecture separates how users see data from how it is stored:

LevelAlso calledDescribesWho uses it
External levelView levelPart of the database relevant to one user group (views)End users, applications
Conceptual levelLogical levelAll tables, columns, relationships and constraintsDatabase designers, DBAs
Internal levelPhysical levelFiles, pages, indexes, storage blocks, compressionDBMS engine, DBAs

The goal is data independence:

  • Physical data independence — change the internal level (add an index, move to SSD, change file organisation) without changing the logical schema or applications. Easy to achieve.
  • Logical data independence — change the conceptual schema (add a column, split a table) without changing external views or applications. Harder to achieve.
Visual Understanding

External views → one conceptual schema → one physical storage layout

Example: The Levels in SQL
SQL
-- Conceptual level: the full table
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name       VARCHAR(100),
    phone      VARCHAR(15),
    fee_paid   DECIMAL(10,2),
    cgpa       DECIMAL(3,2)
);

-- External level: placement cell sees only what it needs
CREATE VIEW placement_view AS
SELECT student_id, name, cgpa FROM students;

-- Internal level change: add an index.
-- No application or view has to change -> physical data independence
CREATE INDEX idx_students_cgpa ON students(cgpa);
Cross Questions
Which data independence is harder to achieve, and why?
Logical data independence. Applications and views are written against the logical schema, so removing or renaming a column or splitting a table can break them. Physical changes (indexes, storage) are hidden by the DBMS completely.
What is a subschema?
Another name for an external schema / view — the subset of the database that a particular user or application is allowed to see.
Where is the schema itself stored?
In the data dictionary (system catalog). In MySQL you can query it through information_schema.tables and information_schema.columns.

What is a Primary Key?

Keys & Constraints 6 min read Difficulty: Basic 7 of 57
Definition

A primary key (PK) is a column, or a set of columns, whose value uniquely identifies each row in a table.

A primary key must be unique and NOT NULL, and a table can have only one primary key (although that key can be made of several columns).

Rules to remember: Unique + Not Null + Only one per table + Should rarely change.
Primary Key Uniqueness NOT NULL Entity Integrity Clustered Index
Example: Defining and Violating a Primary Key
SQL
-- Column-level definition
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL
);

-- Table-level definition with a constraint name (preferred in production)
CREATE TABLE courses (
    course_id   INT,
    course_name VARCHAR(60) NOT NULL,
    CONSTRAINT pk_courses PRIMARY KEY (course_id)
);

-- Auto-generated primary key (MySQL)
CREATE TABLE enquiries (
    enquiry_id INT AUTO_INCREMENT PRIMARY KEY,
    email      VARCHAR(100)
);

INSERT INTO students VALUES (101, 'Asha');
INSERT INTO students VALUES (101, 'Rohit');   -- fails: duplicate
INSERT INTO students VALUES (NULL, 'Meera');  -- fails: NULL not allowed
Output
ERROR 1062 (23000): Duplicate entry '101' for key 'students.PRIMARY'
ERROR 1048 (23000): Column 'student_id' cannot be null
Detailed Explanation

Why every table needs a primary key:

  • Entity integrity — every row can be identified and no row is "lost" as an exact duplicate.
  • Relationships — foreign keys in other tables point to it.
  • Performance — the DBMS automatically creates a unique index on it. In MySQL InnoDB the table data itself is physically ordered by the primary key (clustered index).
  • Updates and deletes — WHERE student_id = 101 touches exactly one row.

Choosing a good primary key: small, stable (never changes), never NULL, and preferably numeric. Avoid email or phone numbers — they change, and every foreign key pointing to them would have to change too.

Cross Questions
Can a primary key have duplicate values if it is made of two columns?
Each individual column can repeat, but the combination must be unique. In enrollments(student_id, course_id) student 101 can appear many times, but (101, 5) only once.
Can we have a table without a primary key?
Yes, SQL allows it, but it is bad practice — duplicate rows cannot be told apart, and replication and many tools expect one. InnoDB silently creates a hidden 6-byte row id if no primary key or unique NOT NULL key exists.
Can a primary key be updated?
Technically yes, but it should be avoided: every referencing foreign key must change too (or be handled with ON UPDATE CASCADE), and in InnoDB the row is physically moved.

Cross Questions
What is a prime attribute?
An attribute that is part of any candidate key. Attributes not in any candidate key are non-prime. This distinction is central to 2NF and 3NF.
How many super keys can a table have?
Potentially many. If a relation has n attributes and one single-column candidate key, the number of super keys is 2n−1 (the key plus any combination of the remaining n−1 attributes).
How do you choose the primary key among candidate keys?
Pick the one that is smallest, stable, never NULL and meaningful to joins — usually a numeric id. Email and phone are poor choices because they change.

What is a Foreign Key and Referential Integrity?

Keys & Constraints 7 min read Difficulty: Basic 9 of 57
Definition

A foreign key (FK) is a column (or set of columns) in one table that refers to the primary key (or a unique key) of another table. The table holding the FK is the child; the referenced table is the parent.

Referential integrity is the rule that every non-NULL foreign key value must match an existing value in the parent table — no "orphan" rows.

Foreign Key Referential Integrity Parent Table Child Table Orphan Rows
How It Works — Step by Step
Step 1 / 4
  1. 1The dept_id column in students is a foreign key referring to departments.dept_id. Students is the child table and departments the parent.
  2. 2Inserting a student with dept_id = 9 fails because department 9 does not exist. The database blocks orphan rows on INSERT and UPDATE.
  3. 3Deleting department 1 also fails (with the default RESTRICT action) because a student still refers to it. The database protects the relationship from the parent side too.
  4. 4A NULL foreign key is allowed unless the column is declared NOT NULL. It means "no relationship yet", and referential integrity only checks non-NULL values.
Example: Parent and Child Tables
SQL
CREATE TABLE departments (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50)
);

CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name       VARCHAR(100),
    dept_id    INT,
    CONSTRAINT fk_student_dept
        FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);

INSERT INTO departments VALUES (1, 'Big Data Analytics');
INSERT INTO students VALUES (101, 'Asha', 1);      -- OK
INSERT INTO students VALUES (102, 'Rohit', 9);     -- fails: dept 9 does not exist
INSERT INTO students VALUES (103, 'Meera', NULL);  -- OK: FK may be NULL
DELETE FROM departments WHERE dept_id = 1;         -- fails: child rows exist
Output
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails
Detailed Explanation

Referential integrity can be broken in four ways, and the DBMS checks each one:

OperationTableCheck performed
INSERTChildThe FK value must exist in the parent
UPDATE of FKChildThe new value must exist in the parent
DELETEParentWhat happens to children? → RESTRICT / CASCADE / SET NULL
UPDATE of PKParentSame choice → RESTRICT / CASCADE / SET NULL
Cross Questions
Can a foreign key be NULL?
Yes, unless declared NOT NULL. A NULL FK means "no relationship yet" — e.g. a student not yet assigned to a department. Referential integrity applies only to non-NULL values.
Can a foreign key reference a non-primary-key column?
Yes — it can reference any column with a UNIQUE constraint (a candidate key). In MySQL the referenced column must at least be indexed.
Can a table have a foreign key to itself?
Yes — a self-referencing foreign key. Example: employees.manager_id references employees.emp_id. This models hierarchies.
Can a table have more than one foreign key?
Yes. A junction table like enrollments has two: one to students and one to courses.
Do foreign keys slow things down?
Slightly — every insert/update must check the parent. Many data warehouses skip enforced FKs for faster bulk loads and rely on the ETL process for integrity. In OLTP systems, keep them.

Example
SQL
-- Composite primary key: one row per student per course
CREATE TABLE enrollments (
    student_id  INT,
    course_id   INT,
    enrolled_on DATE,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(student_id),
    FOREIGN KEY (course_id)  REFERENCES courses(course_id)
);

-- Surrogate key + natural key kept unique
CREATE TABLE books (
    book_id INT AUTO_INCREMENT PRIMARY KEY,   -- surrogate
    isbn    CHAR(13) NOT NULL UNIQUE,         -- natural key
    title   VARCHAR(200)
);
Natural vs Surrogate

Natural key

  • ✅ Meaningful, no extra column
  • ✅ Prevents business duplicates
  • ❌ Can change (email, phone)
  • ❌ Often long strings → large indexes
  • ❌ Sometimes not available for everyone

Surrogate key

  • ✅ Small, fast integer joins
  • ✅ Never changes
  • ✅ Shields design from business changes
  • ❌ No meaning — need a UNIQUE on the natural key too
  • ❌ One extra column
Note: Common practice: use a surrogate primary key and add a UNIQUE constraint on the natural key. In data warehouses, dimension tables always use surrogate keys (needed for SCD Type 2).
Cross Questions
What is the difference between a composite key and a compound key?
Many books treat them as the same. A stricter definition: a compound key is a composite key in which each column is itself a foreign key — like (student_id, course_id) in a junction table.
Why do data warehouses use surrogate keys?
Source systems may reuse or change their ids, several sources may collide, and SCD Type 2 needs multiple versions of the same business entity — each version needs its own key.
Is UUID a good primary key in MySQL?
It is globally unique (good for distributed systems), but random UUIDs make InnoDB insert into random pages of the clustered index, causing page splits. Use an ordered UUID (UUIDv7, or UUID_TO_BIN(uuid, 1)) or an integer.

Cross Questions
Why can a UNIQUE column hold more than one NULL?
NULL means "unknown", and one unknown is not considered equal to another unknown, so they do not violate uniqueness. SQL Server is the exception — it allows only one NULL in a unique column by default.
Can a UNIQUE constraint span multiple columns?
Yes: UNIQUE (dept_id, roll_no) means the same roll number can exist in different departments, but not twice in the same department.

Functionally almost — it is a candidate key. The difference is that only one is designated primary, and in InnoDB only the primary key decides the physical row order.

What is Normalization and why is it needed?

Normalization 6 min read Difficulty: Intermediate 20 of 57
Definition

Normalization is the process of organising columns and tables to reduce data redundancy and eliminate insert, update and delete anomalies. It works by splitting a large table into smaller, well-structured tables and linking them with keys.

It is done step by step through normal forms: 1NF → 2NF → 3NF → BCNF → 4NF → 5NF. Each form removes a specific kind of dependency problem.

Classic memory line: "The key, the whole key, and nothing but the key — so help me Codd." 1NF: atomic values with a key · 2NF: depend on the whole key · 3NF: depend on nothing but the key.

Cross Questions
Who introduced normalization?
E. F. Codd introduced 1NF (1970), 2NF and 3NF (1971). BCNF was defined by Boyce and Codd in 1974; 4NF by Fagin (1977) and 5NF by Fagin (1979).
What is a lossless (non-additive) decomposition?
Splitting a table so that joining the parts back gives exactly the original rows — no rows lost and no spurious extra rows. It is guaranteed when the common column(s) form a key of at least one of the parts.
What is dependency preservation?
After decomposition, every functional dependency can still be checked within a single table, without joins. 3NF decomposition can always preserve dependencies; BCNF sometimes cannot.

Cross Questions
How do you find candidate keys from a set of FDs?
1) Attributes that never appear on the right side of any FD must be in every key. 2) Compute the closure of that set. 3) If it covers all attributes it is the key; otherwise add other attributes one by one and keep only minimal sets.
What is a minimal (canonical) cover?
The smallest equivalent set of FDs: single attribute on the right side, no extraneous attributes on the left, and no redundant FD. It is the starting point for 3NF synthesis.
Can an FD be discovered by looking at data?
Data can disprove an FD (two rows with the same X and different Y) but cannot prove it — FDs are business rules that must hold for all possible data, so they come from understanding the domain.

Is a table in 3NF always free of redundancy?
Almost always for practical designs. The remaining edge case is when a non-key attribute determines part of a candidate key — that is what BCNF fixes.

What is BCNF? How is it different from 3NF?

Definition

What is a Transaction?

Transactions & Concurrency 5 min read Difficulty: Advanced 29 of 57
Definition

A transaction is a sequence of one or more database operations that is treated as a single logical unit of work. Either all of its operations take effect (COMMIT), or none of them do (ROLLBACK).

Classic example: Transferring ₹5,000 from A to B is two updates — debit A, credit B. If the system crashes between them, money must not vanish. A transaction guarantees both happen or neither does.
Transaction Unit of Work COMMIT ROLLBACK Atomicity
Example: Fund Transfer
SQL
START TRANSACTION;

UPDATE accounts SET balance = balance - 5000 WHERE acc_no = 'A101';
UPDATE accounts SET balance = balance + 5000 WHERE acc_no = 'B202';

-- Both succeeded → make them permanent
COMMIT;

-- If anything had failed, we would run:
-- ROLLBACK;   → both updates are undone
Python
# Python (mysql-connector) — how applications use transactions
conn.autocommit = False
try:
    cur.execute("UPDATE accounts SET balance = balance - %s WHERE acc_no = %s", (5000, 'A101'))
    cur.execute("UPDATE accounts SET balance = balance + %s WHERE acc_no = %s", (5000, 'B202'))
    conn.commit()
except Exception:
    conn.rollback()
    raise
Cross Questions
What is autocommit?
In autocommit mode (MySQL's default), every single statement is its own transaction and is committed immediately. START TRANSACTION (or SET autocommit = 0) groups statements until COMMIT/ROLLBACK.
Do SELECT statements run inside transactions?
Yes. A SELECT reads a consistent snapshot according to the isolation level. In InnoDB with REPEATABLE READ, all SELECTs in one transaction see the same snapshot.
Which statements cannot be rolled back in MySQL?
DDL statements — CREATE, ALTER, DROP, TRUNCATE, RENAME — cause an implicit commit. Changes to non-transactional tables (MyISAM) also cannot be rolled back.

How It Works — Step by Step
Step 1 / 5
  1. 1A transfer of ₹5,000 from A to B starts as one transaction: two updates that must succeed or fail together.
  2. 2The debit from A is applied. The old value is recorded in the undo log so it can be reversed.
  3. 3The server crashes before the credit to B and before COMMIT. Without atomicity, ₹5,000 would simply vanish.
  4. 4Atomicity: on restart the database uses the undo log to roll back every uncommitted change, so A is back to ₹10,000. Consistency holds: the total money is unchanged.
  5. 5In a normal run both updates succeed and COMMIT writes to the redo log on disk. Durability means a crash after COMMIT can never lose the transfer, and isolation means nobody saw the half-done state in between.
Visual Understanding

Each ACID property and the mechanism the DBMS uses to provide it

Detailed Explanation

How durability works — write-ahead logging (WAL): before a changed data page is written to the data file, the change is first appended to a sequential log (InnoDB: the redo log) and flushed to disk at COMMIT. After a crash, the DBMS replays the redo log to restore committed changes and uses the undo log to roll back uncommitted ones.

In MySQL, innodb_flush_log_at_trx_commit = 1 (default) flushes the log on every commit — full durability. Values 0 or 2 are faster but can lose about one second of commits on a crash.

Cross Questions
Which ACID property is the responsibility of the application rather than the DBMS?
Consistency, partly. The DBMS enforces declared constraints, but business rules such as "total money is preserved" depend on the transaction being written correctly.
What is BASE?
The NoSQL alternative: Basically Available, Soft state, Eventual consistency. It trades strict consistency for availability and scale (Cassandra, DynamoDB).
Does MongoDB support ACID?
Single-document operations have always been atomic; multi-document ACID transactions are supported since MongoDB 4.0 (replica sets) and 4.2 (sharded clusters).
Is ACID guaranteed in MyISAM?
No. MyISAM has no transactions, no rollback and only table-level locks. InnoDB is the ACID-compliant engine in MySQL.

Definition

When transactions run concurrently without enough isolation, they can see or overwrite each other's intermediate work. These are the standard read phenomena.

How It Works — Step by Step
Step 1 / 4
  1. 1Transaction T1 sets the balance to 0 but has not committed yet.
  2. 2T2 runs at READ UNCOMMITTED and reads the balance: it sees 0, an uncommitted value. This is a dirty read.
  3. 3T1 hits an error and rolls back, so the real balance is 10,000 again.
  4. 4T2 has already made a decision (for example rejecting a payment) based on data that never existed. Any isolation level from READ COMMITTED upward prevents dirty reads.

T2: UPDATE accounts SET balance = 8000 WHERE id = 1; COMMIT;

What is a Deadlock? How can it be prevented?

Transactions & Concurrency 7 min read Difficulty: Advanced 36 of 57
Definition

A deadlock occurs when two or more transactions each hold a lock the other needs, so all of them wait forever. Neither can proceed without the other releasing its lock first.

Simplest case: T1 locks row A and waits for row B. T2 locks row B and waits for row A. Circular wait → deadlock.
Deadlock Circular Wait Wait-for Graph Deadlock Victim Lock Ordering
How It Works — Step by Step
Step 1 / 6
  1. 1T1 starts a transfer from A to B and updates row A, taking an exclusive lock on it.
  2. 2At the same moment T2 transfers from B to A and locks row B.
  3. 3T1 now needs row B to credit it, but B is locked by T2, so T1 waits.
  4. 4T2 needs row A, which T1 holds, so T2 waits too. Each waits for the other: a circular wait that can never resolve on its own.
  5. 5InnoDB's deadlock detector finds the cycle in its wait-for graph, rolls back the cheaper transaction (the victim, error 1213) and lets the other finish. The application should retry the victim.
  6. 6Prevention: make every transaction lock resources in the same order, keep transactions short, and index the WHERE columns so fewer rows get locked.
Example: Transfer in Opposite Directions
SQL
-- Session 1                                  -- Session 2
START TRANSACTION;                            START TRANSACTION;
UPDATE accounts SET balance = balance - 100
  WHERE id = 1;          -- locks row 1
                                              UPDATE accounts SET balance = balance - 50
                                                WHERE id = 2;        -- locks row 2
UPDATE accounts SET balance = balance + 100
  WHERE id = 2;          -- waits for row 2
                                              UPDATE accounts SET balance = balance + 50
                                                WHERE id = 1;        -- waits for row 1 → DEADLOCK

ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
Note: InnoDB detects the cycle immediately, rolls back the transaction that is cheapest to undo (the victim) and lets the other continue. SHOW ENGINE INNODB STATUS shows the latest deadlock.
Prevention & Handling

Four necessary conditions (Coffman) — all must hold for a deadlock: mutual exclusion, hold and wait, no preemption, circular wait. Breaking any one prevents deadlock.

PreventionAlways lock resources in the same order (e.g. lower account id first); lock everything needed at once

Practical tips: keep transactions short, access tables/rows in a consistent order, index the columns in WHERE clauses (fewer rows locked), and make the application retry on error 1213.

A lock wait is temporary: T2 waits until T1 commits. A deadlock is a cycle that can never resolve on its own — the DBMS must break it.

A transaction waits indefinitely because others keep getting the resource first (e.g. always chosen as deadlock victim). Fixed by aging / priorities.

What is MVCC (Multi-Version Concurrency Control)?

Transactions & Concurrency 7 min read Difficulty: Advanced 38 of 57
Definition

MVCC lets readers and writers work at the same time without blocking each other by keeping multiple versions of a row. A writer creates a new version; readers continue to see the version that was committed when their snapshot was taken.

Key benefit: Readers don't block writers, and writers don't block readers.
MVCC Snapshot Undo Log Read View Consistent Read Vacuum
How It Works — Step by Step
Step 1 / 5
  1. 1Session 1 starts a transaction at REPEATABLE READ and reads the fee: 95,000. InnoDB creates a read view, a snapshot of what is committed at that moment.
  2. 2Session 2 updates the fee to 98,000 and commits. It is not blocked by session 1's read. The old version stays in the undo log, linked from the new row.
  3. 3Session 1 reads again inside the same transaction. The newest version was committed after its snapshot, so InnoDB follows the undo chain and returns the old version: still 95,000.
  4. 4After session 1 commits, a new transaction gets a new snapshot and sees 98,000.
  5. 5That is MVCC: several versions of a row coexist, each transaction sees a consistent snapshot, and plain reads take no locks.
Detailed Explanation
DatabaseHow old versions are kept
MySQL InnoDBRow stores the latest version + a pointer into the undo log; older versions are rebuilt from undo records. A purge thread cleans them.
PostgreSQLOld and new versions (tuples) stay in the table itself with xmin/xmax transaction ids; VACUUM removes dead tuples.
OracleUndo tablespace with rollback segments.

Each InnoDB row has hidden columns: DB_TRX_ID (the transaction that last changed it) and DB_ROLL_PTR (pointer to the previous version in the undo log). When a transaction reads, it uses a read view — the list of transactions active at snapshot time — to decide which version is visible.

READ COMMITTED creates a new read view for every statement; REPEATABLE READ creates one at the first read and reuses it for the whole transaction. That is exactly why one sees changes committed by others and the other does not.

Example: Snapshot in Action
SQL

-- Session 1                                   -- Session 2
START TRANSACTION;
SELECT fee FROM courses WHERE id = 1;  -- 95000
                                               UPDATE courses SET fee = 98000 WHERE id = 1;
                                               COMMIT;
SELECT fee FROM courses WHERE id = 1;  -- still 95000 (same snapshot, read from undo)
COMMIT;
SELECT fee FROM courses WHERE id = 1;  -- 98000 (new snapshot)
Cross Questions
What is the cost of MVCC?
Extra storage for old versions, and background cleanup (InnoDB purge, PostgreSQL VACUUM). A very long-running transaction prevents cleanup, so undo logs / table bloat grow.
Does MVCC eliminate the need for locks?
No. Two writers updating the same row still need a lock — MVCC removes reader/writer blocking, not writer/writer conflicts.

Cross Questions
What is selectivity (cardinality) of an index?
The ratio of distinct values to total rows. An index on email (all distinct) is highly selective and very useful; an index on gender (2–3 values) is low-selectivity and the optimizer usually ignores it.
Why B+ tree and not a binary search tree?
A B+ tree node holds hundreds of keys (one disk page), so the tree is very shallow — few disk reads. A binary tree would be ~25 levels deep for 1 crore rows, i.e. 25 disk reads.
Are primary keys indexed automatically?
Yes, and so are UNIQUE constraints. In MySQL InnoDB foreign key columns are also indexed automatically if no suitable index exists.

What is the difference between a Clustered and a Non-clustered index?

Indexing 7 min read Difficulty: Advanced 40 of 57
Definition

A clustered index determines the physical order in which table rows are stored. The leaf level of the index is the table data. Hence a table can have only one clustered index.

A non-clustered (secondary) index is a separate structure: its leaves hold the indexed value plus a pointer to the row. A table can have many non-clustered indexes.

Analogy: Clustered = a telephone directory (the data itself is sorted by name). Non-clustered = the index at the back of a book (sorted list that points to pages).
Clustered Index Non-clustered Index Secondary Index Bookmark Lookup InnoDB
How It Works — Step by Step
Step 1 / 3
  1. 1The query filters on email, which has a secondary (non-clustered) index. InnoDB seeks that index and finds asha@x.com. Its "row pointer" is the primary key value, 101.
  2. 2To get name and city, InnoDB does a second seek into the clustered index by PK 101, whose leaf holds the full row. Two lookups per matching row.
  3. 3If every column the query needs is in the secondary index (plus the PK, which is always included), the second lookup is skipped. That is a covering index, shown as "Using index" in EXPLAIN.

How MySQL InnoDB Does It

In MySQL InnoDB the table is always clustered on the primary key. A secondary index stores the indexed column(s) plus the primary key value as the row pointer. So a lookup through a secondary index is: find PK in secondary index → search the clustered index by PK → get the row.

Consequences for design:

  • Keep the primary key short — it is copied into every secondary index.
  • Use an increasing primary key (AUTO_INCREMENT) so new rows append at the end instead of causing page splits in the middle.
  • If a query needs only columns in the secondary index + PK, the second lookup is skipped (covering index).
Cross Questions

In SQL Server, yes — you can choose any column. In MySQL InnoDB, no — the clustered index is always the primary key (or the first UNIQUE NOT NULL index, or a hidden row id).
Is a heap table the same as a table with no clustered index?
Yes. In SQL Server/PostgreSQL a table without a clustered index is a heap — rows are stored in no particular order. PostgreSQL tables are always heaps; its CLUSTER command sorts once but does not maintain the order.

What is a Covering Index?

Definition

A covering index is an index that contains all the columns a query needs — in SELECT, WHERE, JOIN and ORDER BY. The DBMS answers the query from the index alone, without visiting the table rows ("index-only scan").

Example
SQL

Cross Questions
Why is a covering index faster?
It avoids the second lookup into the clustered index / heap for every matching row — often the most expensive part. The index is also smaller than the table, so more of it fits in memory.
What is the downside?
Wider indexes take more space and make writes slower. Build covering indexes only for frequent, performance-critical queries.
Why is SELECT * bad for performance?
It prevents covering indexes, transfers unnecessary data and breaks when columns are added. Select only the columns you need.

What is the difference between relational algebra and relational calculus?

How is a SQL query processed and executed internally?

Query Processing & DB Objects 8 min read Difficulty: Advanced 46 of 57
Definition

When a SQL statement is submitted, the DBMS passes it through a pipeline: parse → rewrite → optimize → execute. The optimizer chooses the cheapest of many possible execution plans using statistics about the data.

Parser Query Optimizer Execution Plan Cost-based Optimizer Statistics EXPLAIN
How It Works — Step by Step
Step 1 / 5
  1. 1The client sends SQL text. It is only a string until the database understands it.
  2. 2The parser checks the syntax, builds a parse tree, verifies that tables and columns exist and that the user has privileges.
  3. 3The rewriter expands views, turns some subqueries into joins and simplifies expressions.
  4. 4The cost-based optimizer generates candidate plans (join order, join algorithm, which index) and estimates each one's cost from statistics. It picks the cheapest. Stale statistics lead to bad plans.
  5. 5The executor runs the chosen plan through the storage engine, reading pages from the buffer pool or disk, and streams the result rows back. EXPLAIN shows you this plan.
Detailed Explanation
StageWhat happens
1. ParsingChecks syntax, builds a parse tree; checks that tables/columns exist and the user has privileges
2. RewritingExpands views, flattens subqueries into joins, simplifies expressions (e.g. removes 1 = 1)

Rule-based vs cost-based optimizer?
A rule-based optimizer follows fixed heuristics (e.g. "always use an index if available"). A cost-based optimizer estimates I/O and CPU for each plan using statistics. All modern RDBMSs are cost-based.

Stale statistics, data growth changing selectivity, a different parameter value (parameter sniffing), or a dropped/unused index. Check the plan with EXPLAIN and refresh stats with ANALYZE TABLE.

What are Fact tables and Dimension tables?

Design & Architecture 7 min read Difficulty: Expert 51 of 57
Definition

A fact table stores the measurements of a business process — numeric, additive values such as quantity, amount, duration — plus foreign keys to dimensions. It is long and narrow (millions to billions of rows).

A dimension table stores the descriptive context of those measurements — who, what, where, when: customer, product, store, date. It is short and wide (many text attributes).

In one line: Facts answer "how much / how many"; dimensions answer "by what" — revenue (fact) by month, city and product (dimensions).

What is a conformed dimension?
A dimension shared by multiple fact tables / data marts with the same keys and meaning (e.g. one dim_date and one dim_customer used everywhere), so results from different marts can be compared.

A dimension attribute stored directly in the fact table with no dimension table of its own — typically the invoice or order number.

A single dimension that combines several low-cardinality flags and indicators (is_promo, payment_mode, channel) to avoid many tiny dimensions.

A Slowly Changing Dimension (SCD) is a dimension whose attributes change occasionally — a customer moves city, a product changes category. The SCD type decides whether and how the history of those changes is kept.

How It Works — Step by Step
Step 1 / 5
  1. 1Customer C101 has one current row in the dimension: surrogate key 1, city Pune, valid from 2024 to "forever" (9999-12-31), current flag = 1.
  2. 2The source system reports that C101 has moved to Mumbai on 1 June 2026.
  3. 3Step 1: the existing row is expired. Its valid_to becomes 31 May 2026 and its current flag becomes 0. Nothing is deleted.
  4. 4Step 2: a new row is inserted with a new surrogate key (2), the new city, valid from 1 June, current = 1.
  5. 5Facts keep the surrogate key that was current when they happened, so revenue by city stays historically correct. That is why SCD Type 2 needs surrogate keys.

-- SCD Type 2 load in SQL (two steps, inside one transaction)
-- 1) Expire the current row if the tracked attribute changed
UPDATE dim_customer d
JOIN stg_customer s ON s.customer_id = d.customer_id
SET d.valid_to = CURRENT_DATE - INTERVAL 1 DAY,
    d.is_current = 0

SELECT s.customer_id, s.city, CURRENT_DATE, '9999-12-31', 1

WHERE d.customer_id IS NULL;
Interview Tip
Why Type 2 matters: Sales made while the customer lived in Pune stay linked to surrogate key 1 (Pune); new sales link to key 2 (Mumbai). That is why SCD Type 2 needs surrogate keys — customer_id C101 alone cannot tell the versions apart.

In modern stacks SCD2 is built with MERGE (Delta Lake, Snowflake, BigQuery), dbt snapshots, or Spark jobs.

Cross Questions
Which SCD type is most used?
Type 1 for corrections and attributes where history does not matter (spelling of a name), and Type 2 for attributes that affect analysis over time (city, segment, price category).
How do you find the record valid on a given date in Type 2?
WHERE customer_id = 'C101' AND '2025-03-15' BETWEEN valid_from AND valid_to.
What is a rapidly changing dimension?
An attribute that changes too often for Type 2 (e.g. a customer's credit score monthly). It is usually split out into a separate "mini-dimension" of banded values.

What is the CAP theorem? When would you choose RDBMS over NoSQL?

Design & Architecture 8 min read Difficulty: Expert 53 of 57
Definition

The CAP theorem (Eric Brewer, 2000) states that a distributed data store can guarantee at most two of these three properties at the same time:

  • C — Consistency: every read gets the most recent write (all nodes see the same data).
  • A — Availability: every request gets a (non-error) response, even if some nodes are down.
  • P — Partition tolerance: the system keeps working even if the network between nodes is cut.
Practical reading: Network partitions will happen in a distributed system, so P is mandatory. The real choice is: during a partition, stay consistent (CP) or stay available (AP)?

Cross Questions
What is PACELC?
An extension of CAP: if there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. E.g. Cassandra is PA/EL, a typical RDBMS cluster is PC/EC.
Is "C" in CAP the same as "C" in ACID?
No. CAP consistency means linearizability — all replicas return the latest write. ACID consistency means the database moves between states that satisfy all integrity constraints.
What is NewSQL?
Systems that offer SQL and ACID with horizontal scaling — Google Spanner, CockroachDB, TiDB, YugabyteDB.

    order_id   BIGINT,
    order_date DATE,

WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';

Cross Questions
How do you choose a shard key?
High cardinality, even distribution, and present in most queries so each query hits one shard (e.g. customer_id for an e-commerce app). Avoid monotonically increasing keys with range sharding — all new writes hit one shard (hotspot).
What is partition pruning?
The optimizer skips partitions that cannot contain matching rows, based on the WHERE condition on the partition key. Data engineers use the same idea with Hive / Spark partitioned folders (/year=2026/month=10/).

What is Database Replication?

Design & Architecture 7 min read Difficulty: Expert 55 of 57
Definition

Replication is keeping copies of the same data on multiple database servers. Changes made on one server (the primary / source) are copied to others (replicas).

  • High availability — if the primary fails, promote a replica (failover).
  • Read scaling — send reporting and read-only traffic to replicas.
  • Disaster recovery — a replica in another data centre / region.
  • Analytics / CDC — run heavy queries or stream changes without loading the primary.

SynchronousPrimary waits until replicas have applied the changeNo loss; highest latency

How It Works (MySQL)

How MySQL replication works: the primary writes every change to its binary log (binlog). Each replica's I/O thread copies binlog events into its local relay log, and the SQL (applier) thread replays them. Replicas can use GTIDs (global transaction ids) to track their position.

The same binlog is what CDC tools such as Debezium read to stream every insert/update/delete into Kafka — a very common data-engineering pattern.

Cross Questions
What is replication lag and why does it matter?
The delay between a commit on the primary and its appearance on a replica. A user who updates their profile and immediately reads from a lagging replica sees old data ("read-your-writes" problem). Fix: read critical data from the primary.
Is replication a backup?
No. A mistaken DROP TABLE or bad UPDATE is replicated instantly to every replica. You still need backups and point-in-time recovery (or a deliberately delayed replica).

    pincode      CHAR(6)      NOT NULL,

    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE CASCADE
);

    category_id  INT AUTO_INCREMENT PRIMARY KEY,
    name         VARCHAR(80) NOT NULL,
    parent_id    INT NULL,
    FOREIGN KEY (parent_id) REFERENCES categories(category_id)
);

CREATE TABLE products (
    product_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
    sku          VARCHAR(40) NOT NULL UNIQUE,
    name         VARCHAR(200) NOT NULL,
    category_id  INT NOT NULL,
    price        DECIMAL(10,2) NOT NULL CHECK (price >= 0),
    stock_qty    INT NOT NULL DEFAULT 0 CHECK (stock_qty >= 0),
    is_active    BOOLEAN DEFAULT TRUE,
    FOREIGN KEY (category_id) REFERENCES categories(category_id)
);

CREATE TABLE orders (
    order_id     BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id  BIGINT NOT NULL,
    address_id   BIGINT NOT NULL,
    order_date   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status       ENUM('PLACED','PAID','SHIPPED','DELIVERED','CANCELLED') NOT NULL DEFAULT 'PLACED',
    total_amount DECIMAL(12,2) NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),
    FOREIGN KEY (address_id)  REFERENCES addresses(address_id),
    INDEX idx_orders_customer_date (customer_id, order_date)
);

CREATE TABLE order_items (
    order_id     BIGINT,
    product_id   BIGINT,
    quantity     INT NOT NULL CHECK (quantity > 0),
    unit_price   DECIMAL(10,2) NOT NULL,      -- price at the time of order
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id)   REFERENCES orders(order_id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(product_id),
    INDEX idx_items_product (product_id)
);

CREATE TABLE payments (
    payment_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id     BIGINT NOT NULL,
    amount       DECIMAL(12,2) NOT NULL,
    method       ENUM('UPI','CARD','NETBANKING','COD') NOT NULL,
    status       ENUM('PENDING','SUCCESS','FAILED','REFUNDED') NOT NULL,
    paid_at      DATETIME,
    FOREIGN KEY (order_id) REFERENCES orders(order_id)
);

CREATE TABLE reviews (
    customer_id  BIGINT,
    product_id   BIGINT,
    rating       TINYINT NOT NULL CHECK (rating BETWEEN 1 AND 5),
    comment      TEXT,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (customer_id, product_id),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),
    FOREIGN KEY (product_id)  REFERENCES products(product_id)
);
Talking Points

Design decisions to explain — this is what earns the marks:

  • unit_price in order_items — a deliberate copy of the product price, because prices change but an old invoice must not. This is not a normalization violation; it is a different fact (price at sale time).
  • total_amount in orders — derived and denormalized for fast listing; recomputed in the same transaction as items.
  • Address as a separate table referenced by the order — but many systems also copy the shipping address into the order so later edits do not change past orders.
  • Self-referencing categories for unlimited depth; query them with a recursive CTE.
  • Indexes chosen for real queries: "my orders, latest first" → (customer_id, order_date); "who bought product X" → order_items(product_id).
  • Stock update with UPDATE products SET stock_qty = stock_qty - ? WHERE product_id = ? AND stock_qty >= ? to avoid overselling.
  • Scale: read replicas for catalogue browsing, Redis for cart/sessions, partition orders by date, shard by customer_id at very large scale, CDC to a warehouse for analytics.
