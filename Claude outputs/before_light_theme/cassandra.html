What is Apache Cassandra? What are its key features and when should you use it?

Cassandra Foundations 8 min read Difficulty: Beginner 1 of 40
Definition

Apache Cassandra is an open-source, distributed wide-column NoSQL database designed to store very large amounts of data across many commodity servers with no single point of failure. It was built at Facebook (2008) for inbox search, combining Amazon Dynamo's distribution model (consistent hashing, replication, gossip) with Google Bigtable's storage model (memtables, SSTables, column families).

Key features: masterless peer-to-peer architecture, linear horizontal scaling, built-in multi-data-centre replication, tunable consistency per query, very fast writes, and a SQL-like query language (CQL). The current major version is 5.0 (Storage-Attached Indexes, vector search, Unified Compaction, trie-based memtables and SSTables, Java 17).

Distributed Wide-column Masterless Linear scalability Multi-DC Tunable consistency CQL
Analogy
A chain of identical bank branches with no head office. Every branch can serve any customer; each account is kept at three branches, so one branch closing never stops service. To handle more customers you simply open more branches.
How It Works — Step by Step
Step 1 / 5
  1. 1A Cassandra cluster is a set of nodes arranged in a logical ring. Every node runs the same software and has the same role.
  2. 2There is no master. Nodes learn about each other through gossip, so no single machine failing can stop the cluster.
  3. 3A client can connect to any node. That node acts as the coordinator for the request.
  4. 4The coordinator forwards the write to the nodes that own the row. With replication factor 3, three nodes keep a copy.
  5. 5Adding nodes adds capacity almost linearly. This is why Cassandra is used for huge, always-on, write-heavy workloads.
When to Use It
Use Cassandra when…Avoid Cassandra when…
Writes are heavy and continuous (events, IoT, logs, messages)You need joins, ad-hoc queries or complex reporting
You need 24×7 availability, even across data centresData is small enough for one PostgreSQL/MySQL server
Data grows to terabytes or petabytesYou need multi-row ACID transactions (e.g. ledgers)
Queries are known in advance and look up by keyQuery patterns change often or are not known yet
Real-World Scenario
Who uses it
  • Apple runs one of the largest deployments (hundreds of thousands of nodes) for iCloud and other services.
  • Netflix stores viewing history and personalisation data across regions.
  • Uber, Instagram, Discord (earlier), Spotify: messaging, feeds, trip and user data.
  • At C-DAC scale: an online exam platform can log every proctoring event of thousands of simultaneous candidates in Cassandra without a write bottleneck.

Cross Questions
Is Cassandra a column-oriented database like Redshift?
No. "Wide-column" means rows identified by a key, each with many (possibly sparse) columns grouped into partitions. Storage is row-oriented within a partition. Columnar warehouses (Redshift, BigQuery) store each column separately for analytics scans.
Why is Cassandra so good at writes?
A write is an append to the commit log plus an insert into an in-memory memtable: no disk seek, no read-before-write and no locking. Files on disk (SSTables) are immutable and written sequentially.
Who maintains Cassandra?
The Apache Software Foundation, with major contributions from Apple, DataStax, Netflix and others. DataStax Enterprise and Astra DB are commercial distributions; ScyllaDB is a compatible C++ re-implementation.

Explain the architecture of Cassandra: nodes, ring, data centres, racks, gossip and snitch.

Definition
ComponentWhat it is
NodeOne Cassandra process (one server). Stores part of the data and can serve any request.
RingThe logical circle of token ranges. Every node owns some ranges of the hash space.
Data centre (DC)A group of related nodes, often one physical location or one workload (live, analytics). Replication is set per DC.
RackA failure domain inside a DC (a physical rack or cloud availability zone). Replicas are spread across racks.
ClusterAll nodes and DCs that share one schema and cluster name.
CoordinatorThe node a client request arrives at. It forwards the request to the replicas and collects the answers.
GossipPeer-to-peer protocol by which nodes exchange state (up/down, load, schema version) every second.
SnitchTells Cassandra each node's DC and rack (e.g. GossipingPropertyFileSnitch, Ec2Snitch).
PartitionerHashes the partition key to a token (Murmur3Partitioner by default).

Analogy
A national exam board: regional offices (data centres), each with several buildings (racks) and clerks (nodes). Any clerk can take your form (coordinator) and knows which clerks keep your file. Clerks chat every minute about who is on leave (gossip), and the staff directory (snitch) says who sits in which building.
How It Works — Step by Step
Step 1 / 5
  1. 1A cluster is the whole Cassandra installation. It has a name, and all its nodes share one token ring per data centre.
  2. 2A data centre is a group of nodes, often in one location or used for one workload (e.g. live traffic vs analytics). Replication is configured per DC.
  3. 3Inside a DC, nodes sit in racks (failure domains). Cassandra spreads replicas across racks so one failed rack does not lose all copies.
  4. 4Nodes exchange state with a few peers every second through the gossip protocol, so every node knows who is up or down.
  5. 5The snitch (e.g. GossipingPropertyFileSnitch) tells Cassandra which DC and rack each node is in, which drives replica placement and request routing.

The live exam system runs in dc_mumbai with RF 3 and LOCAL_QUORUM. A separate dc_pune with RF 2 receives the same data through replication and is used only by Spark analytics jobs, so heavy reports never slow down candidates taking exams.

    One DC per region or workload; one rack per availability zone.

Cross Questions
What does "UN" mean in nodetool status?
Up and Normal. Other states: DN (down), UJ (joining/bootstrapping), UL (leaving), UM (moving).
What is the role of a seed node?
A contact point for new nodes to learn the cluster topology via gossip. Seeds are not masters; use 2–3 per DC, and do not make every node a seed.
Can a client talk to any node?
Yes. Drivers are token-aware: they compute the token themselves and send the request directly to a replica, saving one network hop.

Analogy
An RDBMS is a library with a card catalogue: books are stored once and you can find them by author, title or subject. Cassandra is a set of ready-made photocopy folders, one per question people ask. Finding an answer is instant, but every new question needs a new folder, and each new page is copied into every folder that needs it.
How It Works — Step by Step
Step 1 / 5
  1. 1In an RDBMS you design normalised tables first (students, marks) and connect them with keys.
  2. 2Any question can be answered later with joins, ACID transactions and a flexible query optimiser, but usually on one primary server.
  3. 3In Cassandra you start from the queries. For "show a student's marks" you create a table partitioned by roll number that already contains everything the screen needs.
  4. 4There are no joins. Data is duplicated into one table per access pattern, and each read touches a single partition.
  5. 5Writes are upserts: inserting an existing key silently overwrites it. There is no "duplicate key" error and no read-before-write.
Real-World Scenario
Keeping both

C-DAC's admission and fee data (needs transactions, joins and reports) stays in PostgreSQL. The exam-attempt event stream (millions of writes per exam day, read by attempt ID) goes to Cassandra. Using the right store for each workload is a common architecture.

Steps to Move a Workload from RDBMS to Cassandra
  1. List the queries first
    Which screen needs which data, given which input?
  2. Pick partition keys from the WHERE clause
    The value the application always has (roll number, user ID, sensor + day).
  3. Duplicate data instead of joining
    Write the same fact to every table that needs it.
  4. Keep relational data relational
    Billing, accounting and ad-hoc reporting are better in an RDBMS or warehouse.
Cross Questions
If INSERT overwrites, how do you insert only if absent?
INSERT … IF NOT EXISTS: a lightweight transaction (Paxos). It is slower, so use it only when duplicates must be prevented, e.g. unique usernames.
Does Cassandra enforce a schema?
Yes: tables, column names and types are defined and enforced. What is flexible is sparsity: a row stores only the columns that were written, and columns can be added with ALTER TABLE without rewriting data.

Explain the CAP theorem. Where does Cassandra fit, and what does "tunable consistency" mean?

Cassandra Foundations 9 min read Difficulty: Beginner 4 of 40
Definition

CAP theorem: when a network partition (P) happens, a distributed system must choose between Consistency (every read sees the latest write or gets an error) and Availability (every request gets a non-error response). Partitions cannot be ruled out in real networks, so the real choice is C or A while the network is split.

Cassandra is usually described as AP: it prefers to stay available and accept writes, and replicas converge later (eventual consistency). But consistency is tunable per request through the consistency level (ONE, QUORUM, ALL…). Choosing QUORUM for both reads and writes gives strong consistency for that data, at the cost of failing requests when a majority of replicas is unreachable.

CAP theorem AP system Eventual consistency Tunable consistency Consistency level R + W > RF
Analogy
Three notice boards in three buildings hold the exam schedule. If the corridor between them is blocked, you can either keep updating the boards you can reach (available, but one board is briefly out of date) or refuse changes until all boards can be updated (consistent, but unavailable). Cassandra lets each notice decide how many boards must agree.
How It Works — Step by Step
Step 1 / 5
  1. 1Three replicas hold the same row. While the network is healthy, every write reaches all of them.
  2. 2A network partition cuts N3 off. CAP says a distributed system must now choose between consistency and availability.
  3. 3Cassandra keeps accepting writes. With consistency level ONE, a write succeeds as soon as one reachable replica stores it; N3 misses the update.
  4. 4This is AP behaviour: always writable and readable, eventually consistent. Hinted handoff and repair bring N3 up to date when the network heals.
  5. 5Consistency is tunable per query: with QUORUM reads and writes (R + W > RF), reads always overlap the latest write, giving strong consistency for that data.
Real-World Scenario
Different levels for different data
  • Proctoring events: write at ONE, maximum availability, a lost event is tolerable.
  • Exam results: write and read at LOCAL_QUORUM, so a published result is never read stale.
  • Unique registration IDs: lightweight transaction with SERIAL consistency.
Example
cqlsh
CONSISTENCY;
CONSISTENCY LOCAL_QUORUM;
Output
cqlsh:cdac> CONSISTENCY;

Current consistency level is ONE.

cqlsh:cdac> CONSISTENCY LOCAL_QUORUM;

Consistency level set to LOCAL_QUORUM.
Consistency per request
-- In application code the level is set per statement, e.g. Python driver:
--   SimpleStatement("SELECT ...", consistency_level=ConsistencyLevel.LOCAL_QUORUM)
-- With RF = 3 in the local DC:
--   LOCAL_QUORUM write (2 replicas) + LOCAL_QUORUM read (2 replicas) = 4 > 3  -> strong consistency
--   ONE write + ONE read = 2, not > 3                                        -> may read stale data
Steps to Choose Consistency
  1. Find the RF of the keyspace
    e.g. 3 replicas per DC.
  2. Decide what stale data costs
    Metrics and logs: low. Balances and results: high.
  3. Pick levels so that W + R > RF where it matters
    Typically LOCAL_QUORUM for both.
  4. Use ONE/LOCAL_ONE for availability-first data
    High-volume telemetry.
Cross Questions
Is Cassandra CP or AP?
By default (CL ONE) it behaves as AP. With QUORUM/ALL it behaves more like CP for those requests: they fail rather than return stale data when too many replicas are unreachable. The trade-off is chosen per query, not for the whole system.
What is PACELC?
An extension of CAP: if Partitioned, choose Availability or Consistency; Else (normal operation), choose Latency or Consistency. Cassandra is PA/EL by default: favours availability and low latency.

Analogy
CQL is like speaking a familiar language with a strict accent rule: the words are SQL, but you may only ask questions the way the data is filed. Asking "find everyone with marks above 80" is like asking a filing clerk to open every drawer in every building.
How It Works — Step by Step
Step 1 / 4
  1. 1CQL (Cassandra Query Language) looks like SQL: tables, rows, columns and the usual statements.
  2. 2Features that need data from many partitions or nodes are deliberately missing: joins, sub-queries, foreign keys and filtering on arbitrary columns.
  3. 3It adds types suited to distributed data: UUIDs and time-based timeuuids, collections, user-defined types, counters and (in 5.0) vectors for similarity search.
  4. 4cqlsh is the interactive shell. Applications use drivers (Java, Python, Go) that speak the same native protocol on port 9042.
Real-World Scenario
Choosing types for an attendance table
  • timeuuid for event IDs: unique and naturally time-ordered.
  • timestamp for clock times, stored in UTC; cqlsh displays them with +0000.
  • date for the day bucket in a partition key.
  • decimal for fees (exact), not double.

Cross Questions
uuid vs timeuuid?
uuid() generates a random version-4 UUID with no ordering. now() generates a version-1 timeuuid containing a timestamp; as a clustering column it sorts by time, and toTimestamp() extracts that time.
text vs varchar?
Identical: varchar is an alias of text (UTF-8).
Can you change a column's type later?
Practically no; only a few compatible changes were ever allowed and Cassandra 4+ forbids most. Add a new column and migrate data instead.

What is a keyspace? Explain SimpleStrategy and NetworkTopologyStrategy.

Keyspaces, Tables & Keys 7 min read Difficulty: Basic 6 of 40
Definition

A keyspace is the outermost container for tables, similar to a database or schema in SQL. Its most important property is replication: the strategy and the replication factor (RF), i.e. how many copies of every row are kept. It also has durable_writes (use the commit log; always keep it true).

StrategyHow replicas are placedUse
SimpleStrategyFirst replica on the token owner, the next RF-1 copies on the following nodes clockwise. Ignores racks and DCs.Single-node labs, tests
NetworkTopologyStrategyRF given per data centre; within each DC, replicas placed on different racks where possible.All production clusters (even with one DC)
Keyspace Replication factor SimpleStrategy NetworkTopologyStrategy durable_writes
Analogy
A keyspace is a filing policy for a department: "keep 3 photocopies of every file in the Mumbai office, in three different cupboards, and 2 copies in the Pune office". Every table in that department follows the policy.
How It Works — Step by Step
Step 1 / 4
  1. 1A keyspace is the top-level container (like a database). Its main setting is replication: how many copies of every row, and where.
  2. 2SimpleStrategy puts the first replica on the token owner and the next copies on the following nodes clockwise. It knows nothing about racks or DCs: only for single-DC labs.
  3. 3NetworkTopologyStrategy takes a replica count for each data centre, so live and analytics DCs can have different RFs.
  4. 4Within each DC it places replicas on different racks where possible. This is the strategy to use in production, even with one DC.
Real-World Scenario
Different keyspaces, different policies
  • exam_live: {'dc_mumbai': 3, 'dc_pune': 2}, critical data in both regions.
  • proctor_events: {'dc_mumbai': 2}, high volume, one region, cheaper.
  • lab_sandbox: SimpleStrategy with RF 1 on a student's laptop.
Example
cqlsh
CREATE KEYSPACE exam_live
  WITH replication = {'class': 'NetworkTopologyStrategy', 'dc_mumbai': 3, 'dc_pune': 2}
  AND durable_writes = true;

CREATE KEYSPACE lab_sandbox
  WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};

-- creating it again fails; IF NOT EXISTS makes the script re-runnable
CREATE KEYSPACE lab_sandbox WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};
CREATE KEYSPACE IF NOT EXISTS lab_sandbox WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};

USE exam_live;

-- on each node in dc_pune:   nodetool repair -full exam_live
Steps
  1. Name the data centres
    The DC names must match what the snitch reports (nodetool status).
  2. Choose RF per DC
    3 is the usual production value: QUORUM still works with one replica down.
  3. Create the keyspace
    Use NetworkTopologyStrategy.
  4. After changing RF
    Run a full repair so existing data is copied to the new replicas.
Cross Questions
Why is RF 3 so common?
QUORUM of 3 is 2, so reads and writes at QUORUM keep working with one replica down while still giving strong consistency. With RF 2, QUORUM is 2, so any single failure blocks QUORUM requests.
Can RF be larger than the number of nodes?
You can create such a keyspace, but writes at levels needing more replicas than exist will fail. Keep RF ≤ number of nodes in each DC.
Is the system keyspace replicated?
system is local to each node. system_auth, system_distributed and system_traces are replicated; increase system_auth RF in production so logins survive node failures.

Explain primary key, partition key and clustering columns.

Keyspaces, Tables & Keys 10 min read Difficulty: Basic 7 of 40
Definition

The primary key of a Cassandra table has two parts: PRIMARY KEY ((partition key columns), clustering columns…).

The partition key (first element) is hashed to a token that decides which nodes store the data. All rows with the same partition key form one partition, stored together on the same replicas. The clustering columns decide the sort order of rows inside the partition and make each row unique within it.

With PRIMARY KEY (a) each partition has one row. With PRIMARY KEY (a, b) partition key is a, clustering column b. With PRIMARY KEY ((a, b), c) the partition key is the pair (a, b).

Primary key Partition key Clustering column Partition Token Wide row
Analogy
A filing cabinet per student: the roll number (partition key) decides which cabinet and in which building it sits; inside the cabinet, the papers are kept sorted by exam date (clustering column). Fetching "all of Anuj's papers since October" means opening one cabinet and taking one contiguous bundle.
How It Works — Step by Step
Step 1 / 5
  1. 1The first part of the primary key is the partition key. Its hash (token) decides which nodes store the data. All rows with the same partition key live together.

  3. 3So all of student 2401's marks form one partition on one set of replicas, and 2402 is a different partition, probably on other nodes.
  4. 4Inside the partition, rows are stored on disk in clustering order (here newest exam first), which makes range scans and "latest N" queries cheap.

What is a composite partition key? Why would you use one?

Keyspaces, Tables & Keys 8 min read Difficulty: Basic 8 of 40
Definition

A composite partition key is made of two or more columns, written in an inner pair of parentheses: PRIMARY KEY ((sensor, day), ts). The token is computed from all of them together.

Reasons to use one: (1) bound partition size by adding a time bucket (day, month) or a bucket number; (2) spread load so that one busy entity does not hit the same nodes all the time; (3) the query naturally always provides both values. The consequence: every query must supply every partition key column (with = or IN).

Composite partition key Bucketing Time bucket Partition size Hot spot
Analogy
Instead of one ever-growing diary per sensor, you start a new notebook every day labelled "lab-1 / 14 Oct". To read a page you must know both the sensor and the date written on the cover.
How It Works — Step by Step
Step 1 / 5
  1. 1If the partition key is only sensor, every reading a sensor ever sends lands in one partition.
  2. 2That partition grows forever: it becomes slow to read, hard to compact and repair, and one node ends up doing all the work for a busy sensor (a hot spot).
  3. 3A composite partition key (sensor, day) starts a new partition every day. This technique is called bucketing.
  4. 4Partitions now have a predictable size and are spread across the cluster.
  5. 5The token is computed from all partition key columns together, so a query must provide both sensor and day to find the partition.

How does clustering order work? What are the rules for ORDER BY?

Keyspaces, Tables & Keys 8 min read Difficulty: Basic 9 of 40
Definition

Rows inside a partition are stored on disk sorted by the clustering columns, in the direction set by WITH CLUSTERING ORDER BY (col ASC|DESC, …) (ASC by default). Reads return rows in this order.

ORDER BY in a SELECT can only (1) be used when the partition key is restricted with = or IN, (2) name clustering columns, (3) in their declared order, and (4) request either the stored order or its exact reverse. Cassandra never sorts by arbitrary columns.

Clustering order ORDER BY ASC / DESC Reverse read Sorted storage
Analogy
Pages in a register are bound in date order. You can read the register front to back or back to front, but you cannot ask the register to rearrange itself by the amount written on each page.
How It Works — Step by Step
Step 1 / 5
  1. 1Rows inside a partition are physically stored sorted by the clustering columns, in the order declared with CLUSTERING ORDER BY.
  2. 2With ts DESC, the newest reading is stored first, so "latest N readings" is a sequential read with no sorting work.
  3. 3ORDER BY can only choose the stored order or its exact reverse; Cassandra simply reads the partition backwards.
  4. 4You cannot sort by a regular column like temp: Cassandra never sorts result sets in memory.
  5. 5Ordering is only defined within one partition, so ORDER BY requires the partition key to be restricted with = or IN.

Why can't you put any column in the WHERE clause in Cassandra? Explain the restriction rules.

Querying with CQL 10 min read Difficulty: Intermediate 11 of 40
Definition

A Cassandra query must be answerable by reading one contiguous slice of known partitions. Therefore:

  • Partition key: restrict all its columns with = or IN (or use token() ranges for full scans). Ranges like roll_no > 2400 are not allowed on the partition key.
  • Clustering columns: restrict them left to right without gaps. All but the last restricted one must use = (or IN); the last may be a range (>, <=…).
  • Regular columns: cannot be restricted unless they have an index (SAI / secondary index) or you add ALLOW FILTERING.
  • Cassandra rejects queries that break these rules with a clear error instead of silently running a slow scan.
WHERE restrictions Partition key = / IN Clustering prefix Range on last column token()
Analogy
A phone directory sorted by city, then surname, then first name. "Pune, Sharma, all first names from A to M" is one contiguous block of pages. "Everyone called Rahul in any city" would mean reading the whole book.
How It Works — Step by Step
Step 1 / 5
  1. 1Giving the full partition key lets the coordinator compute the token and go straight to the replicas: the ideal query.
  2. 2Within the partition you can add clustering-column restrictions in declared order, including one range on the last restricted column. Cassandra reads a contiguous slice.
  3. 3Restricting module without exam_date would need scanning the whole partition, so Cassandra rejects it.
  4. 4Filtering on a regular column like marks without the partition key means reading every partition on every node, which is also rejected.
  5. 5The rule follows the storage layout: partition key to find the data, then clustering columns from left to right to find a contiguous slice.

What does ALLOW FILTERING do? Why is it considered dangerous?

Querying with CQL 8 min read Difficulty: Intermediate 12 of 40
Definition

ALLOW FILTERING tells Cassandra to execute a query that needs to read rows and discard those that do not match, instead of jumping straight to the requested data. Without it, Cassandra refuses with "Cannot execute this query as it might involve data filtering and thus may have unpredictable performance…".

Danger: without the partition key, the query scans every partition on every node. Its cost depends on table size, not on how many rows are returned. On production tables it causes read timeouts and loads the whole cluster. It is reasonable when the partition key is given (filtering inside one partition) or the table is known to be small.

Asking the post office for "all letters with a red stamp". They can do it, but only by opening every sack in every sorting centre. For 12 letters you pay for a national search.
How It Works — Step by Step
Step 1 / 5

  4. 4The work grows with table size, not with result size. On a large table this causes timeouts and load on the whole cluster, so Cassandra refuses unless you add ALLOW FILTERING.

What is an upsert in Cassandra? How does "last write wins" work with write timestamps?

Writes, TTL, Deletes & Counters 9 min read Difficulty: Intermediate 16 of 40
Definition

In Cassandra, INSERT and UPDATE are both upserts: they write the given cells whether or not the row exists, without reading first. There is no "duplicate key" error and an UPDATE of a missing row creates it.

Every cell is stored with a write timestamp in microseconds (assigned by the coordinator or client, or set with USING TIMESTAMP). When two versions of a cell meet (on different replicas, or in different SSTables), the one with the higher timestamp wins: last write wins (LWW). WRITETIME(col) shows a cell's timestamp.

Upsert Last write wins WRITETIME USING TIMESTAMP Cell-level resolution Idempotent writes
Analogy
Every note pinned to a notice board is stamped with the exact time it was written. When two notes say different things, readers always believe the one with the later stamp, no matter which one was pinned last.
How It Works — Step by Step
Step 1 / 5
  1. 1Every value written to Cassandra carries a write timestamp (microseconds), normally set by the coordinator or driver.
  2. 2A later write to the same cell has a higher timestamp.
  3. 3A write with an older timestamp (e.g. a delayed retry, or an explicit USING TIMESTAMP) can arrive later but still loses.
  4. 4When replicas or SSTables disagree, Cassandra keeps the value with the highest timestamp. This is the conflict-resolution rule, called last write wins (LWW).
  5. 5It works cell by cell, needs no locks, and is why INSERT and UPDATE are both upserts. It also means server clocks must be synchronised with NTP.
Real-World Scenario
Retries are safe

A mobile app on a weak network re-sends "set profile city = Pune" three times. Because the write is an idempotent upsert, the result is the same. A delayed old retry carrying an older client timestamp cannot overwrite a newer change.

Example
cqlsh
CREATE TABLE profiles (roll_no int PRIMARY KEY, city text, phone text);

INSERT INTO profiles (roll_no, city, phone) VALUES (2401, 'Pune', '9820011111');
-- UPDATE of a row that does not exist simply creates it
UPDATE profiles SET city = 'Thane' WHERE roll_no = 2402;
-- INSERT on an existing key overwrites only the columns given
INSERT INTO profiles (roll_no, city) VALUES (2401, 'Mumbai');
SELECT roll_no, city, phone, WRITETIME(city), WRITETIME(phone) FROM profiles;

-- a write with an OLDER timestamp loses, even though it arrives later
UPDATE profiles USING TIMESTAMP 1791952200000000 SET city = 'Nashik' WHERE roll_no = 2401;
SELECT roll_no, city, WRITETIME(city) FROM profiles WHERE roll_no = 2401;

cqlsh:cdac> SELECT roll_no, city, phone, WRITETIME(city), WRITETIME(phone) FROM profiles;

---------+--------+------------+------------------+------------------
    2402 |  Thane |       null | 1791952200002000 |             null
    2401 | Mumbai | 9820011111 | 1791952200003000 | 1791952200001000

(2 rows)

Timestamps resolve conflicts per cell: the phone keeps its first write time while the city got a newer one. The Nashik update had a timestamp earlier than the Mumbai write, so it was ignored.

Steps
  1. Design writes to be idempotent
    Same statement applied twice = same result (avoid list appends and counters for critical data).
  2. Let one clock source assign timestamps
    Driver-side timestamps (default in modern drivers) keep a client's writes ordered.
  3. Keep clocks synchronised
    Run NTP/chrony on all servers and clients.
  4. Use LWT when the outcome depends on the current value
    "Insert only if absent" cannot be done with plain upserts.
Cross Questions
What if two writes have exactly the same timestamp?
Cassandra breaks ties deterministically (deletes win over writes; otherwise the greater value wins), so all replicas still converge on the same result.
Why is clock skew dangerous?
If a node's clock runs ahead, its writes get "future" timestamps and later correct writes lose to them, so updates appear to be ignored.

What is TTL in Cassandra? How do you make data expire automatically?

Definition

TTL is a lifetime in seconds attached to written cells: INSERT … USING TTL 300 or UPDATE … USING TTL 300 SET …. When it runs out the data is no longer returned by reads; later, compaction removes it. TTL(col) shows the remaining seconds.

A table can define default_time_to_live so every write expires after that period unless the write sets its own TTL. TTL is tracked per cell, and an expired cell becomes a tombstone until compaction purges it.

TTL USING TTL default_time_to_live Expiry Tombstone
Analogy
A self-destructing OTP SMS: valid for 5 minutes. Nobody has to delete it; after 5 minutes it simply stops working.
How It Works — Step by Step
Step 1 / 5
  1. 1A write can carry a TTL (time to live) in seconds. Cassandra stores the expiry time with each cell.
  2. 2TTL(column) shows the remaining seconds, which keep counting down.
  3. 3When the TTL ends, the data simply stops appearing in reads. No delete job is needed.
  4. 4An expired cell becomes a tombstone and is purged during compaction (after gc_grace_seconds), so heavy TTL use still creates tombstones.
  5. 5A table can set default_time_to_live for all writes. TTL applies per cell: rewriting one column gives only that column a new TTL.

How do deletes work in Cassandra? What are tombstones and gc_grace_seconds?

Writes, TTL, Deletes & Counters 10 min read Difficulty: Intermediate 18 of 40
Definition

Because SSTables are immutable, a DELETE does not remove data. It writes a tombstone, a marker with a timestamp that hides older data during reads. Tombstones can cover a cell, a row, a range of rows (clustering range) or a whole partition; TTL expiry also produces them.

Tombstones are kept for gc_grace_seconds (default 864000 = 10 days) so that every replica receives them, including replicas that were down. After that, compaction may purge them together with the data they shadow. If a replica missed the delete and is not repaired within gc_grace, the old data can come back ("zombie" or resurrected data).

Tombstone gc_grace_seconds Range tombstone Partition tombstone Zombie data TombstoneOverwhelmingException
Analogy
Crossing out a line in a register written in ink: you cannot erase it, so you add "cancelled on 14 Oct". The register only gets rewritten cleanly at the yearly clean-up (compaction), and until then every reader has to read past the crossed-out lines.
How It Works — Step by Step
Step 1 / 6
  1. 1SSTables are immutable, so a DELETE cannot remove the old value from files that already exist.
  2. 2Instead it writes a tombstone: a marker saying "deleted at timestamp t2".
  3. 3Reads merge data from all sources; the tombstone is newer than the value, so the row is not returned.
  4. 4Tombstones are kept for gc_grace_seconds (10 days by default) so that every replica learns about the delete, and are then purged by compaction.
  5. 5If a replica was down and is not repaired within that window, it may still hold the old value and resurrect it after the tombstone is purged ("zombie" data).
  6. 6Reading through many tombstones is slow; past 100,000 in one query Cassandra aborts. Queue-like or delete-heavy patterns are therefore anti-patterns.
Real-World Scenario

Steps to Keep Tombstones Under Control
  1. Prefer TTL or partition-level deletes
    One partition tombstone is far cheaper than many row tombstones.
  2. Avoid delete-and-read-again patterns
    Queues, "latest status" rows that are deleted and recreated.
  3. Never write nulls you do not mean
    Inserting null explicitly creates a tombstone; omit the column instead.
  4. Repair within gc_grace_seconds
    Otherwise deleted data can be resurrected.
  5. Monitor
    Tombstone warnings in system.log, nodetool tablestats (tombstones per slice).

Only for tables never deleted from, or with RF 1 / no repair needs. Otherwise a down replica that missed the delete brings data back. Common values: 1–10 days, matched to the repair schedule.

What are counter columns? What are their limitations?

Writes, TTL, Deletes & Counters 7 min read Difficulty: Intermediate 19 of 40
Definition

A counter is a 64-bit integer column that supports only increment and decrement: UPDATE t SET views = views + 1 WHERE …. Each replica keeps its own contribution (shard), and reads merge them, so concurrent increments from many clients are not lost to last-write-wins.

  • A counter table contains only primary-key columns and counter columns.
  • No INSERT, no setting to a value, no TTL; a counter starts at 0 when first incremented.
  • Increments are not idempotent: a retried increment after a timeout can be counted twice.
  • Deleting and re-creating a counter is unreliable; treat deletions as permanent.
counter Increment Not idempotent Counter table
Analogy
A tally sheet at each gate of the exam centre. Each gatekeeper adds strokes on their own sheet, and the total is the sum of all sheets. Nobody overwrites anybody else's count.
How It Works — Step by Step
Step 1 / 4
  1. 1Many clients can increment the same counter at the same time on different coordinators.
  2. 2Each replica tracks its own share; the value read is the merged sum, so increments are never lost to last-write-wins.
  3. 3Counters have strict rules: only increments and decrements via UPDATE, a counter table holds only counters besides its key, and no TTL.
  4. 4An increment is not idempotent: if a write times out and the client retries, the count may be applied twice. Use counters for approximate metrics such as page views, not money.
Real-World Scenario

What are batches in Cassandra? Logged vs unlogged, and when should you use them?

Writes, TTL, Deletes & Counters 9 min read Difficulty: Intermediate 20 of 40
Definition

A BEGIN BATCH … APPLY BATCH groups INSERT/UPDATE/DELETE statements, all with the same timestamp.

Logged batch (default): the coordinator first writes the batch to the batchlog on other nodes. If the coordinator fails midway, the batch is replayed, so all statements are eventually applied (atomicity). It is not isolated: readers may see some statements applied before others. Use it to keep denormalised tables in sync.

Unlogged batch: no batchlog. Efficient only when all statements target the same partition (sent as one mutation). Counter batch: for counter updates only.

Logged batch Unlogged batch Batchlog Atomic Not isolated Anti-pattern: bulk load
Analogy
A registered parcel containing letters for two offices. The post office logs it, so if the van breaks down the parcel is re-sent and both letters are delivered eventually. It is a delivery guarantee, not a speed-up, and you would never send a whole warehouse as one registered parcel.
How It Works — Step by Step
Step 1 / 4
  1. 1A logged batch groups writes that must all happen, typically the same data written to several denormalised tables.
  2. 2Cassandra first stores the batch in a batchlog on other nodes. If the coordinator dies, the batch is replayed, so all statements are eventually applied. Readers may still see a partial state (no isolation).
  3. 3Batches are not a bulk-load optimisation. A batch touching many partitions puts the entire load on one coordinator.
  4. 4For bulk loads use many concurrent single-partition writes. An unlogged batch is efficient only when all statements hit the same partition.

Definition

Cassandra data modelling is query-driven: you start from the application's access patterns and design one table per query (or per small group of queries), so that every read is served by one partition.   4. 4Denormalisation is intentional. Storage is cheap; reading across many nodes is what makes queries slow.

How do you handle relationships without joins? Explain denormalisation.

Data Modeling 9 min read Difficulty: Intermediate 22 of 40
Definition

Cassandra has no joins, so data that a query needs from several entities is copied into the query's table at write time (denormalisation). The application (or a pipeline) writes every change to all tables that contain the data.

Patterns: lookup tables (students_by_email → roll_no), copying attributes (exam name stored in every result row), static columns for one-to-many in one partition, collections/UDTs for small nested data. Changing a value that is part of a key means deleting and re-inserting the row.

Denormalisation Lookup table Data duplication Write amplification Application-side join
Analogy
A school keeps the student's name on the ID card, the hall ticket and the mark sheet. Nobody looks up a central register to print a hall ticket. When a name changes, every document has to be reprinted.

Step 1 / 4
  1. 1A student registers once, but the application looks students up in two ways: by roll number and by email.

What are hot partitions and large partitions? How do you avoid them?

Data Modeling 9 min read Difficulty: Intermediate 23 of 40
Definition

A large partition holds too much data (common guideline: keep partitions under about 100 MB and 100,000 rows). It slows reads, compaction, repair and streaming, and stresses the JVM heap. Cassandra logs a warning for partitions larger than compaction_large_partition_warning_threshold.

A hot partition receives a disproportionate share of traffic. Because a partition lives on exactly RF replicas, those nodes become the bottleneck while the rest of the cluster is idle. Causes: low-cardinality partition keys (status, country, date only) or celebrity keys. Fixes: time bucketing and synthetic sharding (bucket = hash(id) % N).

Large partition Hot partition Bucketing Synthetic shard Cardinality
Analogy
All admission forms of the state dropped into one counter at one office: the queue there is endless while other counters sit idle. Opening counters by district and day spreads the queue.
How It Works — Step by Step
Step 1 / 5
  1. 1If many writes share one partition key (e.g. one global "all_logins" partition), all of them go to the same few replicas: a hot partition.
  2. 2The partition also grows very large, making reads, compaction and repair slow, and it can never be split across nodes.
  3. 3The fix is to add more to the partition key: a time bucket (day, hour) and/or a synthetic bucket number computed from another field.
  4. 4Writes are now spread over many partitions and therefore over all nodes.
  5. 5Keep partitions bounded (a common rule of thumb: under 100 MB and 100,000 rows). Reads ask each bucket in parallel and combine the results.

How do you model time-series data in Cassandra?

Data Modeling 9 min read Difficulty: Intermediate 24 of 40
Definition

Time-series data (sensor readings, logs, metrics, events) fits Cassandra well: append-only writes, reads of recent ranges, and expiry of old data. The standard design:

  • Partition key = source + time bucket: ((sensor_id, day)), sized to keep partitions bounded.
  • Clustering column = timestamp DESC (or timeuuid when several events can share a timestamp).
  • TTL (or default_time_to_live) for retention.
  • TimeWindowCompactionStrategy (TWCS) with a window matching the bucket, so expired data is dropped file by file.
  • Avoid updates and deletes; write each event once.
Time series Time bucket Clustering DESC TTL TWCS PER PARTITION LIMIT
Analogy
A weather station log book: a new book every day per station, newest entries on top, and books older than 30 days are thrown away as whole books, not page by page.
How It Works — Step by Step
Step 1 / 5
  1. 1Time-series data is partitioned by source and time bucket, with the timestamp as a descending clustering column.
  2. 2The latest readings are the first rows of today's partition (LIMIT N). Time ranges are contiguous slices.
  3. 3A table-level TTL removes old readings automatically after the retention period.
  4. 4TWCS groups SSTables by time window; once a whole window has expired, its files are dropped without rewriting, avoiding tombstone overhead.
  5. 5Append-only writes, recent reads and age-based expiry are exactly the pattern Cassandra handles best (IoT, logs, metrics, events).

What are materialized views? Why are they discouraged in production?

Data Modeling 8 min read Difficulty: Intermediate 25 of 40
Definition

A materialized view (MV) is a table that Cassandra maintains automatically from a base table with a different primary key: CREATE MATERIALIZED VIEW v AS SELECT … FROM base WHERE … IS NOT NULL PRIMARY KEY (…). The view's key must contain all base-table key columns plus at most one other column.

Since Cassandra 4.0 MVs are experimental and disabled by default (materialized_views_enabled: false). The view is updated asynchronously after a read-before-write on the base replica, and views can diverge from their base table without an effective way to detect or fix it. Most teams maintain query tables themselves or use SAI.

Materialized view Experimental materialized_views_enabled View drift Alternative: SAI
Analogy
An automatic photocopier that is supposed to update the copy in the other office whenever you change the original. Convenient, but sometimes a page is not copied, and there is no list of which pages were missed.

Step 1 / 4
  1. 1A materialized view is defined as a SELECT on a base table with a different primary key.
  2. 2On every base-table write, Cassandra reads the old row and updates the view in the background, maintaining the denormalised copy for you.

  4. 4A view can silently diverge from its base table and there is no reliable tool to detect it. Most teams write the second table from the application (with batches) or use SAI.

Explain the write path in Cassandra: commit log, memtable and SSTable.

Storage Engine Internals 9 min read Difficulty: Advanced 26 of 40
Definition

On each replica a write goes through these steps:

  • Commit log: the mutation is appended to a sequential, durable log on disk (for crash recovery). commitlog_sync: periodic (default, fsync every 10 s) or batch/group for stricter durability.
  • Memtable: the mutation is applied to an in-memory, sorted structure for that table (trie-based in 5.0).
  • The replica acknowledges the write to the coordinator. No disk read and no in-place update happened.
  • Flush: when the memtable reaches its size limit (or on nodetool flush, commit-log pressure), it is written to disk as an immutable SSTable, and the corresponding commit-log segments are recycled.
  • Compaction later merges SSTables, keeping the newest version of each cell.
Commit log Memtable Flush SSTable Sequential I/O Durability

How It Works — Step by Step
Step 1 / 6
  1. 1A replica receives a write from the coordinator.
  2. 2It appends the mutation to the commit log on disk (for durability) and applies it to the in-memory memtable.
  3. 3At that point the write is acknowledged; nothing else needs to happen synchronously.
  4. 4When a memtable is full, it is flushed to disk as an immutable, sorted SSTable, and the matching commit-log segments are freed.
  5. 5Over time many SSTables accumulate; background compaction merges them, keeping the newest version of each cell and dropping purgeable tombstones.
  6. 6Every write is a sequential append with no read-before-write and no random in-place update, which is why Cassandra writes are so fast.

Explain the read path. What roles do Bloom filters, the partition index and caches play?

Storage Engine Internals 10 min read Difficulty: Advanced 27 of 40
Definition

A read on a replica combines all places where a partition's data may be:

  • Memtable: newest, not yet flushed data.
  • Row cache (optional, off by default): whole partitions kept in memory.
  • Bloom filter per SSTable: a probabilistic structure answering "definitely not here" or "maybe here", so most SSTables without the key are skipped without disk I/O (false-positive chance tuned by bloom_filter_fp_chance).
  • Key cache / partition index: locate the partition's offset in the Data file (in 5.0, BTI trie indexes).
  • Merge: data from the memtable and each SSTable is merged cell by cell; the newest timestamp wins and tombstones hide older data.
  • Across replicas, the coordinator compares responses (digests) and triggers read repair if they differ.

Analogy

How It Works — Step by Step
Step 1 / 6
  1. 1A replica checks the memtable for the newest, not-yet-flushed data.
  2. 2If a row cache is enabled it may answer immediately; it is off by default.
  3. 3For each SSTable, an in-memory Bloom filter says "definitely not here" or "maybe here", so most files that lack the key are skipped without disk I/O.
  4. 4For candidate SSTables, the key cache or partition index gives the exact offset of the partition in the data file.

What is a partitioner and a token? How are partitions distributed across nodes, and what are vnodes?

Storage Engine Internals 10 min read Difficulty: Advanced 29 of 40
Definition

The partitioner hashes the partition key into a token. The default Murmur3Partitioner produces 64-bit tokens from -263 to 263-1, spreading keys evenly regardless of their values. (ByteOrderedPartitioner keeps key order but causes hot spots; avoid it.)

The token space is a ring; each node owns the ranges ending at its tokens. With virtual nodes (vnodes), each node has many tokens (num_tokens, default 16 since 4.0, previously 256), so it owns many small ranges spread around the ring. This balances data, and when a node joins or leaves, all other nodes share the streaming work.

How It Works — Step by Step
Step 1 / 5
  1. 1The token space of the Murmur3Partitioner runs from -263 to 263-1 and is arranged as a ring. Each node owns the range from the previous node's token (exclusive) up to its own token (inclusive).
  2. 2The partition key is hashed with Murmur3 into a 64-bit token. Roll number 2401 hashes to 6330071308978448828.
  3. 3The token 6.33×1018 is greater than C's token (4.6×1018) and not greater than D's (9.2×1018), so it falls in D's range and D holds the first replica.
  4. 4Further replicas (RF > 1) go to the next nodes on the ring, subject to the DC and rack rules of the replication strategy.
  5. 5With virtual nodes, every node owns many small ranges spread around the ring, so adding or removing a node moves data evenly from or to all others.

What is an SSTable? Why are SSTables immutable and what does that imply?

Storage Engine Internals 8 min read Difficulty: Advanced 30 of 40
Definition

An SSTable (Sorted String Table) is Cassandra's on-disk data file set, written once by a memtable flush or a compaction and never modified afterwards. Partitions are stored in token order and rows in clustering order.

Components: Data.db (compressed rows), the partition index (Index.db/Summary.db, or Partitions.db/Rows.db for the 5.0 BTI format), Filter.db (Bloom filter), Statistics.db (min/max timestamps, tombstone counts), CompressionInfo.db, Digest, TOC.txt.

Immutability means writes never seek or lock, snapshots are instant (hard links) and files can be streamed safely. The costs are that updates and deletes create new versions and tombstones, and reads may have to merge several SSTables until compaction rewrites them.

Step 1 / 5

  2. 2Helper components make lookups fast: the partition index (BTI Partitions.db in 5.0), its summary, and the Bloom filter that skips files without the key.
  3. 3Statistics record min/max timestamps, tombstone counts and more; data is compressed in chunks (LZ4 by default).

How does replication work in Cassandra? How are replicas chosen?

Replication, Consistency & Operations 9 min read Difficulty: Advanced 31 of 40
Definition

Every partition is stored on RF nodes (the replication factor of its keyspace, per data centre). All replicas are equal: there is no primary copy, and any replica can serve reads and accept writes.

Placement: the node owning the partition's token range gets the first replica. NetworkTopologyStrategy then walks the ring clockwise, choosing nodes in racks not yet used until each DC has its RF copies (if there are fewer racks than RF, racks are reused). A write is sent to all replicas in all DCs; the consistency level only decides how many acknowledgements to wait for.

Replication factor Replica placement Rack awareness Multi-DC replication No primary replica
Analogy
Important certificates are kept in three different cupboards in three different rooms of the office, and a copy is couriered to the branch office too. Any cupboard can answer a request; no one cupboard is "the original".
How It Works — Step by Step
Step 1 / 5
  1. 1Six nodes in one data centre, two in each of three racks. The keyspace uses NetworkTopologyStrategy with RF 3.
  2. 2The partition's token makes N1 the primary owner, so N1 gets the first replica.
  3. 3Walking clockwise, N2 is in the same rack as N1, so the strategy skips it to avoid two copies in one failure domain.
  4. 4It continues until it has three replicas in three different racks: N1, N3 and N5.
  5. 5Losing a whole rack still leaves two copies, and each node stores roughly half the data (6 nodes, 3 copies).
Real-World Scenario

A 6-node cluster in AWS uses 3 racks = 3 availability zones and RF 3. When one zone went down, every partition still had 2 replicas, so LOCAL_QUORUM reads and writes continued without errors; hints and repair caught the zone up afterwards.

How do nodes discover each other and detect failures? How do you add or remove a node?

Definition

Gossip: every second each node exchanges versioned state (status, load, schema version, tokens) with up to three other nodes, so cluster state spreads quickly with no central coordinator. Seed nodes are the first contacts for joining nodes.

Failure detection: the phi accrual failure detector uses heartbeat inter-arrival times to estimate how likely a node is to be down (phi_convict_threshold, default 8) and marks it DOWN locally.

Membership operations: bootstrap (new node takes tokens and streams data), decommission (live node streams its data away and leaves), removenode (remove a dead node; others re-replicate), replace (-Dcassandra.replace_address_first_boot=<ip> for a failed node), cleanup (drop data a node no longer owns).

How It Works — Step by Step
Step 1 / 5
  1. 1Nodes share membership and status with the gossip protocol: every second each node exchanges versioned state with up to three others, so news reaches the whole cluster quickly.
  2. 2Seed nodes are just well-known contact points for nodes joining the cluster; they are not masters.
  3. 3The phi accrual failure detector watches heartbeat arrival times and marks a node down when it is unlikely to be alive, so coordinators stop routing to it.
  4. 4A new node bootstraps: it picks token ranges and streams the matching data from existing replicas before serving reads.

What are lightweight transactions (LWT)? When should you use them?

Replication, Consistency & Operations 9 min read Difficulty: Advanced 35 of 40
Definition

A lightweight transaction is a conditional write that is applied only if a condition holds on the current data: INSERT … IF NOT EXISTS, UPDATE … IF col = value, UPDATE/DELETE … IF EXISTS. It gives linearizable compare-and-set on a single partition, implemented with the Paxos consensus protocol among the partition's replicas.

The response has an [applied] column; when false, it also returns the current values so the client can decide what to do. Costs: several round trips (Paxos v2 in 5.0 reduces them), contention on hot rows, and reads should use SERIAL/LOCAL_SERIAL to see in-progress LWT results. Do not mix LWT and non-LWT writes on the same data.

LWT IF NOT EXISTS IF condition Paxos Compare-and-set SERIAL [applied]
Analogy
Booking a seat in an exam hall by phone: the clerk checks the seat chart, confirms with two colleagues that nobody else is booking it right now, and only then writes your name. Slower than writing directly, but two people never get the same seat.
How It Works — Step by Step
Step 1 / 4
  1. 1A conditional write (IF NOT EXISTS, IF col = value, IF EXISTS) runs the Paxos consensus protocol among the partition's replicas, starting with a prepare/promise round.
  2. 2The current value is read at SERIAL consistency and the condition is evaluated. If it fails, the client gets [applied] = False plus the current values.
  3. 3If it holds, the new value is proposed, accepted by a quorum and committed: a linearizable compare-and-set.
  4. 4This costs several round trips (Cassandra 5.0's Paxos v2 reduces them), so use LWTs for real race conditions like unique registrations, not for every write.
Real-World Scenario
Where LWT is the right tool
  • Unique username or email at registration (IF NOT EXISTS).
  • Allocating a limited lab seat (IF seats_left = 3, then set it to 2).
  • State machines: move an exam attempt from "started" to "submitted" only once (IF status = 'started').

  1. Use LWT only where a race matters

Are LWTs ACID transactions?
They are atomic and isolated for one partition only. Cassandra 5.0 does not have general multi-partition transactions; the Accord protocol (CEP-15) for ACID transactions is planned for a later release.
Why not use LWT for every write?
Each LWT needs several round trips between replicas, so latency is roughly 4× and throughput much lower; contention makes it worse.

Scenario: Design a Cassandra schema for an online exam platform.

Definition

Requirements for a C-DAC online exam platform (tens of thousands of candidates per exam):

  • Q1: a student's result history, newest first.
  • Q2: the merit list of an exam, highest marks first.
  • Q3: the proctoring event timeline of one attempt (login, tab switch, answer saves), kept for 90 days.
  • W1: a submitted result must appear in Q1 and Q2; a result can be submitted only once.

Schema design Query-first Logged batch LWT TTL Bounded partitions
Analogy

How It Works — Step by Step
Step 1 / 4
  1. 1Q1, a student's result history (newest first): partition by roll number, cluster by exam date descending.
  2. 2Q2, the merit list of an exam: partition by exam, cluster by marks descending (then roll number so ties stay unique).

Read latency for attendance_by_centre grew from 5 ms to 800 ms over a semester. tablehistograms showed a max partition size of 1.2 GB: the key was just centre, so each centre's partition grew forever. Re-keying to (centre, day) and backfilling with Spark brought reads back under 5 ms.

Steps

    Application metrics, slow query log (slow_query_log_timeout).
  2. Trace it
    TRACING ON: SSTables merged, tombstones, replicas.
  3. Check table statistics
    Partition size, SSTables per read, tombstones per slice.
  4. Check node health

  5. Fix the root cause
    Usually the data model: bucket, re-key or add a query table.
Cross Questions
What does "dropped MUTATION messages" in tpstats mean?
The node was too overloaded to apply some writes before their timeout; they were dropped (hints/repair recover them). It signals overload: too much traffic, slow disks, GC or compaction.
Is adding nodes a fix for a large partition?
No. A partition lives on RF replicas no matter how many nodes exist; only changing the partition key spreads it.

Analogy
Choosing a vehicle: Cassandra is a fleet of identical buses that never all break down at once; HBase is a train on the Hadoop railway; MongoDB is a flexible car that goes anywhere; DynamoDB is a taxi service: no maintenance, pay per ride, but only in AWS city.
How It Works — Step by Step
Step 1 / 5
  1. 1Cassandra: peer-to-peer, multi-data-centre replication out of the box, availability first with tunable consistency, best for massive write volumes and known queries.
  2. 2HBase: also a wide-column store, but with a master and RegionServers on HDFS; strongly consistent per row, natural inside a Hadoop stack.
  3. 3MongoDB: a document database with flexible ad-hoc queries and secondary indexes; one primary per replica set takes writes.
  4. 4DynamoDB: AWS's fully managed key-value/wide-column service from the same Dynamo paper; no servers to run, but tied to AWS and its pricing.
  5. 5The choice depends on access patterns, consistency needs, existing ecosystem and who will operate it.
Real-World Scenario
Decisions in one organisation
  • Exam event logs and IoT telemetry, multi-region, write-heavy → Cassandra.
  • Student portal content with changing fields and ad-hoc admin queries → MongoDB.
  • Random-access lookups on data already in the on-prem Hadoop cluster → HBase.
  • A small AWS-hosted serverless app → DynamoDB.

Steps to Choose
  1. List access patterns and volumes
    Read/write ratio, data size, latency targets.
  2. Decide consistency and availability needs
    Strong vs tunable, multi-region active-active?
  3. Check query flexibility needs
    Known key lookups vs ad-hoc queries.
  4. Consider operations and ecosystem
    Team skills, cloud vs on-prem, managed services (Astra DB, Keyspaces, Atlas).
  5. Prototype with real data
    Measure p99 latency at expected load.
Cross Questions
What is ScyllaDB?
A C++ re-implementation of Cassandra (CQL- and driver-compatible) with a shard-per-core design, aiming for lower latency and fewer nodes. Concepts and data modelling are the same.
What is Amazon Keyspaces?
A serverless, Cassandra-compatible (CQL) managed service on AWS. Many features match Cassandra, but some (e.g. certain consistency levels, materialized views) differ, so check compatibility.
Why does Cassandra appear in so many interviews for data engineers?
It is the standard example of a distributed, AP, write-optimised store and tests understanding of partitioning, replication, consistency and query-first modelling, concepts that transfer to every big data system.
