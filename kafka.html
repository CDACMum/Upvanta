What is Apache Kafka? Why is it used?

Kafka Fundamentals 7 min read Difficulty: Beginner 1 of 35
Definition

Apache Kafka is an open-source distributed event streaming platform used for building real-time data pipelines and streaming applications.

Originally developed at LinkedIn (2011), later open-sourced under Apache. Kafka acts as a durable, fault-tolerant, high-throughput message bus between systems.

Event Streaming Distributed Pub/Sub LinkedIn Open Source
How It Works — Step by Step
Step 1 / 4
  1. 1In a traditional queue, producers send messages that sit in the queue.
  2. 2When one consumer reads a message, it is deleted. Other consumers never see it. This is point-to-point.
  3. 3In Kafka, producers write to a topic log. Messages are appended and retained for a configurable time (default 7 days).
  4. 4Multiple consumer groups can independently read all messages. Each group tracks its own offset. Replay is possible anytime.
Why Kafka?
FeatureDescription
High ThroughputMillions of messages per second — sequential disk writes + zero-copy transfer
DurabilityMessages persisted to disk with configurable replication across brokers
ScalabilityHorizontal scaling by adding brokers and partitions — no downtime
Fault ToleranceReplication factor ensures no data loss even if brokers fail
DecouplingProducers and consumers are independent — add new consumers without changing producers
RetentionMessages retained for configurable time (default 7 days), not deleted on read
Cross Questions
How is Kafka different from RabbitMQ?
Kafka retains messages on disk (log-based); RabbitMQ deletes after delivery. Kafka supports replay; RabbitMQ is a traditional message broker with routing (exchanges, queues). Kafka scales better for high-throughput streaming; RabbitMQ is better for complex routing and low-latency point-to-point.
What are common Kafka use cases?
Real-time analytics, event sourcing, log aggregation, CDC (Change Data Capture), microservice communication, stream processing (with Kafka Streams), metrics collection, and activity tracking.

Explain Kafka architecture

Kafka Fundamentals 9 min read Difficulty: Beginner 2 of 35
Definition

Kafka's architecture consists of producers (write), brokers (store), consumers (read), and ZooKeeper/KRaft (coordinate).

Data is organized into topics, split into partitions for parallelism, and replicated across brokers for fault tolerance.

Producer Broker Consumer Topic Partition ZooKeeper KRaft
How It Works — Step by Step
Step 1 / 5
  1. 1Producers are applications that publish (write) messages to Kafka topics — e.g. an orders service or payments service.
  2. 2Messages are sent to brokers — servers forming the Kafka cluster. Each broker stores a subset of the topic's partitions.
  3. 3Topics are logical channels, each split into partitions for parallelism. Each partition is an ordered, immutable log.
  4. 4Consumer groups read messages from topics. Each partition is consumed by exactly one consumer in a group — enabling parallel processing.
  5. 5ZooKeeper (legacy) or KRaft (Kafka 3.3+) manages cluster metadata: broker registration, topic configs, and leader election.
Kafka Components
ComponentRoleKey Detail
ProducerWrites messages to topicsChooses partition by key hash or round-robin
BrokerStores and serves messagesEach broker stores partitions; one is the controller
TopicLogical channel / categoryLike a database table — messages of one type go here
PartitionOrdered log within a topicUnit of parallelism and replication
ConsumerReads messages from topicsPart of a consumer group for parallel consumption
Consumer GroupSet of consumers sharing workEach partition → one consumer in the group
ZooKeeper/KRaftCluster metadata & coordinationKRaft (Kafka 3.3+) replaces ZooKeeper entirely
Cross Questions
What is a Kafka broker?
A broker is a single Kafka server. It receives messages from producers, stores them on disk, and serves them to consumers. A cluster typically has 3+ brokers for fault tolerance.
What is KRaft mode?
KRaft (Kafka Raft) replaces ZooKeeper with a built-in consensus protocol. Metadata is managed by a quorum of Kafka controller nodes. Fully production-ready since Kafka 3.5. ZooKeeper support is removed in Kafka 4.0.

What is a Kafka topic?

Kafka Fundamentals 5 min read Difficulty: Beginner 3 of 35
Definition

A topic is a named category or feed to which messages are published. Think of it as a table in a database or a folder in a filesystem.

Topics are append-only logs: messages are written at the end and cannot be modified or deleted (they expire based on retention policy).

Topic Append-Only Immutable Log Retention

Cross Questions
Can you delete a topic?
Yes. kafka-topics.sh --delete --topic . Requires delete.topic.enable=true on brokers (default true since Kafka 1.0).
Can you change the number of partitions?
You can increase partitions (kafka-topics.sh --alter --partitions N) but NEVER decrease. Decreasing would break key-based ordering guarantees.

What is a Kafka message / record?

Kafka Fundamentals 5 min read Difficulty: Beginner 4 of 35
Definition

A Kafka message (also called a record) is the unit of data in Kafka. Each message has a key (optional), a value (the payload), a timestamp, and optional headers.

Record Key Value Headers Timestamp Offset
Message Structure

KeyOptionalDetermines partition (hash(key) % N). Same key → same partition → ordering
ValueYesThe actual message payload (JSON, Avro, Protobuf, string, bytes)

Interview Tip

"A Kafka message is immutable once written. The key determines partition placement. The offset is the unique sequential ID within a partition. In interviews, mention that the key is not just metadata — it is critical for ordering guarantees and data locality (same key always goes to the same partition)."

Cross Questions
What happens if the key is null?
The producer distributes messages via round-robin (or sticky partitioning in Kafka 2.4+). No ordering guarantee across messages with null keys.
What is the maximum message size?
Default: 1 MB (message.max.bytes on broker, max.request.size on producer). Can be increased but large messages hurt throughput — consider chunking or using a reference pattern (store in S3, send key in Kafka).

What is the role of ZooKeeper in Kafka? What is KRaft?

Kafka Fundamentals 7 min read Difficulty: Beginner 5 of 35
Definition

ZooKeeper was the external coordination service Kafka used for cluster metadata: broker registration, topic configs, controller election, and consumer group management.

KRaft (Kafka Raft) eliminates ZooKeeper by managing metadata internally using a Raft-based consensus protocol among Kafka controller nodes.

Important: ZooKeeper was deprecated in Kafka 3.5 and removed entirely in Kafka 4.0 (April 2025). All new deployments should use KRaft mode.

How do you migrate from ZooKeeper to KRaft?
Use the kafka-metadata.sh migration tool. Steps: 1) Upgrade to Kafka 3.6+, 2) Set up KRaft controllers, 3) Run the migration tool to copy metadata, 4) Switch brokers to KRaft mode, 5) Decommission ZooKeeper.

How do partitions work in Kafka?

Topics, Partitions & Replication 8 min read Difficulty: Beginner 6 of 35
Definition

A partition is an ordered, immutable sequence of messages (a commit log). Each topic is divided into one or more partitions.

Partitions enable parallelism (multiple consumers read different partitions simultaneously) and horizontal scaling (partitions spread across brokers).

Partition Offset Ordering Parallelism Commit Log
How It Works — Step by Step
Step 1 / 7
  1. 1A topic is split into partitions — each is an ordered, append-only, immutable log of messages.
  2. 2New messages are appended at the end. Each gets a sequential offset number (0, 1, 2, …).
  3. 3Different partitions grow independently at their own rate.
  4. 4Each partition can live on a different broker, enabling horizontal scaling.
  5. 5Key-based routing: messages with the same key always go to the same partition → guarantees order for that key.
  6. 6Messages with no key are distributed via round-robin (or sticky partitioning in newer Kafka).
  7. 7Ordering is guaranteed only within a partition, not across partitions. Design keys accordingly.
Partition Fundamentals
ConceptDetail
OffsetSequential ID (0, 1, 2, …) assigned per partition. Unique within a partition, NOT globally.
OrderingGuaranteed WITHIN a partition. No ordering across partitions.
ImmutabilityMessages cannot be modified or deleted — only appended. Expired by retention policy.
Key Routinghash(key) % numPartitions → same key always goes to same partition
ParallelismMax consumers in a group = number of partitions. More partitions = more parallelism.
Cross Questions
How many partitions should a topic have?
Rule of thumb: target throughput / per-partition throughput. Start with num_brokers × num_disks or 3–12 per topic. You can increase later but never decrease. Too many partitions increase memory, file handles, and leader election time.
What is the difference between offset and position?
Offset is the message's permanent ID in the partition log. Position (or current offset) is where a consumer is currently reading. Committed offset is the last offset the consumer has confirmed processing.

How does partition replication work?

Topics, Partitions & Replication 9 min read Difficulty: Beginner 7 of 35
Definition

Each partition is replicated across multiple brokers for fault tolerance. One replica is the leader (handles reads/writes), the others are followers (replicate data).

The replication factor determines how many copies exist. A factor of 3 means 3 replicas (1 leader + 2 followers) across 3 different brokers.

Best Practice: Standard production setting: replication-factor=3, min.insync.replicas=2. This tolerates one broker failure with zero data loss.
Replication Leader Follower ISR Replication Factor min.insync.replicas
How It Works — Step by Step
Step 1 / 5
  1. 1Each partition has one leader and N-1 follower replicas across different brokers.
  2. 2All reads and writes go through the leader. Producers write to the leader only.
  3. 3Followers replicate (fetch) messages from the leader to stay in sync.
  4. 4The ISR (In-Sync Replicas) set tracks which replicas are fully caught up with the leader.
  5. 5If the leader fails, a follower from the ISR is elected as new leader. With acks=all, no data is lost.
Replication Concepts
ConceptDescription
LeaderThe one replica that handles all reads and writes for a partition
FollowerPassively replicates data from the leader. Can be promoted to leader on failure.
ISR (In-Sync Replicas)Set of replicas that are fully caught up with the leader. Only ISR members can become leader.
Replication FactorTotal number of replicas (including leader). Set per-topic at creation time.
min.insync.replicasMinimum ISR members needed for acks=all to succeed. If ISR drops below this, writes fail (safe!).
Unclean Leader ElectionIf disabled (default), only ISR members can become leader → no data loss. If enabled, an out-of-sync replica can become leader → may lose data.
Cross Questions
What happens when a follower falls behind?
It is removed from the ISR set. It continues trying to catch up. Once caught up, it re-enters the ISR. replica.lag.time.max.ms (default 30s) controls when a follower is considered out of sync.
What is preferred leader election?
The first replica in the replica list is the "preferred leader." Over time, leaders may shift due to failures. auto.leader.rebalance.enable (default true) periodically moves leadership back to preferred replicas for balanced load.

What are offsets in Kafka?

Topics, Partitions & Replication 6 min read Difficulty: Beginner 8 of 35
Definition

An offset is a unique, sequential integer ID assigned to each message within a partition. Offsets start at 0 and increment monotonically.

Consumers use offsets to track their position: the committed offset is the resume point after a restart.

Offset Committed Offset Consumer Position __consumer_offsets Lag
How It Works — Step by Step
Step 1 / 5
  1. 1The committed offset is the last offset persisted to the __consumer_offsets topic — the resume point after a crash.
  2. 2Current position is where the consumer is actually reading — ahead of the committed offset between commits.
  3. 3The log-end offset is where the producer has written up to. New messages keep arriving.
  4. 4Consumer lag = log-end offset − current position. High lag means the consumer is falling behind.
  5. 5Offset commit strategies: auto-commit (easy, at-least-once), commitSync (safe, blocking), commitAsync (faster, may lose commits on crash).
Offset Types
Offset TypeMeaningStored Where
Message OffsetThe permanent ID of a message in a partitionBroker log (partition file)
Current PositionWhere the consumer is reading right nowIn-memory on the consumer
Committed OffsetLast offset confirmed as processed__consumer_offsets topic (on brokers)
Log-End OffsetOffset of the next message to be written (latest + 1)Broker (partition metadata)
Consumer Laglog-end offset − current positionMonitoring tools (Burrow, kafka-consumer-groups.sh)
Cross Questions
What is the __consumer_offsets topic?
An internal Kafka topic (50 partitions by default) where consumer groups store their committed offsets. Key = (group_id, topic, partition), value = committed offset. Compacted — only latest offset per key is kept.
What auto.offset.reset controls?
What happens when a consumer starts with no committed offset. "earliest" → read from the beginning; "latest" → read only new messages; "none" → throw an error. Default is "latest".

What is log compaction?

Topics, Partitions & Replication 7 min read Difficulty: Beginner 9 of 35
Definition

Log compaction is a retention policy that keeps the latest value for each key instead of deleting old messages by time/size.

This makes Kafka act as a durable key-value store: consumers can always rebuild the full current state from a compacted topic (e.g., user profiles, config changes).

Interview Tip

"Log compaction is how the __consumer_offsets and __transaction_state internal topics work — they keep only the latest offset/state per key. It is also essential for Kafka Streams KTables and CDC use cases where you want the latest snapshot, not the full event history."

Cross Questions
What is a tombstone in compaction?
A message with a non-null key and null value. It tells the compactor to eventually delete all records for that key. Tombstones themselves are retained for delete.retention.ms (default 24 hours) before final removal.
Can you use both delete and compact?
Yes: cleanup.policy=delete,compact. This keeps the latest value per key AND deletes very old segments. Useful for bounded compacted topics.

How does a Kafka producer work?

Producers 9 min read Difficulty: Basic 10 of 35
Definition

A Kafka producer sends messages to topics. Internally it follows a pipeline: serialize → partition → batch → compress → send → ack.

The producer is thread-safe and maintains a buffer of unsent records. A background sender thread batches records by partition and sends them to the leader broker.

Producer Serializer Partitioner Batch Sender Thread acks
How It Works — Step by Step
Step 1 / 7
  1. 1The application calls producer.send(topic, key, value) — the message enters the producer pipeline.
  2. 2The serializer converts key and value to bytes (StringSerializer, JsonSerializer, AvroSerializer, etc.).
  3. 3The partitioner decides which partition: hash(key) % numPartitions for keyed messages, round-robin or sticky for null keys.
  4. 4Messages are buffered in batches by partition in the Record Accumulator. Batching improves throughput via fewer network calls.
  5. 5The sender thread picks up full or timed-out batches and sends them over the network.
  6. 6Batches are sent to the leader broker of each target partition.
  7. 7Acknowledgement (acks) controls durability: acks=0 (fire & forget), acks=1 (leader persisted), acks=all (all ISR replicas persisted).
Producer Example
Python Producer (confluent-kafka)
from confluent_kafka import Producer
import json

# Producer configuration
config = {
    'bootstrap.servers': 'localhost:9092',
    'acks': 'all',                     # wait for all ISR replicas
    'retries': 5,                      # retry on transient failures
    'linger.ms': 5,                    # wait 5ms to batch more records
    'batch.size': 32768,               # 32 KB per batch
    'compression.type': 'snappy',      # compress batches
    'enable.idempotence': True,        # no duplicate on retry
}

producer = Producer(config)

# Callback for delivery reports
def on_delivery(err, msg):
    if err:
        print(f"FAILED: {err}")
    else:
        print(f"Delivered to {msg.topic()}[{msg.partition()}] @ offset {msg.offset()}")

# Send messages
for i in range(5):
    event = {"user_id": f"user_{i % 3}", "action": "click", "page": f"/page_{i}"}
    producer.produce(
        topic='user-events',
        key=f"user_{i % 3}",           # same user → same partition
        value=json.dumps(event),
        callback=on_delivery
    )
    producer.poll(0)   # trigger callbacks

producer.flush()      # wait for all messages to be delivered
print("All messages sent!")
Cross Questions
What does producer.poll() do?
Triggers delivery callbacks for completed sends. Must be called regularly. flush() calls poll() internally until all messages are delivered.
What happens if the broker is down?
The producer retries (up to retries times with retry.backoff.ms delay). With acks=all and enable.idempotence=true, retries are safe — no duplicates. If all retries fail, the callback receives an error.

What are the producer acknowledgement modes (acks)?

Producers 7 min read Difficulty: Basic 11 of 35
Definition

The acks setting controls how many broker replicas must confirm receipt before the producer considers a write successful.

This is the durability vs performance trade-off: more acks = more durable but higher latency.

acks Durability Latency acks=0 acks=1 acks=all
acks Settings
SettingBehaviourDurabilityLatencyUse Case
acks=0Fire and forget — no confirmationMay lose dataLowestMetrics, logs (loss OK)
acks=1Leader confirms write to its logLose if leader dies before replicationMediumGood balance for many workloads
acks=all (-1)All ISR replicas confirmNo data loss (with min.insync.replicas)HighestFinancial, orders, CDC — critical data
Interview Tip

"The interview answer: acks=all + min.insync.replicas=2 + replication.factor=3 is the gold standard for zero data loss. This means: at least 2 out of 3 replicas must confirm. If only 1 replica is in the ISR, writes fail with NotEnoughReplicasException — which is safer than silently losing data."

Cross Questions
What is the difference between acks=all and acks=-1?
They are identical. acks=-1 is the numeric form of acks=all.
What happens with acks=all if min.insync.replicas is not met?
The producer gets NotEnoughReplicasException. The message is not written. This is by design — failing safely rather than risking data loss.

What is an idempotent producer?

Producers 6 min read Difficulty: Basic 12 of 35
Definition

An idempotent producer guarantees that retried messages are not duplicated. Even if the producer retries a send (due to network timeout), the broker writes the message exactly once.

Enabled with enable.idempotence=true (default since Kafka 3.0). The broker tracks (ProducerID, Partition, SequenceNumber) to detect and discard duplicate sends.

Cross Questions
What config does enable.idempotence=true enforce?
It automatically sets acks=all, retries=MAX_INT, and max.in.flight.requests.per.connection=5. These are required for idempotent guarantees.
Is idempotent producer the same as exactly-once semantics?
No — idempotent producer is exactly-once per partition (no duplicate writes). Full exactly-once semantics (EOS) across multiple partitions requires Kafka Transactions (transactional.id).

How does Kafka partition assignment work for producers?

The partitioner decides which partition a message goes to. This affects ordering, load distribution, and data locality.

Default strategy: if key is set → hash(key) % numPartitions; if key is null → sticky round-robin (batch to one partition, switch after).

Cross Questions
What is sticky partitioning?
Introduced in Kafka 2.4 (KIP-480). For null-key messages, instead of round-robin per message, the producer sends an entire batch to one partition then switches. This dramatically improves batching efficiency and throughput.
What if I add more partitions to a topic?
Messages with the same key may now route to a different partition (hash % new_N ≠ hash % old_N). This breaks key-based ordering for existing keys. Plan partition count carefully upfront.

How do Kafka consumers work?

Consumers & Consumer Groups 8 min read Difficulty: Basic 15 of 35
Definition

A Kafka consumer subscribes to topics and reads messages by polling. The consumer tracks its position using offsets and processes messages in order within each partition.

The consumer calls poll() in a loop, processes the returned batch, and periodically commits offsets.

Consumer poll() subscribe assign Offset Commit Deserialization
Consumer Example
Python Consumer (confluent-kafka)
from confluent_kafka import Consumer
import json

config = {
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'order-processors',
    'auto.offset.reset': 'earliest',      # start from beginning if no committed offset
    'enable.auto.commit': False,           # manual commit for at-least-once
    'max.poll.interval.ms': 300000,        # 5 min max between polls
}

consumer = Consumer(config)
consumer.subscribe(['user-events'])

try:
    while True:
        msg = consumer.poll(timeout=1.0)    # wait up to 1s for messages
        if msg is None:
            continue
        if msg.error():
            print(f"Error: {msg.error()}")
            continue

        # Process the message
        event = json.loads(msg.value().decode('utf-8'))
        print(f"Topic: {msg.topic()}, Partition: {msg.partition()}, "
              f"Offset: {msg.offset()}, Key: {msg.key()}, Event: {event}")

        # Manual commit after processing
        consumer.commit(asynchronous=False)

except KeyboardInterrupt:
    pass
finally:
    consumer.close()   # leave group, trigger rebalance
Cross Questions
What does consumer.close() do?
It commits the current offsets (if auto-commit is on), leaves the consumer group (triggers a rebalance), and releases all resources. Always call it in a finally block.
What is the difference between subscribe() and assign()?
subscribe(topics) uses consumer group management — Kafka assigns partitions and rebalances. assign(partitions) manually assigns specific partitions — no group management, no rebalance. Use assign for replay or testing.

What are consumer groups? How do they work?

Consumers & Consumer Groups 9 min read Difficulty: Basic 16 of 35
Definition

A consumer group is a set of consumers that cooperate to consume a topic. Kafka assigns each partition to exactly one consumer in the group.

This provides parallel processing: N consumers can process N partitions simultaneously. Different groups independently consume the same topic (pub/sub).

Key Rule: Max parallelism within a group = number of partitions. Adding consumers beyond that leaves them idle.
Consumer Group group.id Partition Assignment Parallelism Independent Groups
How It Works — Step by Step
Step 1 / 5
  1. 1A topic has 6 partitions (P0–P5). Partitions are the unit of parallelism.
  2. 23 consumers in a group: Kafka assigns partitions evenly — C1 gets P0-P2, C2 gets P3-P4, C3 gets P5.
  3. 3When a consumer joins or leaves, a rebalance is triggered — partitions are reassigned.
  4. 4After adding Consumer 4: partitions are redistributed — each consumer gets fewer partitions, increasing parallelism.
  5. 5⚠ If you have more consumers than partitions, extra consumers sit idle. Max parallelism = partition count.
Consumers vs Partitions
ScenarioPartitionsConsumersResult
Under-provisioned62Each consumer handles 3 partitions — works but slower
Balanced63Each consumer handles 2 partitions — optimal
Matched66One partition per consumer — maximum parallelism
Over-provisioned682 consumers sit IDLE — wasted resources
Cross Questions
Can two consumer groups read the same topic?
Yes — each group independently tracks its own offsets. This is the pub/sub pattern: analytics group, fraud detection group, and audit group all consume the same events independently.
What happens if a consumer dies?
Kafka detects the missing heartbeat (session.timeout.ms, default 45s) and triggers a rebalance. The dead consumer's partitions are reassigned to surviving members.

What is consumer rebalancing?

Consumers & Consumer Groups 8 min read Difficulty: Basic 17 of 35
Definition

Rebalancing is the process of reassigning partitions among consumers in a group. It is triggered when a consumer joins, leaves, or crashes, or when topic partitions change.

During a rebalance, all consumers in the group stop processing (stop-the-world) until the new assignment is agreed upon.

Performance Impact: Rebalancing causes a processing pause. Minimize it with cooperative rebalancing and stable consumer instances.

How do you reduce rebalancing?
1) Use CooperativeStickyAssignor. 2) Set group.instance.id (static membership) — restarts within session.timeout.ms skip rebalance. 3) Tune max.poll.interval.ms and session.timeout.ms. 4) Keep processing time per poll consistent.
What is a group coordinator?
A specific broker elected to manage a consumer group. It handles join/leave, triggers rebalances, and stores committed offsets. Each group is assigned to a coordinator based on hash(group.id) % __consumer_offsets partitions.

How does a Kafka broker store data internally?

Broker & Cluster Internals 8 min read Difficulty: Intermediate 19 of 35
Definition

Each partition is stored as a directory of log segments on disk. A segment is a pair of files: a .log file (messages) and an .index file (offset→position mapping).

When a segment reaches log.segment.bytes (default 1 GB) or log.roll.ms, a new segment is created. Only the active segment is open for writes.

Log Segment .log .index .timeindex Active Segment Sequential I/O
How It Works — Step by Step
Step 1 / 5
  1. 1Each partition is stored as a directory containing log segments. Only the latest segment is active (written to).
  2. 2Older segments are closed and immutable. Segment filenames are the base offset of the first message.
  3. 3Index files map offsets and timestamps to byte positions for fast lookups — no scanning required.
  4. 4Segment rotation happens when the active segment exceeds segment.bytes (default 1 GB) or segment.ms.
  5. 5Retention policy determines cleanup: time-based delete (retention.ms), size-based delete (retention.bytes), or log compaction (keep latest value per key).

Why is Kafka fast despite writing to disk?
Three reasons: 1) Sequential writes — append-only to the active segment, which is orders of magnitude faster than random I/O. 2) OS page cache — reads serve from memory without Kafka managing a cache. 3) Zero-copy transfer (sendfile syscall) — data goes from disk to network socket without copying through application memory.
What is the file naming convention?
Segment files are named by the base offset they contain. 00000000000000000000.log starts at offset 0. 00000000000000000457.log starts at offset 457. This allows binary search across segments to find any offset.

How does the ISR (In-Sync Replica) mechanism work?

Broker & Cluster Internals 7 min read Difficulty: Intermediate 21 of 35
Definition

The ISR (In-Sync Replicas) is the set of replicas that are fully caught up with the leader. A follower stays in the ISR as long as it fetches from the leader within replica.lag.time.max.ms (default 30s).

Only ISR members can be elected leader (unless unclean election is on). With acks=all, the leader waits for ALL ISR members to acknowledge before confirming a write.

Interview Tip

"The high watermark is key: consumers can only read committed messages (up to HW). Even if the leader has written offset 100, if the ISR has only replicated to 95, consumers see up to 95. Cross Questions
What causes ISR shrinkage?
Slow followers: GC pauses, disk I/O bottlenecks, network issues, or an overloaded broker. Monitor under-replicated partitions (ISR size < replication factor) — it is the #1 Kafka health metric.
What is the difference between LEO and HW?
LEO is per-replica: how far that replica has written. HW is the minimum LEO across all ISR members. The gap between them is uncommitted data that could be lost on leader failure.

What are the delivery guarantees in Kafka?

Reliability & Delivery Guarantees 8 min read Difficulty: Intermediate 23 of 35
Definition

Kafka supports three delivery guarantees: at-most-once (may lose), at-least-once (may duplicate), and exactly-once (no loss, no duplicates).

The guarantee depends on producer acks, consumer commit strategy, and whether idempotence/transactions are enabled.

At-Most-Once At-Least-Once Exactly-Once Idempotent Transactional
How It Works — Step by Step
Step 1 / 5
  1. 1At-Most-Once: producer sends without retry, consumer commits offset before processing. Fast but messages can be lost.
  2. 2At-Least-Once: producer retries on failure (acks=all), consumer commits after processing. Safe but may produce duplicates on retry.
  3. 3Exactly-Once (EOS): idempotent producer + transactions ensure each message is delivered and processed exactly once.
  4. 4EOS requires: acks=all, enable.idempotence=true, and a transactional.id for cross-partition atomicity.
  5. 5The broker tracks Producer ID + sequence number per partition. Retried messages with the same sequence are silently deduplicated.

Interview Tip

"In practice, at-least-once + idempotent consumers is the most common production pattern. True exactly-once across systems requires Kafka Transactions or external idempotency (dedup in the database). Cross Questions
How do you make consumers idempotent without Kafka Transactions?
Store a unique message ID (e.g., offset or business key) alongside the processing result in the same database transaction. On reprocessing, check if the ID already exists — skip if so. This is the "outbox pattern" or "dedup table" approach.
What is read_committed isolation?
A consumer with isolation.level=read_committed only sees messages that were part of a committed transaction (or non-transactional messages). It ignores aborted transactions. Default is read_uncommitted (sees everything).

How do Kafka Transactions work?

Reliability & Delivery Guarantees 9 min read Difficulty: Intermediate 24 of 35
Definition

Kafka Transactions enable atomic writes across multiple partitions and topics. Either all messages in a transaction are committed, or none are.

This is the foundation of exactly-once semantics (EOS) in Kafka Streams and consume-transform-produce patterns.

Requirements: Transactions require: transactional.id (set on producer), enable.idempotence=true (automatic), and consumers with isolation.level=read_committed.
Transaction transactional.id Atomic Write Exactly-Once Two-Phase Commit
Transactional Pattern
Exactly-Once Consume-Transform-Produce
from confluent_kafka import Producer, Consumer

# Transactional producer setup
producer = Producer({
    'bootstrap.servers': 'localhost:9092',
    'transactional.id': 'order-processor-1',   # unique per instance
    'enable.idempotence': True,                 # automatic with transactional.id
})
producer.init_transactions()  # register with transaction coordinator

# Consume → Transform → Produce (exactly-once pattern)
consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'order-group',
    'enable.auto.commit': False,
    'isolation.level': 'read_committed',
})
consumer.subscribe(['raw-orders'])

try:
    while True:
        msg = consumer.poll(1.0)
        if msg is None or msg.error():
            continue

        # Begin atomic transaction
        producer.begin_transaction()
        try:
            # Transform and produce to output topic
            enriched = transform(msg.value())
            producer.produce('enriched-orders', value=enriched)

            # Commit consumer offsets as part of the transaction
            producer.send_offsets_to_transaction(
                consumer.position(consumer.assignment()),
                consumer.consumer_group_metadata()
            )

            producer.commit_transaction()    # atomic commit
        except Exception:
            producer.abort_transaction()      # rollback everything
finally:
    consumer.close()

What is producer fencing?
If a producer with transactional.id="X" crashes and restarts, the new instance gets a higher epoch. The old instance (zombie) is fenced — any attempt to commit is rejected. This prevents duplicate processing from zombie producers.

How do retries break ordering without idempotence?
With max.in.flight.requests.per.connection > 1, batch A and batch B are sent in parallel. If A fails and B succeeds, B is written first. When A retries, it is written after B — order broken. Idempotence fixes this: the broker uses sequence numbers to write in the correct order.

When you need strict global ordering and throughput is low (e.g., a configuration change log, a schema changelog). But this limits you to one consumer per group — no parallelism.

How do you tune Kafka for high throughput?

Definition

Kafka tuning involves optimizing producers (batching, compression), consumers (fetch size, parallelism), and brokers (threads, memory, disk).

The key trade-off is always throughput vs latency vs durability. Higher throughput often means larger batches (more latency) or fewer acks (less durability).

How It Works — Step by Step
Step 1 / 7
  1. 1Producer batching: batch.size sets the max bytes per batch. linger.ms adds a wait for the batch to fill up.
  2. 2Compression (snappy, lz4, zstd) reduces network and disk I/O — applied per batch. buffer.memory limits total producer buffering.
  3. 3Consumer fetch: fetch.min.bytes sets minimum data per fetch request — avoids many tiny fetches.

  5. 5Broker threads: network threads handle request parsing, I/O threads handle disk reads/writes. Scale with CPU cores.
  6. 6Flush strategy: Kafka relies on OS page cache for performance. Explicit flushing is rarely needed.
  7. 7Trade-off: larger batches + higher linger = higher throughput but higher latency; smaller batches = lower latency but lower throughput.

  2. 2The Kafka Streams app is a JVM library — no separate cluster needed (unlike Flink or Spark Streaming).
  3. 3Stateless operations: filter(), map(), flatMap(), mapValues() transform records one at a time.
  4. 4Stateful operations: groupByKey().count(), windowed aggregations, joins — require maintaining state.
  5. 5Local state stores (backed by RocksDB) hold aggregation results. State is replicated via a changelog topic for fault tolerance.
  6. 6Results are written to an output topic, which downstream consumers or applications can read.
  7. 7Key advantage: no separate processing cluster. Kafka Streams is a library — deploy your app like any microservice.

Cross Questions
When should you use Kafka Streams vs Flink?
Kafka Streams: Kafka-to-Kafka processing, simple to moderate complexity, want to avoid cluster ops. Flink: need to read/write non-Kafka sources, very complex event processing, large-scale stateful processing with advanced windowing, or need event-time processing with sophisticated watermarks.
How does Kafka Streams handle state?
State is stored locally in RocksDB. A changelog topic automatically backs each state store. On failure, the new instance replays the changelog to rebuild state. This gives both fast local access and fault tolerance.

What is KSQL / ksqlDB?

Ecosystem & Integration 7 min read Difficulty: Expert 33 of 35
Definition

ksqlDB (formerly KSQL) is a SQL engine for stream processing on Kafka. It lets you create streaming queries, materialized views, and event-driven microservices using SQL syntax.

ksqlDB runs as a cluster of servers that process SQL statements against Kafka topics. It uses Kafka Streams under the hood.

ksqlDB KSQL STREAM TABLE Materialized View Push Query
ksqlDB Examples
ksqlDB Streaming SQL
-- Create a stream from a topic
CREATE STREAM user_events (
    user_id VARCHAR KEY,
    action VARCHAR,
    page VARCHAR,
    event_time TIMESTAMP
) WITH (
    KAFKA_TOPIC = 'user-events',
    VALUE_FORMAT = 'JSON',
    TIMESTAMP = 'event_time'
);

-- Real-time aggregation: page views per minute
CREATE TABLE page_views_per_minute AS
    SELECT page,
           COUNT(*) AS view_count,
           WINDOWSTART AS window_start
    FROM user_events
    WINDOW TUMBLING (SIZE 1 MINUTE)
    GROUP BY page
    EMIT CHANGES;

-- Filtering: suspicious activity stream
CREATE STREAM suspicious_logins AS
    SELECT user_id, action, page, event_time
    FROM user_events
    WHERE action = 'login_failed'
    EMIT CHANGES;

-- Pull query (point lookup against materialized table)
SELECT * FROM page_views_per_minute WHERE page = '/checkout';

-- Push query (continuous — results stream as they happen)
SELECT * FROM page_views_per_minute EMIT CHANGES;
Cross Questions
What is the difference between a STREAM and a TABLE in ksqlDB?
STREAM = unbounded sequence of events (like KStream) — each record is independent. TABLE = materialized view updated by a changelog (like KTable) — each record is an upsert by key. STREAM for events, TABLE for state.
When should you use ksqlDB vs Kafka Streams?
ksqlDB: rapid prototyping, ad-hoc stream exploration, SQL-familiar teams, simpler transformations. Kafka Streams: complex logic, unit testing, version-controlled code, custom SerDes, CI/CD integration. ksqlDB runs on Kafka Streams internally.

Cross Questions
What is the Lambda architecture?
Batch layer (Spark/Hive for accuracy) + speed layer (Kafka Streams/Flink for real-time) + serving layer (merge both). Complex to maintain. The Kappa architecture simplifies this: use Kafka + stream processing for everything, replay when needed.
How does Kafka handle backpressure?
Producers: buffer.memory limits in-flight data — if full, producer.send() blocks or throws. Consumers: built-in — just poll slower. Kafka itself buffers on disk with configurable retention — it naturally absorbs traffic spikes. This is a key advantage over in-memory message queues.

Cross Questions
How does MM2 handle active-active replication?
Topic prefixing prevents loops: cluster A's topic "orders" is mirrored to cluster B as "A.orders". MM2 never mirrors a topic that starts with the source prefix. Consumer group offsets are translated so failover is seamless.
What is the RPO with MirrorMaker 2?
RPO (Recovery Point Objective) depends on replication lag — typically seconds. With exactly-once replication (Kafka 3.5+), no duplicate or lost messages. For zero RPO, consider synchronous replication or Confluent Cluster Linking.
