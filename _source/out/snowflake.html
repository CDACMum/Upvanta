What is Snowflake? What are its key features and when should you use it?

Snowflake Foundations 8 min read Difficulty: Beginner 1 of 40
Definition

Snowflake is a fully managed cloud data platform offered as software-as-a-service. It began as a cloud data warehouse and now also covers data lakes (Apache Iceberg tables), data engineering, data sharing and machine learning. It runs on AWS, Microsoft Azure and Google Cloud; you choose the cloud and region when the account is created.

Key features: separate storage and compute that scale independently, near-zero administration (no indexes, vacuuming, distribution keys or hardware), per-second billing, automatic micro-partitioning, native semi-structured data (VARIANT), Time Travel, zero-copy cloning and secure data sharing across accounts.

Cloud data warehouse SaaS Separation of storage & compute ANSI SQL AWS / Azure / GCP VARIANT Time Travel
Analogy
A traditional warehouse is a company-owned delivery fleet: you buy trucks, hire mechanics and pay for them even when idle. Snowflake is a ride-hailing app for queries: cars appear when you need them, you pay per minute of the ride, and someone else looks after the vehicles.
How It Works — Step by Step
Step 1 / 4
  1. 1Data arrives from applications, files in cloud storage, streaming systems and SaaS tools.
  2. 2Snowflake is a cloud data platform delivered as a service. You get SQL, storage and compute with no hardware or software to install, and it runs on AWS, Azure or Google Cloud.
  3. 3One copy of data serves many workloads at once: BI reporting, data science and live sharing with other organisations.
  4. 4Billing follows usage: compute is charged per second while a warehouse runs, storage per terabyte per month. Storage and compute scale independently.
When to Use It
Use Snowflake when…Think twice when…
Many teams run SQL analytics on the same dataYou need a transactional (OLTP) database with millisecond single-row updates
Workloads are spiky: heavy at month-end, quiet otherwiseData is tiny and one PostgreSQL server is enough
You load JSON / Parquet and want to query it with SQLYou must run fully on-premises with no cloud
You need to share live data with partnersCost must be fixed and predictable without any monitoring
Real-World Scenario
Who uses it
  • Thousands of companies across retail, finance, healthcare and media use Snowflake for reporting and data sharing.
  • Typical users are data engineers loading data with SQL and dbt, analysts on Power BI or Tableau, and data scientists using Python.
  • At C-DAC scale: exam, attendance and placement data from every centre can land in one account. Each team gets its own warehouse, so the placement cell's dashboards never slow down the exam cell's result processing.

Cross Questions
Is Snowflake built on Hadoop or an open-source database?
No. It is a new SQL engine designed for the cloud, with its own storage format on top of the cloud provider's object storage (S3, Azure Blob, Google Cloud Storage).
Is Snowflake OLTP or OLAP?
Mainly OLAP: large scans and aggregations. Hybrid tables (part of "Unistore") add row-level lookups and enforced primary keys for light transactional use, but it is not a replacement for MySQL or PostgreSQL in an application.
Can you install Snowflake on your own servers?
No. It is only available as a cloud service. You can choose the cloud provider and region, not the hardware.

Explain Snowflake's architecture: storage, compute and cloud services layers.

Snowflake Foundations 9 min read Difficulty: Beginner 2 of 40
Definition
LayerWhat it doesBilled as
Database StorageKeeps all table data as compressed, columnar micro-partitions in cloud object storage. Snowflake manages organisation, compression and statistics.TB per month
Query Processing (compute)Virtual warehouses: MPP clusters that execute queries. Each warehouse is independent and can be started, stopped and resized at any time.credits per second
Cloud ServicesThe "brain": authentication, access control, metadata, query parsing and optimisation, transactions, result cache.free up to 10% of daily compute

Snowflake calls this a multi-cluster, shared-data architecture. Like shared-disk systems, all compute sees one copy of the data; like shared-nothing MPP systems, each warehouse processes its share of the data in parallel on local CPU, memory and SSD cache.

Storage layer Compute layer Cloud services Micro-partitions Virtual warehouse Shared data
Analogy
A public library: the book stacks are the storage layer (one copy for everyone), the reading rooms are warehouses (open as many as you like, each with its own seats), and the front desk with the catalogue is the cloud services layer that checks your card and tells you where everything is.
How It Works — Step by Step
Step 1 / 4
  1. 1The Cloud Services layer is the brain: it handles logins, keeps all metadata, parses and optimises queries, manages transactions and enforces security.
  2. 2The compute layer is made of virtual warehouses: independent clusters of machines that run queries. Each team or job can have its own.
  3. 3All warehouses read the same data from the storage layer, which keeps tables as compressed columnar micro-partitions in the cloud provider's object storage.
  4. 4Because compute is separate from storage, a heavy ETL job and a BI dashboard on different warehouses do not compete for CPU. This is the multi-cluster, shared-data architecture.
Real-World Scenario
Workload isolation at a training centre

The nightly ETL that loads exam submissions runs on ETL_WH (Medium). Faculty dashboards use BI_WH (Small). A data-science intern experimenting with heavy joins uses DS_WH. All three read the same tables, but none slows down the others, and each is billed only while it runs.

Steps to Apply It
  1. Identify workloads
    Loading, transformation, BI, data science, ad hoc.
  2. Create one warehouse per workload
    Size each for its queries; set AUTO_SUSPEND and AUTO_RESUME.
  3. Grant USAGE on each warehouse to the right role
    So analysts cannot run on the ETL warehouse.
  4. Keep all data in shared databases
    No copies per team; access is controlled by roles.
Cross Questions
Where is the data physically stored?
In the cloud provider's object storage in your account's region (S3, Azure Blob or GCS), but in Snowflake's internal format. You cannot read those files directly; you access them only through Snowflake.
What happens to data when all warehouses are suspended?
Nothing: data lives in the storage layer. Suspending compute only stops billing for compute. Some queries (metadata, result cache) still answer without a warehouse.
Is Snowflake shared-nothing or shared-disk?
A hybrid: shared data (one central copy) plus shared-nothing MPP compute clusters with local caches.

How is Snowflake priced? Explain credits, editions and how warehouse size affects cost.

Snowflake Foundations 8 min read Difficulty: Beginner 3 of 40
Definition

You pay for three things: compute (credits used by warehouses and serverless features), storage (average compressed TB per month) and data transfer out of the region or cloud. A credit is the unit of compute; its price in money depends on the edition, cloud, region and contract.

EditionAdds (main points)
StandardCore SQL warehouse, Time Travel up to 1 day, secure data sharing.
EnterpriseMulti-cluster warehouses, Time Travel up to 90 days, materialized views, search optimisation, masking and row access policies.
Business CriticalHigher security and compliance (e.g. HIPAA, PCI), private connectivity, Tri-Secret Secure keys, database failover.
Virtual Private Snowflake (VPS)A completely separate Snowflake environment for the most sensitive customers.
Credits Per-second billing 60-second minimum Editions Serverless Storage per TB
Analogy
Warehouse sizes are like taxis by the minute: a 4-seater costs 1 unit per minute, an 8-seater 2 units. If the bigger car finishes the trip in half the time, you pay exactly the same and arrive earlier.
How It Works — Step by Step
Step 1 / 5
  1. 1Compute is billed in credits for the time a warehouse is running, per second with a 60-second minimum each time it starts.
  2. 2Storage is billed on the average compressed terabytes stored per month, including data kept for Time Travel and Fail-safe.
  3. 3Serverless features (Snowpipe, automatic clustering, search optimisation, serverless tasks and others) use Snowflake-managed compute and are billed separately. Moving data out to another region or cloud costs data-transfer charges.
  4. 4Warehouse sizes double at each step: X-Small 1 credit per hour, Small 2, Medium 4, Large 8, X-Large 16, and so on. If a bigger size halves the run time, the cost stays the same.
  5. 5Cloud services usage is charged only above 10% of that day's warehouse credits. The price of a credit depends on edition, cloud and region.
Real-World Scenario
Month-end result processing

Result processing takes 40 minutes on a Medium warehouse (4 credits/hour = 2.67 credits). On a Large warehouse it finishes in about 20 minutes (8 credits/hour = 2.67 credits): same cost, results published 20 minutes earlier. Scaling up is only wasteful when the query does not get faster, for example when it is already small or limited by a single-threaded step.

Cross Questions
Is storage or compute usually the bigger bill?
For most customers compute (credits) is the larger part. Storage is billed on compressed size, which is typically several times smaller than the raw data.
What are on-demand and capacity pricing?
On-demand: pay monthly for what you use at list price. Capacity: commit to an amount in advance for a lower price per credit.
Do you pay when a query is answered from the result cache?
No warehouse credits are used. Only cloud services work is done, which is free unless it exceeds 10% of that day's warehouse usage.

Describe the Snowflake object hierarchy. How do databases, schemas and identifiers work?

Objects are named database.schema.object. Unquoted identifiers are stored and resolved in UPPER case, so students, Students and STUDENTS are the same table. A double-quoted identifier ("Students") is case-sensitive and must be quoted every time it is used.

Every database also contains an INFORMATION_SCHEMA with views describing its objects. Account-wide history is in the shared SNOWFLAKE.ACCOUNT_USAGE schema.

Organization Account Database Schema Fully qualified name INFORMATION_SCHEMA
Analogy
An address: country (organization), city (account), building (database), floor (schema), room (table). "Room 12" is ambiguous; "C-DAC Kharghar, 3rd floor, room 12" is not.
How It Works — Step by Step
Step 1 / 5
  1. 1An organization groups one or more accounts. An account lives in one cloud region and is what you log in to.
  2. 2Account-level objects include warehouses, users, roles, resource monitors and databases themselves.
  3. 3A database is a logical container. It holds no compute; any warehouse can query any database the role is allowed to use.
  4. 4A schema inside the database holds the actual objects: tables, views, stages, file formats, sequences, streams, tasks, pipes, UDFs and stored procedures.
  5. 5Objects are addressed as database.schema.object. Unquoted names are stored in UPPER case.

Cross Questions
What is the difference between INFORMATION_SCHEMA and ACCOUNT_USAGE?
INFORMATION_SCHEMA is per database, real-time, and keeps limited history (e.g. 7 to 14 days of query history depending on the function). ACCOUNT_USAGE is account-wide, has 45 minutes to 3 hours of latency, keeps 1 year of history and includes dropped objects.
Why would someone use double-quoted identifiers?
Usually by accident: tools that create tables from mixed-case DataFrame columns. Then every query must write "rollNo" exactly. Upper-casing column names before loading avoids this.
Can a query join tables from two databases?
Yes, if the role has access: SELECT … FROM exam.raw.papers p JOIN placement.mart.offers o …. Databases are only namespaces.

What are permanent, transient and temporary tables? When would you use each?

Snowflake Foundations 7 min read Difficulty: Beginner 5 of 40
Definition

Permanent tables (the default) get full Continuous Data Protection: Time Travel (1 day by default, up to 90 on Enterprise) plus 7 days of Fail-safe. Transient tables persist until dropped and are visible to all sessions, but have at most 1 day of Time Travel and no Fail-safe. Temporary tables exist only for the current session and are dropped automatically when it ends.

Databases and schemas can also be created as TRANSIENT; every table inside them is then transient. Snowflake additionally offers external, Iceberg, dynamic and hybrid tables for special purposes.

Permanent Transient Temporary Fail-safe Time Travel Storage cost
Analogy
Permanent is a document in a bank locker with a backup copy. Transient is a document in your office drawer: it stays until you throw it out, but there is no backup. Temporary is a sticky note on your desk that the cleaner throws away when you leave.
How It Works — Step by Step
Step 1 / 2
  1. 1All three types store data the same way. They differ in how long deleted or changed data is kept for recovery, and who can see them.
  2. 2Use transient tables for data you can rebuild (staging, intermediate ETL output). They skip the 7-day Fail-safe, so they cost less to store.
Real-World Scenario
Cutting storage on staging data

A pipeline truncates and reloads STG_ATTENDANCE every hour. As a permanent table, every reload keeps the old data in Time Travel and then 7 more days in Fail-safe, so storage is billed many times over. Making it transient, with DATA_RETENTION_TIME_IN_DAYS = 0, removes that cost; the data can always be reloaded from source files.

Cross Questions
Can you convert a permanent table to transient?
Not with ALTER TABLE. Create a new transient table with CREATE TRANSIENT TABLE t_new AS SELECT * FROM t, then swap the names with ALTER TABLE t SWAP WITH t_new.
What if a temporary table has the same name as a permanent table?
The temporary table takes precedence in that session and hides the permanent one, which can cause confusing results. Use distinct names.
Do temporary tables cost money?
Yes, storage is billed while they exist (and up to 1 day of Time Travel if set), but they are dropped when the session ends.

What is a virtual warehouse? How do you create, size and resize one?

Virtual Warehouses & Caching 7 min read Difficulty: Beginner 6 of 40
Definition

A virtual warehouse is a named cluster of compute resources (CPU, memory, local SSD) that executes SQL queries, DML and data loading. It holds no data. Sizes are X-Small, Small, Medium, Large, X-Large, 2X-Large … 6X-Large; each size up roughly doubles the compute and the credits per hour (1, 2, 4, 8, 16, 32 …).

Warehouse types: Standard for most work and Snowpark-optimized, which has much more memory per node for memory-heavy Python and ML workloads. A warehouse is either started (billing) or suspended (not billing).

WAREHOUSE_SIZE Credits per hour Started / Suspended Resize online Snowpark-optimized USE WAREHOUSE
Analogy
A warehouse is a team of cooks hired by the hour. The pantry (storage) is shared. A bigger team cooks a big order faster; when the kitchen is quiet you send them home and stop paying.
How It Works — Step by Step
Step 1 / 4
  1. 1A virtual warehouse is a named cluster of compute that runs your SQL. Sizes go from X-Small to 6X-Large.
  2. 2Every step up roughly doubles the compute resources, and doubles the credits charged per hour.
  3. 3You can resize a warehouse at any time, even while it is running. Queries already running finish on the old size; new and queued queries use the new size.
  4. 4A warehouse stores no tables. It reads micro-partitions from the storage layer and keeps a temporary cache on its local SSD while it is running.
Real-World Scenario
Choosing sizes
  • Ad hoc analyst queries on a few GB: X-Small or Small.
  • Nightly transformation of the full exam dataset (hundreds of GB): Medium or Large, sized by testing.
  • A one-off backfill of five years of attendance: temporarily resize to X-Large, then back to Small.
Example
Snowflake SQL (shown, not executed)
CREATE WAREHOUSE lab_wh
  WAREHOUSE_SIZE      = 'XSMALL'
  AUTO_SUSPEND        = 60          -- seconds of idle time before suspending
  AUTO_RESUME         = TRUE
  INITIALLY_SUSPENDED = TRUE
  COMMENT             = 'PGCP-BDA lab sessions';

USE WAREHOUSE lab_wh;

ALTER WAREHOUSE lab_wh SET WAREHOUSE_SIZE = 'LARGE';   -- resize, even while running
ALTER WAREHOUSE lab_wh SUSPEND;
ALTER WAREHOUSE lab_wh RESUME;

SHOW WAREHOUSES LIKE 'LAB%';
Steps
  1. Create
    Give a name, size, auto-suspend and auto-resume; start suspended.
  2. Grant access
    GRANT USAGE ON WAREHOUSE lab_wh TO ROLE bda_student;
  3. Use it
    USE WAREHOUSE lab_wh; or set it as the user's default warehouse.
  4. Measure
    Check execution time, spilling and queuing in the Query Profile and QUERY_HISTORY.
  5. Resize if needed
    Scale up for slow queries, scale out (multi-cluster) for concurrency.
Cross Questions
Does resizing affect queries that are already running?
No. Running queries finish on the resources they started with; queued and new queries use the new size. Resizing a suspended warehouse only takes effect when it next starts.
Is bigger always faster?
Not always. Small queries finish in seconds on X-Small and gain nothing. Bigger sizes help large scans, big joins and sorts, and queries that spill to disk.
Does a warehouse cost money while suspended?
No compute cost while suspended. You only pay storage for the data, which is separate.

What are micro-partitions? How does Snowflake store table data?

Micro-partitions, Pruning & Performance 8 min read Difficulty: Intermediate 11 of 40
Definition

Snowflake automatically divides every table into micro-partitions: contiguous units of storage holding 50 to 500 MB of uncompressed data (much less once compressed). Rows are grouped in the order they are loaded, and inside each micro-partition the data is stored column by column, each column compressed with the best algorithm for its values.

Micro-partitions are immutable. An UPDATE or DELETE writes new micro-partitions and marks the old ones as replaced; this is what makes Time Travel and zero-copy cloning possible. For every micro-partition Snowflake stores metadata: the range of values (min/max) of each column, the number of distinct values and other statistics.

Step 1 / 5
  1. 1You see a normal table of rows and columns.
  2. 2Snowflake splits it automatically into micro-partitions: contiguous groups of rows, each 50–500 MB before compression (much smaller on disk). They are immutable: a change writes new micro-partitions.
  3. 3Inside each micro-partition data is stored by column and every column is compressed separately, so a query reads only the columns it needs.
  4. 4For every column in every micro-partition the Cloud Services layer keeps metadata: the min and max value, the number of distinct values and null count.
  5. 5You never declare partitions. They are created as data is loaded, so their contents follow the order of loading.

What is a clustering key? When should you define one, and what does clustering depth mean?

Definition

A clustering key is one or more columns (or expressions) that Snowflake should use to co-locate rows in the same micro-partitions. Once defined, Automatic Clustering re-organises data in the background using serverless compute, billed in credits.

Clustering depth is the average number of micro-partitions whose value ranges overlap for a given value. A perfectly clustered table has a depth close to 1; a high depth means filters must read many micro-partitions. Use SYSTEM$CLUSTERING_INFORMATION and SYSTEM$CLUSTERING_DEPTH to measure it.

Analogy
A library returns trolley: books come back in random order and are shelved wherever there is space, so every shelf has a bit of everything. Clustering is the librarian re-shelving by subject so that one shelf holds one subject.
How It Works — Step by Step
Step 1 / 4
  1. 1When data arrives in random order, every micro-partition holds values from the whole range, so filters can prune nothing.
  2. 2A clustering key asks Snowflake to keep rows with similar key values together, so each micro-partition covers a narrow range.
  3. 3The clustering depth measures how many micro-partitions overlap for a value. Check it with SYSTEM$CLUSTERING_INFORMATION.
  4. 4Once a key is defined, Automatic Clustering maintains it in the background using serverless compute, billed in credits. It is worth it only for large tables with selective, frequent filters.

  • Table is multi-terabyte (many thousands of micro-partitions) and queries filter on the same column most of the time.

  • The table is queried far more often than it changes, so the re-clustering credits pay for themselves.
  • It is not worth it for small tables or tables rewritten completely every day.

How does COPY INTO work? Explain load metadata, ON_ERROR and VALIDATION_MODE.

Loading & Unloading Data 9 min read Difficulty: Intermediate 17 of 40
Definition

COPY INTO <table> FROM @stage bulk-loads staged files using a running warehouse, many files in parallel. You can select files with FILES = (…) or PATTERN = 'regex', and apply simple transformations by selecting $1, $2 … in a sub-query (reorder, cast, add METADATA$FILENAME).

How It Works — Step by Step
Step 1 / 4
  1. 1COPY INTO reads all matching files in the stage, in parallel, and loads them into the table.
  2. 2For every table, Snowflake records which files were loaded (name and checksum) and keeps this load metadata for 64 days.

What happens if a file is loaded, then modified and re-uploaded with the same name?
Its checksum changes, so COPY treats it as a new file and loads it again, which can duplicate rows. Use new file names for corrections, or dedupe with MERGE.
What if load metadata has expired (file older than 64 days)?
COPY cannot tell whether it was loaded. By default it skips files whose load status is uncertain; LOAD_UNCERTAIN_FILES = TRUE loads them.
COPY INTO vs INSERT … SELECT?
COPY reads files from a stage in parallel with load metadata and error handling. INSERT … SELECT moves data between tables already in Snowflake.

How do you change a pipe's COPY statement?
Pause it (ALTER PIPE … SET PIPE_EXECUTION_PAUSED = TRUE), recreate it with CREATE OR REPLACE, then refresh for any files that arrived in between.

What does LATERAL FLATTEN do? How do you turn a JSON array into rows?

Semi-structured Data (JSON, VARIANT) 9 min read Difficulty: Intermediate 22 of 40
Definition

FLATTEN is a table function that explodes an array or object into one row per element (or per key). Used with LATERAL (or a comma join), it is evaluated once for each row of the table on its left, and its output rows are joined back to that parent row.

Output columns: SEQ (input row sequence), KEY (for objects), PATH, INDEX (for arrays), VALUE (the element) and THIS (the array/object being flattened). Options: OUTER => TRUE keeps parent rows whose array is empty or missing (like a LEFT JOIN); RECURSIVE => TRUE expands every nested level; PATH => '…' starts at a sub-path.

FLATTEN LATERAL VALUE INDEX OUTER RECURSIVE Explode
Analogy
A parent row is a tiffin box with compartments. FLATTEN puts each compartment's food on its own plate, and writes the owner's name on every plate so you still know whose lunch it is.
How It Works — Step by Step
Step 1 / 4
  1. 1Each student row holds an array of exam objects.
  2. 2LATERAL FLATTEN(input => v:exams) produces one output row per array element, joined back to its parent row.
  3. 3FLATTEN returns the columns SEQ, KEY, PATH, INDEX, VALUE and THIS. You normally use VALUE (the element) and INDEX (its position).
  4. 4Without OUTER => TRUE, a parent with an empty array disappears from the result, just like an inner join. RECURSIVE => TRUE expands all nested levels.

What is Time Travel? How do you query or restore historical data?

Time Travel, Fail-safe & Cloning 9 min read Difficulty: Intermediate 26 of 40
Definition

Time Travel lets you access data as it was at any point within a retention period: query it, clone it, or restore dropped tables, schemas and databases. It works because micro-partitions are immutable: changes write new ones, and the old ones are kept for the retention period.

Retention is set by DATA_RETENTION_TIME_IN_DAYS on the account, database, schema or table: default 1 day; up to 90 days for permanent objects on Enterprise edition and above; 0 or 1 day for transient and temporary tables. Setting it to 0 disables Time Travel for that object.

SyntaxMeaning
AT(TIMESTAMP => '2026-02-15 10:00'::TIMESTAMP_LTZ)Data as of that moment
AT(OFFSET => -60*30)Data as of 30 minutes ago (seconds, negative)
AT(STATEMENT => '<query_id>')Data including the changes of that statement
BEFORE(STATEMENT => '<query_id>')Data just before that statement ran
UNDROP TABLE | SCHEMA | DATABASERestore the most recently dropped object with that name
Time Travel AT BEFORE OFFSET UNDROP DATA_RETENTION_TIME_IN_DAYS
Analogy
Version history in Google Docs: you can open the document as it looked yesterday at 10 a.m., copy from it, or restore it, but only for as long as the history is kept.
How It Works — Step by Step
Step 1 / 4
  1. 1Every change creates new micro-partitions; the old ones are kept for the retention period (DATA_RETENTION_TIME_IN_DAYS).
  2. 2Query the table as it was at a timestamp with AT(TIMESTAMP => …), or AT(OFFSET => -seconds).
  3. 3BEFORE(STATEMENT => query_id) returns the data just before a given statement ran, which is perfect for undoing one bad DELETE.
  4. 4Restore with UNDROP for dropped objects, or clone the old version into a new table.
Real-World Scenario
The marks that changed overnight

A coordinator reports that some SQL marks changed after a moderation script ran at 22:00. Comparing the table AT(TIMESTAMP => '… 21:55') with the current table using MINUS shows exactly which rows the script changed, before anyone decides whether to roll back.

Steps
  1. Set retention per table
    Longer for critical tables, 0–1 day for scratch and staging.
  2. Find the moment or statement
    Query history gives timestamps and query IDs.
  3. Look before restoring
    Query with AT/BEFORE and compare with the current data.
  4. Restore
    UNDROP, clone the old version, or INSERT the missing rows back.
Cross Questions
What if you UNDROP a table but a new table with the same name exists?
UNDROP fails. Rename the existing table first, then UNDROP.
Does Time Travel cost money?
Yes, storage for the changed and deleted micro-partitions kept during the retention period. Tables that are rewritten often can have a large Time Travel footprint.

No. Snowflake returns an error saying the requested time is out of the Time Travel range.

Analogy
Time Travel is your own recycle bin: you can open it and take things back. Fail-safe is the city's landfill for the next week: the municipality might dig something out for you in an emergency, but you cannot go in yourself.
How It Works — Step by Step
Step 1 / 5
  1. 1Live data is what normal queries see.
  2. 2Changed or deleted data enters Time Travel, where you can query and restore it yourself for the retention period.
  3. 3After Time Travel expires, permanent-table data moves into Fail-safe for 7 more days. You cannot query it; only Snowflake Support can recover it after a disaster.

Real-World Scenario

Can you shorten or disable Fail-safe?
Not for permanent tables. Use transient or temporary tables when Fail-safe is not wanted.
How long does a Fail-safe recovery take?
It is a support process and can take hours or days; it is not meant for quick fixes.
Is Fail-safe a backup?
It is part of Snowflake's data protection, but it is not under your control. For guaranteed recovery points use longer Time Travel, clones, replication, or Snowflake's backup features where available.

What is zero-copy cloning? How does it work and what is it used for?

Time Travel, Fail-safe & Cloning 8 min read Difficulty: Intermediate 28 of 40
Definition

CREATE TABLE | SCHEMA | DATABASE new_name CLONE source creates a copy that shares the source's micro-partitions. Only metadata is written, so a clone of terabytes is created in seconds and initially uses no additional storage. After that the two objects are fully independent: changes to either write new micro-partitions belonging only to that object, and you pay storage only for those changes.

Clones can be combined with Time Travel: CLONE results AT(OFFSET => -3600). Cloning a database or schema clones the objects inside it (tables, views, sequences, file formats, streams, tasks…); cloned tasks start suspended, and internal named stages are not cloned.

CLONE Zero-copy Metadata only Dev/Test environments AT / BEFORE Copy-on-write
Analogy
Two shortcuts on your desktop pointing to the same photo album. The moment someone edits a page through one shortcut, that page is copied for them and the other person still sees the original.
How It Works — Step by Step
Step 1 / 4

  4. 4You can clone whole databases or schemas (for a dev or test copy) and clone a past state with AT or BEFORE.

What is a stream in Snowflake? How is it used for change data capture (CDC)?

Streams, Tasks, Dynamic Tables & Sharing 9 min read Difficulty: Advanced 31 of 40
Definition

A stream is an object that records the row-level changes (inserts, updates, deletes) made to a table, view or external table since the stream was last consumed. It stores only an offset into the table's version history, not a copy of the data. Selecting from it returns the changed rows plus metadata columns:

ColumnMeaning
METADATA$ACTION'INSERT' or 'DELETE'
METADATA$ISUPDATETRUE when the row is part of an UPDATE (which appears as a DELETE + INSERT pair)
METADATA$ROW_IDA stable unique ID for the row, to track it across changes

Types: standard (all DML; returns the net change), append-only (inserts only; cheaper; for insert-only tables), insert-only (for external and Iceberg tables). The offset advances only when the stream is read by a DML statement that commits (INSERT, MERGE…); a plain SELECT does not consume it.

If a stream is not consumed within the table's data retention period it becomes stale. Snowflake extends retention for tables with streams, up to MAX_DATA_EXTENSION_TIME_IN_DAYS (14 days by default).

CREATE STREAM METADATA$ACTION METADATA$ISUPDATE Offset Append-only Stale stream CDC
Analogy
A stream is a bookmark with sticky notes in a ledger: it shows every entry added or crossed out since you last processed the ledger. When you finish processing and sign off, the bookmark moves forward.
How It Works — Step by Step
Step 1 / 4
  1. 1Rows are inserted and updated in the source table.
  2. 2Selecting from the stream returns the net changes with metadata columns: METADATA$ACTION (INSERT/DELETE), METADATA$ISUPDATE and METADATA$ROW_ID. An update appears as a DELETE plus an INSERT pair.
  3. 3When a DML statement (such as MERGE) reads the stream inside a transaction that commits, the stream's offset advances and those changes are no longer returned.
  4. 4A stream holds no copy of the data: it is an offset into the table's version history. Types: standard, append-only and insert-only.

What are tasks in Snowflake? How do you schedule and chain them?

Streams, Tasks, Dynamic Tables & Sharing 8 min read Difficulty: Advanced 32 of 40
Definition

A task runs a single SQL statement, a call to a stored procedure, or procedural logic (Snowflake Scripting) on a schedule. The schedule is an interval ('5 MINUTE') or a CRON expression with a time zone. Tasks can run on a named warehouse or, if no warehouse is given, on serverless compute that Snowflake sizes automatically.

Tasks form task graphs (DAGs): child tasks declare AFTER parent1, parent2, and only the root task has a schedule. A WHEN condition, typically SYSTEM$STREAM_HAS_DATA('stream'), skips a run (without starting compute) when there is nothing to do. New tasks are created suspended; ALTER TASK … RESUME starts them.

CREATE TASK SCHEDULE CRON AFTER Task graph WHEN Serverless task TASK_HISTORY
Analogy
Tasks are alarm clocks with to-do notes. The root alarm rings at 2 a.m.; finishing one note rings the next ones; and an alarm can be set to stay silent if the in-tray is empty.
How It Works — Step by Step
Step 1 / 5
  1. 1A task runs one SQL statement or stored procedure on a schedule (minutes or a CRON expression with a time zone).
  2. 2Child tasks declare AFTER parent, forming a task graph (DAG). Only the root task has a schedule.
  3. 3A task can wait for several predecessors, so the report is built only after both cleaning tasks succeed.
  4. 4A WHEN condition such as SYSTEM$STREAM_HAS_DATA skips the run when there are no new changes, avoiding needless compute.
  5. 5Tasks use a named warehouse or, if none is given, serverless compute. New tasks are suspended until you resume them.
Real-World Scenario
Nightly result pipeline

At 02:00 IST the root task loads new raw files, two child tasks clean results and attendance in parallel, and a final task rebuilds the rank list after both finish. Each step uses a stream condition, so on holidays with no new data no credits are spent.

Example (shown, not executed)
Snowflake SQL (shown, not executed)
CREATE OR REPLACE TASK load_raw
  WAREHOUSE = etl_wh
  SCHEDULE  = 'USING CRON 0 2 * * * Asia/Kolkata'
AS
  COPY INTO raw_results FROM @s3_results PATTERN = '.*[.]csv';

CREATE OR REPLACE TASK clean_results
  WAREHOUSE = etl_wh
  AFTER load_raw
  WHEN SYSTEM$STREAM_HAS_DATA('RAW_RESULTS_S')
AS
  MERGE INTO results_clean t USING raw_results_s s ON t.roll_no = s.roll_no
  WHEN MATCHED THEN UPDATE SET marks = s.marks
  WHEN NOT MATCHED THEN INSERT (roll_no, marks) VALUES (s.roll_no, s.marks);

CREATE OR REPLACE TASK build_ranklist      -- serverless: no WAREHOUSE
  AFTER clean_results, clean_attendance
AS
  CALL refresh_ranklist();

-- resume children first, then the root (or use SYSTEM$TASK_DEPENDENTS_ENABLE)
ALTER TASK build_ranklist RESUME;
ALTER TASK clean_results  RESUME;
ALTER TASK load_raw       RESUME;

EXECUTE TASK load_raw;                     -- run once now, for testing

SELECT name, state, scheduled_time, completed_time, error_message
FROM   TABLE(INFORMATION_SCHEMA.TASK_HISTORY()) ORDER BY scheduled_time DESC LIMIT 20;
Steps
  1. Write and test the SQL by hand
    Including the MERGE that consumes a stream.
  2. Create the root task with a schedule
    CRON with an explicit time zone avoids UTC surprises.
  3. Add children with AFTER
    Add WHEN conditions to skip empty runs.
  4. Resume the graph
    Children first, then root; check privileges (EXECUTE TASK, warehouse USAGE).
  5. Monitor
    TASK_HISTORY and the task graph view in Snowsight; set error notifications.
Cross Questions
What happens if a run takes longer than the schedule interval?
By default the next run is skipped until the current run finishes (only one instance of a task graph runs at a time).
Serverless or warehouse task?
Serverless suits short, regular tasks (Snowflake right-sizes and you pay only for use). A user-managed warehouse is better when tasks are heavy or can share a warehouse already running.
Tasks vs Airflow?
Tasks are simple and run inside Snowflake. Airflow orchestrates across many systems (APIs, Spark, S3, Snowflake) with richer retries and monitoring. Many teams use Airflow for cross-system flows and tasks for in-Snowflake steps.

What are dynamic tables? How do they compare with streams + tasks and materialized views?

Definition

A dynamic table is defined by a query and a target lag; Snowflake refreshes it automatically so its contents are never more than that lag behind its sources. Refreshes are incremental when the query allows it (only changed rows processed) and full otherwise. Dynamic tables can read other dynamic tables, forming a declarative pipeline; TARGET_LAG = DOWNSTREAM means "refresh only when a downstream table needs it".

Analogy
Streams + tasks is giving a clerk step-by-step instructions on how to update the register. A dynamic table is telling the clerk what the register must show and "never more than 10 minutes out of date"; the clerk works out how.
How It Works — Step by Step
Step 1 / 2
  1. 1Streams and tasks are imperative: you write the MERGE and the schedule. Dynamic tables are declarative: you write the query and how stale it may be. Materialized views are for accelerating queries on one table.
  2. 2A dynamic table refreshes automatically to stay within its TARGET_LAG, incrementally when the query allows it, and can be chained into a pipeline.
Real-World Scenario
Replacing 300 lines of MERGE code

The centre-wise daily summary used a stream, a task and a 120-line MERGE. It became one dynamic table: SELECT centre, att_date, COUNT_IF(present) … GROUP BY ALL with a 15-minute target lag. Snowflake handles the incremental refresh, and the pipeline graph in Snowsight shows lag and refresh history.

Example (shown, not executed)
Snowflake SQL (shown, not executed)
CREATE OR REPLACE DYNAMIC TABLE exam_marks_dt
  TARGET_LAG = '5 minutes'
  WAREHOUSE  = etl_wh
AS

FROM   raw.submissions s, LATERAL FLATTEN(input => s.v:exams) e;

  TARGET_LAG = '15 minutes'

FROM   exam_marks_dt

Steps
  1. Write the transformation as a SELECT
    Test it as a normal query.
  2. Create the dynamic table
    Choose a target lag the business needs (shorter lag = more refreshes = more cost).
  3. Chain
    Downstream dynamic tables read upstream ones; use DOWNSTREAM lag for intermediate steps.
  4. Check refresh mode
    Make sure it is INCREMENTAL for large data; rewrite the query if it falls back to FULL.
Cross Questions
Can you INSERT into a dynamic table?
No. Its contents come only from its query. To change data, change the sources or the query.
When are streams + tasks still the right tool?
When you need procedural logic, calls to external functions, SCD Type 2 history with custom rules, or very precise control over when and how changes are applied.
Does a smaller target lag guarantee fresher data?
It sets the goal; Snowflake schedules refreshes to meet it, as long as each refresh finishes in time on the chosen warehouse.

Explain Secure Data Sharing. What are shares, reader accounts and the Marketplace?

Streams, Tasks, Dynamic Tables & Sharing 8 min read Difficulty: Advanced 34 of 40
Definition

Secure Data Sharing gives another Snowflake account read-only access to selected objects without copying or moving data. The provider creates a share, grants it privileges on a database, schemas, tables and secure views, and adds consumer accounts. The consumer creates a database from the share and queries it with its own warehouse. Updates by the provider are visible immediately.

A reader account is a Snowflake account created and paid for by the provider, for consumers who do not have Snowflake. Listings package shares with descriptions and terms, privately to chosen accounts or publicly on the Snowflake Marketplace; listings can be auto-fulfilled to other regions and clouds.

Share Provider Consumer Secure view Reader account Listing Marketplace
Analogy
Instead of photocopying the attendance register for the university (copies go out of date and can leak), you give their auditor a read-only window into your register that always shows the current page, and only the columns you allow.
How It Works — Step by Step
Step 1 / 5
  1. 1The provider owns the data in its own account.
  2. 2It creates a share and grants access to chosen databases, schemas, tables and secure views.
  3. 3The consumer creates a read-only database from the share. Nothing is copied: queries read the provider's micro-partitions directly.
  4. 4Changes are visible immediately. The provider pays for storage; the consumer pays for the warehouse it queries with. Cross-region sharing needs replication or listings with auto-fulfilment.
  5. 5A consumer without Snowflake can get a reader account managed (and paid for) by the provider. Public datasets are offered through the Snowflake Marketplace.
Real-World Scenario
Sharing results with the university

C-DAC shares a secure view of final results (roll number, course, grade, but no phone numbers) with the university's Snowflake account. The university joins it with their own records using their warehouse. When a revaluation changes a grade, the university sees it immediately, and C-DAC can revoke access at any time.

Steps
  1. Prepare what to share
    Secure views to hide columns/rows and the underlying logic.
  2. Create the share and grant objects
    USAGE on database and schema, SELECT on views/tables.
  3. Add consumers
    Accounts in the same region; for others, use a listing with auto-fulfilment or replication.
  4. Consumer mounts the share
    CREATE DATABASE … FROM SHARE, then grant IMPORTED PRIVILEGES to roles.
  5. Review regularly
    SHOW SHARES; remove consumers who no longer need access.
Cross Questions
Why must shared views be secure views?
A normal view's definition is visible and the optimiser could expose hidden rows through some query plans. Secure views hide the definition and prevent such leakage.
Who pays for what?
Provider: storage of the data. Consumer: the compute used to query it. With reader accounts the provider also pays the compute.
Can the consumer modify or re-share the data?
No. Shared databases are read-only, and the consumer cannot share them onwards. They can copy query results into their own tables (CTAS), so share only what they are allowed to keep.

Definition

Snowflake combines role-based access control (RBAC), where privileges are granted to roles and roles to users, with discretionary access control, where every object has an owner role that can grant privileges on it. Roles can be granted to other roles, forming a hierarchy in which privileges flow upward.

Masking policy vs a view that hides the column?
A view must be maintained per audience and users could query the base table if granted. A policy protects the column itself, everywhere.

Slightly: the policy expression is evaluated per row. Keep them simple and use mapping tables for row access rather than complex logic.

How do you monitor and control Snowflake costs?

Definition
  • Resource monitors: credit quotas per month/week/day for chosen warehouses or the whole account, with actions at thresholds (NOTIFY, SUSPEND after running queries finish, SUSPEND_IMMEDIATE).
  • Budgets: monthly spending limits with notifications that also cover serverless features.
  • Warehouse hygiene: right size, short AUTO_SUSPEND, separate warehouses per workload, multi-cluster only where concurrency needs it.
  • Query guards: STATEMENT_TIMEOUT_IN_SECONDS and STATEMENT_QUEUED_TIMEOUT_IN_SECONDS on warehouses or users.
  • Storage hygiene: transient tables for re-creatable data, sensible Time Travel retention, drop unused clones and tables.
  • Serverless review: automatic clustering, search optimisation, materialized views, Snowpipe, tasks.
  • Visibility: SNOWFLAKE.ACCOUNT_USAGE views (WAREHOUSE_METERING_HISTORY, QUERY_HISTORY, METERING_DAILY_HISTORY…), Snowsight Cost Management, and object tags to attribute cost to teams.

-- CLEAN: latest submission per candidate, one row per subject
CREATE OR REPLACE TABLE clean_marks AS
SELECT s.v:roll::INT          AS roll_no,
       s.v:centre::STRING     AS centre,
       s.v:course::STRING     AS course,
       e.value:sub::STRING    AS subject,
       e.value:m::INT         AS marks,
       s.loaded_at
FROM   raw_submissions s, LATERAL FLATTEN(input => s.v:exams) e
QUALIFY ROW_NUMBER() OVER (PARTITION BY s.v:roll::INT, e.value:sub::STRING
                           ORDER BY s.loaded_at DESC) = 1;

-- MART: result per candidate and merit rank
SELECT roll_no, centre,
       SUM(marks)::INT                                AS total,
       IFF(MIN(marks) >= 40, 'PASS', 'FAIL')          AS result,
       IFF(MIN(marks) >= 40, RANK() OVER (PARTITION BY (MIN(marks) >= 40) ORDER BY SUM(marks) DESC), NULL) AS merit_rank
FROM   clean_marks
GROUP  BY roll_no, centre
ORDER  BY merit_rank NULLS LAST, roll_no;

-- MART: centre-wise pass percentage
SELECT centre,
       COUNT(*)                                                   AS candidates,
       COUNT_IF(min_marks >= 40)                                  AS passed,
       (COUNT_IF(min_marks >= 40) * 100 / COUNT(*))::NUMBER(5,1)  AS pass_pct
FROM  (SELECT roll_no, centre, MIN(marks) AS min_marks FROM clean_marks GROUP BY roll_no, centre)
GROUP BY centre
ORDER BY centre;

Snowflake offers separate per-second compute for each workload, near-zero tuning, multi-cloud and easy sharing. Redshift can be cheaper for steady, predictable workloads with reserved nodes and fits tightly into AWS. The right answer depends on workload pattern, cloud strategy and team skills.
Is Snowflake a lakehouse?
With Apache Iceberg tables (data in open format in your own storage, managed by Snowflake or an external catalog) it can play that role, while keeping its managed tables for the best performance.

Snowflake's built-in AI features: SQL functions that call large language models (summarise, translate, classify, complete), plus search and analyst services, running inside Snowflake's security boundary.
