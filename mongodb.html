What is NoSQL? Why was it needed?

NoSQL Foundations 7 min read Difficulty: Beginner 1 of 40
Definition

NoSQL ("Not only SQL") is a family of databases that store data in models other than relational tables: documents, key-value pairs, wide columns or graphs. They are designed to scale horizontally across many servers, handle flexible or changing schemas, and stay available at very large scale.

They became popular in the late 2000s (Google Bigtable, Amazon Dynamo, then MongoDB, Cassandra, Redis) when web companies outgrew single relational servers.

NoSQL Horizontal Scaling Flexible Schema Distributed Big Data
Analogy
A relational database is a government office register with fixed printed columns: every entry must fit the columns, and when one register is full you buy a bigger, costlier register. A NoSQL database is a set of folders in many cupboards: each folder can hold whatever papers that person has, and when space runs out you simply add another cupboard.
How It Works — Step by Step
Step 1 / 5
  1. 1For decades most applications used one relational database on one large server, with a fixed schema and joins between normalised tables.
  2. 2Web-scale applications brought new pressures: huge numbers of users and writes, data whose shape changes every release, and the need to stay online across regions.
  3. 3NoSQL databases spread data over a cluster of ordinary machines, so capacity grows by adding nodes (horizontal scaling).
  4. 4They store data in flexible models (documents, key-value, wide columns, graphs) that need no upfront schema, and replicate it automatically.
  5. 5The price is usually fewer joins and transactions across records, and sometimes eventual instead of immediate consistency.
Real-World Scenario
C-DAC online exam platform

During an all-India entrance exam, 30,000 candidates save answers every few seconds. Each candidate's attempt has a different number of questions answered, flags and timings. Storing each attempt as one MongoDB document, spread over a replica set, handles the write burst and the varying structure without schema migrations on exam day.

Industry
  • Product catalogues with thousands of different attributes per category (e-commerce) → document databases.
  • Sessions, carts and caches → key-value stores (Redis).
  • IoT readings and time series at millions of writes/second → wide-column stores (Cassandra).
  • Fraud rings and recommendations → graph databases (Neo4j).

Steps to Decide Whether to Use NoSQL
  1. Identify the access patterns
    Which screens/APIs read and write which data, how often, how much.
  2. Check the data shape
    Nested, varying, hierarchical data suits documents; simple lookups suit key-value; relationships suit graphs.
  3. Check scale and availability needs
    Writes per second, data growth, multi-region, tolerance for stale reads.
  4. Pick the model and product
    e.g. MongoDB for documents, Redis for cache, Cassandra for time series.
  5. Prototype with real queries
    Measure before committing; keep the RDBMS where transactions and joins dominate.
Cross Questions
Does NoSQL mean "no SQL at all"?
No, "Not only SQL". Many NoSQL systems have SQL-like languages (Cassandra CQL, MongoDB SQL interface in Atlas), and the idea is to use the right model for each job alongside relational databases.
Is NoSQL always faster than SQL?
No. It is faster for the access patterns it is designed for (lookups by key, reading whole documents). Ad-hoc joins and complex multi-table transactions are often better in an RDBMS.
Name NoSQL databases you know and their type.
MongoDB, Couchbase (document); Redis, DynamoDB (key-value); Cassandra, HBase (wide-column); Neo4j, Amazon Neptune (graph).

Step 1 / 4
  1. 1Key-value: the simplest model, a giant dictionary. Lookups by key are extremely fast; the value is opaque. Ideal for caches, sessions, OTPs, carts.

  • PostgreSQL: fee payments that need strict transactions.

Explain the CAP theorem. Where does MongoDB fit?

NoSQL Foundations 9 min read Difficulty: Beginner 3 of 40
Definition

The CAP theorem (Eric Brewer, 2000) says a distributed data system can guarantee at most two of: Consistency (every read sees the latest write), Availability (every request to a working node gets a response) and Partition tolerance (the system keeps working despite lost messages between nodes).

Because network partitions cannot be avoided, the real choice is: during a partition, prefer C or A? PACELC adds: Else (no partition), trade Latency against Consistency.

CAP Theorem Consistency Availability Partition Tolerance PACELC CP AP
Analogy
Two branches of a bank share account balances by phone. The phone line goes dead (partition). A customer at the second branch asks to withdraw money. The branch can refuse until the line is back (consistent, not available) or pay out based on its last known balance (available, possibly wrong). It cannot do both safely.
How It Works — Step by Step
Step 1 / 6
  1. 1Two replicas of the same data normally stay in sync over the network.
  2. 2A network partition cuts the link. In a distributed system partitions will happen, so Partition tolerance is not optional.
  3. 3A client writes a new value (91) on the Mumbai side. Pune cannot learn about it.
  4. 4CP choice: Pune refuses requests (or only the majority side accepts writes) so nobody reads stale data. Consistent, but partly unavailable. MongoDB with majority writes behaves like this.
  5. 5AP choice: Pune keeps serving, possibly the old value, and the sides reconcile later. Always available, eventually consistent. Cassandra and DynamoDB default to this.
  6. 6CAP only forces the choice during a partition. The PACELC extension adds: Else (normal operation) you trade Latency against Consistency.
Real-World Scenario
MongoDB's position

MongoDB is usually described as CP: writes go only to the primary, and if the primary is cut off from the majority it steps down; the minority side cannot accept writes. With w: "majority" and readConcern: "majority", acknowledged data is never lost or seen stale on the primary. Reading from secondaries (readPreference: "secondary") trades some consistency for availability and latency, so MongoDB is tunable.

Other systems
  • Cassandra, DynamoDB: AP by default, tunable consistency per query (e.g. QUORUM).
  • HBase, ZooKeeper, etcd: CP.
  • Single-node RDBMS: no partitions to tolerate, so CAP does not really apply.
Example
Consistency settings (need a replica set)
// Tune the C/A trade-off per operation in MongoDB
db.attempts.insertOne(
  { roll: 2401, exam: 'SQL', score: 82 },
  { writeConcern: { w: 'majority', wtimeout: 5000 } }   // durable across failover
)
db.attempts.find({ roll: 2401 }).readConcern('majority')      // only majority-committed data
db.attempts.find({ exam: 'SQL' }).readPref('secondaryPreferred') // may be slightly stale, offloads primary
Steps to Apply CAP in a Design
  1. Ask "what happens during a partition?"
    Is a stale or missing answer worse than no answer?
  2. Classify each operation
    Payments, seat allocation → consistency. Feeds, counters, recommendations → availability.
  3. Configure the database
    MongoDB: write concern, read concern, read preference per operation.
  4. Test failure
    Kill the primary or block network in staging and observe behaviour.
Cross Questions
Why can't you pick CA?
In a distributed system, partitions will happen. A system that is "CA" simply has no defined behaviour when they do, so it is not really an option for distributed databases.
What is eventual consistency?
If no new writes occur, all replicas will eventually return the same value. In between, different replicas may answer differently.
Is MongoDB strictly CP?
With default settings (majority writes, primary reads) it behaves CP. Read preferences and lower write concerns let you move towards availability and lower latency for chosen operations.

What is the difference between ACID and BASE?

NoSQL Foundations 7 min read Difficulty: Beginner 4 of 40
Definition

ACID: Atomicity (all or nothing), Consistency (constraints always hold), Isolation (concurrent transactions do not see each other's partial work), Durability (committed data survives crashes).

BASE: Basically Available, Soft state, Eventually consistent: the design philosophy of many distributed NoSQL stores that favour availability and scale over immediate consistency.

ACID BASE Transactions Eventual Consistency Atomicity
Analogy
ACID is a bank transfer: money leaves one account and arrives in the other together, or not at all. BASE is a WhatsApp group: a message reaches everyone eventually, and for a few seconds some members see it while others do not, which is acceptable.
How It Works — Step by Step
Step 1 / 3
  1. 1ACID guarantees that a transaction is all-or-nothing, keeps data valid, is isolated from concurrent transactions, and is never lost once committed.
  2. 2BASE favours availability and scale: the system always responds, replicas may briefly disagree, and they converge over time.
  3. 3Choose per use case: fee payments and seat allocation need ACID; view counts, likes and activity feeds tolerate eventual consistency.
Real-World Scenario
MongoDB gives you both levels
  • Every single-document write is ACID (atomic, isolated) by design.
  • Multi-document ACID transactions exist since 4.0 for when you need them (fee payment + seat update).
  • Reading from secondaries or using w:1 relaxes guarantees for speed: closer to BASE.
Example: Single-Document Atomicity
mongosh

  { _id: 2401 },
  { $inc: { feesPaid: 45000 }, $push: { receipts: { no: 'R-1001', amount: 45000 } } }
)
db.students.findOne({ _id: 2401 }, { name: 1, feesPaid: 1, receipts: 1 })

  _id: 2401,

  feesPaid: 45000,

Steps to Choose Guarantees
  1. List operations that must never be partial
    Payments, seat booking, inventory decrement.
  2. Try to keep them in one document
    Single-document writes are atomic in MongoDB without transactions.
  3. Use transactions only when necessary
    When several documents/collections must change together.
  4. Relax where acceptable
    Counters, analytics, feeds can use eventual consistency.
Cross Questions
Is the "C" in ACID the same as the "C" in CAP?
No. ACID consistency means the database moves from one valid state to another (constraints hold). CAP consistency means every read sees the latest write across replicas (linearizability).

What is MongoDB? Explain its architecture and main components.

MongoDB Basics 8 min read Difficulty: Basic 6 of 40
Definition

MongoDB is an open-source (SSPL licence), document-oriented NoSQL database that stores data as BSON documents in collections. It provides rich queries, secondary indexes, an aggregation framework, replication (replica sets) and horizontal scaling (sharding). MongoDB Atlas is its managed cloud service.

mongoshInteractive JavaScript shell for administration and queries (replaced the old mongo shell)
DriversOfficial libraries: PyMongo, Node.js, Java, C#, Go… used by applications
Replica setA primary + secondaries with the same data, for high availability

ToolsCompass (GUI), mongodump/mongorestore (backup), mongoimport/mongoexport (CSV/JSON)

Analogy
MongoDB is like a library system: mongod is the library building that holds the books, mongosh and Compass are the librarian's desk, drivers are the online catalogue apps that patrons use, a replica set is a set of identical branch libraries that can take over if one closes, and sharding splits a huge collection across several buildings by book number.
How It Works — Step by Step
Step 1 / 4
  1. 1Applications use an official driver (PyMongo, Node.js, Java); humans use mongosh or the Compass GUI.
  2. 2They talk to mongod, the database server process, on port 27017 using the BSON wire protocol. mongod stores data with the WiredTiger storage engine (compression, document-level locking).
  3. 3In production, mongod runs as a replica set: one primary takes writes, secondaries keep copies for high availability.
  4. 4For very large data, a sharded cluster splits collections across several replica sets; applications connect to mongos routers, which use config servers to find the right shard.
Real-World Scenario
Typical deployments
  • Development: one local mongod or a free Atlas cluster.
  • Production: a 3-member replica set (primary + 2 secondaries) across availability zones.
  • Very large scale: a sharded cluster, each shard a replica set, with mongos routers next to the application servers.

MongoDB's default storage engine since 3.2: document-level concurrency control, compression (snappy/zstd/zlib), checkpoints plus a write-ahead journal for durability.

What are databases, collections and documents in MongoDB?

MongoDB Basics 6 min read Difficulty: Basic 7 of 40
Definition

A document is a single record: an ordered set of field–value pairs (values can be strings, numbers, dates, arrays or nested documents), with a unique _id. A collection is a group of documents, usually of the same kind; it has no enforced schema by default. A database is a namespace that holds collections, each with its own files and permissions.

Databases and collections are created implicitly the first time you insert into them.

Database Collection Document Field Namespace Capped Collection
Analogy
A database is a filing cabinet, a collection is a drawer labelled "students", and each document is a file folder for one student. Folders in the same drawer can contain different papers.
How It Works — Step by Step
Step 1 / 4

  2. 2A collection is a group of related documents (like a table), but without a fixed set of columns.
  3. 3A document is one record: field–value pairs, stored as BSON, with a unique _id.
  4. 4Documents in the same collection may have different fields: Vineeta has skills, Anuj has marks. Structure is enforced only if you add schema validation.

How It Works — Step by Step
Step 1 / 5

  2. 2The driver encodes them as BSON (Binary JSON) before sending them to the server, which stores BSON on disk.

  4. 4Every element carries its length, so the server can traverse and skip fields efficiently without parsing text.

What is _id and ObjectId? Can you use your own _id?

MongoDB Basics 7 min read Difficulty: Basic 9 of 40
Definition

Every document must have a unique _id field, which acts as its primary key and is automatically indexed (unique index _id_). If you do not supply one, the driver generates an ObjectId: a 12-byte value made of a 4-byte timestamp, a 5-byte random value and a 3-byte counter.

You may use any unique, immutable value as _id: a roll number, an email, a composite object.

_id ObjectId Primary Key Unique Index Natural Key
Analogy
An ObjectId is like a railway ticket PNR: generated at the counter without asking a central office, it encodes when it was issued, and no two tickets share it.
How It Works — Step by Step
Step 1 / 5
  1. 1The first 4 bytes are a timestamp in seconds, so ObjectId.getTimestamp() tells you when the document was created.
  2. 2The next 5 bytes are a random value unique to the machine and process that generated it.
  3. 3The last 3 bytes are an incrementing counter, so one process can create millions of unique ids per second.
  4. 4Because ids are created by the client driver, inserts need no central sequence, which is essential in a sharded, distributed database.
  5. 5Ids increase roughly with time, so sorting by _id approximates insertion order.
Real-World Scenario
Natural vs generated keys
  • students: _id: 2401 (roll number) is natural, short and always known, so lookups need no extra index.

How do you insert documents? What is the difference between ordered and unordered inserts?

Definition

insertOne(doc) inserts one document; insertMany([docs], {ordered}) inserts a batch. With ordered: true (default) the server stops at the first error; with ordered: false it continues with the remaining documents and reports all errors. Each document insert is atomic; the batch is not a transaction.

insertOne insertMany ordered bulkWrite Duplicate Key
Analogy
Posting a stack of letters: ordered is a clerk who stops at the first letter with a wrong address and returns the rest unposted; unordered is a clerk who posts all good letters and gives you back only the faulty ones.
How It Works — Step by Step
Step 1 / 4
  1. 1A batch of four documents, one of which repeats an existing _id.
  2. 2With the default ordered: true, MongoDB inserts in order and stops at the first error. Documents after the failure are not inserted.
  3. 3With ordered: false, it attempts every document, reports which ones failed, and inserts the rest. Faster for bulk loads.
  4. 4Each individual document insert is atomic, but the batch as a whole is not a transaction (unless you run it inside one).
Real-World Scenario
Bulk loading exam registrations

  1. Prepare documents
    Clean types; set _id if you have a natural key.

    500–1,000 documents per insertMany for bulk loads.

Analogy

How do you query arrays and embedded documents? When do you need $elemMatch?

Definition

Arrays: {skills: 'sql'} matches if any element equals 'sql'; $all requires all listed values; $size matches an exact length; {'skills.0': 'sql'} checks a position.

Embedded documents: use dot notation, {'address.city': 'Pune'}.

Arrays of documents: separate conditions on 'scores.sub' and 'scores.m' may be satisfied by different elements; $elemMatch forces one element to satisfy all of them.

Dot Notation $elemMatch $all $size Arrays Embedded Documents
Analogy
Asking a class "has anyone scored above 80 in Spark?" Without $elemMatch it is like asking "is there a Spark marksheet and some marksheet above 80?", so a student with Spark 61 and SQL 82 says yes. $elemMatch asks about the same marksheet.
How It Works — Step by Step
Step 1 / 5
  1. 1A document with an array of strings, an array of sub-documents and an embedded object.
  2. 2An equality condition on an array field matches when any element matches. No special syntax needed.
  3. 3Dot notation reaches into embedded documents and arrays of documents: 'address.city', 'scores.sub'.
  4. 4Trap: separate conditions on array sub-fields can be satisfied by different elements. Here "Spark" comes from one score and "> 80" from another, so the document wrongly matches.
  5. 5$elemMatch requires one single element to satisfy all conditions. Anuj's Spark score is 61, so he is correctly excluded.

Definition

Embedding stores related data inside the parent document (sub-documents, arrays). Referencing stores the related document's _id and keeps it in its own collection (like a foreign key).

MongoDB modelling is driven by access patterns: "data that is accessed together should be stored together", while keeping documents bounded in size.

Prefer embedding when…Prefer referencing when…
The child belongs to one parent ("contains")The child is shared by many parents (many-to-many)
It is read together with the parentIt is often read on its own

How It Works — Step by Step
Step 1 / 5

  2. 2One read returns everything and one update changes it atomically. Ideal when the child belongs to one parent, stays small and is read with it.
  3. 3Referencing stores an id pointing to a document in another collection, like a foreign key.
  4. 4Needed when the related data is shared by many parents (a course), large or growing without limit, or updated on its own. Reads need a second query or $lookup.

What is an index in MongoDB? How does it speed up queries?

Indexing & Performance 9 min read Difficulty: Advanced 28 of 40
Definition

An index is a separate, sorted data structure (a B-tree) that stores the values of one or more fields with pointers to the documents. With a suitable index the query planner performs an IXSCAN (index scan) and fetches only matching documents, instead of a COLLSCAN that reads every document.

Every collection has a unique index on _id. Indexes speed up reads (filters, sorts, range queries) but cost disk/RAM and slow down writes, because each insert/update must also update every index.

Index B-tree IXSCAN COLLSCAN createIndex Query Planner
Analogy
The index at the back of a textbook: to find "partitioning" you look it up alphabetically and jump to pages 112 and 140, instead of reading the whole book. Each new edition must also update the index, which is the write cost.
How It Works — Step by Step
Step 1 / 4
  1. 1Without an index, MongoDB must examine every document in the collection (COLLSCAN) to find matches.
  2. 2An index keeps the values of a field sorted (a B-tree) with pointers to documents. MongoDB jumps straight to 90 and reads only the qualifying keys (IXSCAN).
  3. 3Only the matching documents are fetched. On millions of documents the difference is milliseconds vs seconds.
  4. 4Indexes are not free: they use disk and RAM, and every insert/update must maintain them. Index for your real queries only.

How should fields be ordered in a compound index? Explain the ESR rule.

Indexing & Performance 9 min read Difficulty: Advanced 30 of 40
Definition

In a compound index, entries are sorted by the first field, then the second, and so on. Order fields as Equality → Sort → Range (ESR): fields compared with equality first, then fields used in sort(), then fields with range conditions ($gt, $lt, $in with many values, $regex).

A compound index also serves queries on its prefixes: {a, b, c} supports {a} and {a, b}, but not {b} or {c} alone.

Compound Index ESR Rule Index Prefix In-memory Sort Equality Sort Range
Analogy
A telephone directory is sorted by city, then surname, then first name. Finding "Mumbai, Sharma" is fast; finding everyone named "Rohit" (third field) means reading the whole book. Put the field you always know exactly (city) first.
How It Works — Step by Step
Step 1 / 5
  1. 1Fields with equality conditions go first in a compound index: they narrow the index to a contiguous range of entries.
  2. 2Fields used for sort go next: within that range, entries are already in sort order, so MongoDB avoids an expensive in-memory sort.
  3. 3Fields with range conditions ($gt, $lt, $in on many values) go last.
  4. 4This is the ESR rule: Equality, Sort, Range.
  5. 5Putting the range field before the sort field breaks the ordering and forces a blocking SORT stage. Compound indexes also serve queries on any prefix of their fields.
Real-World Scenario

What is a covered query? How do you read an explain plan?

Definition

A covered query is answered entirely from an index: all filter fields and all returned fields are in the index, so no document is fetched (totalDocsExamined: 0, plan has PROJECTION_COVERED/IXSCAN but no FETCH). You must exclude _id unless it is in the index.

Step 1 / 4

  2. 2Normally MongoDB finds keys in the index and then fetches each full document from disk.
  3. 3Here every returned field is already in the index, so no document is fetched: a covered query, the fastest kind of read.
  4. 4You must exclude _id (unless it is in the index), and covered queries are not possible on multikey (array) index fields.

What is a replica set? How does failover work?

Replication, Sharding & Transactions 10 min read Difficulty: Advanced 33 of 40
Definition

A replica set is a group of mongod processes that hold the same data: one primary (receives all writes) and one or more secondaries (replicate the primary's oplog and apply it). If the primary becomes unavailable, the members hold an election and a secondary that can reach a majority becomes primary.

Typical size: 3 members (tolerates 1 failure) or 5 (tolerates 2). An arbiter votes but holds no data (avoid in production where possible). Special members: hidden, delayed (protection against bad deletes), priority 0.

Replica Set Primary Secondary Oplog Election Failover Arbiter
Analogy
A head teacher and two deputies. Only the head signs orders (writes); the deputies copy every order into their own register (oplog). If the head falls ill, the staff vote, and the deputy with the most up-to-date register who gets a majority of votes becomes the new head.
How It Works — Step by Step
Step 1 / 5
  1. 1A replica set is a group of mongod processes with the same data. Only the primary accepts writes and records them in its oplog (operations log).
  2. 2Secondaries continuously copy and replay the oplog, staying close to the primary. They can serve reads if the application allows.
  3. 3If the primary crashes, the others stop receiving heartbeats (default election timeout 10 seconds).
  4. 4The remaining members hold an election; a secondary with up-to-date data and votes from a majority becomes the new primary. An odd number of voting members (3, 5) avoids ties.
  5. 5Drivers discover the new primary and retryable writes resend the failed write, so applications see only a short pause.

When one zone had a network failure mid-exam, the primary in that zone stepped down, a secondary was elected in ~8 seconds, and drivers with retryable writes resubmitted pending answer saves. Cross Questions
Why an odd number of voting members?
Elections need a strict majority. With 4 members a 2–2 network split leaves no majority, so no primary can be elected; 3 or 5 avoid ties.
What is the oplog?
A capped collection (local.oplog.rs) recording every write as an idempotent operation. Secondaries tail it; its size determines how long a secondary can be down and still catch up.
What is a rollback?
If a primary accepted writes that were not replicated to a majority before it failed, those writes are rolled back when it rejoins. w: "majority" prevents acknowledged writes from being rolled back.

What is sharding? Explain the architecture of a sharded cluster.

Replication, Sharding & Transactions 10 min read Difficulty: Advanced 35 of 40
Definition

Sharding partitions a collection's data across several shards (each a replica set) based on a shard key, so storage and throughput scale horizontally. Components: mongos routers (clients connect to them), config servers (a replica set storing metadata: which ranges/chunks live on which shard) and the shards.

Data is divided into chunks (ranges of shard-key values); the balancer migrates chunks to keep shards even.

Sharding Shard mongos Config Servers Chunk Balancer Horizontal Scaling
Analogy
A national exam board with regional offices. Each office (shard) holds records for a range of roll numbers. The reception desk (mongos) checks the master list (config servers) and sends your request to the right office. If one office gets too full, some files are moved to another (balancer).
How It Works — Step by Step
Step 1 / 5
  1. 1Applications connect to mongos, a lightweight router; they never talk to shards directly.
  2. 2Config servers store cluster metadata: how each sharded collection is split into chunks by shard key range and which shard holds each chunk.
  3. 3Each shard is itself a replica set holding a subset of the data. Adding shards adds storage and write capacity.
  4. 4A query that includes the shard key is routed only to the shard(s) owning those values: a targeted query.
  5. 5A query without the shard key must be sent to every shard and merged (scatter-gather), which scales poorly. The balancer migrates chunks to keep shards evenly loaded.
Real-World Scenario
When sharding became necessary

Attempt data grew past 4 TB and peak exam writes exceeded what one primary could handle. The attempts collection was sharded on {exam: 1, roll: 1} across 4 shards; queries for one exam or one student stay targeted, and write load is spread.

    Data size or write throughput beyond one replica set after optimisation.
  2. Deploy the topology
    Config server replica set, shard replica sets, mongos routers.
  3. Choose the shard key carefully

Cross Questions
Replication vs sharding?
Replication copies the same data to several servers for availability and read scaling. Sharding splits different data across servers for capacity and write scaling. Production clusters use both.
What is a jumbo chunk?
A chunk that grew beyond the maximum size and cannot be split because all its documents share the same shard-key value, so the balancer cannot move it: a symptom of a low-cardinality shard key.

How do you choose a good shard key? Ranged vs hashed sharding?

Replication, Sharding & Transactions 9 min read Difficulty: Advanced 36 of 40
Definition

A good shard key has high cardinality (many distinct values), low frequency (no value dominates), is not monotonically increasing (or is hashed), and appears in most queries so they can be targeted.

Ranged sharding keeps nearby values together (efficient range queries) but monotonic keys create a hot shard. Hashed sharding spreads writes evenly but range queries become scatter-gather.

Shard Key Cardinality Hot Shard Hashed Sharding Ranged Sharding Targeted Query
Analogy
Dividing exam papers among evaluators: by date received (monotonic) means today's evaluator gets everything; by "pass/fail" (2 values) means only two evaluators can ever work; by exam + roll number spreads the work and still lets you find one student's paper quickly.
How It Works — Step by Step
Step 1 / 4
  1. 1With a monotonically increasing ranged shard key (a timestamp or ObjectId), every new document has the highest value, so all inserts go to the last chunk on one shard: a hot spot.
  2. 2A hashed shard key distributes documents by the hash of the value, spreading writes evenly over all shards.
  3. 3The trade-off: values that are adjacent are scattered, so range queries on that field must ask every shard.
  4. 4A good shard key has many distinct values, no very frequent value, does not increase monotonically (or is hashed), and appears in most queries so they can be targeted. Compound keys (e.g. { centre: 1, roll: 1 }) often achieve this.

Does MongoDB support transactions? When should you use them?

Replication, Sharding & Transactions 9 min read Difficulty: Advanced 37 of 40
Definition

Operations on a single document are always atomic. Since 4.0 (replica sets) and 4.2 (sharded clusters), MongoDB supports multi-document ACID transactions with snapshot isolation, using a session: startTransaction → operations → commitTransaction / abortTransaction.

Limits: 60-second default lifetime, more memory/locking overhead, not available on standalone servers. Use them when several documents must change together and the model cannot put them in one document.

Transactions ACID Session commitTransaction Snapshot Isolation withTransaction
Analogy
A transaction is a sealed envelope of instructions given to the office: either every instruction inside is carried out, or the envelope is returned unopened. Single-document updates are like a single form, which is always processed completely.
How It Works — Step by Step
Step 1 / 5
  1. 1Since MongoDB 4.0 (replica sets) and 4.2 (sharded clusters), several operations can run in one ACID transaction inside a session.
  2. 2Recording a payment touches three collections: the payment record, the student's paid amount and the course's seat count.
  3. 3On commit, all three changes become visible together.
  4. 4On error or abort, none of them is applied: no half-paid student.
  5. 5Transactions cost performance (locks, oplog size, 60-second default limit), so first try to design so that one document holds what must change together; single-document writes are always atomic.
Real-World Scenario
Seat allocation and fee payment

Accepting an admission offer inserts a payment, updates the student's status and decrements available seats in the course. Running these in one transaction guarantees a seat is never taken without payment, or paid for without a seat, even under concurrent offers.

Example
Transaction in mongosh (needs a replica set)
const session = db.getMongo().startSession()
const cdac = session.getDatabase('cdac')
session.startTransaction({ readConcern: { level: 'snapshot' }, writeConcern: { w: 'majority' } })
try {
  cdac.payments.insertOne({ roll: 2410, amount: 95000, at: new Date() })
  cdac.students.updateOne({ _id: 2410 }, { $set: { status: 'admitted' } })
  const r = cdac.courses.updateOne({ _id: 'PG-DBDA', seats: { $gt: 0 } }, { $inc: { seats: -1 } })
  if (r.modifiedCount === 0) throw new Error('No seats left')
  session.commitTransaction()
} catch (e) {
  session.abortTransaction()
  print('rolled back: ' + e.message)
} finally {
  session.endSession()
}

    def admit(s):

        db.payments.insert_one({"roll": 2410, "amount": 95000}, session=s)

Steps to Use a Transaction
  1. First try a single-document design
    Atomic without a transaction (e.g. embed seat counts and holders).
  2. Use a replica set
    Transactions do not work on a standalone mongod.
  3. Wrap the operations
    Start a session and use withTransaction (handles retries).
  4. Keep them short
    Few documents, well under 60 seconds, no user interaction inside.
  5. Handle errors
    Abort on business-rule failure; retry on TransientTransactionError.
Cross Questions
If MongoDB has transactions, should you model it like an RDBMS?
No. Transactions are for the cases that need them; an RDBMS-style normalised model with transactions everywhere loses MongoDB's performance benefits.
What is a write conflict?
Two transactions modifying the same document: one aborts with a WriteConflict (TransientTransactionError) and should be retried.

  3. 3attempts: one document per student per exam (unbounded over time, so not embedded in students), holding answers and score.
  4. 4exam_stats: the computed pattern; updated with $inc on each submission so the dashboard never has to aggregate thousands of attempts.
  5. 5Indexes follow the queries: a unique index stops double attempts; another serves "leaderboard for an exam".
Real-World Scenario
Why not one document per student with all attempts inside?

A student takes dozens of exams over a course and each attempt holds all answers: the array would grow without limit and every answer save would rewrite a large document. Attempts are independent, queried by exam, and therefore their own collection.

How is MongoDB used in data engineering pipelines (CDC, Spark, Kafka)?

Real-World Scenarios 10 min read Difficulty: Expert 39 of 40
Definition

MongoDB is usually the operational store; analytics run elsewhere. Data moves out by: batch export (mongoexport, mongodump, Spark connector reads), or change data capture with change streams, real-time insert/update/delete events built on the oplog, consumed by Kafka connectors (MongoDB Kafka Connector, Debezium) or applications.

Data also flows in: Spark or Kafka sink connectors write processed results back for applications to serve.

Change Streams CDC Kafka Connector Spark Connector mongoexport Debezium Data Lake
Analogy
MongoDB is the shop counter where sales happen live. Change streams are a CCTV feed of every sale sent to head office as it happens; the nightly export is the end-of-day ledger copy.
How It Works — Step by Step
Step 1 / 4
  1. 1MongoDB usually holds live application data; analytics happen elsewhere.
  2. 2Change streams (built on the oplog, replica set required) let consumers subscribe to every insert, update and delete as it happens; Kafka connectors use them for CDC.
  3. 3Events flow through Kafka to Spark Structured Streaming or straight into a data lake as Parquet, keeping analytical copies minutes behind production.
  4. 4For simpler needs, a nightly batch reads collections with the Spark connector or mongoexport.
Real-World Scenario
Near-real-time attendance analytics

A change stream on attendance feeds a Kafka topic through the MongoDB source connector; Spark Structured Streaming aggregates attendance per centre every minute into Parquet on the data lake and a summary collection for the dashboard. The nightly batch job is kept only for reconciliation.

Steps to Build the Pipeline
  1. Decide latency needs
    Daily batch is enough? Use the Spark connector or mongoexport. Minutes or seconds? Change streams + Kafka.
  2. For CDC, use a replica set
    Change streams require the oplog.
  3. Persist resume tokens
    So consumers continue exactly where they stopped after a restart.
  4. Flatten documents for analytics
    Explode arrays and nested fields into columns in Spark.
  5. Land in the lake/warehouse
    Parquet/Iceberg or a warehouse table; schedule with Airflow.
Cross Questions
What happens if a change-stream consumer is down for a long time?
It can resume only while its resume token is still in the oplog window; after that it must re-snapshot the collection. Size the oplog for the longest expected outage.
Why not run analytics directly on the production MongoDB?
Heavy aggregations compete with application traffic. Use a dedicated analytics secondary (hidden member/analytics nodes) or move data to a lake/warehouse.

MongoDB troubleshooting scenarios commonly asked in interviews

Real-World Scenarios 10 min read Difficulty: Expert 40 of 40
Definition

Interviewers present symptoms and expect a structured diagnosis: symptom → evidence (logs, explain, metrics) → root cause → fix → prevention. Most MongoDB problems come from missing indexes, poor data models, shard keys, or misunderstood consistency settings.

Troubleshooting Duplicate Key Slow Query 16 MB Hot Shard Replication Lag
Analogy
Like a mechanic: a strange noise (symptom), a diagnostic scan (explain, profiler), the worn part (root cause), a replacement (fix) and a service schedule (monitoring) so it does not happen again.
How It Works — Step by Step
Step 1 / 5
  1. 1Duplicate key errors usually mean a retried or concurrent insert. Make writes idempotent: natural unique keys, upserts.
  2. 2Slow queries with high CPU are most often collection scans: find them in the profiler and add the right compound index.
  3. 3Documents hitting 16 MB come from arrays that grow forever. Move the children to their own collection or bucket them.
  4. 4One busy shard while others idle points to a monotonically increasing or low-cardinality shard key.
  5. 5Users not seeing their own updates often read from lagging secondaries; use primary reads or causal consistency for that flow.
Real-World Scenario
1. Duplicate students after a network retry
  • The app retried an insert with a new ObjectId after a timeout; both inserts succeeded.
  • Fix: use the roll number as _id (or a unique index on it) and updateOne(..., {upsert: true}) so retries are idempotent.
2. Dashboard query takes 8 seconds
  • Profiler shows COLLSCAN on 5 million attempts and an in-memory SORT.
  • Fix: compound index in ESR order matching the filter and sort; project only needed fields.
3. "BSONObj size … is invalid. Size must be between 0 and 16793600"
  • An activity array inside the student document grew for years.
  • Fix: move activities to their own collection (child references parent); keep a bounded "recent" subset.
4. One shard at 95% CPU, others idle
  • Shard key {createdAt: 1}: all new inserts land in the last chunk.
  • Fix: reshard to a hashed or compound key such as {exam: 1, roll: 1}.
5. Student updates marks but still sees the old value
  • Reads use secondaryPreferred and the secondary lags.
  • Fix: read-your-own-writes flows read from the primary or use causally consistent sessions.

Steps for Any MongoDB Problem
  1. Collect the exact error and timing
    Driver error code, server logs, when it started.
  2. Gather evidence
    Profiler/slow log, explain(), rs.status(), sh.status(), Atlas/mongostat metrics.
  3. Name the root cause
    Index, model, shard key, consistency setting, capacity.
  4. Fix and verify
    Re-run explain/load test; compare metrics.
  5. Prevent
    Validation rules, unique indexes, alerts on slow queries and replication lag.
Cross Questions
How do you find which queries are slow in production?
Enable the profiler for slow operations (db.setProfilingLevel(1, {slowms: 100})), read the slow-query entries in the mongod log, or use Atlas Query Profiler / Performance Advisor.
What is replication lag and how do you monitor it?
How far a secondary's applied oplog is behind the primary. Check rs.printSecondaryReplicationInfo() or monitoring metrics; causes are slow disks, heavy writes or network issues.
