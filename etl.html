What is ETL?

Foundations 6 min read Difficulty: Beginner 1 of 50
Definition

ETL — Extract, Transform, Load — is the process of moving data from source systems into a target system (usually a data warehouse) in a form that is ready for analysis.

StepWhat happensExamples
ExtractRead data from one or more sourcesMySQL orders table, CRM API, CSV files on SFTP, Kafka topic
TransformClean, standardise, join, deduplicate, aggregate, apply business rulesTrim names, convert currencies, map status codes, derive revenue
LoadWrite the result into the targetInsert into fact_sales, upsert dim_customer, write Parquet to S3
ETL Extract Transform Load Data Warehouse Data Pipeline
How It Works — Step by Step
Step 1 / 5
  1. 1Three source systems hold the raw data, each in a different format and owned by a different team.
  2. 2Extract copies only what is needed (ideally only what changed since the last run) into the pipeline, so the live systems are disturbed as little as possible.
  3. 3Transform applies the business rules on a processing engine: clean names, map codes, compute attendance %, join everything on student id, derive CTC bands.
  4. 4Load writes the clean, integrated result into warehouse tables in one controlled step.
  5. 5Analysts and dashboards read from the warehouse. They never query the source systems directly.
Real-World Scenario
C-DAC placement analytics

Every night: extract student marks from the exam MySQL database, attendance from the face-attendance system's API, and company offers from a Google Sheet export; transform — standardise student ids, calculate attendance %, derive CTC bands, join everything per student; load into a reporting table that powers the placement dashboard.

Cross Questions
Why not run reports directly on the source databases?
Sources are built for transactions, not analysis: heavy queries slow down the live application, data is spread across systems with different formats and keys, and sources often overwrite history. ETL integrates, cleans and preserves it.
Name some ETL tools.
GUI/enterprise: Informatica PowerCenter, Talend, SSIS, Azure Data Factory, AWS Glue, Matillion. Code-based: Python, PySpark, dbt (transform), Airflow (orchestration). Ingestion SaaS: Fivetran, Airbyte, Stitch.

What is the difference between ETL and ELT?

Foundations 7 min read Difficulty: Beginner 2 of 50
Definition

In ETL, data is transformed on a separate processing engine before it is loaded into the target.

In ELT, raw data is loaded into the target first, and transformed inside the target using its own compute — typically SQL in a cloud warehouse or lakehouse (Snowflake, BigQuery, Redshift, Databricks).

How It Works — Step by Step
Step 1 / 5
  1. 1ETL: data is transformed on a separate engine (Informatica, Spark, a Python server) and only the cleaned result reaches the warehouse.
  2. 2The warehouse never sees the raw data. To fix a transformation bug you must extract from the source again, and the source may no longer have the old data.
  3. 3ELT: data is loaded into the warehouse as-is first, into raw tables. Loading is fast because nothing is transformed yet.
  4. 4Transformations then run inside the warehouse with SQL (often dbt models), using the warehouse's scalable compute.
  5. 5Because the raw data stays in the warehouse, reprocessing is just re-running SQL. That flexibility is why ELT dominates in the cloud.
Example: ELT with SQL
SQL (MySQL)

INSERT INTO raw_orders VALUES
 (1, '  asha ', '1,200.50', 'paid'),
 (2, 'ROHIT',   '300',      'PAID'),
 (3, 'meera',   'n/a',      'cancelled');

CREATE TABLE stg_orders AS
SELECT order_id,
       CONCAT(UPPER(LEFT(TRIM(cust), 1)), LOWER(SUBSTRING(TRIM(cust), 2))) AS customer,
       CASE WHEN amount REGEXP '^[0-9,.]+$'
            THEN CAST(REPLACE(amount, ',', '') AS DECIMAL(10,2)) END     AS amount,
       UPPER(status)                                                    AS status
FROM raw_orders;

SELECT * FROM stg_orders;

Cross Questions
Which is better?
Neither universally. ELT dominates modern cloud stacks because warehouse compute is elastic and keeping raw data enables reprocessing. ETL still fits when data must be masked or reduced before landing, when the target is not a powerful engine, or for heavy non-SQL transformations (ML features, complex parsing in Spark).
What is "reverse ETL"?
Moving modelled data out of the warehouse back into operational tools — e.g. pushing a customer churn score into the CRM (tools: Hightouch, Census).
What is EtLT?
A hybrid: light transformations during extraction (masking PII, type fixes, deduplication), load, then heavy business transformations in the warehouse.

What is the difference between batch processing and stream processing?

Foundations 7 min read Difficulty: Beginner 4 of 50
Definition

Batch processing collects data over a period and processes it together on a schedule — hourly, daily. Stream processing processes each event (or small micro-batch) continuously, within seconds or milliseconds of it occurring.

Cross Questions
How do you decide between batch and streaming?
Ask what latency the business actually needs and what it is worth. "Real-time" is often requested but a 15-minute batch is enough. Choose streaming when a decision must be made while the event still matters — fraud, alerts, live pricing.
What is event time vs processing time?
Event time is when the event happened (the timestamp in the record); processing time is when the system handles it. Networks and outages delay events, so correct streaming aggregations use event time with watermarks to handle late data.

What is the difference between a data lake, a data warehouse and a lakehouse?

Foundations 8 min read Difficulty: Beginner 5 of 50
Definition

A data warehouse stores structured, cleaned, modelled data in tables, optimised for SQL analytics (schema-on-write).

A data lake stores any data — structured, semi-structured, unstructured — as files in cheap object storage, in raw form (schema-on-read).

A lakehouse adds warehouse features (ACID transactions, schema enforcement, updates/deletes, time travel, fast SQL) on top of lake storage using open table formats (Delta Lake, Apache Iceberg, Apache Hudi).

What is a data swamp?
A data lake where files are dumped without metadata, ownership, quality checks or cataloguing, so nobody can find or trust the data.
What is a data mart?
A subject-specific subset of the warehouse for one department — sales mart, finance mart — usually a star schema.
Why do lakes use Parquet?
Columnar, compressed, stores schema and statistics, and supports predicate/column pruning — far faster and cheaper for analytics than CSV/JSON.

Questions to Ask About Every Source

What is the difference between full extraction and incremental extraction?

Extraction 6 min read Difficulty: Basic 7 of 50
Definition

Full extraction reads the entire source dataset every run.

Incremental (delta) extraction reads only the records that were inserted, updated (or deleted) since the previous successful run.

AspectFull extractionIncremental extraction
Data read per runEverythingOnly changes

Example
SQL (MySQL)
CREATE TABLE orders (
  order_id INT PRIMARY KEY, amount DECIMAL(10,2), status VARCHAR(10),
  updated_at DATETIME NOT NULL,
  INDEX idx_updated_at (updated_at)               -- essential for incremental queries
);
INSERT INTO orders VALUES
 (1, 500, 'PAID',    '2026-10-06 09:00:00'),
 (2, 750, 'PAID',    '2026-10-07 18:30:00'),
 (3, 120, 'PENDING', '2026-10-08 08:15:00'),
 (4, 999, 'PAID',    '2026-10-08 10:45:00');

-- Full extraction
SELECT COUNT(*) AS full_rows FROM orders;

-- Incremental: everything changed after the last successful run
SET @last_run = '2026-10-07 23:59:59';
SELECT order_id, amount, status, updated_at
FROM orders
WHERE updated_at > @last_run
ORDER BY updated_at;

|         4 |

| order_id | amount | status  | updated_at          |

Cross Questions
Why is an index on updated_at important?
Without it, the incremental query scans the whole table — defeating the purpose. With the index, only the changed rows are read.
Can you rely on updated_at being correct?
Only if every write path updates it. Bulk fixes run directly in SQL, triggers that are disabled, or app bugs can change rows without changing updated_at. Verify with periodic full reconciliations, or use log-based CDC.

How does a watermark (high-water mark) based incremental load work?

Extraction 8 min read Difficulty: Basic 8 of 50
Definition

A watermark is the highest value of a change-tracking column (e.g. updated_at or an auto-increment id) that was successfully processed in the previous run. It is stored in a small control (audit) table. Each run extracts rows above the stored watermark, then advances the watermark only after the load succeeds.

Watermark High-water Mark Control Table Incremental Load Overlap Window
How It Works — Step by Step
Step 1 / 6
  1. 1Rows in the source carry an updated_at timestamp. The control table etl_watermark remembers the highest value already loaded: 10-07 23:59.
  2. 2Run N reads only rows with updated_at greater than the watermark (up to a fixed upper bound taken at the start), and loads them into staging and then the target.
  3. 3Only after the load succeeds is the watermark moved forward to the highest value processed: 10-08 10:45.
  4. 4During the day the application inserts and updates more rows, each with a newer updated_at.
  5. 5Run N+1 reads only the rows after the new watermark. Old rows are never re-read, so each run stays small however big the table grows.
  6. 6Safety: if a run fails part-way, the watermark stays where it was, so the next run re-reads the same window. Load with MERGE/upsert so that re-reading never creates duplicates.
Example: Watermark Load in SQL
SQL (MySQL)
CREATE TABLE etl_watermark (table_name VARCHAR(50) PRIMARY KEY, last_value DATETIME, updated_on DATETIME);
INSERT INTO etl_watermark VALUES ('orders', '2026-10-07 23:59:59', NOW());

CREATE TABLE src_orders (order_id INT PRIMARY KEY, amount DECIMAL(10,2), updated_at DATETIME, INDEX(updated_at));
INSERT INTO src_orders VALUES (1, 500, '2026-10-06 09:00:00'), (2, 750, '2026-10-08 08:15:00'),
                              (3, 120, '2026-10-08 10:45:00');
CREATE TABLE stg_orders LIKE src_orders;

-- 1) Read the watermark
SELECT last_value INTO @wm FROM etl_watermark WHERE table_name = 'orders';

-- 2) Fix the upper bound BEFORE extracting (rows written during the run go to the next run)
SET @upper = (SELECT MAX(updated_at) FROM src_orders);

-- 3) Extract the window (wm, upper]
INSERT INTO stg_orders
SELECT * FROM src_orders WHERE updated_at > @wm AND updated_at <= @upper;

-- 4) Advance the watermark only after the load succeeded
UPDATE etl_watermark SET last_value = @upper, updated_on = NOW() WHERE table_name = 'orders';

SELECT order_id, updated_at FROM stg_orders;
SELECT table_name, last_value FROM etl_watermark;
Output
+----------+---------------------+
| order_id | updated_at          |
+----------+---------------------+
|        2 | 2026-10-08 08:15:00 |
|        3 | 2026-10-08 10:45:00 |
+----------+---------------------+
+------------+---------------------+
| table_name | last_value          |
+------------+---------------------+
| orders     | 2026-10-08 10:45:00 |
+------------+---------------------+
Design Rules
  • Advance the watermark last. If the job fails midway, the next run re-reads the same window — so the load must be idempotent (MERGE/upsert).
  • Use a fixed upper bound captured at the start, so rows committed during extraction are not half-included.
  • Overlap / lookback window: subtract a few minutes from the watermark to catch long transactions that committed late with an earlier timestamp; the upsert removes the duplicates.
  • Store per table (and per source) in a control table with run id, row counts and status — this doubles as an audit log.
  • Auto-increment id as watermark works for append-only tables (logs, events) but misses updates.
Cross Questions
Why use > and not >= on the watermark?
> avoids re-reading the last row every run. But if many rows share the exact same timestamp and the previous run stopped part-way through them, some could be missed — which is why an overlap window plus idempotent upsert is the robust choice.
In Airflow, where would the watermark come from?
Often from the run's data interval: data_interval_start and data_interval_end. Each run processes a fixed, reproducible window — backfills and re-runs then become trivial.

What is Change Data Capture (CDC)? Explain its types

Extraction 9 min read Difficulty: Basic 9 of 50
Definition

Change Data Capture is the set of techniques for identifying and capturing the inserts, updates and deletes made in a source database, so that only the changes are propagated downstream — ideally in near real time.

CDC typeHow it worksProsCons
Timestamp / query-basedQuery rows where updated_at > watermarkSimple, no special accessMisses hard deletes; misses intermediate changes; load on source; depends on correct timestamps
Trigger-basedDB triggers write every change into a shadow/audit tableCaptures deletes and every changeAdds overhead to every write; triggers must be maintained
Snapshot diffCompare today's full extract with yesterday'sWorks with any sourceExpensive for large tables; only daily granularity
Log-basedRead the database transaction log (MySQL binlog, PostgreSQL WAL, Oracle redo)Captures everything incl. deletes, in order, with very low source impact, near real timeNeeds log access/permissions and retention; more infrastructure
CDC Binlog WAL Debezium Kafka Connect Log-based CDC Triggers
How It Works — Step by Step
Step 1 / 6
  1. 1The application inserts order 5001 with status PENDING. MySQL writes the row and also records a create event in its binary log.
  2. 2The order is paid: an UPDATE changes the status. The binlog records an update event with both the before and the after values.
  3. 3The order is cancelled and deleted. The row is gone from the table, but the binlog still has a delete event. A timestamp-based query could never see this.
  4. 4Debezium (a Kafka Connect connector) reads the binlog like a replica would and publishes each event to a Kafka topic. No extra queries hit the orders table.
  5. 5The consumer applies the events in order (create, then update, then delete) using MERGE, so the lakehouse table ends up with exactly the same state as the source.
  6. 6That is why log-based CDC is preferred: low impact on the source, near real-time, captures deletes and every intermediate change.
Example
A Debezium change event (simplified)
{
  "op": "u",                                  // c = create, u = update, d = delete, r = snapshot read
  "ts_ms": 1791479700123,
  "source": {"db": "shop", "table": "orders", "file": "binlog.000042", "pos": 18734},
  "before": {"order_id": 5001, "status": "PENDING", "amount": 1499.00},
  "after":  {"order_id": 5001, "status": "PAID",    "amount": 1499.00}
}
Applying CDC events
# Applying a stream of CDC events to a target (key -> current row)
events = [
    {"op": "c", "key": 1, "after": {"status": "PENDING"}},
    {"op": "c", "key": 2, "after": {"status": "PENDING"}},
    {"op": "u", "key": 1, "after": {"status": "PAID"}},
    {"op": "d", "key": 2, "after": None},
    {"op": "c", "key": 3, "after": {"status": "PAID"}},
]
target = {}
for e in events:                       # events must be applied IN ORDER per key
    if e["op"] == "d":
        target.pop(e["key"], None)
    else:
        target[e["key"]] = e["after"]
print(target)
Output
{1: {'status': 'PAID'}, 3: {'status': 'PAID'}}
Cross Questions
What MySQL settings does log-based CDC need?
binlog_format = ROW, binlog_row_image = FULL, binary logging enabled with enough retention, a unique server_id, and a user with REPLICATION SLAVE / REPLICATION CLIENT privileges.
What is the initial snapshot in CDC?
Before streaming changes, the connector reads the current full table (op = "r") and records the log position, so the target starts complete and then stays in sync from that exact point.
Name some CDC tools.
Debezium (open source, Kafka Connect), AWS DMS, Oracle GoldenGate, Qlik Replicate, Fivetran/Airbyte log-based connectors, Striim; Databricks and Snowflake also have native CDC ingestion features.

How do you handle deleted records in the source during incremental loads?

A timestamp-based incremental query only sees rows that still exist. If a row is hard-deleted in the source, it simply disappears and the target keeps a stale copy forever. Deletes need a deliberate strategy.

Example: Detecting Deletes by Key Comparison
SQL (MySQL)
CREATE TABLE src_keys (customer_id INT PRIMARY KEY);            -- keys extracted from source today
INSERT INTO src_keys VALUES (1), (2), (4);

FROM dim_customer d

WHERE s.customer_id IS NULL;

-- Mark them as deleted in the warehouse (keep history)
UPDATE dim_customer d

SET d.is_deleted = 1
WHERE s.customer_id IS NULL;

SELECT * FROM dim_customer;

Cross Questions
Should the warehouse also hard-delete?
Usually not — mark as deleted (soft delete, or close the SCD2 record) so historical facts still join to their dimension. Exception: legal deletion requests (right to be forgotten), where data must be physically removed or anonymised.
What is a tombstone?
A marker record meaning "this key was deleted". In Kafka/Debezium it is a message with the key and a null value, which also lets log compaction remove the key.

What is a landing zone / raw layer, and why keep raw data?

Extraction 5 min read Difficulty: Basic 11 of 50
Definition

The landing zone (raw, bronze layer) is where extracted data is first stored exactly as received — same format, no transformations — usually in object storage, partitioned by source and load date.

Typical raw layout
s3://cdac-datalake/raw/
  mysql/shop/orders/load_date=2026-10-08/part-0000.parquet
  api/crm/contacts/load_date=2026-10-08/page-001.json
  sftp/vendor_x/stock/load_date=2026-10-08/stock_20261008.csv
Landing Zone Raw Layer Bronze Immutable Replay Audit
Why Keep Raw Data
  • Reprocessing: when a transformation bug is found, rebuild downstream tables from raw without hitting the source again (the source may no longer have the old data).
  • Auditability: prove exactly what the source sent on a given day.
  • Decoupling: extraction and transformation can fail and retry independently.
  • New use cases: a column nobody needed last year is still available.
  • Keep raw data immutable and append-only; add metadata columns such as _load_ts, _source_file, _batch_id.
  • Apply lifecycle rules (move to cheaper storage after N days, delete after the retention period) and protect PII with access controls.
Cross Questions
Should raw data be stored as CSV/JSON or converted to Parquet?
Store files exactly as received when auditability matters (original CSV/JSON); many teams additionally write a Parquet copy in bronze for efficient processing. Database extracts are usually written straight to Parquet/Avro.

What is a staging area and why is it used?

Extraction 5 min read Difficulty: Basic 12 of 50
Definition

A staging area is an intermediate storage location (tables or files) where extracted data is held temporarily for cleansing, validation and transformation before being loaded into the final target tables.

Staging Intermediate Tables Validation Isolation Swap
Why Use Staging
  • Isolation from sources: extract quickly, release the source, then transform at leisure.
  • Validation before publishing: run quality checks on staging; only load the target if they pass, so consumers never see half-loaded or bad data.
  • Set-based operations: join and merge large batches efficiently inside the database.
  • Restartability: if the load fails, the staged data is still there.
  • Atomic publish: build a new table in staging and swap it in with a rename.
Atomic swap pattern
CREATE TABLE sales_summary     (city VARCHAR(20), revenue DECIMAL(12,2));

How do you remove duplicates in a pipeline?

Definition

Duplicates arrive from retries, overlapping extraction windows, at-least-once delivery, files sent twice, or genuine repeats in the source. The right method depends on what "duplicate" means: exact copy, same business key, or same key with a newer version.

TypeMethod
Exact duplicate rowsSELECT DISTINCT / dropDuplicates()
Same key, keep latestROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC) = 1

Fuzzy duplicates ("Asha Patil" vs "A. Patil")Matching rules / record-linkage libraries — a data-quality project, not plain ETL

How It Works — Step by Step
Step 1 / 5
  1. 1Staging holds 4 rows: customer 101 appears three times (an old version, a newer version and an exact duplicate from a retry); customer 102 appears once.
  2. 2PARTITION BY customer_id splits the rows into one group per business key. Each group is handled independently.
  3. 3ORDER BY updated_at DESC sorts each group newest-first and ROW_NUMBER() numbers the rows 1, 2, 3… Add a tie-breaker (such as batch_id) so equal timestamps are numbered the same way every run.
  4. 4The filter WHERE rn = 1 keeps only the newest row of each group. The older version and the duplicate are discarded.
  5. 5Result: exactly one current row per customer, ready to be merged into the target.
Example
SQL (MySQL)

FROM (

         ROW_NUMBER() OVER (PARTITION BY customer_id

  FROM stg_customers s
) t

Generating Keys

Ways to generate surrogate keys: database identity / AUTO_INCREMENT, sequences, ROW_NUMBER() + max(existing key) in Spark, or a deterministic hash of the business key (e.g. md5(source || customer_id), common in dbt and distributed systems because it needs no coordination).

Cross Questions
Why load unmatched facts with key −1 instead of dropping them?
Dropping silently loses revenue from reports. Loading to an "Unknown" member keeps totals correct and makes the problem visible; a later job can re-point them when the dimension arrives (see late-arriving dimensions).
Hash keys vs integer keys?
Hash keys can be computed anywhere in parallel and are stable across reloads, but are larger (slower joins) and have a tiny collision risk. Integer keys are compact but need a central generator.

What is MERGE / UPSERT? How is it written in different systems?

Loading 8 min read Difficulty: Intermediate 21 of 50
Definition

Upsert = UPDATE if the key exists, otherwise INSERT. The SQL-standard statement is MERGE, which compares a source (staging) set with a target table on a key and applies matched / not-matched actions — insert, update and optionally delete — in one atomic statement.

MERGE UPSERT ON DUPLICATE KEY UPDATE ON CONFLICT Delta Lake Idempotent Load
How It Works — Step by Step
Step 1 / 6
  1. 1The target table already holds products 1 and 2.
  2. 2The staging table holds today's changes: product 2 has a new price and product 3 is new. Staging must contain at most one row per key, so deduplicate first.
  3. 3MERGE joins staging to the target ON t.id = s.id. Product 2 matches, so the WHEN MATCHED branch updates its price from 120 to 135.
  4. 4Product 3 has no match in the target, so the WHEN NOT MATCHED branch inserts it.
  5. 5Product 1 is not in staging, so it is untouched. With CDC data, an extra branch can delete rows whose change operation is "D".
  6. 6All of this happens in one atomic statement. Re-running it with the same staging data gives the same result, which makes MERGE the foundation of idempotent loads.

What is idempotency and why is it critical for pipelines?

Loading 7 min read Difficulty: Intermediate 22 of 50
Definition

A pipeline run is idempotent if running it once or many times for the same input/window produces the same result in the target — no duplicates, no double counting.

Why it matters: Pipelines fail and get retried — by Airflow, by an on-call engineer, by a backfill. If a retry doubles the revenue in a dashboard, the pipeline is not production-ready.
Idempotency Retry Re-run Backfill Deterministic Exactly-once
How It Works — Step by Step
Step 1 / 4
  1. 1Both pipelines load the sales for 8 October. After the first run both show the correct revenue of ₹1,000.
  2. 2The job crashes after the data was written but before it reported success, so the orchestrator retries it. This happens all the time in production.
  3. 3The append-only pipeline inserts the same rows again, and revenue doubles to ₹2,000. The pipeline is not idempotent.
  4. 4The second pipeline first deletes the 8-October window and then inserts it, inside one transaction (or uses MERGE / partition overwrite). Revenue stays ₹1,000 however many times it runs.

What is the Medallion Architecture (Bronze, Silver, Gold)?

Architecture 7 min read Difficulty: Advanced 26 of 50
Definition

The medallion architecture organises a lakehouse into layers of increasing quality. Data flows Bronze → Silver → Gold, and each layer has a clear contract about what it contains. The term was popularised by Databricks; the same idea is called raw / staging / curated, or landing / conformed / presentation, elsewhere.

Medallion Bronze Silver Gold Lakehouse Layered Architecture
How It Works — Step by Step
Step 1 / 5
  1. 1Bronze stores data exactly as it arrived from each source, append-only, plus metadata (load time, source file, batch id). Nothing is lost.
  2. 2Silver applies technical clean-up: correct types, standard formats, deduplication, NULL handling and joining keys across sources. It is the trusted single version of each entity.
  3. 3Gold holds business-ready data: star schemas, aggregates and KPI tables shaped for specific uses such as the sales dashboard or the placement report.
  4. 4Consumers (BI tools, data scientists, applications) read mostly from Gold, sometimes from Silver, and never from Bronze.
  5. 5Because Bronze keeps the raw history, any downstream layer can be rebuilt after a logic change. That is the main reason for the layered design.

It is an organisation of storage layers. ELT/ETL jobs move data between the layers: ingestion fills bronze, transformation jobs build silver and gold.

No. Small projects may combine silver and gold; some add a "platinum" or "semantic" layer. What matters is the principle: keep raw data, and separate cleaning from business logic.

What is the difference between Lambda and Kappa architectures?

Architecture 7 min read Difficulty: Advanced 27 of 50
Definition

Both are architectures for combining large-scale historical processing with low-latency results.

Lambda (Nathan Marz) runs a batch layer and a speed (streaming) layer in parallel and merges their outputs in a serving layer.

Kappa (Jay Kreps) uses only a streaming layer over a replayable log; historical reprocessing is done by replaying the log.

Lambda Architecture Kappa Architecture Batch Layer Speed Layer Kafka Replay
How It Works — Step by Step
Step 1 / 6
  1. 1Lambda: every event goes to a batch layer that periodically recomputes complete, accurate results over all history.
  2. 2The same events also go to a speed layer (streaming) that covers the hours since the last batch run with fast, approximate results.
  3. 3A serving layer merges both views for queries. The drawback is that the business logic must be written and maintained twice, in batch and in streaming code, and the two often drift apart.
  4. 4Kappa removes the batch layer: all data flows through a durable, replayable log such as Kafka with long retention.
  5. 5A single stream-processing codebase (Flink or Spark Structured Streaming) produces the serving tables.
  6. 6To fix a bug or change logic, you replay the log from the start through the new code. One codebase, one truth. Modern lakehouses with streaming tables follow this idea.

What are row groups and why do they matter?
A Parquet file is split into row groups (e.g. 128 MB); each stores column chunks with min/max stats. Engines skip whole row groups whose stats do not match the filter — "predicate pushdown". Sorting data on a common filter column makes this much more effective.
Why is CSV dangerous for data pipelines?
No types (everything is text), ambiguous dates, delimiters and quotes inside values, encoding issues, no schema, and no compression. Convert to Parquet as early as possible.

How does partitioning work in a data lake, and what is the small-files problem?

Architecture 8 min read Difficulty: Advanced 29 of 50
Definition

Partitioning stores a table as sub-folders based on the values of one or more columns (order_date=2026-10-08/). Queries filtering on that column read only the matching folders — partition pruning.

The small-files problem occurs when a table consists of thousands or millions of tiny files (KBs instead of ~128 MB–1 GB). Every file costs a metadata lookup, an open/close and task scheduling, so queries become slow and storage listing becomes expensive.

Partitioning Partition Pruning Small Files Compaction Over-partitioning Z-order
How It Works — Step by Step
Step 1 / 4
  1. 1The table is stored as one folder per order_date. Each folder holds that day's Parquet files.
  2. 2A query filters on the partition column: only orders from 7 October onward are needed.
  3. 3The engine compares the filter with the folder names before reading any data and skips the partitions that cannot match. This is partition pruning: 60% less data scanned, faster and cheaper.
  4. 4Pruning only works when the filter is on the partition column in a form the engine understands. Wrapping it in a function or filtering only on other columns forces a full scan.

Cross Questions
repartition vs coalesce before writing?
coalesce(n) reduces partitions without a full shuffle (cheap, but can create uneven files); repartition(n or col) does a full shuffle and gives evenly sized output. Use repartition by the partition column for balanced files per folder.
Partitioning vs bucketing?
Partitioning creates folders by column value; bucketing hashes a column into a fixed number of files within each partition, which helps joins and aggregations on that key (Hive/Spark bucketed tables).

What is orchestration? Explain DAGs, scheduling and dependencies (Airflow)

Architecture 8 min read Difficulty: Advanced 31 of 50
Definition

Orchestration is the automated coordination of pipeline tasks: when they run (schedules, sensors, events), in what order (dependencies), with what parameters, and what happens on failure (retries, alerts).

Workflows are modelled as a DAG — Directed Acyclic Graph of tasks. Apache Airflow is the most widely used orchestrator; others include Dagster, Prefect, Azure Data Factory, AWS Step Functions and Databricks Workflows.

Orchestration DAG Airflow Scheduler Sensor Retries Backfill
How It Works — Step by Step
Step 1 / 7
  1. 1A DAG (Directed Acyclic Graph) declares tasks and their dependencies. Arrows mean "must finish before". There are no cycles, so there is always a valid order.
  2. 2Tasks with no upstream dependency start in parallel: two extracts and a sensor that waits until the vendor file lands.
  3. 3load_dim_customer succeeds, but stage_orders fails with a timeout. Its downstream tasks wait. They do not run on incomplete data.
  4. 4The orchestrator retries the failed task automatically (with a delay, as configured with retries and retry_delay). The retry succeeds. This is safe only because the task is idempotent.
  5. 5Once all upstream tasks have succeeded, load_fact_sales runs. Dimensions are always loaded before facts.
  6. 6Data-quality checks pass, so the publish step makes the new data visible to dashboards.
  7. 7If the checks had failed, publishing would be skipped and the team alerted. A quality gate stops bad data from reaching users.

What is a backfill and how do you reprocess historical data safely?

Architecture 6 min read Difficulty: Advanced 32 of 50
Definition

A backfill runs a pipeline for past periods — to load history for a new table, to fix data after a bug, or after a source re-sends corrected data. Doing this safely depends on the pipeline being parameterised by time window and idempotent.

Backfill Reprocessing Idempotency Parameterised Window Airflow
How to Backfill Safely
  • Parameterise everything by the logical date / window — never use NOW() or "latest" inside the job.
  • Write idempotently: overwrite the date partition or MERGE, so a backfill replaces old results instead of duplicating them.
  • Respect dependencies: backfill upstream tables first, then downstream ones (or the DAG in order).
  • Limit concurrency so the backfill does not overload the source or the cluster (max_active_runs).
  • Use the right reference data: SCD2 lookups must use versions valid on the historical date.
  • Validate and communicate: compare totals before/after, and warn consumers that numbers will change.
Terminal
# Airflow CLI: re-run the DAG for the first week of October
airflow dags backfill daily_sales \
    --start-date 2026-10-01 --end-date 2026-10-07 \
    --reset-dagruns
Cross Questions
What makes a pipeline impossible to backfill?
Reading "current" state that has since changed (e.g. a dimension without history), using now() for windows, appending instead of overwriting, or sources that no longer keep old data. Keeping a raw/bronze layer solves the last one.

Definition

How It Works — Step by Step
Step 1 / 6
  1. 1A batch of 10,000 rows arrives from a vendor file.
  2. 2Every row passes through validation rules: the expected columns and types, mandatory fields, value ranges, formats (email, PAN, pincode) and references (does the customer exist?).

How do you make pipelines restartable? Explain checkpoints

Data Quality & Reliability 6 min read Difficulty: Advanced 39 of 50
Definition

A restartable pipeline can resume after a failure without manual cleanup and without reprocessing everything from scratch. It records progress (checkpoints) and makes each step idempotent so a step can safely run again.

Restartability Checkpoint Idempotency Control Table Streaming Checkpoint
Detailed Explanation
  • Split the pipeline into small, independent steps with clear inputs/outputs (stage → transform → publish), so a failure re-runs one step, not the whole chain.
  • Keep a control table of processed units (files, partitions, watermarks) with status; skip units already marked SUCCESS.
  • Write outputs atomically (temp location + rename/commit, table formats, transactions) so a crash never leaves half-written results.
  • Streaming engines persist offsets and state in a checkpoint location (Spark checkpointLocation, Flink savepoints); on restart they continue exactly where they stopped.
Example: Resume From Where It Failed
Python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE file_log (file_name TEXT PRIMARY KEY, status TEXT)")
files = ["sales_01.csv", "sales_02.csv", "sales_03.csv", "sales_04.csv"]

def process(name, fail_on=None):
    if name == fail_on:
        raise RuntimeError(f"crash while processing {name}")
    return f"loaded {name}"

def run(fail_on=None):
    done = {r[0] for r in conn.execute("SELECT file_name FROM file_log WHERE status='SUCCESS'")}
    for f in files:
        if f in done:
            print("  skip  ", f)
            continue
        print(" ", process(f, fail_on))
        with conn:
            conn.execute("INSERT OR REPLACE INTO file_log VALUES (?, 'SUCCESS')", (f,))

print("Run 1:")
try:
    run(fail_on="sales_03.csv")
except RuntimeError as e:
    print("  FAILED:", e)
print("Run 2 (restart):")
run()

It holds the offsets and state of that exact query. Sharing it between queries corrupts both; deleting it makes the query start again from the configured starting offsets — causing duplicates or data loss.

What is data skew and how do you handle it?

Performance & Operations 7 min read Difficulty: Expert 41 of 50
Definition

Data skew is an uneven distribution of data across partitions/tasks, usually because a few key values are far more frequent than others (a "hot key" such as a default customer id, NULL, or a very large city). The job is only as fast as its slowest task.

Data Skew Hot Key Salting Broadcast Join AQE Shuffle
How It Works — Step by Step
Step 1 / 3
  1. 1After a shuffle (a groupBy or join on city), all rows with the same key go to the same task. Most cities have similar volumes.
  2. 2One key, Mumbai, has 10× more rows than the others. Its task runs far longer while every other executor sits idle. This is data skew: the stage is as slow as its slowest task.
  3. 3Fixes: salt the hot key (add a random suffix so its rows spread across many tasks, then combine the partial results), broadcast the small side of a join, or let Spark 3's Adaptive Query Execution split skewed partitions automatically.
Example
PySpark
from pyspark.sql import functions as F

# 1) Let Spark 3 split skewed partitions automatically
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")

# 2) Broadcast the small side so the big side is never shuffled
result = orders.join(F.broadcast(dim_city), "city")

# 3) Salting a hot key for an aggregation
SALT = 10
partial = (orders.withColumn("salt", (F.rand() * SALT).cast("int"))
                 .groupBy("city", "salt").agg(F.sum("amount").alias("amt")))
final = partial.groupBy("city").agg(F.sum("amt").alias("revenue"))

# 4) Handle NULL keys separately (they all hash to one partition)
nulls, non_nulls = orders.filter("customer_id IS NULL"), orders.filter("customer_id IS NOT NULL")

What is predicate pushdown and projection pushdown?

Performance & Operations 5 min read Difficulty: Expert 42 of 50
Definition

Predicate pushdown moves filters (WHERE conditions) as close to the data source as possible, so less data is read. Projection pushdown (column pruning) reads only the columns that the query needs.

Predicate Pushdown Projection Pushdown Column Pruning JDBC Parquet Statistics
How It Works — Step by Step
Step 1 / 3
  1. 1Without pushdown, the engine reads every row and every column from the source, moves it all across the network, and only then filters. That is slow, memory-hungry and expensive.
  2. 2Predicate pushdown sends the filter (WHERE city = 'Pune') to the source: the database uses its index, and Parquet skips row groups whose min/max statistics cannot match.
  3. 3Projection pushdown reads only the columns the query actually uses. Together they move a tiny fraction of the data.

How It Works — Step by Step
Step 1 / 7
  1. 1The source is the production MySQL database. The goal is to get its changes into the warehouse every few minutes without slowing the application down.
  2. 2Debezium reads the binlog (log-based CDC) after an initial snapshot and publishes one Kafka topic per table. The production tables are never queried in a loop.
  3. 3A streaming job (or Kafka Connect sink) appends raw change events, unchanged, into Bronze with metadata. This is the replayable history.
  4. 4A job MERGEs the latest change per primary key into Silver: ordered by binlog position, deletes applied, types fixed. Silver mirrors the source tables.
  5. 5Gold builds the business model: SCD2 dimensions first, then facts with surrogate-key lookups, then aggregates.
  6. 6Data-quality tests (row counts vs source, not-null, uniqueness, freshness) gate publishing, and failures alert the on-call engineer.
  7. 7Everything is idempotent and restartable: streaming checkpoints, MERGE-based loads, and an orchestrator for the batch parts and backfills.
Proposed Design
  • Ingestion: Debezium MySQL connector (initial snapshot, then binlog streaming) → Kafka topics per table. Alternative for simpler needs: watermark-based extraction every 15 min from a read replica.
  • Bronze: raw change events appended to Delta/Iceberg tables, partitioned by ingestion date, with binlog position.
  • Silver: Spark Structured Streaming (trigger every 5 min) or scheduled job that deduplicates by primary key, orders by binlog position and MERGEs into mirror tables, applying deletes.
  • Gold: dbt or Spark builds dim_customer (SCD2), dim_product, fact_order_items, and daily aggregates; facts partitioned by order date.
  • Orchestration: Airflow for batch steps, backfills and dependencies; streaming jobs monitored separately.
  • Quality: row-count reconciliation vs source per day, unique/not-null tests, freshness alerts (> 30 min lag pages on-call).
  • Reliability: idempotent MERGEs, streaming checkpoints, schema registry for evolution, dead-letter topic for malformed events.
  • Security: CDC user with replication privileges only; PII hashed in silver; secrets in a vault.

Scenario: 40 vendors upload a stock file each night to s3://incoming/<vendor>/. Files sometimes arrive late, twice, partially uploaded, with an extra column, or with bad rows. The business needs a consolidated stock table by 8 AM.

Example: File Control Table
SQL (MySQL)
CREATE TABLE file_control (
  file_name VARCHAR(100), vendor VARCHAR(20), file_date DATE, checksum CHAR(32),
  status VARCHAR(12), rows_ok INT, rows_bad INT, processed_at DATETIME,
  PRIMARY KEY (file_name, checksum)
);
INSERT INTO file_control VALUES
 ('stock_V01_20261008.csv', 'V01', '2026-10-08', 'a1b2c3', 'SUCCESS',  1200, 0,  '2026-10-09 01:10'),
 ('stock_V02_20261008.csv', 'V02', '2026-10-08', 'd4e5f6', 'REJECTED', 0,  640, '2026-10-09 01:12'),
 ('stock_V02_20261008.csv', 'V02', '2026-10-08', '9f8e7d', 'SUCCESS',  640, 0,  '2026-10-09 05:40');

-- Has this exact file (same content) been processed already?
SELECT COUNT(*) AS already_done FROM file_control
WHERE file_name = 'stock_V01_20261008.csv' AND checksum = 'a1b2c3' AND status = 'SUCCESS';

-- Morning status per vendor (latest attempt wins)
SELECT vendor, file_date, status, rows_ok, rows_bad
FROM (SELECT f.*, ROW_NUMBER() OVER (PARTITION BY vendor, file_date ORDER BY processed_at DESC) rn
      FROM file_control f) t
WHERE rn = 1;

Cross Questions
Why use the checksum and not just the file name?
Vendors re-send corrected files with the same name. Same name + different checksum = new content to process; same name + same checksum = duplicate to skip.

Scenario: a critical pipeline failed at 3 AM. What do you do?

What the Interviewer Is Testing

This question tests operational maturity: calm triage, communication, a correct fix, and preventing recurrence. Structure the answer as a runbook.

Runbook
PhaseActions
1. Assess impactWhich pipeline, which tables, which dashboards/consumers, which SLA? Is data wrong, or only late?
2. CommunicateAcknowledge the alert; post a short status in the incident channel; inform stakeholders if the SLA will be missed — before they discover it
3. DiagnoseRead the task log and error; check what changed (deploy, source schema, credentials expired, disk/quota, upstream late, volume spike)
4. MitigateFix forward or roll back the deploy; re-run the failed task (safe because idempotent); if data is bad, hold publishing so dashboards keep yesterday's correct data
5. VerifyReconcile counts/totals, run quality checks, confirm dashboards
6. Close & learnBlameless post-mortem: root cause, timeline, action items (new test, alert, retry policy, runbook update)
Interview Tip
What earns the marks: Mention idempotent re-runs, not publishing bad data, proactive stakeholder communication and a post-mortem with a preventive action. These four points separate strong answers from "I would check the logs and re-run it".
Cross Questions
What are common root causes of pipeline failures?
Upstream schema changes, late or missing source data, expired credentials/certificates, out-of-memory from volume growth, skew, dependency/library upgrades, quota limits, and bad deploys.

How do you handle duplicate events? Explain at-most-once, at-least-once and exactly-once

Scenario & Design 8 min read Difficulty: Expert 49 of 50
Definition
GuaranteeMeaningRisk
At-most-onceEach message processed 0 or 1 timesData loss
At-least-onceEach message processed 1 or more timesDuplicates
Exactly-onceEach message affects the result exactly onceNeeds coordination: idempotent or transactional sinks
At-least-once Exactly-once Idempotent Consumer Kafka Offsets Event ID Deduplication
How It Works — Step by Step
Step 1 / 3
  1. 1At-most-once: the consumer acknowledges (commits its offset) before processing. If it crashes mid-way, the message is never processed again, so data can be lost.
  2. 2At-least-once (the usual default): the consumer commits after processing. If it crashes after writing but before committing, the message is delivered again, so data can be duplicated.
  3. 3True end-to-end exactly-once is achieved in practice by combining at-least-once delivery with an idempotent sink (deduplicate on a unique event id, MERGE on key), or with transactional writes that commit data and offsets together.
Example
Idempotent consumer: the unique event_id absorbs duplicates
CREATE TABLE payments (event_id VARCHAR(40) PRIMARY KEY, order_id INT, amount INT, received_at DATETIME);

-- The same event delivered three times (retries / consumer restart)
INSERT IGNORE INTO payments VALUES ('evt-7f1c', 5001, 1499, NOW());
INSERT IGNORE INTO payments VALUES ('evt-7f1c', 5001, 1499, NOW());
INSERT IGNORE INTO payments VALUES ('evt-7f1c', 5001, 1499, NOW());
INSERT IGNORE INTO payments VALUES ('evt-90aa', 5002,  299, NOW());

SELECT order_id, COUNT(*) AS rows_stored, SUM(amount) AS total FROM payments GROUP BY order_id;
Output
+----------+-------------+-------+
| order_id | rows_stored | total |
+----------+-------------+-------+
|     5001 |           1 |  1499 |
|     5002 |           1 |   299 |

Cross Questions
Does Kafka support exactly-once?
Within Kafka (consume → process → produce to Kafka) yes: idempotent producers plus transactions (enable.idempotence, transactional.id, consumers with isolation.level=read_committed). Writing to an external database needs an idempotent or transactional sink.
What if events have no unique id?
Create a deterministic one — e.g. a hash of source system + key + event timestamp — or use the source position (Kafka topic-partition-offset, binlog file+position) as the id.
