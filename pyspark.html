What is Apache Spark? Why is it faster than Hadoop MapReduce?

Spark Fundamentals & Architecture 8 min read Difficulty: Beginner 1 of 44
Definition

Apache Spark is a unified, distributed computing engine for large-scale data processing. It provides APIs in Python (PySpark), Scala, Java and R, and supports batch processing, streaming, SQL, ML and graph analytics — all on one engine.

Spark was created at UC Berkeley in 2009 and became an Apache top-level project in 2014. The current release is Spark 4.x (runs on Java 17+).

Why Faster?: Spark processes data in memory across stages, while MapReduce writes intermediate results to disk after every stage. This removes repeated I/O and makes Spark 10–100× faster for iterative workloads (ML, multi-step ETL).
Distributed Computing In-Memory PySpark Unified Engine Batch + Streaming
How It Works — Step by Step
Step 1 / 6
  1. 1MapReduce reads from HDFS, runs mappers, writes intermediate results to disk.
  2. 2Reducers re-read from disk, process, and write again if another step follows.
  3. 3Every step writes and reads disk: multiple rounds of disk I/O. Iterative algorithms are very slow.
  4. 4Spark reads data once and keeps intermediate results in memory as RDDs.
  5. 5Subsequent stages read from memory, not disk. This makes iterative ML algorithms and interactive queries 10–100× faster.
  6. 6Spark only spills to disk when executor memory is full, and it avoids unnecessary serialization through the Tungsten engine.
MapReduce vs Spark
AspectHadoop MapReduceApache Spark
Processing modelDisk-based: HDFS → Map → Disk → Reduce → HDFSIn-memory: data stays in RAM between stages
SpeedSlow for iterative jobs (disk I/O each step)10–100× faster for iterative/interactive workloads
Ease of useVerbose Java codeConcise: Python, Scala, SQL, DataFrame API
Fault toleranceReplication (3 copies on HDFS)RDD lineage — recomputes lost partitions
Real-timeBatch onlyStructured Streaming (micro-batch + continuous)
LibrariesSeparate tools (Hive, Mahout, …)Built-in: Spark SQL, MLlib, GraphX, Streaming
Cross Questions
Does Spark replace Hadoop?
Not entirely. Spark replaces MapReduce as the processing engine but can still use HDFS for storage and YARN for cluster management.
Is Spark always faster?
For single-pass ETL on huge data, MapReduce can match Spark. Spark shines when a job has multiple stages or needs to revisit data (joins, ML iterations, interactive queries).

Explain the Spark cluster architecture

Spark Fundamentals & Architecture 9 min read Difficulty: Beginner 2 of 44
Definition

A Spark application runs as a driver program that creates a SparkSession, connects to a cluster manager to request resources, and then distributes work to executors — JVM processes on worker nodes that run tasks and cache data.

Driver SparkSession Cluster Manager Executor Worker Node Task
How It Works — Step by Step
Step 1 / 6
  1. 1The driver program is where your PySpark code runs. It creates a SparkSession (which wraps SparkContext) and plans the work.
  2. 2The driver asks the cluster manager (YARN, Kubernetes, Standalone, or Mesos) for resources (CPU cores + memory).
  3. 3The cluster manager launches executors — JVM processes on worker nodes, each with a fixed number of cores and memory.
  4. 4The driver breaks the job into tasks (one task per partition) and sends them to executor cores. Tasks run in parallel.
  5. 5Executors have cache memory for persisted RDDs/DataFrames, avoiding re-reads from disk.
  6. 6Results flow back to the driver: collect() brings all data; show() or take(n) bring only what is needed.
Components
ComponentRoleKey Details
DriverRuns your PySpark code, plans jobs, distributes tasksContains SparkSession / SparkContext; single point of coordination
Cluster ManagerAllocates containers (executor JVMs) on the clusterYARN, Kubernetes, Standalone, or Mesos; Spark itself is agnostic
ExecutorRuns tasks, stores cached dataOne per worker node (default); configurable cores + memory
TaskSmallest unit of work — processes one partitionOne task per partition per stage; runs on a single executor core
Worker NodePhysical/virtual machine hosting executorsManaged by the cluster manager, not by Spark directly

What is the difference between SparkSession and SparkContext?
SparkContext is the low-level entry point (RDD API). SparkSession wraps it and adds DataFrame/SQL support. Since Spark 2.0, always start with SparkSession.

What is PySpark? How does it communicate with the JVM?

Spark Fundamentals & Architecture 7 min read Difficulty: Beginner 6 of 44
Definition

PySpark is the Python API for Apache Spark. It lets you write Spark applications in Python while the actual distributed computation runs on JVM-based executors.

PySpark uses Py4J to bridge Python and the JVM: the Python driver calls Java/Scala objects through a gateway, and DataFrame operations are translated into JVM calls — no data serialization needed for most operations.

PySpark Py4J JVM Python API DataFrame API
How It Works — Step by Step
Step 1 / 6
  1. 1With RDDs, Python lambda functions cause data to be serialized between the Python process and the JVM for every row — costly.
  2. 2Spark cannot optimize opaque Python functions: it just runs your code as-is, partition by partition.
  3. 3With DataFrames, you express operations using column expressions, not lambdas — Spark understands what you want, not just how.
  4. 4The Catalyst optimizer rewrites the logical plan: pushes predicates down, reorders joins, folds constants, eliminates unnecessary columns.
  5. 5The Tungsten engine generates optimized Java bytecode (whole-stage codegen) and manages memory off-heap to avoid garbage collection.
  6. 6DataFrame operations run entirely in the JVM — no Python serialization cost. This is why DataFrames are the recommended API.
PySpark Performance Layers
LayerWhat HappensPerformance
DataFrame / SQL operationsTranslated to JVM calls via Py4J — runs as native SparkSame speed as Scala
Python UDFsData serialized to Python, processed, serialized backSlow: serialization overhead
Pandas UDFs (Arrow)Batched via Apache Arrow (columnar, zero-copy)Much faster than row-at-a-time UDFs
RDD with Python lambdasEach row pickled to Python worker processSlowest: pickle + IPC per row
Interview Tip

"For DataFrame operations, PySpark is as fast as Scala Spark because the optimizer (Catalyst) and execution engine (Tungsten) run on the JVM. Performance drops only when data crosses the Python–JVM boundary — in UDFs or RDD lambdas. Use built-in functions and Pandas UDFs to stay fast."

Cross Questions
What is Py4J?
A library that lets Python programs call Java objects. PySpark's driver uses a Py4J gateway to communicate with the Spark JVM. No data is serialized for DataFrame ops — only method calls cross the bridge.
Why learn PySpark if Scala is faster for RDDs?
For DataFrames (95% of work), speed is identical. Python has better data-science libraries (pandas, scikit-learn, TensorFlow) and is the dominant language in data engineering.

What is an RDD? How is it different from a DataFrame?

RDDs — Resilient Distributed Datasets 8 min read Difficulty: Beginner 7 of 44
Definition

An RDD (Resilient Distributed Dataset) is Spark's fundamental, low-level data abstraction — an immutable, partitioned collection of records that can be processed in parallel. Each RDD remembers the chain of transformations (its lineage) used to build it, so lost partitions can be recomputed without replication.

DataFrames sit on top of RDDs and add schema, columnar storage, and the Catalyst optimizer. For almost all modern work, use DataFrames — RDDs are for cases that need fine-grained control.

RDD Immutable Partitioned Lineage Fault Tolerant Low Level
How It Works — Step by Step
Step 1 / 7
  1. 1textFile() creates the first RDD — a reference to data on disk. No data is read yet.
  2. 2flatMap() is a transformation: it describes what to do, but builds only a plan (new RDD linked to the previous).
  3. 3map() adds another transformation to the lineage: (word) → (word, 1).
  4. 4reduceByKey() is a wide transformation — it requires a shuffle (data exchange between partitions). Still nothing runs.
  5. 5Spark has built a DAG: each RDD knows its parent and the function to apply. The shuffle marks a stage boundary.
  6. 6Until an action is called, the DAG is just a plan — this is lazy evaluation.
  7. 7Calling collect() (an action) triggers the scheduler. It splits the DAG into stages, each stage into tasks (one per partition), and ships them to executors.
RDD vs DataFrame
AspectRDDDataFrame
SchemaNo schema (opaque objects)Named columns with types
OptimizationNone — you write the planCatalyst + Tungsten optimize automatically
SerializationJava/Python object serializationTungsten binary format (off-heap, compact)
PySpark speedSlow — data pickled to/from PythonFast — runs on JVM, same as Scala
API styleFunctional: map, filter, reduceDeclarative: select, filter, groupBy, SQL
Use whenUnstructured data, custom partitioning, low-level controlStructured / semi-structured data (99% of cases)

Cross Questions
Are RDDs obsolete?
Not obsolete, but rarely used directly. DataFrames compile down to RDD operations internally. You might use RDDs for custom accumulator logic or when processing unstructured binary data.
How does lineage provide fault tolerance?
Each RDD records which parent RDDs and transformations created it. If a partition is lost (node crash), Spark replays the lineage on another node to recompute just that partition.

What is lazy evaluation in Spark? Why does it matter?

RDDs — Resilient Distributed Datasets 7 min read Difficulty: Beginner 9 of 44
Definition

Lazy evaluation means Spark does not execute transformations immediately. Instead it builds a logical plan (a DAG of transformations). Execution is triggered only when an action is called — like show(), collect(), count(), or write.

This lets the Catalyst optimizer see the entire plan before execution and apply optimizations: predicate pushdown, column pruning, join reordering, and whole-stage code generation.

Lazy Evaluation Transformation Action Catalyst DAG Optimization
How It Works — Step by Step
Step 1 / 5
  1. 1spark.read.csv(…) creates a plan to load data. No file is opened yet.
  2. 2filter() adds a predicate to the plan. Still no data moves.
  3. 3groupBy() adds an aggregation. The plan keeps growing, but nothing executes.
  4. 4Calling .show() — an action — triggers execution. Spark submits the plan to the scheduler.
  5. 5Benefit of laziness: Spark sees the entire plan at once and optimizes it (push the filter to the data source, prune columns, generate efficient bytecode).
Lazy Evaluation in Action
PySpark
from pyspark.sql import SparkSession

What are narrow vs wide transformations?

RDDs — Resilient Distributed Datasets 8 min read Difficulty: Beginner 10 of 44
Definition

Narrow transformations process each input partition independently — each output partition depends on at most one input partition. No data moves between executors.

Wide transformations require data from multiple input partitions to produce each output partition. This causes a shuffle — data is redistributed across the network.

Key Insight: Shuffles are the most expensive operation in Spark. Every wide transformation creates a stage boundary and requires writing shuffle files to disk.
Narrow Wide Shuffle Stage Boundary Pipeline
How It Works — Step by Step
Step 1 / 4
  1. 1Start with 3 partitions of data distributed across executors.
  2. 2Narrow transformations (map, filter, flatMap, mapPartitions) work partition-by-partition: each input partition produces exactly one output partition. No data moves between nodes.
  3. 3Now consider data with keys (A, B, C) spread across partitions.
  4. 4Wide transformations (groupByKey, reduceByKey, join, repartition) must move data so all records with the same key land in the same partition. This is a shuffle — expensive network and disk I/O.
Narrow vs Wide Transformations
TypeExamplesData MovementStage
Narrowmap, filter, flatMap, select, withColumn, unionNone — partition stays localSame stage (pipelined)
WidegroupByKey, reduceByKey, join, repartition, distinct, orderByShuffle across networkNew stage boundary
Narrow vs Wide Example
PySpark
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.master("local[*]").appName("narrow_wide") \
    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1") \
    .config("spark.sql.shuffle.partitions","4").getOrCreate()

marks = spark.createDataFrame([
    ("Anuj","DBDA",85), ("Vineeta","PGCP",92), ("Aarshvi","DBDA",78),
    ("Anuj","PGCP",88), ("Vineeta","DBDA",95)

narrow = marks.filter(col("marks") > 80).select("name", "marks")

wide = marks.groupBy("course").avg("marks")

print("=== Narrow (filter + select) — no shuffle ===")
narrow.show()

wide.show()
spark.stop()

Cross Questions
Is join always wide?
Usually yes (shuffle both sides). But a broadcast join is narrow on the large side — the small table is sent to every executor, so no shuffle of the big table.
Why does Spark pipeline narrow transformations?
Since each partition is independent, Spark chains multiple narrow transformations into a single task. Data flows through map→filter→select without materializing intermediate results.

What are common RDD transformations and actions?

Definition

Transformations create a new RDD from an existing one (lazy). Actions trigger computation and return a result to the driver or write to storage.

RDD Transformations & Actions
PySpark
from pyspark.sql import SparkSession
spark = SparkSession.builder.master("local[*]").appName("rdd_ops") \
    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1").getOrCreate()
sc = spark.sparkContext

words = sc.parallelize(["Anuj loves Spark", "Vineeta loves PySpark", "Aarshvi loves Python"])

# --- Transformations (lazy) ---
# flatMap: one row → many rows
tokens = words.flatMap(lambda line: line.split())
print(f"flatMap    : {tokens.collect()}")

# map: one row → one row
upper = tokens.map(lambda w: w.upper())
print(f"map        : {upper.collect()}")

# filter: keep matching rows
long_words = tokens.filter(lambda w: len(w) > 4)
print(f"filter     : {long_words.collect()}")

# Word count: classic MapReduce in Spark
wc = tokens.map(lambda w: (w.lower(), 1)).reduceByKey(lambda a, b: a + b)
print(f"word count : {sorted(wc.collect())}")

# --- Actions ---
print(f"count      : {tokens.count()}")
print(f"first      : {tokens.first()}")
print(f"take(3)    : {tokens.take(3)}")
spark.stop()

How does Spark execute a job? Explain Jobs, Stages and Tasks

Execution Model — Jobs, Stages & Caching 9 min read Difficulty: Intermediate 23 of 44
Definition

When an action is called, Spark creates a Job. The job is split into Stages at shuffle boundaries (wide transformations). Each stage is split into Tasks — one per partition — that run in parallel on executors.

Narrow transformations within a stage are pipelined (fused into a single task), so data flows through map→filter→select without materializing intermediate results.

Job Stage Task DAG Scheduler Task Scheduler Pipeline
How It Works — Step by Step
Step 1 / 4
  1. 1Each action (collect, show, write, count) triggers one job.
  2. 2Spark splits a job into stages at shuffle boundaries (wide transformations like groupBy, join, repartition).
  3. 3Each stage is split into tasks — one task per partition. Tasks within a stage run the same code on different data slices.
  4. 4Tasks are distributed to executor cores and run in parallel. More partitions = more parallelism (up to the number of cores).

JobEach action (show, collect, write, count)1 action = 1 job
StageShuffle boundaries (groupBy, join, repartition)1 job = 1+ stages separated by shuffles
TaskOne partition in a stage1 stage = N tasks (N = number of partitions)

What is caching / persistence? When should you use it?

Definition

df.cache() stores a DataFrame in executor memory so it is not recomputed when used multiple times. df.persist(level) lets you choose the storage level: memory only, memory + disk, disk only, serialized, or replicated.

How It Works — Step by Step
Step 1 / 5
  1. 1A DataFrame is built through transformations (lazy — nothing runs yet).
  2. 2Without cache: every action recomputes the entire lineage from scratch. If data is read from HDFS, it reads the file again each time.
  3. 3.cache() marks the DataFrame for persistence. Nothing happens yet (still lazy).
  4. 4The first action computes the DataFrame and stores the result in executor memory (MEMORY_ONLY by default).
  5. 5The second action reads directly from cache — no re-reading from disk, no re-computing transformations.

What is a shuffle in Spark? Why is it expensive?

Execution Model — Jobs, Stages & Caching 8 min read Difficulty: Intermediate 25 of 44
Definition

A shuffle is the redistribution of data across partitions — required when a transformation needs data from multiple input partitions (groupBy, join, repartition, distinct, orderBy).

Shuffles are expensive because they involve: serialization of data, writing to local disk (shuffle files), network transfer between executors, and deserialization on the receiving side.

Key Rule: Shuffles create stage boundaries. Minimizing shuffles is the #1 Spark optimization strategy.
Shuffle Exchange Network I/O Stage Boundary Shuffle Write Shuffle Read
How It Works — Step by Step
Step 1 / 4
  1. 1Map side: tasks process partitions and produce key-value pairs.
  2. 2Shuffle write: each map task sorts output by key, partitions it by reducer, and writes shuffle files to local disk.
  3. 3Shuffle transfer: reduce tasks pull their partition data over the network from all map tasks. This is the expensive part.
  4. 4Reduce side: each reduce task gets all records for its key range, merges and aggregates them. The new RDD/DataFrame has one partition per reducer.

What Causes ShuffleWhyHow to Avoid
groupBy / reduceByKeySame keys must end up on same partitionPre-partition data; combine before shuffle (reduceByKey > groupByKey)
join (both sides)Matching keys must be co-locatedBroadcast small side; pre-partition on join key
repartition(n)Full redistribution to n partitionsUse coalesce(n) to reduce partitions without shuffle
distinct / orderByGlobal operationapproxCountDistinct(); sort only when needed

What are partitions in Spark? How do they affect parallelism?

Definition

A partition is a chunk of data that one task processes. Partitions are the unit of parallelism — more partitions means more tasks running concurrently.

Default number of partitions: for RDD parallelize, it is sc.defaultParallelism (number of cores). For file reads, it is the number of HDFS blocks or file splits. After shuffles, it is spark.sql.shuffle.partitions (default 200).

What are broadcast variables? When do you use them?

Broadcast Variables, Accumulators & UDFs 7 min read Difficulty: Advanced 30 of 44
Definition

A broadcast variable is a read-only variable sent to every executor once, cached in memory, and shared across all tasks on that executor.

Without broadcast, Spark ships the variable with every task (serialized per task closure). For large lookup tables, this wastes network bandwidth and memory.

broadcast Read-Only Lookup Table Driver → Executors Closure
How It Works — Step by Step
Step 1 / 4
  1. 1A regular shuffle join re-partitions both tables by the join key. Even the 100M-row table gets shuffled — slow!
  2. 2With a broadcast join, the driver collects the small table (<10 MB by default).
  3. 3The small table is broadcast to every executor — each gets a full copy.
  4. 4Each executor joins its local partition of the big table with the local copy. No shuffle of the big table — the network moves only the small table once.
Broadcast Variables
PySpark

    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1").getOrCreate()

# Lookup table: course → full name

result2 = rdd.map(lambda x: (x[0], bc_courses.value.get(x[1], "Unknown"))).collect()
print(f"With broadcast   : {result2}")

# Destroy when done

# Numeric accumulator

total_marks = sc.accumulator(0)

    if marks < 0:
        error_count.add(1)      # count bad records
    else:
        total_marks.add(marks)  # sum valid marks
    return (name, max(marks, 0))

print(f"Error count  : {error_count.value}")
print(f"Total marks  : {total_marks.value}")

What are UDFs? Why should you avoid them in PySpark?

Broadcast Variables, Accumulators & UDFs 8 min read Difficulty: Advanced 32 of 44
Definition

A UDF (User Defined Function) is a custom function registered for use in Spark SQL / DataFrame operations. In PySpark, UDFs run in a Python worker process — data is serialized from the JVM, processed in Python, and serialized back.

This Python ↔ JVM serialization is expensive. Prefer built-in functions, which run entirely on the JVM.

UDF Pandas UDF Built-in Functions Serialization Arrow Performance
How It Works — Step by Step
Step 1 / 3
  1. 1Python UDFs serialize each row from the JVM to a Python worker, process one at a time, and serialize back. Very slow, and the optimizer cannot see inside them.
  2. 2Pandas UDFs (vectorized) transfer data in Arrow columnar batches — much less serialization overhead, and pandas/numpy run fast on arrays.
  3. 3Built-in functions (pyspark.sql.functions) run entirely in the JVM with Tungsten codegen. No Python at all. Always prefer them.
UDF vs Pandas UDF vs Built-in Functions

Definition

A broadcast join (or map-side join) sends the small table to every executor, so each task can join locally without shuffling the large table.

Spark auto-broadcasts tables smaller than spark.sql.autoBroadcastJoinThreshold (default 10 MB). Use broadcast() to force it for larger tables.

Definition

Catalyst is Spark SQL's query optimizer. It takes your logical plan (DataFrame operations or SQL) and transforms it through four phases to produce an efficient physical plan.

Catalyst is rule-based and cost-based: it applies rewrite rules (predicate pushdown, column pruning, constant folding) and then uses statistics to choose the best physical strategy (join type, scan method).

Catalyst Logical Plan Physical Plan Predicate Pushdown Column Pruning CBO
How It Works — Step by Step
Step 1 / 6
  1. 1Your DataFrame/SQL code becomes an unresolved logical plan — column names only, no types yet.
  2. 2The analyzer resolves column names and types against the catalog (schema registry, Hive metastore).
  3. 3The optimizer rewrites the plan: pushes filters closer to the data source, prunes unused columns, folds constants, simplifies expressions.
  4. 4Catalyst generates multiple physical plans (different join strategies: sort-merge, broadcast hash, shuffle hash).
  5. 5The cost model picks the cheapest plan using table and column statistics (row count, distinct values, histogram).
  6. 6Whole-stage code generation (Tungsten) fuses operators into a single optimized function — like hand-written Java code, avoiding virtual calls.

What is Adaptive Query Execution (AQE)?

Optimization & Performance Tuning 8 min read Difficulty: Expert 38 of 44
Definition

Adaptive Query Execution (AQE) re-optimizes the query plan at runtime based on actual data statistics collected during shuffle stages. Enabled by default since Spark 3.2.

Three key features: coalescing shuffle partitions (merges small partitions), switching join strategy (converts sort-merge to broadcast if one side is small), and handling skewed joins (splits large partitions).

AQE Runtime Optimization Coalesce Partitions Skew Join Dynamic Planning
How It Works — Step by Step
Step 1 / 4
  1. 1Catalyst creates the initial plan based on statistics (which may be stale or missing): e.g. sort-merge join with 200 shuffle partitions.
  2. 2Spark executes the first stage and writes shuffle files to disk.
  3. 3AQE inspects the actual shuffle data sizes and makes runtime decisions: convert to broadcast join if one side turned out small, coalesce many tiny partitions, split skewed ones.
  4. 4The next stage uses the re-optimized plan. AQE repeats this after every stage boundary.

What is data skew? How do you fix it?

Optimization & Performance Tuning 9 min read Difficulty: Expert 39 of 44
Definition

Data skew occurs when some partitions have much more data than others. The slowest task (processing the largest partition) becomes the bottleneck — other executors sit idle.

Common cause: a few keys dominate (e.g., country="India" has 1 billion rows, "Bhutan" has 1000). Joins and groupBy on skewed keys are the usual victims.

Interview Gold: Data skew is the #1 cause of slow Spark jobs. Look for it when one task takes much longer than others in the Spark UI.
Data Skew Salting Broadcast Join AQE Hot Key Straggler Task
How It Works — Step by Step
Step 1 / 5
  1. 1After a shuffle (groupBy, join), one partition gets most of the data (a hot key like "null" or "Unknown"). Other partitions are small.
  2. 2Small partitions finish quickly, but the skewed partition takes 10-100× longer. The job is as slow as its slowest task.
  3. 3Salting: add a random suffix to the hot key to split it across partitions, then re-aggregate.
  4. 4Broadcast join: if one side is small, broadcast it to avoid the skew-prone shuffle entirely.
  5. 5AQE (Adaptive Query Execution): Spark 3+ can detect skew at runtime and split oversized partitions automatically. Enable with spark.sql.adaptive.enabled=true.
Detecting & Fixing Skew with Salting

    [("MLAI", i) for i in range(2)]         #  2 rows

# Aggregate on salted key, then combine

partial.show()
spark.stop()

Cross Questions
What is the difference between spark.executor.memory and spark.executor.memoryOverhead?
executor.memory is the JVM heap. memoryOverhead (default 10% of executor.memory, min 384 MB) is non-heap memory for Python processes, serialization buffers, and OS overhead. Total = heap + overhead.
Why not set executor cores to 16?
Too many cores per executor causes HDFS I/O contention (> 5 concurrent HDFS connections per JVM is slow) and GC pressure. 4–5 cores per executor is the sweet spot.

How do window functions work in PySpark?

Window Functions & Real-World Scenarios 9 min read Difficulty: Expert 41 of 44
Definition

Window functions compute a value for each row based on a window of rows related to the current row — without collapsing rows like groupBy.

Define a window with Window.partitionBy() (groups) and orderBy() (order), then apply ranking, aggregate, or analytic functions over it.

Window partitionBy orderBy row_number rank dense_rank lag lead over
How It Works — Step by Step
Step 1 / 4
  1. 1Source DataFrame with employees, departments and salaries.
  2. 2A window spec says: partition by department, order by salary within each partition.
  3. 3Spark groups rows into windows (partitions) and sorts each independently — like a GROUP BY that keeps every row.
  4. 4rank() assigns a rank within each window. Unlike groupBy, window functions do not collapse rows — every original row is preserved.
Window Functions: Ranking, Running Totals, lag/lead
PySpark

from pyspark.sql.functions import (col, row_number, rank, dense_rank,
    lag, lead, avg, sum as spark_sum, round as spark_round)

spark = SparkSession.builder.master("local[*]").appName("window") \
    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1") \
    .config("spark.sql.shuffle.partitions","4").getOrCreate()

scores = spark.createDataFrame([
    ("Anuj","DBDA",85), ("Vineeta","DBDA",92), ("Aarshvi","DBDA",78),
    ("Anuj","PGCP",88), ("Vineeta","PGCP",95), ("Aarshvi","PGCP",82),
], ["name","course","marks"])

# Define window: partition by course, order by marks DESC
w = Window.partitionBy("course").orderBy(col("marks").desc())

print("=== Ranking within each course ===")
scores.select(
    "name", "course", "marks",
    row_number().over(w).alias("row_num"),
    rank().over(w).alias("rank"),
    dense_rank().over(w).alias("dense_rank"),
).show()

# Running total and moving average
w2 = Window.partitionBy("course").orderBy("marks").rowsBetween(Window.unboundedPreceding, Window.currentRow)
print("=== Running total per course ===")
scores.select(
    "name", "course", "marks",
    spark_sum("marks").over(w2).alias("running_total"),
    spark_round(avg("marks").over(w2), 1).alias("running_avg"),
).show()

# lag / lead
w3 = Window.partitionBy("course").orderBy("marks")
print("=== lag and lead ===")
scores.select(
    "name", "course", "marks",
    lag("marks", 1).over(w3).alias("prev_marks"),
    lead("marks", 1).over(w3).alias("next_marks"),
).show()

Complete ETL Pipeline

from pyspark.sql import SparkSession, Window
from pyspark.sql.functions import (col, when, upper, trim, avg, count,
    row_number, current_timestamp, lit, round as spark_round)
from pyspark.sql.types import *

spark = SparkSession.builder.master("local[*]").appName("etl_pipeline") \
    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1") \
    .config("spark.sql.shuffle.partitions","4").getOrCreate()

# ═══ EXTRACT ═══
raw_data = spark.createDataFrame([
    ("anuj", "DBDA", 85, "Kharghar"), ("VINEETA", "pgcp", 92, "Panvel"),
    ("aarshvi", "DBDA", 78, None), ("anuj", "DBDA", 85, "Kharghar"),  # duplicate
    ("vineeta", "PGCP", None, "Panvel"), ("Anuj", "PGCP", 88, "Kharghar"),
], ["name", "course", "marks", "city"])

print(f"=== EXTRACT: {raw_data.count()} raw records ===")
raw_data.show()

# ═══ TRANSFORM ═══
# 1. Standardize: trim, uppercase names, uppercase courses
clean = (raw_data
    .withColumn("name", upper(trim(col("name"))))
    .withColumn("course", upper(trim(col("course"))))
)

# 2. Handle NULLs
clean = (clean
    .fillna({"city": "Unknown", "marks": 0})
    .filter(col("marks") > 0)    # remove rows with no real marks
)

# 3. Deduplicate (keep highest marks per name+course)
w = Window.partitionBy("name", "course").orderBy(col("marks").desc())
deduped = (clean
    .withColumn("rn", row_number().over(w))
    .filter(col("rn") == 1)
    .drop("rn")
)
print(f"=== TRANSFORM: {deduped.count()} clean records ===")
deduped.show()

# 4. Enrich: add grade and processing timestamp
enriched = (deduped
    .withColumn("grade", when(col("marks") >= 90, "A+")
                         .when(col("marks") >= 80, "A")
                         .when(col("marks") >= 70, "B")
                         .otherwise("C"))
    .withColumn("processed_at", current_timestamp())
)

# 5. Aggregate: summary per course
summary = enriched.groupBy("course").agg(
    count("*").alias("students"),
    spark_round(avg("marks"), 1).alias("avg_marks"),
)
print("=== Course Summary ===")
summary.show()

# ═══ LOAD ═══
enriched.write.mode("overwrite").partitionBy("course").parquet("/tmp/etl_output")
print("=== LOAD: Written to /tmp/etl_output (partitioned by course) ===")

# Verify
spark.read.parquet("/tmp/etl_output").show(truncate=False)
spark.stop()

Cross Questions
How do you make an ETL pipeline idempotent?
Use overwrite mode (full refresh) or dynamic partition overwrite. For incremental: write to date-partitioned paths and overwrite only the current partition. Delta Lake adds MERGE for upserts.
What is Delta Lake?
An open-source storage layer that adds ACID transactions, schema enforcement, time travel, and MERGE (upsert) on top of Parquet files. Developed by Databricks. Think of it as "Parquet with a transaction log."

What is Structured Streaming in Spark?

Window Functions & Real-World Scenarios 7 min read Difficulty: Expert 44 of 44
Definition

Structured Streaming treats a live data stream as an unbounded table that grows with new data. You write stream processing using the same DataFrame API as batch — Spark handles incrementalizing the computation.

Data arrives as micro-batches (default) or in continuous processing mode (experimental). Supports exactly-once semantics with checkpointing.

from pyspark.sql.functions import col, current_timestamp
from pyspark.sql.types import *
import os, time

spark = SparkSession.builder.master("local[*]").appName("streaming_demo") \
    .config("spark.ui.enabled","false").config("spark.driver.bindAddress","127.0.0.1").getOrCreate()

# Simulate: write some CSV files
os.makedirs("/tmp/stream_input", exist_ok=True)
for batch_id in range(3):
    with open(f"/tmp/stream_input/batch_{batch_id}.csv", "w") as f:
        f.write("name,marks\n")
        f.write(f"Anuj,{80 + batch_id * 5}\n")
        f.write(f"Vineeta,{90 + batch_id}\n")

schema = StructType([
    StructField("name", StringType()),
    StructField("marks", IntegerType()),
])

# readStream from a directory (simulated stream)
stream_df = (spark.readStream
    .schema(schema)
    .option("header", True)
    .csv("/tmp/stream_input"))

# Transform (same API as batch!)
enriched = stream_df.withColumn("received_at", current_timestamp())

# writeStream to console (for demo)
query = (enriched.writeStream
    .format("console")
    .outputMode("append")
    .trigger(once=True)    # process everything available, then stop
    .start())

query.awaitTermination()
print(f"\nStream status: {query.status}")
spark.stop()

What are the common stream sources?
Kafka (most common in production), file sources (CSV, JSON, Parquet directories), socket (testing only), Delta Lake, and Rate source (for testing throughput).
What is a watermark?
A threshold for handling late data. withWatermark("event_time", "10 minutes") tells Spark to wait up to 10 minutes for late events before finalizing aggregation windows.
