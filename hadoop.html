What is Hadoop and why was it created?

Hadoop Foundations 6 min read Difficulty: Beginner 1 of 48
Definition

Apache Hadoop is an open-source framework for storing and processing very large datasets across a cluster of ordinary (commodity) machines. It splits data into blocks, spreads them over many nodes, and sends the computation to the nodes where the data already sits.

It grew out of two Google papers — the Google File System (2003) and MapReduce (2004) — and was built by Doug Cutting and Mike Cafarella for the Nutch search engine, then developed at Yahoo! and released as an Apache project.

Hadoop Distributed Storage Distributed Processing Commodity Hardware Scale-out
Why Hadoop?

By the mid-2000s, web companies had more data than any single server could store or scan in reasonable time. Buying bigger machines (scale-up) became very expensive and still hit a ceiling. Hadoop's answer was scale-out: add more cheap machines and let software handle the rest.

ProblemHadoop's answer
Data too big for one diskHDFS splits files into blocks spread across many disks
Machines fail often at scaleEvery block is replicated (default 3 copies); failed tasks are re-run elsewhere
Moving terabytes over the network is slowData locality: ship the small program to the data, not the data to the program
Parallel programming is hardMapReduce: write map and reduce functions; the framework handles distribution, retries and sorting
Expensive specialised hardwareRuns on commodity servers; reliability comes from software

Cross Questions
Is Hadoop a database?
No. Hadoop is a storage + processing framework. HDFS is a file system, not a database: there are no tables, indexes or transactions. Tools such as Hive and HBase add SQL tables or key-value access on top of it.
What does "commodity hardware" mean? Is it cheap desktop PCs?
Standard rack servers from any vendor, not specialised high-end hardware. They still need decent RAM, disks and networking. "Commodity" means reliability is provided by Hadoop's software (replication, re-execution), not by expensive hardware.
Is Hadoop still relevant today?
Its ideas are everywhere: Spark, Hive, Iceberg and cloud object stores all reuse HDFS/YARN concepts. Many banks, telecoms and government organisations still run on-premise Hadoop clusters, and Spark on YARN with HDFS is common. New projects increasingly use cloud storage (S3/ADLS/GCS) instead of HDFS, but interviewers still test these fundamentals.

How It Works — Step by Step
Step 1 / 5
  1. 1A client (the hdfs dfs shell, a Spark job, a Hive query) wants to read or write a file.
  2. 2It first asks the NameNode. The NameNode holds only metadata in memory: the directory tree, which blocks make up each file and which DataNodes hold each block. It stores no file data.
  3. 3The actual data lives on the DataNodes as blocks (128 MB by default). Each block is stored on 3 different DataNodes, so losing one machine loses no data.
  4. 4Every DataNode sends a heartbeat to the NameNode every 3 seconds ("I am alive") and periodically a block report listing every block it holds. This is how the NameNode knows where blocks are.
  5. 5Data itself never passes through the NameNode. After getting block locations, the client reads and writes directly with the DataNodes. This keeps the master from becoming a bandwidth bottleneck.
How They Fit Together

Think of it as an operating system for a cluster: HDFS is the disk, YARN is the CPU and memory scheduler, and MapReduce (or Spark, Tez) is an application that runs on top.

  • Master-worker design everywhere: one master keeps the global picture, many workers do the heavy lifting.
  • Workers are usually co-located: every worker machine runs a DataNode (storage) and a NodeManager (compute), which is what makes data locality possible.
Interview Tip
Answer structure: Name the four modules, then the daemons of each, then say how a job uses them: data sits on DataNodes, the job asks the ResourceManager for containers on NodeManagers, and tasks run next to the data blocks.
Cross Questions
What does a typical worker node run?
A DataNode and a NodeManager. Master nodes run the NameNode(s), ResourceManager(s), JournalNodes, ZooKeeper and the MapReduce JobHistory Server.
Can you use YARN without HDFS, or HDFS without MapReduce?
Yes. Spark on YARN can read from S3. HDFS is used by Spark, Hive, Presto/Trino and HBase without any MapReduce at all.

Key Takeaways

The biggest change was Hadoop 2's YARN. In Hadoop 1, the JobTracker did both resource management and job monitoring for every job, which limited clusters to roughly 4,000 nodes and allowed only MapReduce. YARN split those duties: one ResourceManager for resources, and a separate ApplicationMaster per job. Any engine could now share the cluster.

Hadoop 3's headline feature is erasure coding, which roughly halves the storage cost of fault tolerance for cold data.

Cross Questions
Why did the default block size grow from 64 MB to 128 MB?
Disks and networks got faster and datasets grew. Bigger blocks mean fewer blocks to track in NameNode memory and fewer, longer-running map tasks, while keeping seek time a small fraction of transfer time.
What were the limitations of the JobTracker?
Single point of failure, a scalability ceiling (~4,000 nodes / 40,000 tasks), poor utilisation because map and reduce slots were fixed, and no support for non-MapReduce workloads.

What is HDFS? What are its key design goals?

HDFS Architecture 6 min read Difficulty: Basic 6 of 48
Definition

HDFS (Hadoop Distributed File System) is a distributed file system that stores very large files as blocks spread across many machines, replicating each block for fault tolerance. It presents one file system namespace (/user/vineeta/marks.csv) even though the data lives on hundreds of disks.

HDFS Distributed File System Write Once Read Many High Throughput Fault Tolerance
Design Goals
Design goalWhat it means
Very large filesOptimised for files of hundreds of MB to TBs, and millions (not billions) of files
Streaming data accessWrite once, read many: data is written, then scanned many times from start to end
High throughput over low latencyReading a whole dataset fast matters more than fetching one record fast
Hardware failure is normalDetect failures and recover automatically through replication
Move computation to dataExpose block locations so schedulers can run tasks where the data is
PortabilityRuns on commodity hardware and many OSs (Java)
Write Semantics
  • Files can be appended to but not modified in place: there are no random writes.
  • Only one writer per file at a time (enforced with a lease from the NameNode).
  • Not POSIX-compliant: no seek-and-write, relaxed semantics for speed.
Cross Questions
Why is HDFS write-once?
It keeps replication and consistency simple: blocks never change after they are written, so replicas cannot diverge, and readers never see partially updated blocks. Updates are done by rewriting files or partitions (table formats like Hudi, Iceberg and Delta handle this for you).
What is a lease in HDFS?
A time-limited lock the NameNode gives to the client writing a file, so no other client can write it at the same time. The client renews it while writing; if the client dies, the lease expires and the NameNode recovers the file.

Key Point: Metadata Lives in RAM

The NameNode does not store the block-to-DataNode mapping on disk. It rebuilds it at start-up from the block reports that DataNodes send. That is why a freshly started NameNode stays in safe mode until enough block reports arrive.

Because the whole namespace lives in the NameNode's heap, the number of files and blocks (not the data size) limits how big a cluster can grow. A common rule of thumb is about 150 bytes of heap per file, directory or block.

Example: Estimating NameNode Memory
Python
# Rule of thumb: ~150 bytes of NameNode heap per object (file, directory or block)
BYTES_PER_OBJECT = 150
BLOCK_MB = 128

def namenode_heap(files, avg_file_mb, dirs):
    blocks_per_file = max(1, -(-avg_file_mb // BLOCK_MB))      # ceiling division
    objects = files + dirs + files * blocks_per_file
    return objects, objects * BYTES_PER_OBJECT / 1024**3

for files, size_mb in [(10_000_000, 512), (100_000_000, 1)]:
    objs, gb = namenode_heap(files, size_mb, dirs=files // 100)
    data_tb = files * size_mb / 1024**2
    print(f"{files:>11,} files x {size_mb:>3} MB = {data_tb:>7,.0f} TB data -> "
          f"{objs:>11,} objects, ~{gb:5.1f} GB heap")
Output
 10,000,000 files x 512 MB =   4,883 TB data ->  50,100,000 objects, ~  7.0 GB heap
100,000,000 files x   1 MB =      95 TB data -> 201,000,000 objects, ~ 28.1 GB heap
Notice: The second case stores 50× less data but needs more NameNode memory: this is the small files problem.
Cross Questions
Does a client's data pass through the NameNode?
No. The NameNode only returns block locations; data is streamed directly between the client and DataNodes.
Why do DataNodes use JBOD instead of RAID?
HDFS already replicates blocks across machines, so RAID redundancy is wasted space. JBOD lets each disk work independently (no slowest-disk penalty), and one failed disk loses only its blocks.
What commands does the NameNode send in heartbeat replies?
Replicate a block to another DataNode, delete (invalidate) a block, re-register or send a full block report, recover a block, or shut down.

What is a block in HDFS? Why is the block size so large?

HDFS Architecture 8 min read Difficulty: Basic 8 of 48
Definition

A block is the unit in which HDFS stores and replicates data. Every file is split into blocks of dfs.blocksize (default 128 MB in Hadoop 2/3, 64 MB in Hadoop 1). Each block is stored as an ordinary file on a DataNode's local disk.

A file smaller than the block size occupies only its real size on disk: a 1 MB file uses 1 MB, not 128 MB. But it still costs one block entry in NameNode memory.

Block dfs.blocksize 128 MB Seek Time Input Split
How It Works — Step by Step
Step 1 / 5
  1. 1A 500 MB file is copied into HDFS. HDFS never stores it as one piece.
  2. 2It is cut into fixed-size blocks of 128 MB (the default dfs.blocksize since Hadoop 2).
  3. 3The last block holds only the remaining 116 MB. A block is not padded: a small or partial block uses only as much disk as its data.
  4. 4Each block is replicated 3 times on different DataNodes. The NameNode chooses where, spreading copies across nodes and racks.
  5. 5Total raw storage is file size × replication = 1,500 MB. That 3× overhead is the price of fault tolerance (Hadoop 3 erasure coding reduces it).
Why Large Blocks?
  • Less seek overhead: a disk seek takes ~10 ms; transferring 128 MB takes about a second. With big blocks, time is spent reading data, not seeking.
  • Less NameNode memory: fewer blocks to track per TB of data.
  • Fewer tasks: one map task per block, so fewer, longer tasks with less scheduling overhead.
  • But not too large: too few blocks means too few parallel tasks and slower recovery of a lost block.
Example: Blocks for a 500 MB File
Python
import math

def plan(file_mb, block_mb=128, replication=3):
    blocks = math.ceil(file_mb / block_mb)
    last = file_mb - (blocks - 1) * block_mb
    print(f"{file_mb} MB file, {block_mb} MB blocks, replication {replication}")
    print(f"  blocks          : {blocks} ({blocks - 1} x {block_mb} MB + 1 x {last} MB)")
    print(f"  block replicas  : {blocks * replication}")
    print(f"  raw disk used   : {file_mb * replication} MB")
    print(f"  map tasks (default, 1 per block): {blocks}")

plan(500)
plan(500, block_mb=256)

Cross Questions
If a 1 MB file is stored in HDFS, how much disk does it use?
1 MB per replica (3 MB with replication 3). The block is not padded to 128 MB. The cost of small files is NameNode memory and task overhead, not disk space.
Can different files have different block sizes?
Yes. Block size is set per file when it is written (-D dfs.blocksize=… or in the client API). Changing dfs.blocksize later does not affect existing files.
Block vs input split?
A block is a physical division of stored data. An input split is a logical chunk of input given to one map task; a split may cross block boundaries so that a record is never cut in half. See the MapReduce section.

What is the replication factor? What is rack awareness?

HDFS Architecture 8 min read Difficulty: Basic 9 of 48
Definition

The replication factor is the number of copies kept of each block (dfs.replication, default 3). It can be set per file.

Rack awareness means the NameNode knows which rack each DataNode is in and places replicas so that the data survives the loss of a whole rack while keeping cross-rack traffic low.

Replication Factor dfs.replication Rack Awareness Replica Placement setrep
How It Works — Step by Step
Step 1 / 4
  1. 1Replica 1 goes on the node where the writer runs (if that node is a DataNode), otherwise on a random node. Writing locally is fastest.
  2. 2Replica 2 goes on a node in a different rack. If the whole of Rack A loses power or its switch fails, the data is still available.
  3. 3Replica 3 goes on a different node in the same rack as replica 2. Only one copy crosses between racks during the write, which saves inter-rack bandwidth.
  4. 4Result: survives any single node failure and any single rack failure, with only one cross-rack transfer per block. The NameNode learns the topology from a rack-awareness script (net.topology.script.file.name).
Commands and Configuration
HDFS shell
# Change replication of existing data (-w waits until done)
hdfs dfs -setrep -w 2 /data/archive/2023

# Replication is the 2nd column of -ls output for files
hdfs dfs -ls /data/exams

# Show the rack of each DataNode
hdfs dfsadmin -printTopology

Cross Questions
Why is the default 3 and not 2?
With 2 copies, a second failure during the hours it takes to re-replicate loses data. 3 copies tolerate two simultaneous failures and allow the cross-rack placement (1 + 2) at reasonable cost.
What happens if no rack script is configured?
Every node is placed in /default-rack. Replicas are still on different nodes, but all three could be in the same physical rack.
Can the replication factor be higher than the number of DataNodes?
It can be set, but a DataNode never holds two replicas of the same block, so the blocks stay under-replicated (shown by hdfs fsck).

What are fsimage and edit logs? What does the Secondary NameNode do?

HDFS Architecture 8 min read Difficulty: Basic 10 of 48
Definition

fsimage: a checkpoint file holding the complete namespace (directories, files, block IDs, permissions) at a point in time.

Edit log (edits): an append-only journal of every change since the last fsimage.

Secondary NameNode: a helper that periodically merges fsimage + edits into a new fsimage (a checkpoint) so the edit log stays small and restarts stay fast.

fsimage Edit Log Checkpoint Secondary NameNode Standby NameNode
How It Works — Step by Step
Step 1 / 6
  1. 1The NameNode keeps the whole namespace in RAM for speed, and persists it on disk as an fsimage: a snapshot of the namespace at some point in time.
  2. 2Changes are not written into the fsimage directly. Every change (create, rename, delete) is appended to the edits log, which is cheap and safe.
  3. 3If edits grow unbounded, a restart takes very long (all edits must be replayed). So a Secondary NameNode (or, in HA, the Standby NameNode) periodically copies fsimage and edits.
  4. 4It loads the fsimage, replays the edits on top, and writes a new fsimage. This merge is a checkpoint.
  5. 5The new fsimage replaces the old one and the old edits can be discarded, so the next restart only replays a short log.
  6. 6Defaults: dfs.namenode.checkpoint.period = 3600 s and dfs.namenode.checkpoint.txns = 1,000,000, whichever comes first. Note: the Secondary NameNode is a checkpoint helper, not a backup.
Classic Trap: The Secondary NameNode is not a hot standby or backup NameNode. If the NameNode dies, the Secondary does not take over. At best its latest checkpoint can help recover metadata, losing changes made since.
Points to Remember
  • In an HA cluster there is no Secondary NameNode. The Standby NameNode performs checkpoints.
  • Hadoop also has a Checkpoint Node and a Backup Node (keeps an in-memory, up-to-date copy), but they are rarely used; HA replaced them.
  • Metadata directories (dfs.namenode.name.dir) are usually written to several disks, including an NFS mount, for safety.
Cross Questions
What happens at NameNode start-up?
It loads the latest fsimage into memory, replays the edit log on top, writes a new checkpoint, then waits in safe mode for DataNode block reports to rebuild the block-location map.
Why not update the fsimage directly on every change?
The fsimage is large (GBs). Rewriting it per operation would be far too slow. Appending a small record to the edit log is fast and durable.
How can you inspect an fsimage?
With the Offline Image Viewer: hdfs oiv -p XML -i fsimage_000… -o fsimage.xml. Edits use the Offline Edits Viewer (hdfs oev).

Explain how a file is written to HDFS.

HDFS Read, Write & Operations 9 min read Difficulty: Intermediate 12 of 48
Definition

A write is coordinated by the NameNode but the data goes straight from the client to a pipeline of DataNodes. The client sends each packet once; the DataNodes forward it to each other.

Write Pipeline Packet ACK DFSOutputStream Lease
How It Works — Step by Step
Step 1 / 5
  1. 1The client calls create(). The NameNode checks permissions and that the file does not already exist, and records the new file in the namespace.
  2. 2For each block, the client asks the NameNode for target DataNodes. The NameNode returns a list chosen by the placement policy (here DN1, DN3, DN4).
  3. 3The client streams the data in small packets to DN1 only. DN1 stores each packet and forwards it to DN3, which forwards it to DN4: a pipeline. The client uploads each byte once, not three times.
  4. 4Acknowledgements flow back from DN4 → DN3 → DN1 → client. A packet is removed from the client's ack queue only when all replicas have it.
  5. 5When the block is full, the client asks for a new set of DataNodes for the next block. On close(), the NameNode marks the file complete once the minimum replicas are confirmed.
Details Interviewers Ask
  • Data is buffered and split into packets (64 KB by default) placed on a data queue; sent packets move to an ack queue until every DataNode in the pipeline confirms them.
  • If a DataNode in the pipeline fails, the pipeline is closed, unacknowledged packets are put back on the data queue, the failed node is removed and writing continues with the remaining nodes. The NameNode later re-replicates the block to restore the replication factor.
  • The write succeeds once dfs.namenode.replication.min (default 1) replicas are written.
  • Data written is not guaranteed visible to readers until the block completes or the writer calls hflush()/hsync().
Cross Questions
Why a pipeline instead of the client writing 3 copies?
The client's network link would carry 3× the data. With a pipeline the client uploads once and the copies travel between DataNodes, usually only one hop crossing racks.
What is the difference between hflush and hsync?
hflush() guarantees the data has reached all DataNodes' memory and is visible to new readers. hsync() also forces it to disk on the DataNodes.
What happens if the client dies while writing?
It stops renewing its lease. Once the lease's hard limit expires, the NameNode performs lease recovery, finalising the last block at a length all replicas agree on, and closes the file.

Explain how a file is read from HDFS.

HDFS Read, Write & Operations 7 min read Difficulty: Intermediate 13 of 48
Definition

The client gets block locations from the NameNode, then reads each block directly from the closest DataNode holding it, verifying checksums as it goes.

Read Path DFSInputStream Network Distance Checksum Short-circuit Read
How It Works — Step by Step
Step 1 / 5
  1. 1The client calls open() and asks the NameNode for the file's block locations.
  2. 2The NameNode returns, for each block, the DataNodes that hold a replica, sorted by network distance from the client.
  3. 3The client reads block B1 directly from the closest replica. Here it is on the same node, so it is a fast local read (short-circuit reads can even bypass the DataNode process).
  4. 4Then it reads B2 from the closest replica of B2, here in the same rack. Data is streamed block by block; the NameNode is not involved in transferring data.
  5. 5Every block has checksums. If a read fails or the checksum does not match, the client reports the bad replica to the NameNode and reads from the next DataNode in the list.

What is the small files problem in Hadoop? How do you solve it?

Definition

A small file is one much smaller than the HDFS block size. Large numbers of them hurt HDFS and processing engines because each file and block is an object in NameNode memory, and engines typically create one task per file.

Small Files NameNode Heap Compaction HAR SequenceFile CombineFileInputFormat
How It Works — Step by Step
Step 1 / 5
  1. 1Both sides store about 1 GB of data. On the left it is one large file; on the right it is 10,000 small files.
  2. 2Every file, directory and block is an object in NameNode memory. The large file needs 9 objects; the small files need 20,000, because each small file still has its own block.
  3. 3At a rule of thumb of ~150 bytes per object, the small files use over 2,000× more NameNode heap for the same data. At billions of objects, the NameNode runs out of memory.
  4. 4Processing suffers too: by default each small file becomes its own input split, so a MapReduce or Spark job launches 10,000 tasks instead of 8, and task start-up dominates the run time.
  5. 5Fixes: merge files at ingestion, compact periodically into large Parquet/ORC files, pack them into a Hadoop Archive (HAR) or SequenceFile, or read them with CombineFileInputFormat.
Example: The Cost in Numbers

def cost(n_files, file_kb, block_mb=128):
    blocks = n_files * max(1, -(-file_kb // (block_mb * 1024)))
    objects = n_files + blocks
    return objects, objects * BYTES

How does NameNode High Availability work?

High Availability & Fault Tolerance 9 min read Difficulty: Intermediate 19 of 48
Definition

In Hadoop 1 the NameNode was a single point of failure (SPOF): if it went down, the whole file system was unavailable. HDFS High Availability (Hadoop 2+) runs an Active and one or more Standby NameNodes that share the edit log through a quorum of JournalNodes, with ZooKeeper and ZKFC handling automatic failover.

High Availability Active/Standby JournalNode QJM ZKFC ZooKeeper Fencing Split-brain
How It Works — Step by Step
Step 1 / 6
  1. 1Two (Hadoop 3: two or more) NameNodes run. Only one is Active and serves clients; the other is a Standby with the same namespace in memory.
  2. 2The Active NameNode writes every edit to a group of JournalNodes (usually 3 or 5). A write succeeds once a majority confirms it.
  3. 3The Standby continuously reads (tails) the edits from the JournalNodes and applies them. DataNodes send block reports and heartbeats to both NameNodes, so the Standby is ready instantly. The Standby also does the checkpointing.
  4. 4A ZKFailoverController (ZKFC) runs next to each NameNode, checks its health and holds a lock in ZooKeeper for the Active one.
  5. 5If the Active NameNode crashes, its ZooKeeper session expires and the lock is released. The other ZKFC fences the old Active (the JournalNodes also reject writes from it) to prevent split-brain.
  6. 6The Standby is promoted to Active. Clients configured with the logical nameservice (e.g. hdfs://mycluster) fail over automatically.

What is split-brain and how does HDFS prevent it?
Two NameNodes both believing they are active and both modifying the namespace, corrupting it. QJM prevents it: each new active gets a higher epoch number and JournalNodes reject writes with an older epoch, so a stale active cannot write edits.
Why an odd number of JournalNodes?
A quorum needs a majority. 4 JNs tolerate only 1 failure, the same as 3, so the extra node adds cost without extra safety.
Is the Secondary NameNode used in HA?
No. The Standby NameNode does the checkpointing, so running a Secondary NameNode in an HA cluster is an error.

What happens when a DataNode fails? How does HDFS detect it?

High Availability & Fault Tolerance 7 min read Difficulty: Intermediate 21 of 48
Definition

DataNodes send a heartbeat every 3 seconds (dfs.heartbeat.interval). If none arrives for 2 × dfs.namenode.heartbeat.recheck-interval + 10 × dfs.heartbeat.interval = 2 × 5 min + 10 × 3 s = 10.5 minutes, the NameNode marks the DataNode dead and re-replicates its blocks from the surviving copies.

Heartbeat Dead Node Under-replicated Re-replication Block Report
How It Works — Step by Step
Step 1 / 5
  1. 1Each block has 3 replicas spread over the DataNodes, and every DataNode sends a heartbeat every 3 seconds.
  2. 2DN2 crashes (disk, power, network). Its heartbeats stop.
  3. 3The NameNode waits before acting, to avoid a re-replication storm on short glitches. With defaults it declares a node dead after 2 × 5 min recheck + 10 × 3 s heartbeat = 10.5 minutes. Blocks that were on DN2 are now under-replicated.
  4. 4The NameNode tells DataNodes that still hold good replicas to copy them to other nodes (respecting rack placement). Here DN1 copies B2 to DN3 and DN3 copies B1 to DN4. Clients can keep reading the whole time.
  5. 5Once every block is back to its target replication, the cluster has healed itself. If DN2 returns later with old copies, the extra (over-replicated) replicas are deleted.
Example: Detection Timeout and Recovery Time
Python
heartbeat_s = 3          # dfs.heartbeat.interval
recheck_ms = 300_000     # dfs.namenode.heartbeat.recheck-interval
timeout_s = 2 * recheck_ms / 1000 + 10 * heartbeat_s
print(f"DataNode declared dead after {timeout_s:.0f} s = {timeout_s / 60} minutes")

dead_node_tb = 24
live_nodes = 99
per_node_mb_s = 50       # replication bandwidth each surviving node contributes

Points to Remember
  • Disk failure (not the whole node): by default (dfs.datanode.failed.volumes.tolerated = 0) the DataNode shuts down on one bad disk; set it to e.g. 1 or 2 so a node with many disks keeps running.
  • Recovery is parallel across the cluster: many nodes copy a little each, which is why recovery is fast on large clusters.
  • Re-replication is prioritised: blocks with only one remaining replica are copied first.
  • A node that returns is not a problem: extra replicas are simply deleted.
Cross Questions
Why does the NameNode wait 10 minutes instead of acting immediately?
A short network glitch or a DataNode restart would otherwise trigger copying terabytes for nothing (a "replication storm"). Reads simply switch to other replicas in the meantime.
What is a stale DataNode?
One that has not sent a heartbeat for 30 s (dfs.namenode.stale.datanode.interval). If enabled, the NameNode avoids it for reads/writes before it is declared dead.

What is erasure coding in HDFS? When would you use it?

High Availability & Fault Tolerance 8 min read Difficulty: Intermediate 22 of 48
Definition

Erasure coding (EC), added in Hadoop 3, stores data cells plus computed parity cells instead of full copies. With the Reed-Solomon policy RS-6-3-1024k, every 6 data cells get 3 parity cells: any 3 of the 9 can be lost, at only 50% storage overhead versus 200% for 3× replication.

Erasure Coding Reed-Solomon RS-6-3 Parity Striping Hadoop 3
How It Works — Step by Step
Step 1 / 5
  1. 1Take 6 blocks of data. With replication each block is stored once…
  2. 2…and then twice more. 6 units of data occupy 18 units of disk: 200% storage overhead. It tolerates the loss of 2 replicas of any block.
  3. 3Erasure coding (Hadoop 3) with the Reed-Solomon policy RS-6-3-1024k stores the 6 data cells plus 3 computed parity cells: 9 units, only 50% overhead.
  4. 4Any 3 of those 9 cells can be lost and the missing ones are recomputed from the remaining 6. That is better fault tolerance than 3× replication with a third of the extra storage.
  5. 5The trade-off: rebuilding needs CPU and network, reads are striped across many nodes (no locality), and small files waste space. Use EC for cold/archival directories, replication for hot data.
Example: Storage for 100 TB of Data

What is MapReduce? Explain its phases.

MapReduce 9 min read Difficulty: Intermediate 24 of 48
Definition

MapReduce is a programming model and execution engine for processing large datasets in parallel. You write two functions; the framework handles splitting input, scheduling tasks near the data, moving and sorting intermediate data, and retrying failures.

How It Works — Step by Step
Step 1 / 5
  1. 1The input file is divided into input splits (usually one per HDFS block). Each split is fed to one map task, record by record (here, line by line).
  2. 2Each map task runs in parallel, ideally on the node that stores its block (data locality), and emits intermediate (key, value) pairs: (word, 1) for every word.
  3. 3Shuffle & sort: map output is partitioned by key (which reducer gets which key), sorted, copied over the network to the reducers and merged, so each reducer sees each key once with all its values.
  4. 4Each reduce task receives key → [values] and aggregates them: big → [1,1,1] becomes big 3.
  5. 5Each reducer writes one output file (part-r-00000, part-r-00001…) to HDFS. Intermediate map output is written only to the mapper's local disk and deleted after the job.
Cross Questions
Is the reduce phase mandatory?
No. With mapreduce.job.reduces = 0 the job is map-only: mapper output is written straight to HDFS (part-m-NNNNN), with no shuffle. Used for filtering, format conversion and DistCp.
Can reducers start before all mappers finish?
Reducers can start copying map output early (slow start, mapreduce.job.reduce.slowstart.completedmaps, default 0.05), but the reduce function itself runs only after every map has finished, because any mapper could still produce a value for any key.
Where is map output stored?
On the local disk of the node that ran the mapper, not in HDFS: it is temporary and replicating it would waste I/O. If that node dies before reducers fetch it, the map task is re-run.

public class WordCount {
  public static class TokenizerMapper extends Mapper<Object, Text, Text, IntWritable> {
    private final static IntWritable one = new IntWritable(1);
    private Text word = new Text();
    public void map(Object key, Text value, Context ctx) throws IOException, InterruptedException {
      StringTokenizer itr = new StringTokenizer(value.toString().toLowerCase());
      while (itr.hasMoreTokens()) { word.set(itr.nextToken()); ctx.write(word, one); }
    }
  }
  public static class IntSumReducer extends Reducer<Text, IntWritable, Text, IntWritable> {
    public void reduce(Text key, Iterable<IntWritable> values, Context ctx) throws IOException, InterruptedException {
      int sum = 0;
      for (IntWritable v : values) sum += v.get();
      ctx.write(key, new IntWritable(sum));
    }
  }
  public static void main(String[] args) throws Exception {
    Job job = Job.getInstance(new Configuration(), "word count");
    job.setJarByClass(WordCount.class);
    job.setMapperClass(TokenizerMapper.class);
    job.setCombinerClass(IntSumReducer.class);     // reducer reused as combiner
    job.setReducerClass(IntSumReducer.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(IntWritable.class);
    FileInputFormat.addInputPath(job, new Path(args[0]));
    FileOutputFormat.setOutputPath(job, new Path(args[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Example: Simulating Shuffle & Sort

This Python simulation reproduces what the framework does between map and reduce: partition, sort, group.

from itertools import groupby

map_outputs = {
    "map-0": [("big", 1), ("data", 1), ("big", 1)],
    "map-1": [("data", 1), ("is", 1), ("big", 1)],
}
R = 2
def partition(key):                      # simple stand-in for hashCode() % R
    return len(key) % R

# map side: partition then sort each map's output
for m, pairs in map_outputs.items():
    parts = {r: sorted(p for p in pairs if partition(p[0]) == r) for r in range(R)}
    print(m, parts)

# reduce side: fetch the reducer's partition from every map, merge-sort, group by key
for r in range(R):
    fetched = sorted(p for pairs in map_outputs.values() for p in pairs if partition(p[0]) == r)
    groups = {k: [v for _, v in g] for k, g in groupby(fetched, key=lambda kv: kv[0])}
    print(f"reducer {r} input: {groups}  ->  output: { {k: sum(v) for k, v in groups.items()} }")

What is a combiner? When can you use one?

MapReduce 7 min read Difficulty: Intermediate 27 of 48
Definition

A combiner is an optional "mini-reducer" that runs on each mapper's output, on the map node, before the shuffle. It pre-aggregates values with the same key to reduce the data sent over the network.

Hadoop may run it zero, one or many times, so the result must not depend on how often it runs: the function must be commutative and associative, and its input and output types must match the map output types.

Combiner Mini-reducer Commutative Associative Shuffle Reduction
How It Works — Step by Step
Step 1 / 4
  1. 1A mapper on one node emits six pairs. Four of them have the same key big.
  2. 2A combiner is a "mini-reducer" that runs on the mapper's node, on that mapper's output, before the shuffle. It sums the local counts to (big,4) and (data,2).
  3. 3Without a combiner, 6 records are shuffled across the network; with it, only 2. On real data (millions of repeated keys) this cuts shuffle I/O dramatically.
  4. 4Hadoop may run the combiner zero, one or many times, so the operation must give the same answer regardless: commutative and associative (sum, count, max, min). Averaging averages is wrong; emit (sum, count) instead and divide in the reducer.

Cross Questions
Combiner vs reducer?
A reducer is mandatory for aggregation and sees all values of a key from all mappers; a combiner is an optimisation that sees only one mapper's (or one spill's) values and is not guaranteed to run.
Which operations are safe in a combiner?
Sum, count, min, max, and set union. Not average, median or distinct-count (unless you change what is emitted, e.g. (sum, count) pairs for average).

What is a partitioner? When do you write a custom one?

MapReduce 7 min read Difficulty: Intermediate 28 of 48
Definition

The partitioner decides which reducer receives each intermediate key. The default HashPartitioner computes (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks, so the same key always goes to the same reducer and keys are spread roughly evenly.

Partitioner HashPartitioner numReduceTasks Custom Partitioner TotalOrderPartitioner
How It Works — Step by Step
Step 1 / 4
  1. 1With R reducers, every map output key must be sent to exactly one of them. The default HashPartitioner computes the partition from the key's hash.
  2. 2Each key's hashCode() (for a Text key, a hash of its UTF-8 bytes) is taken modulo the number of reducers (3 here). These are the real values Hadoop computes for these words (verified in the Partitioner question).
  3. 3All pairs with the same key, from every mapper, land on the same reducer. That is what allows the reducer to see the complete list of values for a key.
  4. 4You write a custom Partitioner when keys must be grouped differently (e.g. by country so each output file holds one country) or to spread out a skewed hot key.

def text_hash(s):                     # org.apache.hadoop.io.Text.hashCode()
    h = 1
    for b in s.encode("utf-8"):
        b = b - 256 if b > 127 else b    # Java bytes are signed
        h = ctypes.c_int32(31 * h + b).value
    return h

def hash_partition(key, reducers):    # HashPartitioner.getPartition
    return (text_hash(key) & 0x7FFFFFFF) % reducers

public class StatePartitioner extends Partitioner<Text, IntWritable> {
  @Override
  public int getPartition(Text key, IntWritable value, int numPartitions) {
    String state = key.toString().split(",")[0];          // key = "MH,Mumbai"

When would you write a custom partitioner?

import math
MB = 1024**2

def split_size(block, min_size=1, max_size=2**63 - 1):
    # FileInputFormat.computeSplitSize
    return max(min_size, min(max_size, block))

def n_maps(file_sizes, block=128 * MB, **kw):
    s = split_size(block, **kw)
    total = 0
    for size in file_sizes:
        # the last split may be up to 10% bigger (SPLIT_SLOP = 1.1)
        n, rest = 0, size
        while rest / s > 1.1:
            n, rest = n + 1, rest - s
        total += n + (1 if rest else 0)
    return total, s // MB

Points to Remember
  • Mappers = number of input splits (you influence it with mapreduce.input.fileinputformat.split.minsize/maxsize, not by setting a number). Each file gets its own splits, which is why small files create many mappers.
  • Reducers are set explicitly: mapreduce.job.reduces (default 1) or job.setNumReduceTasks(). A common guideline is 0.95 or 1.75 × (nodes × containers per node).
  • Non-splittable files (e.g. gzip) always produce one split per file, however large.
Cross Questions
A line is split across two blocks. Is it processed twice or lost?
Neither. The RecordReader for the first split reads past its end (remote read if needed) to complete the line; the second split's reader skips everything up to the first newline.
What happens with too many or too few reducers?
Too few: each reducer handles a huge partition, runs long and may spill heavily. Too many: many tiny output files and scheduling overhead.

How does MapReduce handle task failures? What is speculative execution?

MapReduce 7 min read Difficulty: Intermediate 31 of 48
Definition

Task failure: if a task attempt throws an exception, its JVM dies or it stops reporting progress for 10 minutes (mapreduce.task.timeout), the ApplicationMaster reschedules it, preferably on another node. After 4 failed attempts (mapreduce.map.maxattempts / reduce.maxattempts) the job fails.

Speculative execution: if a task runs much slower than the average of its peers (a straggler, e.g. on a node with a failing disk), the AM launches a duplicate attempt elsewhere. Whichever finishes first wins; the other is killed.

When should you disable speculative execution?
When tasks have side effects that must not run twice (writing to an external database or calling an API), or on busy clusters where duplicates waste resources. Properties: mapreduce.map.speculative, mapreduce.reduce.speculative.
Does speculative execution fix data skew?
No. A task slow because it has more data will be just as slow on another node. Speculation only helps with slow machines.

Explain the flow of a job submitted to YARN.

YARN 8 min read Difficulty: Advanced 34 of 48
Definition

From submission to completion: client → RM → AM container → AM negotiates task containers → NMs run tasks → AM reports and unregisters.

Job Submission ApplicationMaster Container Allocation Heartbeat
How It Works — Step by Step
Step 1 / 6
  1. 1The client submits an application (a MapReduce job, a Spark app) to the ResourceManager, the cluster-wide master that owns all resources.
  2. 2The RM's ApplicationsManager finds a NodeManager with free capacity and launches the application's ApplicationMaster in a first container. Each application gets its own AM.
  3. 3The ApplicationMaster works out how many tasks are needed and asks the RM's Scheduler for containers: amount of memory and vcores, preferably on nodes holding the input data.
  4. 4The Scheduler grants containers; the AM contacts the NodeManagers directly to launch tasks inside them. A container is a slice of memory and CPU on one node.
  5. 5NodeManagers monitor their containers (killing those exceeding their memory) and send heartbeats with node health and available resources to the RM.
  6. 6The AM tracks task progress, re-requests containers for failed tasks, reports status to the client, and unregisters from the RM when the job finishes, releasing all containers.
Details
  • Before submitting, the client copies the job resources (jar, config, split information) to a staging directory in HDFS so any node can fetch them.
  • The AM sends heartbeats to the RM; resource requests and container grants travel on these heartbeats.
  • Requests carry locality preferences (node, rack, any). The scheduler tries to honour them.
  • If the AM itself fails, the RM launches a new attempt; MapReduce's AM can recover the tasks already completed.

The application is queued but there is no capacity in its queue (or AM resource limit reached) to start the AM. Check the queue's usage and maximum-am-resource-percent.

Why Columnar Formats Are Faster for Analytics
  • Column pruning: SELECT AVG(marks) reads only the marks column chunks.

Parquet or ORC?

For write-heavy, record-at-a-time workloads (streaming ingestion, Kafka) and when schemas evolve often, since Avro handles added/removed/renamed fields with defaults and aliases. For analytical reads, Parquet/ORC win.

What is data skew in MapReduce, and how do you handle it?

Definition

Data skew happens when some keys have far more records than others. All values of a key go to one reducer, so that reducer runs for hours while the others finish in minutes. The job is only as fast as its slowest task.

from collections import Counter

    return sum(map(ord, key)) % R

How do you join two datasets in MapReduce?

Ecosystem, Admin & Scenarios 8 min read Difficulty: Expert 43 of 48
Definition

Reduce-side join: both datasets are mapped to (join_key, tagged_record); the shuffle brings matching keys together and the reducer combines them. Works for any sizes.

Map-side join: the small dataset is loaded into memory in every mapper (Distributed Cache) and the big dataset is joined while it is read; no shuffle or reduce phase is needed.

Reduce-side Join Map-side Join Replicated Join Distributed Cache Broadcast Join
How It Works — Step by Step
Step 1 / 4
  1. 1Reduce-side join: mappers read both datasets, emit the join key (cust_id) as the key and tag each record with its source.
  2. 2Shuffle brings all records with the same key to one reducer, which combines the customer rows with the order rows. It works for any data sizes, but both datasets cross the network: slow and skew-prone.
  3. 3Map-side (broadcast/replicated) join: the small table is shipped to every mapper (Distributed Cache in MapReduce, broadcast in Spark, MAPJOIN in Hive).
  4. 4Each mapper loads it into a hash table and joins its slice of the big table locally. No shuffle and no reduce phase, so it is much faster, but the small side must fit in memory.
Example: Both Joins in Python
Python
from itertools import groupby

students = [("2401", "Anuj"), ("2402", "Vineeta"), ("2403", "Aarshvi")]
marks    = [("2401", "SQL", 82), ("2402", "SQL", 91), ("2401", "Spark", 77), ("2403", "Spark", 88)]

# ---- reduce-side join: tag, shuffle (sort by key), combine per key
mapped = [(r, "S", n) for r, n in students] + [(r, "M", f"{s}={m}") for r, s, m in marks]
print("reduce-side join:")
for roll, group in groupby(sorted(mapped), key=lambda x: x[0]):
    group = list(group)
    name = [v for _, t, v in group if t == "S"][0]
    for _, t, v in group:
        if t == "M":
            print("  ", roll, name, v)

# ---- map-side join: small table becomes an in-memory dict in every mapper
lookup = dict(students)
print("map-side join:")
for roll, subject, m in marks:
    print("  ", roll, lookup[roll], f"{subject}={m}")

3. hdfs fsck / reports missing or corrupt blocks
  • Missing: all replicas are on dead nodes. Bring those nodes/disks back first.
  • If truly lost, list affected files with -list-corruptfileblocks, restore them from source/backup, then hdfs fsck / -delete (or -move to /lost+found).
4. A job worked yesterday, today one reducer runs for hours
  • Compare per-task input records: a new hot key (skew), e.g. a default value like NULL or unknown.
  • Filter or salt it; use a combiner or map-side join.
5. Spark on YARN application stuck in ACCEPTED
  • Queue full or AM limit reached, or requested container bigger than yarn.scheduler.maximum-allocation-mb.
  • Check the RM scheduler page, lower executor size/count, or submit to another queue.
6. DataNodes are unevenly full after adding new nodes
  • New nodes receive only new data. Run hdfs balancer -threshold 10 during off-peak hours with a bandwidth limit.
