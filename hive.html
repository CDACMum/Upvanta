What is Apache Hive? Why is it used?

Hive Foundations 7 min read Difficulty: Beginner 1 of 40
Definition

Apache Hive is a data warehouse system built on top of Hadoop that lets you query and manage large datasets stored in HDFS (or cloud storage) using a SQL-like language called HiveQL.

Hive converts each query into distributed jobs (Tez, MapReduce or Spark) that run on the cluster. It was created at Facebook (2007–08) so analysts could use SQL on Hadoop instead of writing Java MapReduce programs, and became a top-level Apache project in 2010.

Hive HiveQL Data Warehouse SQL on Hadoop Batch Analytics Metastore
Analogy
Think of HDFS as a huge library store-room full of boxes of loose papers (files). Finding anything means opening boxes by hand. Hive is the librarian with a catalogue: you ask a question in plain language (SQL), the librarian looks up in the catalogue (metastore) which boxes hold the answer, sends a team of assistants (parallel tasks) to read only those boxes, and hands you a neat summary. The papers never leave the store-room; the catalogue just describes them.
How It Works — Step by Step
Step 1 / 5
  1. 1An analyst writes ordinary SQL (HiveQL). They do not need to know Java, MapReduce or how the cluster works.
  2. 2Hive parses the query, checks the table definition in its metastore, and builds an optimised execution plan.
  3. 3The plan is turned into a distributed job (Tez, MapReduce or Spark) whose tasks run in parallel across the cluster under YARN.
  4. 4The tasks read the table's data straight from files in HDFS or cloud storage. A Hive table is just a directory of files plus a schema.
  5. 5The aggregated result is returned to the analyst like any database query. Hive feels like a database, but it is a SQL layer over files.
Real-World Scenario
C-DAC: five years of exam data

Every exam produces CSV exports of answers, marks and proctoring logs: billions of rows over the years, far too much for a single MySQL server to scan. The files are copied to HDFS and exposed as Hive tables. Coordinators then answer questions like "average marks per centre per module over 5 years" with one SQL query, which Hive runs in parallel across the cluster.

Industry

Facebook built Hive for petabyte-scale log analysis; banks and telecoms run nightly regulatory and billing reports in Hive; and the Hive Metastore is still the standard table catalogue used by Spark, Trino and Impala even where Hive's query engine is not used.

Cross Questions
Is Hive a database?
Not in the OLTP sense. Hive stores no data itself; tables are files in HDFS/S3 plus metadata. It is a SQL engine and catalogue for batch analytics, with high latency (seconds to minutes) and no indexes.
When should you not use Hive?
For low-latency lookups or row-by-row transactions (use an RDBMS or HBase), for sub-second interactive dashboards (Impala, Trino, Druid, or Hive LLAP), or for small data that fits in one database.
Who uses HiveQL in a project?
Data engineers (building ETL and tables), analysts (reporting), and other engines: Spark SQL understands most HiveQL and reads Hive tables through the same metastore.

Explain the architecture of Hive.

Hive Foundations 9 min read Difficulty: Beginner 2 of 40
Definition

Hive has four layers: clients (Beeline, JDBC/ODBC), HiveServer2 (the service clients connect to), the Driver (compiler, optimizer, executor) and the Metastore (table metadata in an RDBMS). Queries run on an execution engine (Tez, MapReduce or Spark) over HDFS/S3.

ComponentRole
Beeline / JDBC / ODBCClients that submit HiveQL. The old hive CLI talked to the metastore directly and is deprecated.
HiveServer2 (HS2)Thrift service (port 10000) accepting concurrent sessions, with Kerberos/LDAP authentication
DriverManages the query lifecycle: session, compile, optimise, execute, fetch
CompilerParses HiveQL into an AST, checks semantics against metastore metadata, builds a logical plan
OptimizerRule- and cost-based (Apache Calcite) rewriting: predicate pushdown, partition pruning, join reordering, map joins
ExecutorSubmits the physical plan (DAG of stages) to the execution engine and tracks it
Metastore (HMS)Schemas, table locations, partitions, statistics; stored in MySQL/PostgreSQL/Oracle; Thrift service on port 9083
Execution engineTez (default), MapReduce (deprecated) or Spark, on YARN
StorageHDFS, S3, ADLS… Hive tables are directories of files
HiveServer2 Beeline Driver Compiler Optimizer Metastore Tez YARN
Analogy
A restaurant: customers (Beeline, BI tools) give orders to the waiter (HiveServer2). The head chef (Driver) reads the order, checks the recipe book and pantry list (Metastore: what ingredients exist and where they are), plans the cooking steps (compiler and optimizer), and the kitchen staff (Tez tasks on YARN) cook in parallel using ingredients from the cold store (HDFS). The recipe book contains no food; the cold store has no recipes.
How It Works — Step by Step
Step 1 / 5
  1. 1Clients: Beeline (the command-line client), applications over JDBC/ODBC, and tools such as Hue, Tableau or Power BI.
  2. 2HiveServer2 is the server clients connect to (default port 10000). It handles many concurrent sessions and authentication (Kerberos, LDAP).
  3. 3The Driver receives the query. The compiler parses it and checks it; the optimizer rewrites the plan (predicate pushdown, partition pruning, join order); the executor runs the resulting stages in order.
  4. 4During compilation the driver asks the Metastore for the table's columns, file format, location and partitions. The metastore keeps this metadata in a normal relational database such as MySQL.
  5. 5The plan runs as Tez, MapReduce or Spark jobs on YARN, which read and write the data files in HDFS or S3. Hive itself stores no data.
Real-World Scenario
A typical cluster layout
  • 2 HiveServer2 instances behind ZooKeeper service discovery (high availability), on edge/master nodes.
  • 2 Metastore services sharing one MySQL database, also used by Spark and Trino.
  • Queries run as Tez applications in a dedicated YARN queue (e.g. analytics).
  • Analysts connect from DBeaver/Power BI via JDBC/ODBC; Airflow submits ETL through Beeline.
Example
Connecting and starting services

# With ZooKeeper service discovery (HA HiveServer2)

  1. Set up the metastore database
    Create a MySQL/PostgreSQL database and user for Hive.
  2. Configure hive-site.xml
    javax.jdo.option.ConnectionURL, driver, user/password; hive.metastore.uris=thrift://host:9083; hive.execution.engine=tez.
  3. Initialise the schema

  4. Start the Metastore, then HiveServer2
    hive --service metastore, hive --service hiveserver2.

    beeline -u jdbc:hive2://host:10000 then SHOW DATABASES;
Cross Questions
Hive CLI vs Beeline?
The old Hive CLI ran the driver inside the client and accessed the metastore directly, bypassing HiveServer2 security. Beeline is a thin JDBC client to HiveServer2, supporting authentication, authorisation and concurrency. Beeline is the standard.
HiveServer1 vs HiveServer2?
HS1 could not handle concurrent clients safely and had no proper authentication. HS2 (Hive 0.11+) supports multi-client concurrency, Kerberos/LDAP, and a JDBC/ODBC API. HS1 has been removed.
What is Hive LLAP?
Live Long And Process: long-running daemons that cache data in memory and execute query fragments, giving interactive (sub-second to seconds) performance while still using Tez.

What happens internally when you run a Hive query?

Hive Foundations 8 min read Difficulty: Beginner 3 of 40
Definition

A Hive query goes through parse → semantic analysis (with metastore lookups) → logical plan → optimisation → physical plan (DAG of stages) → execution on Tez/YARN → fetch results.

Query Lifecycle AST Logical Plan Physical Plan EXPLAIN Stages
Analogy
Like an online food order: the app (Beeline) sends your order to the restaurant (HiveServer2); the manager (compiler) checks the menu and stock list (metastore), writes a ticket that splits the order into stations (plan with stages), the kitchen stations cook in parallel (Tez tasks), and the delivery partner brings the packed food back (fetch).
How It Works — Step by Step
Step 1 / 7
  1. 1The user runs a query in Beeline. It is sent to HiveServer2, which creates a session and hands the query to the Driver.
  2. 2The Driver asks the Compiler for an execution plan. The compiler parses the SQL into an abstract syntax tree and checks the syntax.
  3. 3For semantic analysis the compiler needs metadata: does the table exist, what are its columns and types, where are its files? It asks the Metastore.
  4. 4The Metastore returns the schema, storage format, HDFS location and the list of partitions (which is how partition pruning becomes possible).
  5. 5The compiler and optimizer produce a DAG of stages (map/reduce or Tez vertices, plus metadata operations) and send the plan back to the Driver.
  6. 6The Executor submits the stages to the execution engine. Tez runs them as YARN containers that read the table's files from HDFS.
  7. 7Results are written to a temporary location and fetched back through HiveServer2 to Beeline, row by row.
Real-World Scenario
Why understanding the flow matters

A query that "hangs before starting" is usually stuck in compilation or metastore calls (e.g. a table with 100,000 partitions). A query slow "at 99%" is an execution problem (skew). Knowing the phases tells you where to look.

Example: Look at the Plan
HiveQL
CREATE TABLE marks (roll_no INT, subject STRING, marks INT) STORED AS ORC;
EXPLAIN
SELECT subject, AVG(marks) FROM marks WHERE marks >= 40 GROUP BY subject;

+- Exchange hashpartitioning(subject#72, 4), ENSURE_REQUIREMENTS, [plan_id=144]
   +- *(1) HashAggregate(keys=[subject#72], functions=[partial_avg(marks#73)])

Hive's own EXPLAIN lists STAGE DEPENDENCIES and STAGE PLANS (Tez vertices: Map 1 → Reducer 2) with operators such as TableScan, Filter Operator, Group By Operator and File Output Operator. The plan above is Spark SQL's equivalent; the idea is the same: scan → filter → partial aggregate → shuffle → final aggregate.

Other EXPLAIN forms in Hive
EXPLAIN EXTENDED   SELECT ...;   -- more detail (paths, serde)
EXPLAIN DEPENDENCY SELECT ...;   -- tables and partitions the query will read
EXPLAIN VECTORIZATION SELECT ...;
Steps to Analyse a Query
  1. Write the query
    Start with the business question and the filter columns.
  2. Run EXPLAIN
    Check that partition filters appear (pruning) and which join strategy was chosen.
  3. Run the query
    Watch the Tez progress bars per vertex in Beeline.
  4. Check the Tez/YARN UI
    Look at the slowest vertex and tasks if it is slow.
Cross Questions
Does every Hive query launch a job?
No. Simple queries such as SELECT * FROM t LIMIT 10 or filters on partition columns can be answered by a fetch task that reads files directly (hive.fetch.task.conversion=more). Metadata commands (SHOW, DESCRIBE) never launch jobs.
What is a stage in Hive?
A unit of the plan: a Tez DAG, a MapReduce job, a move of files into the table, a stats task, etc. EXPLAIN shows them and their dependencies.

Analogy
An RDBMS is a bank teller: fast, precise, one customer and one account at a time, and every form is checked before it is accepted. Hive is the bank's auditor: slow to start, but able to read every transaction of the last ten years in one go and summarise it. You would not ask the auditor to withdraw ₹500 for you.
How It Works — Step by Step
Step 1 / 4
  1. 1In an RDBMS every INSERT goes through validation: types, NOT NULL, primary and foreign keys.
  2. 2A bad value (text in an INT column) is rejected at write time. Data in the table is always valid, but every write pays for the checks.
  3. 3In Hive, data arrives as files and is stored exactly as received. Nothing is validated, so loading terabytes is fast.
  4. 4Problems appear only when you read: the bad value becomes NULL. Data quality checks become the pipeline's responsibility.
Real-World Scenario
Both in one system

The C-DAC admission portal stores applications in MySQL (each form submission is a transaction). Each night the day's rows are exported to HDFS into a Hive table partitioned by date, where years of applications are analysed (applications per state per year, conversion to admission).

Example: Constraints Are Not Enforced
HiveQL
-- Hive accepts constraints, but does NOT enforce them
CREATE TABLE centres (centre_id INT, name STRING,
  PRIMARY KEY (centre_id) DISABLE NOVALIDATE)
STORED AS ORC;
Output
Error: [PARSE_SYNTAX_ERROR] Syntax error at or near 'DISABLE'. (line 2, pos 26)

On Hive 3 this statement succeeds and duplicate centre_id values can still be inserted: the constraint is metadata only (DISABLE NOVALIDATE is mandatory). Spark SQL, used to run these examples, rejects Hive's DISABLE NOVALIDATE syntax (error above), another reminder that such constraints are engine-specific optimizer hints, not guarantees.

Steps: Moving Data From an RDBMS to Hive
  1. Keep transactions in the RDBMS
    Applications write to MySQL/PostgreSQL.
  2. Extract daily
    Spark JDBC, Sqoop (legacy) or CDC with Debezium/Kafka.
  3. Land in HDFS
    Write Parquet/ORC into a date-partitioned folder.
  4. Expose in Hive
    External or managed partitioned table; MSCK REPAIR or ADD PARTITION.
  5. Analyse
    Reports and dashboards query Hive/Trino, never the live database.
Cross Questions
Why doesn't Hive have indexes?
Hive scans large files in parallel; partition pruning, bucketing and the min/max/bloom-filter indexes inside ORC/Parquet files skip data more effectively. The old Hive indexes were rarely useful and were removed in Hive 3.
Can Hive do UPDATE and DELETE?
Yes, since Hive 0.14, but only on transactional (ACID) ORC tables. It writes delta files rather than changing rows in place. See the ACID question.

Analogy
Three vehicles on the same roads (the same tables in the metastore): Hive is a goods train, slow to start but carries enormous loads reliably; Spark is a truck, flexible and fast for most deliveries; Trino/Impala is a motorbike courier, very quick for small urgent trips but not for moving a warehouse.
How It Works — Step by Step
Step 1 / 4
  1. 1Different engines suit different workloads: Hive for heavy batch, Spark for pipelines and ML, Trino/Impala for fast interactive SQL.
  2. 2They all ask the same Hive Metastore where a table lives and what its schema is, so a table created once is visible to all.
  3. 3The data exists only once, as ORC/Parquet files in HDFS or S3.
  4. 4Each engine then reads those files with its own execution model, so you choose the engine per query without copying data.
Real-World Scenario
One catalogue, three engines

A bank defines all its tables once in the Hive Metastore. Overnight ETL runs in Hive/Spark; analysts explore with Trino from DBeaver; Power BI dashboards hit Impala. Everyone sees the same table names and data files.

For new ETL code, Spark (or dbt on a warehouse) is more common. But the Hive Metastore remains the de-facto catalogue, Hive is still heavily used in on-prem Cloudera estates, and HiveQL knowledge transfers directly to Spark SQL.

What is the Hive Metastore? What are its deployment modes?

Metastore, Databases & Loading Data 8 min read Difficulty: Basic 6 of 40
Definition

The Hive Metastore (HMS) is the central repository of metadata: databases, tables, columns and types, storage format and SerDe, HDFS/S3 location, partitions, statistics, and privileges. It stores this in a relational database (MySQL, PostgreSQL, Oracle) and exposes it through a Thrift API (port 9083).

It holds no table data, only the description of where the data is and how to read it.

ModeMetastore service runsDatabaseUse
EmbeddedInside the Hive JVMEmbedded DerbySingle-user testing only
LocalInside each Hive/HS2 processExternal MySQL/PostgreSQLSmall setups; clients need DB credentials
RemoteSeparate Thrift serviceExternal MySQL/PostgreSQLProduction; shared by Hive, Spark, Trino, Impala
Metastore HMS Thrift Derby MySQL schematool Catalog
Analogy
The metastore is a library catalogue card index. Each card says a book's title, author, shelf number and language. The cards are tiny and the books stay on the shelves. If the card index is lost, the books still exist, but nobody can find or read them in the right language. That is why the metastore database must be backed up.
How It Works — Step by Step
Step 1 / 4
  1. 1Embedded: the metastore service and an embedded Derby database run inside the same JVM as Hive. Only one session can use it. Fine for a laptop, never for a cluster.
  2. 2Local: the metastore code still runs inside each Hive process, but the metadata is in a separate MySQL/PostgreSQL server, so several users can share it. Every client needs the database credentials.
  3. 3Remote: the metastore runs as its own service (Thrift, default port 9083). HiveServer2, Spark and other clients talk to it over the network; only it talks to the database.
  4. 4Remote mode is the production standard because one metastore becomes the shared catalog for Hive, Spark, Trino/Presto and Impala: a table created in one is visible in all.
Real-World Scenario
Shared catalogue in a data platform

A telecom company runs one remote metastore (2 instances for HA) backed by a replicated MySQL. Hive ETL creates the tables, Spark jobs write to them, and Trino serves analysts. When the metastore database was corrupted once, all engines lost sight of every table even though HDFS was fine. Since then the MySQL database is backed up hourly.

Steps to Set Up a Remote Metastore
  1. Create the backing database
    CREATE DATABASE hive_metastore; CREATE USER 'hive'@'%' ...; GRANT ALL ... in MySQL.
  2. Add the JDBC driver
    Copy the MySQL connector jar into $HIVE_HOME/lib.
  3. Configure connection properties
    Set the javax.jdo.option.* properties in hive-site.xml.
  4. Initialise the schema
    schematool -dbType mysql -initSchema (and -upgradeSchema on upgrades).
  5. Start the service
    hive --service metastore and point clients to it with hive.metastore.uris.
Cross Questions
Why is Derby not used in production?
Embedded Derby allows only one connection: a second Hive session fails with a lock error. It is also local to one machine.
Which important metastore tables exist in the backing DB?
DBS (databases), TBLS (tables), SDS (storage descriptors: location, formats), COLUMNS_V2, PARTITIONS, PARTITION_KEY_VALS, TABLE_PARAMS (stats).
How do Spark and Trino use the Hive Metastore?
They connect to the same Thrift URI, read table definitions and partition lists, then read the files themselves with their own engines.

How do you create and manage databases in Hive?

Definition

A Hive database (synonym: schema) is a namespace for tables, mapped to a directory. By default CREATE DATABASE cdac creates <hive.metastore.warehouse.dir>/cdac.db, usually /user/hive/warehouse/cdac.db (in Hive 3 managed tables go under /warehouse/tablespace/managed/hive).

Tables are referred to as database.table. The default database is default.

CREATE DATABASE Schema Warehouse Directory LOCATION DBPROPERTIES CASCADE
Analogy
A database is a cupboard in the store-room and tables are labelled boxes in it. Creating a database just adds a new cupboard (a folder); dropping a cupboard that still has boxes in it is refused unless you say CASCADE ("throw away the boxes too").
How It Works — Step by Step
Step 1 / 5
  1. 1Everything Hive manages lives under the warehouse directory (hive.metastore.warehouse.dir).
  2. 2CREATE DATABASE raw creates a folder raw.db/ and a metastore entry. The default database uses the warehouse root.
  3. 3CREATE TABLE raw.students creates a sub-folder for the table inside its database folder (for managed tables).
  4. 4Data files go inside the table folder; partitioned tables get one sub-folder per partition value.
  5. 5Dropping a database that still contains tables fails; CASCADE drops the tables as well (and the data of managed tables).
Real-World Scenario
Layered databases

Projects often create one database per layer: raw (external tables over landing files), staging (cleaned), dw (fact and dimension tables) and reports. Permissions are then granted per database.

Analogy
Complex types are like the sections of a student file folder: an ARRAY is the list of certificates (several items of the same kind, in order); a MAP is the marksheet (subject → marks, look up by name); a STRUCT is the address block (fixed fields: city, pin, state) kept together as one unit.
How It Works — Step by Step
Step 1 / 5
  1. 1One row can hold nested values: a list of skills, a map of subject to marks, and an address with fixed fields.
  2. 2An ARRAY is an ordered list; elements are read by position starting at 0: skills[0].
  3. 3A MAP stores key → value pairs; read a value by its key: marks['Spark']. A missing key returns NULL.
  4. 4A STRUCT groups named fields of different types; read one with a dot: address.city.
  5. 5Helper functions work on them: size(), map_keys(), map_values(), array_contains(), and explode() to turn elements into rows.
Real-World Scenario
Why complex types matter

Clickstream and API data arrive as nested JSON. Instead of flattening everything into dozens of tables, Hive keeps one row per event with arrays and structs, and queries them with [], .field and explode(). This avoids expensive joins.

Steps to Model Nested Data
  1. Identify nested fields
    Lists → ARRAY, key/value pairs → MAP, fixed groups of fields → STRUCT.
  2. Declare the table
    Use the complex types in CREATE TABLE.

Cross Questions
STRING vs VARCHAR in Hive?
STRING has no length limit and is the usual choice. VARCHAR(n) truncates longer values; useful mainly for compatibility with other databases.
Why DECIMAL for money instead of DOUBLE?
DOUBLE is binary floating point and cannot represent many decimal values exactly (0.1 + 0.2 ≠ 0.3), so sums drift. DECIMAL(p,s) is exact.
What happens if you access an array index that does not exist?
Hive returns NULL instead of failing.

How It Works — Step by Step
Step 1 / 6
  1. 1A Hive table is a directory. Loading data means getting files into that directory.
  2. 2LOAD DATA LOCAL INPATH reads a file from the machine running the client/HiveServer2 and copies it into the table directory in HDFS.
  3. 3Now the file is already in HDFS, in a landing folder.
  4. 4LOAD DATA INPATH (without LOCAL) treats the path as an HDFS path. A move inside HDFS is only a rename in the NameNode, so it is instant even for huge files…
  5. 5…but the source file no longer exists in the landing folder. That surprises many people.
  6. 6Either way Hive does not parse or check the data. It only places files. Bad rows show up later as NULLs at query time (schema-on-read).

Cross Questions
Why might LOAD DATA into an ORC table give garbage?
LOAD DATA does not convert anything. Loading a CSV file into a table declared STORED AS ORC puts a text file where ORC is expected, and queries fail or return nonsense. Load text into a text table, then INSERT ... SELECT into the ORC table.
INSERT INTO vs INSERT OVERWRITE?
INTO appends new files; OVERWRITE deletes the existing files of the table/partition first. OVERWRITE makes reruns safe (idempotent).
Why avoid many INSERT ... VALUES?
Each statement launches a job and writes at least one new small file.

What is the difference between managed (internal) and external tables?

Tables, SerDes & Schema-on-Read 9 min read Difficulty: Basic 10 of 40
Definition

A managed (internal) table is fully owned by Hive: its data lives in the warehouse directory and DROP TABLE deletes both metadata and data.

An external table (CREATE EXTERNAL TABLE ... LOCATION '...') only registers metadata over files that someone else owns. DROP TABLE removes only the metadata; the files stay.

Managed Table Internal Table External Table LOCATION DROP TABLE external.table.purge
Analogy
A managed table is a book you bought: when you throw it away, it is gone. An external table is a library card for a book in the public library: tearing up your card (DROP TABLE) does not destroy the book, and other people can still read it.
How It Works — Step by Step
Step 1 / 4
  1. 1A managed table is owned by Hive: its metadata is in the metastore and, by default, its files live under the warehouse directory.
  2. 2An external table also has a metastore entry, but it only points to files at a LOCATION you choose. Hive does not own them.
  3. 3Dropping a managed table deletes both the metadata and the data files (to trash, if enabled).
  4. 4Dropping an external table deletes only the metadata. The files stay, so other tools (Spark jobs, other tables) can keep using them and you can recreate the table any time.

Cross Questions
How do you tell whether a table is managed or external?
DESCRIBE FORMATTED t → Table Type: MANAGED_TABLE or EXTERNAL_TABLE.
Can an external table be in the warehouse directory?

What does external.table.purge do?
Setting TBLPROPERTIES ('external.table.purge'='true') makes DROP delete the external table's files too. Hive 3 uses it for tables created by some tools.

With strict managed tables, non-ORC managed tables are converted: managed tables must be transactional ORC, so other formats are created as external tables with purge enabled.

How It Works — Step by Step
Step 1 / 4

  3. 3When Hive writes (INSERT), the Serializer turns each row back into bytes in the table's format, and the OutputFormat writes them to files.
  4. 4You choose the SerDe in ROW FORMAT SERDE … or implicitly with STORED AS ORC/PARQUET. This is how one SQL engine can read many file formats.

What is schema-on-read? What happens when data does not match the table schema?

Tables, SerDes & Schema-on-Read 7 min read Difficulty: Basic 12 of 40
Definition

Schema-on-read means the schema is applied when data is read, not when it is written. Loading just places files; the SerDe parses and casts values at query time.

Values that do not fit the declared type become NULL, missing trailing fields become NULL, and extra fields are ignored. Hive does not raise an error.

Schema-on-read Schema-on-write NULL Data Quality Late Binding
Analogy
Schema-on-write is a school admission office that refuses incomplete forms at the counter. Schema-on-read is a drop box: every form is accepted, and problems are noticed only when someone later reads the forms. Faster intake, but you must check quality yourself.
How It Works — Step by Step
Step 1 / 5
  1. 1The file in HDFS is just text. Nothing checked it when it was loaded: row 3 has text in the marks column and row 4 has a missing field.
  2. 2The table definition in the metastore says how to interpret the bytes: column names, types, and the field delimiter (via the SerDe).
  3. 3Only when a query reads the data does Hive split each line and convert the fields to the declared types.
  4. 4Values that cannot be converted, and missing fields, become NULL. Hive does not reject the row or fail the query, so bad data can go unnoticed.
  5. 5Because the schema is not baked into the data, you can drop and recreate the table with a different schema and read the same files again. That is the flexibility of schema-on-read.
Real-World Scenario
A silent data-quality bug

A source system started sending marks as "78.5" instead of 78. The Hive column was INT, so every value became NULL and the average-marks dashboard silently dropped to "no data". The fix was a data-quality check that counts NULLs per load and fails the pipeline above a threshold.

What is partitioning in Hive? How does it improve performance?

Partitioning 9 min read Difficulty: Intermediate 15 of 40
Definition

Partitioning divides a table into sub-directories based on the values of one or more partition columns, e.g. PARTITIONED BY (dt STRING) → .../attendance/dt=2026-10-13/.

When a query filters on a partition column, Hive reads only the matching directories: partition pruning. Partition columns are not stored inside the data files; their values come from the directory names.

Partitioning PARTITIONED BY Partition Pruning Sub-directory Predicate
Analogy
An almirah with one drawer per month for fee receipts. To find October receipts you open only the October drawer instead of searching every receipt. The drawer label (the month) is not written on each receipt; it is known from the drawer you took it out of.
How It Works — Step by Step
Step 1 / 4
  1. 1A table partitioned by dt stores each day in its own sub-directory: dt=2026-10-11/, dt=2026-10-12/ … The partition column is not stored inside the files; it is the folder name.
  2. 2When the query has a filter on the partition column, Hive asks the metastore which partitions match, before any data is read.
  3. 3All non-matching folders are pruned: they are never opened. This is partition pruning.
  4. 4Only the dt=2026-10-13 folder is read: 2 GB instead of 8 GB. With years of daily data the saving is often 99% or more.

    A column used in most WHERE clauses with moderate cardinality: date, month, country, course.

Definition

How It Works — Step by Step

  1. 1Static: you write the partition value in the statement, e.g. PARTITION (course='DBDA'). Every row the SELECT returns goes into that one folder.

Definition

What is bucketing in Hive? How does it work?

Bucketing & Sampling 9 min read Difficulty: Intermediate 19 of 40
Definition

Bucketing (CLUSTERED BY (col) INTO n BUCKETS) divides a table, or each partition, into a fixed number of files. Each row goes to bucket hash(col) mod n, so all rows with the same key are always in the same bucket file.

It is used for high-cardinality columns where partitioning would create too many folders, and it enables bucket map joins, SMB joins and efficient sampling.

Bucketing CLUSTERED BY INTO n BUCKETS SORTED BY Hash hive.enforce.bucketing
Analogy
Exam answer sheets are sorted into 4 trays by the last digits of the roll number (roll mod 4). The number of trays never changes, however many students write the exam, and a given roll number always ends up in the same tray. To find, or to match, roll 2403 you only look in tray 3.
How It Works — Step by Step
Step 1 / 4
  1. 1Bucketing splits a table (or each partition) into a fixed number of files chosen at CREATE time, based on a hash of a column.
  2. 2For each row Hive computes hash(roll_no) mod 4. For integer columns the hash is the number itself, so roll 2403 goes to bucket 3.
  3. 3Each bucket is one file. All rows with the same key always land in the same bucket file, and the number of files never grows with the data.
  4. 4Because both tables bucketed the same way have matching keys in matching files, Hive can join bucket-to-bucket without a full shuffle, and sample data by reading just one bucket.
Real-World Scenario
Joining two large tables on roll_no

students (2 million rows) and exam_attempts (500 million rows) are both bucketed by roll_no into 64 buckets and sorted. The nightly join runs as a sort-merge-bucket join, bucket 0 with bucket 0, etc., without shuffling 500 million rows across the network.

  1. Choose the bucket column

Cross Questions
How is the bucket number computed for a STRING column?
Using the Java-style hash of the value: (hashCode & Integer.MAX_VALUE) % numBuckets. For INT the hash is the value itself. Hive 3 bucketing version 2 uses Murmur3.
Can you change the number of buckets later?
ALTER TABLE ... INTO n BUCKETS changes only metadata; existing files are not rebucketed, so you must rewrite (INSERT OVERWRITE) the data.
Can a table be both partitioned and bucketed?
Yes: each partition folder then contains n bucket files. This is very common: partition by date, bucket by id.

What are bucket map join and sort-merge-bucket (SMB) join?

Bucketing & Sampling 8 min read Difficulty: Intermediate 21 of 40
Definition

Bucket map join: when both tables are bucketed on the join key and one table's bucket count is a multiple of the other's, each mapper loads only the matching bucket of the smaller table into memory instead of the whole table.

SMB join: when both tables are bucketed and sorted on the join key with the same number of buckets, each task merges two sorted bucket files, a streaming merge join needing very little memory, with no shuffle.

Bucket Map Join SMB Join Sort-Merge-Bucket hive.optimize.bucketmapjoin Join Optimization
Analogy
Two registers, both organised into 4 sections by roll mod 4 and sorted inside each section. To match every student with their marks, four clerks work in parallel, each taking section k of both registers and running a finger down both lists at once. Nobody needs to carry pages between sections.
How It Works — Step by Step
Step 1 / 4
  1. 1Both tables are bucketed on the join key roll into the same number of buckets.
  2. 2A row with a given roll number is in bucket k of both tables. Matching rows can only ever be in matching buckets.
  3. 3So Hive starts one task per bucket pair: task 0 joins students bucket 0 with marks bucket 0, and so on. No task needs data from other buckets, so the big shuffle of a normal join disappears.
  4. 4If the buckets are also sorted on the key (SORTED BY), each task does a streaming merge of two sorted files: the SMB join, which works even when neither table fits in memory.
Real-World Scenario
Customer 360 in a bank

Accounts (300 M rows) and transactions (20 B rows) are both bucketed and sorted by customer_id into 256 buckets. The daily join changed from a 2-hour shuffle join to a 25-minute SMB join.

How It Works — Step by Step
Step 1 / 4
  1. 1ORDER BY guarantees a total order of the whole result, so all rows must pass through a single reducer. On large data that one task becomes the bottleneck (strict mode requires a LIMIT).

Step 1 / 4

  3. 3Each map task loads the hash table and streams its slice of the big table through it, looking up the matching course for every row.
  4. 4No data is shuffled and there is no reduce phase, which is usually many times faster. Hive converts joins to map joins automatically when the small table is below the size threshold.

Analogy
Each student's row gets a rank badge computed by looking only at classmates in the same course (the window), while everybody stays in the hall. GROUP BY would instead send everyone home and keep just one summary card per course.
How It Works — Step by Step
Step 1 / 5
  1. 1Start with one row per student: course, name, marks.
  2. 2PARTITION BY course splits the rows into independent windows, one per course (this has nothing to do with table partitions).
  3. 3Inside each window, ORDER BY marks DESC sorts the rows and RANK() numbers them: 1 for the topper of each course.
  4. 4Anuj and Meera both have 78, so both get rank 2 (the next would be 4). DENSE_RANK() would give 3 next; ROW_NUMBER() gives unique numbers.
  5. 5Window functions keep every row and add a computed column, whereas GROUP BY collapses rows. That is why they are used for top-N per group, running totals and deduplication.
Real-World Scenario

  • Running total of fee collection by date (SUM ... OVER (ORDER BY dt)).

  1. Decide the window
    PARTITION BY = the group (course, student); ORDER BY = the sequence (marks, date).

Cross Questions
RANK vs DENSE_RANK vs ROW_NUMBER for marks 91, 78, 78, 72?

How do you remove duplicates keeping the latest row?
ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC) = 1 in a subquery.
What is the default frame with ORDER BY?
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which is why LAST_VALUE often surprises people: specify ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.

How do you work with arrays and nested data? Explain LATERAL VIEW and explode().

Querying: Sorting, Joins, Windows & UDFs 8 min read Difficulty: Intermediate 26 of 40
Definition

explode(array) and explode(map) are UDTFs (table-generating functions) that turn one value into several rows. LATERAL VIEW attaches those generated rows to the original row, so other columns can be selected alongside. posexplode also returns the position; LATERAL VIEW OUTER keeps rows with empty arrays.

The reverse (rows → array) is done with collect_list() (keeps duplicates) or collect_set() (distinct).

LATERAL VIEW explode posexplode UDTF collect_list collect_set
Analogy
A student's profile card lists skills in one box: "SQL, Spark". explode is photocopying the card once per skill and highlighting a different skill on each copy, so you can count how many students know Spark. collect_set is stapling the copies back into one card.
How It Works — Step by Step
Step 1 / 4
  1. 1Each student row has an ARRAY<STRING> of skills. Reports usually need one row per skill.
  2. 2explode() is a table-generating function (UDTF): it turns one array into several rows. Used alone it can only return the exploded column.
  3. 3LATERAL VIEW joins each input row with the rows its own array produced, so other columns (name) are repeated next to each skill.
  4. 4Students with an empty or NULL array disappear from the result. LATERAL VIEW OUTER explode(...) keeps them with a NULL skill.
Real-World Scenario
Skill demand vs supply

Placement drives list required skills as arrays; student profiles list skills as arrays. Exploding both and joining on the skill shows which in-demand skills students lack, information that guided which modules to strengthen.

Example

SELECT p.name, m.subject, m.score
FROM profiles p LATERAL VIEW explode(p.marks) m AS subject, score ORDER BY p.name, m.subject;

-- and back again: rows -> array
SELECT s.skill, collect_list(p.name) AS students
FROM profiles p LATERAL VIEW explode(p.skills) s AS skill GROUP BY s.skill ORDER BY s.skill;

  1. Identify the array/map column
    From JSON or a complex-typed table.

Analogy

import org.apache.hadoop.hive.ql.exec.UDF;
import org.apache.hadoop.io.Text;

// Simple (legacy-style) UDF: keep first 2 and last 2 digits
public class MaskPhone extends UDF {
    public Text evaluate(Text phone) {
        if (phone == null) return null;
        String p = phone.toString();
        if (p.length() < 5) return phone;
        return new Text(p.substring(0, 2) + "X".repeat(p.length() - 4) + p.substring(p.length() - 2));
    }
}

What are GROUPING SETS, ROLLUP and CUBE?

Querying: Sorting, Joins, Windows & UDFs 7 min read Difficulty: Intermediate 28 of 40
Definition

They compute several GROUP BY levels in one query (one scan of the data):

ClauseGroups produced for (a, b)
GROUPING SETS ((a,b),(a),())Exactly the sets you list
WITH ROLLUP(a,b), (a), () : hierarchical subtotals and a grand total
WITH CUBE(a,b), (a), (b), () : all combinations

Columns not part of a given grouping are NULL in that row; GROUPING__ID / grouping(col) tells subtotal rows apart from real NULLs.

GROUPING SETS ROLLUP CUBE Subtotals GROUPING__ID
Analogy
A fee report with subtotals per course, per centre, and a grand total at the bottom. Instead of running three separate summaries and stitching them together, ROLLUP prints all of them in one pass.
How It Works — Step by Step
Step 1 / 3
  1. 1ROLLUP first produces the normal groups, one row per (centre, course).
  2. 2Then it adds a subtotal per centre: course is NULL in those rows (Juhu 130, Kharghar 180).
  3. 3Finally a grand total row where both columns are NULL. All levels come from one scan of the data.
Real-World Scenario
One query for a management dashboard

Enrolment counts by centre and course, by centre only, and overall feed three dashboard tiles. A single ROLLUP query replaces three UNION ALL-ed GROUP BY queries and scans the table once instead of three times.

Example: Subtotals and Grand Total

FROM enrol
GROUP BY centre, course WITH ROLLUP

  1. List the levels you need
    e.g. centre+course, centre, total.
  2. Pick the clause

    COALESCE(centre, 'ALL CENTRES') or use grouping(centre).

Which file formats does Hive support? Why is ORC preferred?

Storage, Engines & Performance 10 min read Difficulty: Advanced 29 of 40
Definition

Hive tables can be stored as TEXTFILE (default), SEQUENCEFILE, AVRO, PARQUET or ORC (STORED AS ...). ORC (Optimized Row Columnar) was built for Hive: columnar storage in stripes (~64–256 MB) with min/max indexes per stripe and per 10,000 rows, optional bloom filters, lightweight encodings plus ZLIB/Snappy/ZSTD compression, and it is required for ACID tables.

ORC Parquet Avro TEXTFILE Stripe Predicate Pushdown Bloom Filter Compression
Analogy
A text file is a diary: to find all marks you read every page line by line. ORC is a well-organised register with one column per subject and a summary on top of every page ("marks on this page: 35–98"), so you can jump straight to the marks column and skip pages that cannot contain what you need.
How It Works — Step by Step
Step 1 / 4
  1. 1An ORC file is divided into stripes; inside each stripe every column is stored separately. The footer holds the schema and statistics.
  2. 2Each stripe has min/max statistics per column. "Pune" cannot be in a stripe whose city range is Bengaluru–Hyderabad (alphabetical), so those stripes are skipped without reading them.
  3. 3In the remaining stripe only the city and marks columns are read; roll and course are never touched.
  4. 4Predicate pushdown plus column pruning is why ORC/Parquet queries read a small fraction of the bytes a CSV table needs.
Real-World Scenario

Cross Questions
ORC vs Parquet?
Both columnar and splittable. ORC has richer built-in indexes and is required for Hive ACID; Parquet has broader ecosystem support (Spark default, Impala, cloud warehouses). Use ORC for Hive-centric warehouses, Parquet when many engines share data.
When is TEXTFILE still used?
For landing/raw data exactly as received, and for exchange with systems that only understand CSV.
Is Snappy-compressed ORC splittable?
Yes. Compression is applied per stripe/stream inside the file, so the file can still be split at stripe boundaries.

Analogy
MapReduce is sending a parcel through several courier companies, each one unpacking, storing it in its warehouse and repacking it for the next. Tez is one company with one route plan: the parcel moves directly from van to van.
How It Works — Step by Step
Step 1 / 4
  1. 1With MapReduce, a query with a join, a GROUP BY and an ORDER BY becomes a chain of separate jobs. Each one writes its full output to HDFS for the next to read.
  2. 2Every job also starts fresh containers and JVMs, and HDFS writes are replicated 3×. Most of the time is overhead, not computation.
  3. 3Tez compiles the same query into one DAG of vertices (map and reduce steps) with edges between them, submitted as a single application.
  4. 4Intermediate data flows directly between vertices (no HDFS round trips), containers are reused, and the session stays warm, so the same query is typically several times faster. MapReduce as Hive's engine is deprecated.

Definition

The cost-based optimizer (CBO), built on Apache Calcite, chooses join order, join type (map join or shuffle) and other plan details by estimating the cost of alternatives. Its estimates come from statistics stored in the metastore: row counts, sizes, and per-column number of distinct values, NULLs, min/max.

Vectorization processes data in batches of 1,024 rows per column instead of one row at a time, using tight loops that suit modern CPUs (works with ORC; Parquet in newer versions).

Definition

Does Hive support ACID transactions, UPDATE, DELETE and MERGE? How does it work?

Storage, Engines & Performance 10 min read Difficulty: Advanced 34 of 40
Definition

Since Hive 0.14 (and fully in Hive 3), transactional tables support INSERT, UPDATE, DELETE and MERGE with ACID guarantees (snapshot isolation). Requirements: managed table, ORC format, 'transactional'='true', and the transaction manager DbTxnManager. In Hive 3, managed ORC tables are transactional by default; 'transactional_properties'='insert_only' allows other formats for inserts only.

Data is never modified in place. Changes are written as delta and delete_delta directories; readers merge them with the base; compaction periodically rewrites them.

ACID Transactional Table UPDATE DELETE MERGE Delta Files Compaction DbTxnManager
Analogy
A printed register that cannot be erased. To correct marks you attach a correction slip ("roll 2402: cancel 85, now 91"). Readers look at the page and all slips together. When the slips pile up, a clerk rewrites a clean page including all corrections (compaction).
How It Works — Step by Step
Step 1 / 5
  1. 1A transactional (ACID) table stores its data as ORC files. The initial data is in a base directory.
  2. 2Files in HDFS cannot be edited, so each INSERT writes a new delta directory tagged with the transaction id.
  3. 3A DELETE writes a delete_delta that lists the ids of removed rows. An UPDATE is a delete of the old version plus a delta with the new version.
  4. 4Readers merge base and deltas on the fly, seeing only committed transactions (snapshot isolation). Many small deltas make reads slower.
  5. 5Background compaction fixes that: minor compaction merges deltas together; major compaction rewrites base + all deltas into a new base, after which old files are cleaned up.
Real-World Scenario
Re-evaluation results and GDPR-style deletes
  • After re-evaluation, 300 marks change: one MERGE from the re-evaluation table updates them in place, instead of rewriting the whole year's partition.
  • A student withdraws consent: DELETE FROM students WHERE roll_no = 2405 removes them from all history.
  • SCD Type 2 dimensions are maintained with MERGE.
Example
HiveQL on Hive 3

SET hive.txn.manager = org.apache.hadoop.hive.ql.lockmgr.DbTxnManager;

UPDATE marks_acid SET marks = 91 WHERE roll_no = 2402 AND subject = 'SQL';
DELETE FROM marks_acid WHERE roll_no = 2405;

-- Upsert from a staging table
MERGE INTO marks_acid AS t
USING reeval AS s
ON t.roll_no = s.roll_no AND t.subject = s.subject
WHEN MATCHED AND s.new_marks IS NULL THEN DELETE
WHEN MATCHED THEN UPDATE SET marks = s.new_marks
WHEN NOT MATCHED THEN INSERT VALUES (s.roll_no, s.subject, s.new_marks);

No. Hive must own the files to manage deltas and compaction.

Scenario: How do you implement SCD Type 2 in Hive?

Real-World Scenarios 12 min read Difficulty: Expert 36 of 40
Definition

A Slowly Changing Dimension Type 2 keeps full history: when an attribute changes, the current row is closed (end date, is_current = N) and a new version is inserted. In Hive this is done either with MERGE on an ACID table, or, on non-ACID tables, by rebuilding the dimension with INSERT OVERWRITE from (old rows ∪ changes).

SCD Type 2 Slowly Changing Dimension History MERGE INSERT OVERWRITE Effective Dates
Analogy
A passport's address history: when you move, the old address is not erased; it is marked "valid until" a date, and the new address is added "valid from" the next day. You can always tell where someone lived on any date.
How It Works — Step by Step
Step 1 / 5
  1. 1The dimension has one current row for student 2402: city Pune, valid from July 2025 with an open end date.
  2. 2Today's source says the student now lives in Mumbai. Comparing source with the current row detects the change.
  3. 3The old row is closed: its end date becomes yesterday and current = N. The history is not overwritten.
  4. 4A new row is added with Mumbai, starting today, current = Y. In Hive this is done with MERGE on ACID tables, or by rebuilding the table/partition with INSERT OVERWRITE.
  5. 5Reports can now show the city a student had at the time of any event, by joining on the id and the validity dates.
Real-World Scenario
Why history matters

A placement report by city must show where a student lived when they were placed. If the city were simply overwritten (SCD Type 1), last year's report would change every time a student moved.

Example
HiveQL
-- Rebuild approach (works on any table format)
INSERT OVERWRITE TABLE dim_student_new
SELECT * FROM (
  -- 1. history rows and unchanged current rows stay as they are
  SELECT d.id, d.city, d.start_dt, d.end_dt, d.is_current
  FROM dim_student d LEFT JOIN src s ON d.id = s.id
  WHERE d.is_current = 'N' OR s.id IS NULL OR d.city = s.city
  UNION ALL
  -- 2. changed current rows are closed (end = yesterday)
  SELECT d.id, d.city, d.start_dt, date_sub('2026-10-13', 1), 'N'
  FROM dim_student d JOIN src s ON d.id = s.id
  WHERE d.is_current = 'Y' AND d.city <> s.city
  UNION ALL
  -- 3. new versions for changed rows, and brand-new ids

SCD2 with MERGE (Hive 3 ACID)
-- ACID approach (Hive 3, dim_student is a transactional ORC table)
MERGE INTO dim_student AS t
USING (
  SELECT s.id AS join_id, s.* FROM src s            -- rows to update/insert by id
  UNION ALL
  SELECT NULL AS join_id, s.* FROM src s            -- extra copy: forces INSERT of the new version
  JOIN dim_student d ON s.id = d.id AND d.is_current = 'Y' AND s.city <> d.city
) AS u
ON t.id = u.join_id AND t.is_current = 'Y'
WHEN MATCHED AND t.city <> u.city THEN
  UPDATE SET end_dt = date_sub(current_date, 1), is_current = 'N'
WHEN NOT MATCHED THEN
  INSERT VALUES (u.id, u.city, current_date, DATE '9999-12-31', 'Y');
Steps to Implement SCD2
  1. Design the dimension
    Business key, tracked attributes, start_dt, end_dt, is_current (optionally a surrogate key).
  2. Stage today's source
    One row per business key (deduplicate first).
  3. Detect changes
    Join current rows to the source on the key and compare tracked attributes (or a hash of them).
  4. Close and insert
    MERGE on ACID tables, or rebuild with the three-part UNION ALL into a new table and swap.
  5. Validate
    Exactly one current row per key: SELECT id FROM dim WHERE is_current='Y' GROUP BY id HAVING COUNT(*) > 1 must return nothing.
Cross Questions
Why the "UNION ALL with NULL join key" trick in MERGE?
One MERGE can apply only one action per source row. A changed row needs two actions (close the old, insert the new), so the source row is duplicated: one copy matches and updates, the other (NULL key) never matches and inserts.
SCD Type 1 vs Type 2 vs Type 3?
Type 1 overwrites (no history); Type 2 adds a new row per change (full history); Type 3 keeps a "previous value" column (limited history).

Scenario: Remove duplicate records and find the latest record per key.

Definition

Duplicates arrive from retries, overlapping extracts and CDC replays. Exact duplicates can be removed with DISTINCT or GROUP BY; "keep the latest version per key" needs ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC) and a filter on row number 1.

Deduplication ROW_NUMBER Latest Record DISTINCT CDC
Analogy
Several copies of the same leave application, some edited later. You keep only the one with the most recent date stamp for each employee and shred the rest.
How It Works — Step by Step
Step 1 / 5
  1. 1The change log has several rows for 2401, including an exact duplicate from a retried load.
  2. 2The window groups rows per roll_no and sorts each group newest first.
  3. 3ROW_NUMBER() numbers the rows 1, 2, 3 within each group. Ties still get different numbers, so exactly one row is number 1.
  4. 4Filtering rn = 1 drops older versions and duplicates.
  5. 5One row per student remains: their latest profile.
Real-World Scenario
Student profile updates

The admission portal sends every profile change as a new row. The Hive job keeps the latest row per roll number for the current-profile table, using updated_at plus a tie-breaker so reruns always pick the same row.

Example
HiveQL

INSERT INTO profile_changes VALUES
  (2401, '98xxxxxx01', 'Pune',   TIMESTAMP '2026-07-01 10:00:00'),
  (2401, '98xxxxxx01', 'Mumbai', TIMESTAMP '2026-09-15 18:30:00'),
  (2401, '98xxxxxx01', 'Mumbai', TIMESTAMP '2026-09-15 18:30:00'),   -- exact duplicate (retry)
  (2402, '98xxxxxx02', 'Vashi',  TIMESTAMP '2026-08-20 09:00:00');

SELECT roll_no, phone, city, updated_at
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY roll_no ORDER BY updated_at DESC) AS rn
  FROM profile_changes
) t
WHERE rn = 1
ORDER BY roll_no;

-- How many duplicates were there?
SELECT COUNT(*) AS total_rows, COUNT(DISTINCT roll_no) AS distinct_students FROM profile_changes;

Steps
  1. Define the key and the "latest" rule
    e.g. roll_no; newest updated_at; tie-breaker: highest batch_id.
  2. Number rows per key

  3. Keep rn = 1

Cross Questions
Why ROW_NUMBER and not RANK here?
RANK gives equal ranks to ties, so two rows with the same timestamp would both survive. ROW_NUMBER always picks exactly one.

Troubleshooting scenarios frequently asked in Hive interviews

Real-World Scenarios 10 min read Difficulty: Expert 39 of 40
How to Approach It
Troubleshooting Hive is like a doctor's visit: symptom (error message or slowness) → tests (EXPLAIN, logs, Tez UI, metastore) → diagnosis (root cause) → treatment (fix) → prevention (so it does not happen again).
How It Works — Step by Step
Step 1 / 5
  1. 1Start from the exact symptom: the full error message, which stage is slow, or which numbers are wrong.
  2. 2Collect evidence: EXPLAIN, HiveServer2 and Tez task logs, the Tez/YARN UI, and the actual files in HDFS.
  3. 3Name the root cause: is it the data (delimiter, skew, small files), the metadata (partitions, stats) or resources (memory, queue)?
  4. 4Apply the fix at the right level: table DDL, session settings or the query itself.
  5. 5Prevent recurrence: add a data-quality check, an alert, or automatic statistics to the pipeline.
Real-World Scenario
1. "SELECT returns all NULLs" after creating a table over CSV files
  • Wrong delimiter (e.g. table says , but file uses |), quoted fields, or a header row.
  • Check with hdfs dfs -cat ... | head; fix ROW FORMAT / SerDe; add skip.header.line.count.
2. New data written by Spark is not visible in Hive
  • New partition folders are not registered → ALTER TABLE ADD PARTITION / MSCK REPAIR.
  • Or stale stats answering COUNT(*) from metadata → ANALYZE TABLE or set hive.compute.query.using.stats=false.
3. Query stuck at 99% for hours
  • One reducer with a hot key (skew): check task input records in Tez UI.
  • Fix: map join, skew join settings, salting, or filter NULL keys.
4. "Container killed by YARN for exceeding memory limits" / OutOfMemory in map join
  • Raise hive.tez.container.size with -Xmx ≈ 80% of it.
  • For map joins: stats wrong → small table not small; refresh stats or lower noconditionaltask.size.
5. "Number of dynamic partitions created is 1500, which is more than 1000"
  • Check the partition column is not accidentally high-cardinality (a timestamp?).
  • If intended, raise hive.exec.max.dynamic.partitions / .pernode.
6. Query takes minutes before any task starts
  • Too many partitions or files to list (metastore + NameNode calls).
  • Add partition filters, coarsen partitioning, compact small files.
7. Table dropped by mistake
  • External table: recreate it with the same DDL and LOCATION; run MSCK REPAIR. Data is safe.
  • Managed table: recover from HDFS trash (/user/hive/.Trash) if enabled, else from backup/snapshot. Prevention: external tables for raw data, HDFS snapshots, Ranger permissions.

Where does Hive fit in a modern data platform (Spark, Trino, Iceberg, cloud)?

Real-World Scenarios 8 min read Difficulty: Expert 40 of 40
Definition

Hive has two roles today. As a query engine (HiveServer2 + Tez/LLAP) it is mainly used in on-prem Cloudera/HDP estates for batch ETL. As a catalogue, the Hive Metastore is everywhere: Spark, Trino, Impala, Flink and many cloud services (AWS Glue Data Catalog is Hive-Metastore-compatible) use it to find tables.

Newer open table formats, Apache Iceberg, Delta Lake and Hudi, solve Hive table limitations (directory-based partitions, slow listing, no safe concurrent writes on plain tables, no time travel) and are often registered in the Hive Metastore. Hive 4 (2024) supports Iceberg tables natively.

Hive Metastore Iceberg Delta Lake Hudi AWS Glue Trino Hive 4
Analogy
The Hive Metastore is like a city's address directory: many delivery companies (Spark, Trino, Impala) use the same directory to find houses. Iceberg is a modern building with its own security desk and visitor log: it is still listed in the city directory, but it tracks exactly who lives where and keeps the history of every change.

How It Works — Step by Step
Step 1 / 4
  1. 1A classic Hive table is "a directory": the metastore keeps the partition list, and the files are whatever sits in each folder.
  2. 2To plan a query, engines list folders and files. On object storage that is slow, and a half-finished write can be seen by readers.
  3. 3An Iceberg table is still registered in the catalog, but the catalog points to a metadata file that lists snapshots, manifests and the exact data files.
  4. 4Each write creates a new snapshot atomically. This enables time travel, safe concurrent writers, and partitioning that users do not have to know about.

Migration path

A company moving from on-prem Hadoop to AWS keeps its HiveQL knowledge and table names: tables move to S3 as Iceberg, the catalogue becomes AWS Glue (Hive-Metastore-compatible), ETL runs on Spark (EMR), and analysts query with Athena/Trino.

  2. Store data in open formats

  4. Migrate gradually
